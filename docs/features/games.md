  - **Steam** is the far more stable of the two: a **personal Web API key** (steamcommunity.com/dev/apikey) + your own SteamID64 is all that's needed for read access — no OAuth ("Sign in through Steam" OpenID only proves identity, grants zero extra data access). Real endpoints confirmed: `IPlayerService/GetOwnedGames` (playtime per game), `GetRecentlyPlayedGames`, `GetSteamLevel`/`GetBadges`, `ISteamUserStats/GetPlayerAchievements` (per-achievement, % computed client-side) + `GetSchemaForGame` (achievement names/icons), `ISteamUser/GetPlayerSummaries` (currently-playing status, online state). **No CORS headers at all on `api.steampowered.com`** — confirmed mandatory server-side proxy. Wishlist has NO official endpoint — deliberately NOT built (would need the reverse-engineered `IWishlistService/GetWishlist`).
  - **PlayStation has NO official public API at all** — the only working approach is the community-reverse-engineered `npsso` cookie flow. **Real, current blocker as of 2026: Sony added a reCAPTCHA to the login flow that blocks scripted npsso refresh** — a human must periodically (roughly every 1-2 months) re-login in a real browser and re-paste a fresh npsso via the Connect form; this cannot be fully automated, unlike every other OAuth integration in this app. Confirmed available once authenticated: owned/purchased games, trophy list per game (bronze/silver/gold/platinum + rarity %), online/presence status. **Confirmed NOT available**: PS Store wishlist, clean PS Plus subscription status — neither built. **Explicitly best-effort, low-priority** — never load-bearing, given the manual-reconnect chore and coverage gaps.

Live concurrent-player count is a **deliberate explicit-tap action inside the modal, never fetched on open** (the user's own instruction).
  - **Loading priority is a deliberate design, not an accident** (the user's own instruction: "no need to fetch everything at once… the pictures, game names and basics should load fast; the rest is detail work"). The tab's first paint costs exactly **two** requests — profile + library. Everything else is tiered: the **"Last 2 weeks" strip is DERIVED, not fetched** (`GetRecentlyPlayedGames` is a strict subset of `GetOwnedGames`, and `playtime_2weeks` is already in the owned-games payload — the `recent_games` action and its client hook were deleted, not just left unused); **level/badges** is `enabled`-gated behind the library landing (two Steam round trips for one line of header text); the modal's hero art and title are painted from the appid and the owned-games row so the popup is legible on its **first frame with zero network**, and never swap when metadata arrives; **store metadata + reviews** load per opened game; **achievements load only when scrolled into view** (an `IntersectionObserver` inside `SteamAchievementGrid`, 150px root margin) since they are three uncacheable Steam round trips rendering below the fold; the **player count** waits for an explicit tap. Keep this tiering when adding to either tab — a new eager call on mount is a regression, not a feature. The one owner-approved exception (05.10.2026): opening Games syncs each library once a day (`useProviderAutoSync`).
  - **PSN phase 2 — the playtime library (2026-09-15).** `PlayStationTab` is now **two views over two genuinely different Sony datasets, deliberately not merged**: **📚 Library** (`getUserPlayedGames` — real lifetime playtime, play count, first/last played, PS4/PS5/PC category, cover art; sort by playtime/recency/name + search + a total-hours readout) and **🏆 Trophies** (the pre-existing `getUserTitles` trophy-set grid). **They cannot be joined across a library**: PSN keys playtime by store SKU (`npTitleId`, CUSA…/PPSA…) and trophies by trophy-set id (`npCommunicationId`, NPWR…), and Sony's only bridge (`getUserTrophiesForSpecificTitle`) takes **5 titles per request** — 300 games would be 60 calls. So `PsnGameModal` bridges **one** game's id when it opens, and the trophy view (which already holds NPWR ids) needs no bridge at all. `PsnTrophyPanel` is shared by both entry points: per-trophy name/icon/hidden-flag joined server-side with the user's earned state on `trophyId`, carrying **Sony's own rarity tier** (Ultra Rare→Common) and earn-rate %, DLC group tabs (a second call, made only when the title row says `hasTrophyGroups`), earned-then-rarest sort, and the PS5 partial-progress fields that are real in Sony's response but **absent from psn-api's own TypeScript types**. `getPurchasedGames` supplies **PS Plus badges** (the only source of "came with the subscription" and of never-launched games) and is the most fragile call in the library — a Sony-side GraphQL hash rotation breaks it alone, so it degrades to an empty list with a note rather than taking the tab down. **No `getRecentlyPlayedGames`**: it is a strict subset of `getUserPlayedGames` (which already carries `lastPlayedDateTime`) *and* the other fragile GraphQL call — dropping it removes a round trip and a failure mode at once, same reasoning as Steam's `recent_games`. `parsePlayDurationMinutes` (`psnApi.ts`) parses Sony's ISO-8601 duration (`"PT228H56M33S"`) — the ONLY playtime figure PSN exposes anywhere, and a cumulative lifetime total with no per-session records; **verified:** `scripts/verify-psn-playtime.cjs`, 14 assertions (real observed values, each component alone, a day component, and every degenerate input returning 0 rather than a `NaN` that would poison the sort comparator and the hours total).
  - **`steam_apps` (migration `092`) is the ONE Steam table, and only because Steam forces it.** Everything about the USER (owned games, playtime, achievements) stays a live passthrough with no local row — Steam is the source of truth and nothing else in this app joins against it. Store METADATA is different: `store.steampowered.com/api/appdetails` is rate-limited to ~200 requests / 5 min per IP and returns ~36 KB per app, so a 400-game library cannot be enriched on every page load. So `steam_apps` mirrors the **`movies` shared-catalog shape** (no `user_id`, `SELECT` for `authenticated`, written only by the edge function's service-role client, **no `trg_audit`** per the bulk-synced exemption): promoted columns only for what the library filters/sorts on (`name`/`type`/`genres`/`metacritic_score`/`is_free`), the whole `appdetails` payload in a `details` jsonb (the `health_workouts.raw` precedent — a later UI addition needs no migration), and reviews on their own `reviews_fetched_at` cadence since a review score moves daily while a store page rarely does. TTLs: details 14 days, reviews 24h. `app_details` caps live store fetches at **20 per request** and returns the rest in `missing` so the client can page through without tripping the rate limit; a delisted app caches a `details: null` tombstone rather than being retried forever. Missing table (092 unapplied) degrades to an uncached live fetch, never a crash. `psn-api` (edge function, uses the `psn-api` npm package via a Deno `npm:` specifier rather than hand-rolled fetch calls — the auth exchange/GraphQL-backed calls are too finicky to safely guess at) resolves the caller via `supabase.auth.getUser` (the `calendar-oauth` pattern) and reads/writes **`psn_tokens`** (migration `091`, singleton per user, **deliberately no `trg_audit`** — it holds live secrets, and this table must never enter `ai-proxy`'s `DB_CATALOG`); `psnApi.ts`/`usePlayStation.ts` → `PlayStationTab.tsx`. **Genuinely unverified against a real account** — this authoring session has no PSN/Steam credentials to test against; the response-shape reads (`profile?.profile?.onlineId` etc.) are defensive with fallbacks, not confirmed live. Deploy `steam-api`/`psn-api` and report back what the first real connect actually returns.
  - Neither table/function touches `ai-proxy`'s `DB_CATALOG`.
  - **Provider-library behaviour (2026-09-25, migration `102`).** Five rules, all deliberate:
    - **`finished_at` is the day you finished, not the day you pressed the button.** `setPlayStatus` stamps it from the row's own `last_played_at` (the provider's last session) and falls back to `now()` only for a game no provider ever reported a session for. The old `now()` collapsed an imported library's years of history onto one afternoon when many old games were marked completed at once. Migration 102 backfills existing `completed` rows the same way — only rows with no `finished_at`, only where a session exists; a manually corrected date is never overwritten. **That left the real bug in place:** rows the old code had already stamped with `now()` weren't NULL, so 102 skipped them. Migration `103` repairs them: a `finished_at` more than a day after the game's own last session (the later of `last_played_at`/`esde_last_played`, matching `playStatsOf`) can only be a button-press stamp, and is replaced by that session.
    - **`hidden` is a `play_status`, not a separate flag** — the user's explicit call ("save it in the status; let the UI read the status and decide"). A row therefore holds a play status OR `'hidden'`, never both: hiding replaces the status and un-hiding resets it to `backlog` (the previous one isn't recorded anywhere). `STATUSES` (the picker) deliberately omits it; `LibraryControls` sets it with its own 🙈 button so it can't read as a kind of progress.
    - **`isHiddenEntry(kind, playStatus)`** (`providerEntries.ts`) is the one predicate both tabs use: an explicit `'hidden'` always hides, ANY real status always shows (a deliberately-tracked app stays visible even if the provider calls it a non-game), and only with NO status does the provider's type decide — `unknown` stays visible, so an unclassified Steam library never empties itself. The toggle is **Show hidden (N)**, off by default.
    - **PlayStation paints from the saved library first.** `psnGamesFromLibrary` (`psnLibraryFallback.ts`) projects `games` rows back into Sony's own `PsnPlayedGame` shape — round-tripping `play_seconds` through `secondsToIsoDuration` so the SAME `parsePlayDurationMinutes` reads saved and live rows identically, one shape for every consumer. Once anything is saved, the connection state only decides which banner sits above the grid (`ExpiredBanner` / `ExpiringSoonBanner`), never whether the grid renders. The PSN **Last 2 weeks** strip is "played in the last 14 days" by `lastPlayedDateTime`, never hours: Sony exposes only a lifetime total and the last session's timestamp, so claiming Steam's per-period hours here would invent a number.
    - Both libraries default to **last-played** order. `formatPlaytime` (`playtimeFormat.ts`) is the single days/hours/minutes formatter for every playtime figure AND the PSN token countdown (`npssoLifetimeLabel` → "PSN token expires in 64d 5h 41m"); library totals read "… played" so a duration next to "total" can't be mistaken for that countdown.

## ScreenScraper — the Scrape page (rewrite, 2026-09-25)

Rewritten from scratch on the owner's call ("this version is f up"). The measured starting point: of 1,030 retro games only 45 had ever been matched, `provider_data` was filled on 1 and `games.media` on 0 — the old per-game path (`apply_match`) never wrote either, and only ~11 of the ~25 fields their API returns were mapped. Full API map, storage research and design: `docs/games/screenscraper-integration.md` §16.

- **Where:** a first-class section `scrape` — phone More → "Scrape (ScreenScraper)", desktop sidebar "Scrape". The detail's **Scrape** button (retro games) is `openScrape(gameId)`: the SAME page with that game picked and its search already running — there is no second flow anywhere. Header tabs switch **One game / Many games**. The last search (game + exact form + results) and the batch session live in `testGameStore`, so switching modes or leaving the page never throws away lookups that cost requests. Phone: search → review are steps; **Back to results** and the **What to save** gear sit in the phone header (always on screen); tablet/desktop show results and review side by side.
- **Owner only.** `screenscraper-sync` refuses every caller but `HEVY_USER_ID` (403) — the ScreenScraper account is one person's paid membership.
- **Search** (`planSearch`): name (jeuRecherche, ≤30 results, ≥4 letters with "the" ignored), ROM identity (hash → jeuInfos with every hash + filename + size, no system needed; filename alone needs the system — "systemeid obligatoire si aucun CRC"), serial, ScreenScraper id — any mix, run in parallel and merged (`mergeCandidates`: exact matches first, one row per entry with every way it was found). Name and ROM info each switch off with one tap. A game's previous match id is sent as `previous_id` and labelled "previous match", never "exact". A lookup that cannot run says why. A filename match is **verified** (`verifyFilenameMatch`) before dump-specific values (ROM region, release date of this version) may be saved; a hash match marks the variant `rom_status='verified'`.
- **Review** (`TgScrapeReview`): every field yours-vs-theirs with Keep / Fill / Replace (Fill only on an empty field, Replace only on a filled one; identical and absent fields fold into one line each); pickable title region and description language (sent as `overrides`); every media file ScreenScraper has, one card per type with preview, version (region/disc) and **Copy / Online / Skip** (+ group "All:" shortcuts); "Everything else" (every regional title/date, every rating board, series/themes/styles, tips, hacks without download links, control mappings, matched dump + hashes, every known dump, and their raw answer). One sticky Save with a live summary; the result screen lists each field old → new, every file copied/online/failed (with the reason, e.g. "storage budget reached — shown online instead"), with **Undo**. **Recent saves** (from the journal) keeps Undo available later.
- **Many games** (`TgScrapeBatch`): filters Not scraped / Old matches / No cover / No description / All + system; "Find matches for the next 10" (`find_batch`: previous id → filename (verified) → name), tick, "Save N ticked" (`apply_batch`, ≤5 per call, deadline-bounded, remaining ones reported as not started) using the saved "What to save".
- **What to save** (`screenscraper_prefs`, migration `104`, a jsonb doc normalized by `normalizePrefs`): per-field default policy, per-media-type mode, image size (0.5×/1×/1.5×/original), region and language order, the full-record switch, and the **storage budget** (default 800 MB, **never above 850 MB** server-side). The sheet shows the bucket's real usage by category (ES-DE originals / ES-DE covers / ScreenScraper / old previews) against the budget and the 1 GB plan, today's ScreenScraper allowance (requests + misses), and **Find unused ScreenScraper copies** (`cleanup`, dry run first, then delete).
- **Storage strategy — the 1 GB wall is the constraint** (Free plan: over it the project goes read-only and then answers every request with 402). **Copy** = a copy resized by ScreenScraper itself (`maxwidth` + `outputformat`, JPEG for big opaque art, PNG for transparency and small pixel-art screens — `outputFormatFor`), written only while `game_media_usage()` + a reservation for the whole save stays under the budget (`decideMediaModes`); otherwise it is shown online and the result says so. **Online** = nothing stored; the `screenscraper-media` proxy streams it when viewed (`ssImageQueue` loads 3 at a time with retries because the account has 7 threads). **Skip** = ignored. Defaults: box front/back, screenshot, title screen, fan art and HD logo copied (≈ 285 MB worst case for 1,100 games); 3D box, spine, texture, cartridge, Steam grid, logos, marquees and the manual online; composites, bezels, themes, pictograms and video skipped. Manuals and videos can never be copied. **The ES-DE pushes obey the same wall:** `esde-content-sync` and `esde-media-sync` refuse an upload that would cross 850 MB with 413 `storage_full`.
- **Credentials never leave the server.** Every ScreenScraper media URL carries devid/devpassword/ssid/sspassword, so none is ever stored, logged or returned: copies are downloaded server-side, and online images go through `screenscraper-media` (JWT verification OFF — an `<img>` sends no header), which only serves a request signed with HMAC-SHA256 over `jeu|system|expiry` (key `SCREENSCRAPER_MEDIA_KEY`, else derived from the service-role key), limited to fixed widths (120/200/360/640/1280), a whitelisted image/PDF/video content type, `nosniff` + a sandbox CSP, and one bare redirect hop. **Signatures expire** (end of next week, one value all week so browser caches stay stable) and are **never stored** — search results carry one, and the detail asks for a fresh one per visit (`sign` action).
- **What is stored:** columns per field policy (`games` + the primary `game_platforms` row: release date, ROM region, their /20 score ×5); image columns (`primary_cover_url`/`screenshot_url`/`fanart_url`) only ever take a STORED copy (a proxied cover in the grid would be a request per card); `games.media` only the list-read types (`LIST_MEDIA_TYPES`: box-2D, box-3D, fanart, ss, sstitle). The match marker is **`games.ss_jeu_id`** (+ `ss_scraped_at`) — **never `external_source`/`external_ref`**, which belong to the ES-DE sync (the old scraper overwrote them and broke `esde-sync`'s upsert key; migration 104 repairs those rows). `provider_data` holds only a small v2 pointer (`{v:2, fetched_at, run_id, jeu_id, rom_id, system, matched_by, verified_rom, saved, linked (type → chosen version), media_count}`); the heavy record — normalized summary incl. the full media inventory, and their raw answer when "Save their full record" is on — lives in **`game_scrape_records`** (one row per game, owner read-only, service-role written, no audit trigger), so the library list never carries it. The detail's **ScreenScraper** section (`TgDetailScreenScraper`) reads it for the open game only: every file (copies from Storage, the rest online, every version under "Show all"), the full record, and **Undo last scrape**.
- **Journal:** every apply writes `scrape_decisions` (browser: **read-only**; written by the function only, no audit trigger) with `written_values`, `prior_values` and `replaced_paths` (migration 104); a save whose journal row is refused writes nothing. Undo is **newest-apply-only per game** — once undone, the older apply never becomes undoable (its copies were deleted when the newer one landed) — and "undone" is tracked **per journal row** (the undone row's `written_values.undid` names the apply it reverted; older undone rows fall back to their run). It restores a prior value only where the live value is still what was written (a later edit is kept), goes through a column allow-list, deletes the heavy record, and removes stored copies nothing references any more. **A game's own "Undo last scrape" (detail, Saved screen) undoes only that game** (`undo` with `game_ids`) — a batch shares one run id, and undoing the run from one game used to revert the whole batch; run-wide undo lives only in Recent saves and "Undo this batch". Every undo asks first; the detail and Recent saves offer Undo only when the server would do it (`ssJournal.ts`, the same newest-only rule). Pre-104 rows (no prior values) undo to empty, which was the old fill-only inverse.
- **Re-matching** (a different entry than the game's current match) reverts the previous apply only **after** the new entry has been fetched and checked (a failed lookup never throws the old match away), then clears every column still showing one of that game's copies (`scrubCopies`), so an entry applied twice by mistake leaves no art behind. A copy that cannot be (re)made — quota, unknown usage, budget — **keeps** the copy the game already has; a copy one of the game's columns still shows is never released.
- **Match proof:** a hash lookup is exact only when the returned dump carries a hash that was asked for (`verifyHashMatch` — ScreenScraper answers an unknown hash with its filename guess); a filename answer is verified (`verifyFilenameMatch`). Without proof, the dump's region and version are not written and the review does not offer them; "ROM verified" only comes from a hash.
- **The handheld's pictures count:** an image column that is empty while ES-DE already uploaded that picture (screenshot, fan art…) is not "empty" — Fill skips it on the server, and the review shows the handheld picture as yours (Replace, never a silent Fill). The review's starting copy decisions are the same `decideMediaModes` Many games uses (a copy only when the game will use it).
- **Quota:** `requeststoday` and the miss counter are ACCOUNT-wide (the handheld's ES-DE scraper spends them too), so search/apply/batch refuse below a floor (300 requests / 50 misses) rather than assuming a fresh budget; ScreenScraper's plain-text errors (often HTTP 200) are classified (`classifyText`: closed, busy, quota, no match).
- **Cleanup** pages everything past PostgREST's 1,000-row cap (`game_media_scrape_objects` is ordered and returns `created_at`), aborts before deleting anything if any read fails, and never touches a copy younger than 30 minutes or one a save made in the last hour (it may still be writing its game). The storage split identifies ES-DE covers by what a variant's `cover_url` points at (originals can be WebP too).
- **Proxy details:** the upstream timeout covers only the wait for response headers (a long manual or video is never cut off mid-file); manuals are served without the sandbox CSP (PDF viewers refuse to render under it) — type allow-list and `nosniff` still apply.
- **Layout:** results and review side by side only at desktop widths; phones and tablets use the step flow (Back to results in the phone header, an inline Results link on tablets, the results' scroll position restored); the media grid follows its own width (container queries). Many games keeps lookups and saves in the page store (`scrapeBatch.inFlight`) so leaving mid-run neither loses results nor sends a game twice, and refreshes the library once per save.
- **Shared code:** the pure modules in `src/features/games/scraper/` (`ssTypes`, `ssMediaCatalog`, `ssRules`, `ssProxy`, `ssPlan`) are GENERATED into both functions by `scripts/sync-screenscraper-shared.mjs` (`--check` in CI-less review); `scripts/verify-screenscraper-v2.cjs` (142 assertions, incl. credential stripping, token parsing, mapping, planning, merging, filename and hash verification, media-mode decisions against the budget, policies, prefs, proxy parsing/signing/expiry, and the generated regions being current) and `scripts/verify-tg-scrape-model.cjs` (59 assertions, incl. the journal's newest-only undo rule) cover them.

## IGDB — game length, scores and a link (01.10.2026, migration `121`)

Its own source, deliberately **separate from ScreenScraper** (owner: "separate from screenscraper"): match marker `games.igdb_id` (never `ss_jeu_id`/`external_*`), its own columns (`igdb_slug`/`igdb_url`, `igdb_match` steam|exact|picked, member/critic/total scores 0–100 + counts, `ttb_main/extra/full_seconds` + `ttb_count` from IGDB's `game_time_to_beats`, and a small `igdb_data` jsonb: themes, modes, perspectives, franchises, engines, studios, platforms, release date, summary, ≤ 10 similar games), and it never writes a title, cover, description or any other column. Works for **every library** (retro, Steam, PlayStation).
- **`igdb-api`** (JWT ON, writes scoped to `getUser`): Twitch app Client ID + Secret (Edge Function secrets `IGDB_CLIENT_ID`/`IGDB_CLIENT_SECRET`) → app token by client credentials, kept in memory; calls run one at a time ≥ 260 ms apart (IGDB: 4/s, 8 open, 500 rows, 10 per multiquery), one retry on 429/401. Actions `status` · `match` (≤ 50: Steam rows by app id through `external_games` with the Steam `external_game_source` looked up by name, the rest by `search` in multiqueries of 10, `version_parent = null`) · `search` · `apply` (≤ 50, fetches `games` + `game_time_to_beats` and writes) · `refresh` (200 matched rows per call) · `unlink`. Field names from api-docs.igdb.com (v4; the deprecated `category`/`collection` are not used) — **not yet run against a live account**.
- **Matching** (`igdb/igdbMatch.ts`, pure; `verify-igdb-match`, 56): titles normalised (region/dump tags, accents, ™, punctuation, leading/trailing "The", roman numerals → digits **except X** — "Mega Man X" is not "Mega Man 10"), compared with IGDB's alternative names too; platform (this app's key → IGDB platform ids, IGDB's platform names as fallback; a signal, never a filter) and year (±1) add or subtract. **Exact** = same title + nothing disagreeing + platform or year agreeing + not a DLC/bundle/pack; two exact rivals the year can't separate are both demoted to "likely". Steam app-id matches are exact whatever the title says.
- **Games → IGDB** (a tool section next to Scrape; `components/igdb/`): filters Not matched / To review / Matched / No length / All × library; **Match N games** runs 25 per request with a progress bar and Stop (the run lives in `igdb/igdbBatchStore.ts`, so leaving the page doesn't stop it), saves exact matches by itself, leaves the rest with their best result to tick (**Tick all likely**, **Save N ticked**), each row has Results / Search by hand / Change; **Refresh scores and lengths**. Not configured → the Twitch setup steps. The library refreshes once per run.
- **Detail → IGDB block** (`TgDetailIgdb`): How long to beat (Main story · + Extras · 100 %, members count, "You've played X of about Y"), Scores (Members · Critics · Overall with counts), facts from `igdb_data`, IGDB's summary only when the game has no description, Similar games ("In your library" opens it), **Open on IGDB**, Change match, Remove match (confirmed). Unmatched → Find on IGDB.
- **Uses:** sorts **Shortest first** (`gameLengthSeconds` = extras, else main story; unknown last) and **IGDB score**; the Play Queue's estimate uses each game's IGDB length minus what you've played, the median of your completed games only for games without one (`queueInsights.fromIgdb`). Lists read the promoted columns (one missing-column group drops all IGDB columns at once before 121, `COLUMN_GROUPS` in `gamesApi.ts`); `igdb_data` is read per game (`fetchIgdbData`).
