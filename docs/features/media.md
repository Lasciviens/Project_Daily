## Media Feature Detail
Standard page frame; the header holds ONE control (Overview · Library · Lists · Stats, full width on a phone), in the header band with the film strip (`MediaHeroArt`, THEME.md §6.5; it was behind the search card until 12.10.2026). The Movies | TV switch (`MediaTypePills`) sits with what it scopes — beside the search box (carrying each type's result count while searching; the results have no type pills of their own) and in the Library view's controls; Lists and Stats cover both types and have none (design pass 03.10.2026). Layout is a PageBoard (`mediaBoard.ts`) of ONE column at every width (owner, 05.10.2026 — the right-hand library/tools column is gone): the search card (with **What to watch?** as an icon button beside the box — `WhatToWatchButton` opens the whole picker in a `ModalShell`), Continue watching, **Coming soon** (a `CollapsibleCard`, always closed at first), then Discover across the whole page with bigger posters (`DISCOVER_GRID`: 11rem from a 70rem grid). Poster grids are three across a phone (`POSTER_GRID` 6rem, 9rem from a 40rem grid). Discover's tab row shows a › button while more lists sit beyond its edge (`useScrollEdges`, shared with Games); its Filters button is icon-only below 36rem. Search results: Sort + a Filters toggle (genre/year/score/not in library open under it, wrapping). Coming soon shows placeholders while the library loads. **Upcoming episodes** (Coming soon, Airing this week on Home/Daily) only for shows you're Watching or have Completed (`libraryModel.showsEpisodes`) — Trakt's "my shows" calendar also holds the watchlist. Continue watching hides playbacks paused over 60 days ago behind "Show N older" (no card when only old ones remain). In the title popup the poster's rail carries **Follow** and **TMDB** beside the poster, the Queue button reads "+ Queue" / "Queue #3", and a Watching movie says when (`MovieWatchingInfo`: Trakt's paused playback "Paused at 42% on …", else "in your library since …" — movies keep no start date). Titles open as the `media` entity popup (`MediaDetailModal`); TMDB reads use `qk.media.tmdbQuery` + `STALE`. Key components:
- **Search (03.10.2026, round 2 same day)** — `MediaSearch` only edits the query. `useMediaSearchSession` keeps the box in LOCAL state and writes `?q=` once typing settles (200 ms); the first letter pushes ONE history entry tagged `{mediaSearch:true}`; ✕, Esc, the Overview tab, Back **and emptying the box** pop exactly that entry and put the overview back at the top. While searching, `MediaSearchResults` takes Discover's slot (Continue watching and, on a phone, the tools step aside): both types searched from one letter on (`useSearchTitles`, infinite, `keepPreviousData`), one compact scrolling row — Movies N · TV N, sort (Best match/Newest/Oldest/Best rated), Genre, Year, Score (needs ≥ 20 votes), Not in library, Clear — no "Results for" heading; filters run over the loaded pages (pure `searchFilters.ts`, `verify-media-search`) and load up to 6 pages by themselves when they leave fewer than 12. A title opens as the popup over the results. The search box is its own card; **Continue watching is a separate card under it** (hidden while searching): Completed/Dropped titles are left out, a title not in the library says so, ✕ removes the playback on Trakt (`playback_remove`).
- **Overview | Library | Lists** (header control, `?view=library&status=` / `?view=lists` so Back returns to the overview; 30.09.2026, owner: "too crowded"): the overview has no library card any more (05.10.2026; the Library tab is the same list); `LibraryView` is the whole library (status chips, title search that folds accents, sort Recently added / Title / Release year / Release date (soonest) / Your rating — each status opens in its own default order, `defaultSortFor`: Coming soon by release date, nearest first — a poster grid `minmax(6.5rem,1fr)`). One pure model, `libraryModel.ts` (`verify-media-library`). **Groups: Coming soon / Wishlist / Watching / Paused (TV) / Completed / Dropped.** **"Coming soon" is DATE-derived, not a manual status** (release/first_air date in the future) — the fix for "Wishlist ≠ Coming soon": Wishlist = want-to-watch AND already out; Coming soon = not out yet. Deriving it also auto-resolves the legacy manual `upcoming` movie status (nothing ever migrated it, so a released film stayed pinned under a stale "Upcoming" label forever). `CompactLibraryStrip` was deleted.
- `DiscoveryTabs` — Today/This Week/Popular/Upcoming/Norway tabs (scrollable row, refresh button, error state; the poster grid follows its own width: 6.5–9rem posters on a phone, from 36rem the columns share the row (`minmax(8rem,1fr)`)); manual sync only (24h stale)
- `EpisodesPanel` — season selector, per-episode watched checkbox (saves `watched_on`), plan checkbox → time blocks, Select All season. **Watched state is Netflix-style obvious**: season tabs show `n/total` + a green progress fill (✓ when complete); watched rows get a green tint, dimmed title and a filled green ✓ badge. Planning a **single** episode stamps `season_number`/`episode_number` on the created `time_blocks` row (migration `043`) — `source_id` alone identifies the show, not the episode, so this is what lets a DB trigger match "this episode got marked watched" back to exactly the one planned block and delete it. A multi-episode batch plan is intentionally NOT stamped and NOT auto-cleaned (deleting a 3-episode reminder because one was watched would be wrong); see AGENTS.md's "Linked-entity sync".
- `MediaDetailBody` = `MediaDetailInfo` (TMDB facts, error + Try again) + `MediaLibraryControls` (add/remove — remove confirms — status, rating, note, next episode): personal 1-10 rating, **private note** (`personal_note`, saves on blur), status buttons (movie completion stamps `watched_at`; TV completion/first-watch stamps `finished_at`/`started_at` — none of these columns were ever written before). Status pills: Wishlist/Watching/(Paused TV)/Completed/**Dropped**; the manual "Upcoming" pill was removed (coming-soon is date-derived). **"Advance to next episode"** uses `useNextEpisode` (real season rollover), fixing a bug where the last episode of a season recorded a nonexistent `S?E(n+1)` instead of `S(n+1)E1`. Star fill is `accent-500`.
- `TonightPicker` (random from My List / Trending / Popular) · `ReleaseCalendar` (upcoming from wishlist) · (both on the shared `CollapsibleCard`; the old `MediaStats` card is replaced by the Stats view, see Round 6) · `MediaHeroArt` (a still drawn film strip, the page's header art; replaced the rotating backdrops)
- **Episode watched has ONE write path:** `useMarkEpisodeWatched` (single or batch, optimistic with rollback, refreshes the `episodeWatched` group) — used by `EpisodesPanel`, `MediaLibraryControls` and Daily's `WatchNextCard`. Marking an already-watched episode never overwrites its date (`markEpisodeWatched` returns the existing row — it used to stamp today over a Trakt date). `EpisodesPanel`'s action bar splits the selection: unwatched → Mark watched; watched → **Watched again** (`rewatchEpisodes`: one more `media_watches` row at the chosen time — every other watch keeps its date; rows show "3 watches · last 08.01.2026") or **Not watched** (asks, then "· Undo"). A watched movie shows the same pair in `MovieWatchedControls` (Watched again = one more watch; Not watched asks, then Wishlist with no watches, "· Undo"). See **Every watch with its own date** below (migration 149). Every one of these reaches Trakt through the outbox (below). A watch date Trakt doesn't know shows as "date unknown" (`traktDates.ts`).
- **Watches** (`WatchesSheet`, 14.10.2026 — replaced the 07.10.2026 "Plays and date" sheet, `PlaysSheet`/`usePlaysPrompt`, which set a play count and the one kept date): a faint history icon on a watched movie and on each watched episode row (and **Watches** in the selection bar) opens its watch list — each watch with its own date (DD.MM.YYYY or "date unknown"), a pencil to change that one date (a day or Date unknown), a bin to remove that one watch (the one delete flow with Undo, `useDeleteWatches`; the last watch = not watched / back on the Wishlist, and on Trakt only that play goes), and **Add a watch**. A placeholder waiting for Trakt's dates is shown, not editable. Before migration 149 the list only shows the plays at the one kept date. (Migration 132's play-count outbox rules are superseded by 149.)
- **Spread watched dates** (Episodes → Spread, `SpreadWatchedSheet`, pure `spreadWatched.ts`, `verify-spread-watched` — 2,148 assertions in four time zones): mark a run of episodes (from–to, skip or re-date watched ones) between a start and finish date, minus any number of breaks and turned-off weekdays, in a Steady / Mixed / Binge pattern (More options: most a day, evening start, episode length, never before air date). Days are yyyy-MM-dd UTC maths; the exact count is kept, the first and last active day always get one, the plan is seeded (Shuffle) and replans on every change; an impossible cap offers "Allow N a day" / "Finish on …". The result (headline, days, month bars) sits beside the fields from tablet width. Saves through `useMarkEpisodeWatched` / `useSetEpisodeDates` (`spreadWrites`: an unwatched episode is marked, a watched one gets one more watch or one watch re-dated). **Spread over dates…** is the when-watched sheet's 5th option whenever it asks about more than one episode (`askMany`, `offersSpread`; owner, 13.10.2026): Mark watched, Watched again, Up to here, the gaps' Mark them, Change date / Dates, and completing a series. From the sheet the Spread popup plans exactly those episodes (`only`, `fixedSpreadEpisodes` — shown as "S01E02, S01E05 · 2 episodes", no from–to pickers) and saves by its `mode`: `watched` marks them, `again` (Watched again) adds one more watch to each at its planned time — the start is suggested as the day after their latest watch (`spreadDefaultStart`) — and `redate` (Change date) moves ONE watch of each to its planned time (the latest, or the first when Change date's "Which watch gets the new date?" said so — `WatchPickSheet`), every other watch keeps its date. One title or one episode keeps the four answers (a movie has nothing to spread). Completing a series: its save marks the episodes then sets Completed with the plan's first/last times as `started_at` (kept if set) / `finished_at`; adding a new title this way adds it as Watching first, so closing the popup unsaved leaves it Watching.

DB tables: `movies`, `user_movie_entries` (watching/wishlist/completed/dropped/upcoming — `upcoming` is movie-only by design), `tv_series`, `user_tv_entries` (watching/wishlist/completed/dropped/paused), `user_tv_episodes` (season_number, episode_number, watched_at — **the ONE source of truth for TV progress**: a row with a watched_at is a watched episode), `media_watches` (migration 149: **every watch** of an episode or a movie with its own date; the entry/episode rows' `watched_at` + `repeat_count` are its cache). Both entry types have `rating int (1-10)`, `genres jsonb`, `personal_note`, `priority`, `rewatch_round` (149).

**TV progress architecture (migration `050`, root-cause fix)**: THREE disjoint progress systems used to coexist — a legacy `watched_episodes` table (bulk-marked data incl. The Office's 169 rows lived ONLY there; no current code read or wrote it), `user_tv_episodes` (what the UI writes), and `user_tv_entries.current_season/current_episode` cache columns that migration 011 promised "application logic" would maintain but never did — so Daily Watch-next, the AI briefing, Ask-AI context, `get_media`, the detail chip and MediaStats all showed S1·E0 forever despite hundreds of real watched rows. Migration 050 backfills `user_tv_episodes` from the legacy table (union — each had rows the other lacked), DROPS the legacy table, installs a trigger keeping the cache synced to max-watched, one-time recomputes it, and adds the missing UPDATE RLS on `movies`/`tv_series` (metadata upserts silently couldn't refresh — rows were frozen at first insert). `markEpisodeWatched`/`unmarkEpisodeWatched` also sync the cache app-side (instant UI, works pre-migration). Anything needing "next unwatched" uses `useNextEpisode` (max watched + TMDB season data → SxxEyy/title/air-date, rolls into the next season, `caughtUp` when none). **The cache columns are for cheap reads only — never write them directly.**

TMDB images: `posterUrl(path, size)` from `src/integrations/tmdb/client.ts`.

**Trakt (phase 1 of `docs/trakt/REFERENCE.md`, 30.09.2026).** Trakt becomes the source of truth for what it holds (watched + play counts, movie/show ratings, watchlist + order, favorites, dropped shows, paused progress, notes, the episode calendar); app-only data (paused status, dropped movies, priority, plans) stays local. One title = one row by `tmdb_id`; plays lived in the existing `repeat_count` (= plays − 1, now on `user_tv_episodes` too) — no per-play history then (superseded 14.10.2026: every watch is a `media_watches` row with its own date, migration 149, below), no season/episode ratings, and `personal_note` IS the Trakt note. Built so far: migration `116` (ids + RT/Metacritic columns with partial unique indexes, the user-table columns, `trakt_tokens`/`trakt_sync_state`/`trakt_unmatched`/`trakt_outbox`), the `trakt-api` edge function (connect/status/disconnect/snapshot), and the Trakt card on Settings → Subscriptions with **Preview import** — a dry run (`traktPreview.ts`, pure, `verify-trakt-preview`) that writes nothing. The OAuth return (`?code=&state=` before the hash) is parked by `captureTraktCallback()` in `main.tsx` before the router starts, then finished by the card. `trakt_tokens` is service-role only and never enters `DB_CATALOG`. **Trakt API change (live since 03.07.2026, trakt-api discussion #775):** `/sync/watched/*` is paginated (100 items without a limit) and leaves out seasons unless `extended=progress` (≤ 100 per page) — the first snapshot read shows with no episodes and stopped at 100 movies; every list is now read through `getAll`. The preview's **Copy report** puts every count and the titles behind it on the clipboard (`previewReport`). **Phase 2 — the first import (30.09.2026):** the preview's **Import now** (confirmed once) runs `traktImport.ts` over a plan from the pure `traktImportPlan.ts` (`verify-trakt-import-plan`, 30): library first (catalogue rows from TMDB for new titles, entries, episodes, trakt/imdb/tvdb ids backfilled — a clashing id is skipped), then `trakt-api`'s `push` action sends the app-only facts (history — one entry per play, a minute apart — ratings, watchlist add/remove, dropped shows via `POST /users/hidden/dropped` (API blueprint, Add Hidden Items), one write per second) and stamps `trakt_sync_state`. Rules: Trakt wins where both know a fact; **watched or watching beats wishlist on both sides** (a watched title leaves the Trakt watchlist, a wishlist show with watched episodes becomes Watching); a show with episodes is Completed once every aired regular episode (TMDB `last_episode_to_air`) is watched, else Watching (Paused/Dropped kept; no TMDB details → Watching). Every write is an upsert, so a second run plans no pushes and no episode writes. Not yet: playback/favorites/notes (phase 5). **Phases 3–4 — automatic two-way sync (30.09.2026, migration `117`):** (1) **App → Trakt:** triggers on `user_movie_entries`/`user_tv_entries`/`user_tv_episodes` queue every change to a Trakt-held fact in `trakt_outbox` (watched, extra plays, rating, watchlist, dropped; a movie moved to Wishlist or removed, and an episode unmarked, remove their plays) — from ANY writer (web, AI, SQL), only while Trakt is connected. A write that carries the `x-trakt-sync: 1` request header (the sync's own client; PostgREST exposes it as `request.headers`) is skipped, so nothing loops. (2) `trakt-api`'s **`sync`** sends the outbox oldest-first (same-op runs batched, 1 write/s, a failure keeps its order and backs off), then reads `last_activities` and, only when it changed, mirrors Trakt into the library with the pure `traktSyncPlan.ts` (`verify-trakt-sync-plan`, 39): additions AND removals, leaving alone items still waiting in the outbox or just sent this run; app-only states (Paused, a Watching/Dropped movie, a show marked Watching/Completed without episode rows) stay; an entry is deleted only when Trakt holds none of its facts and it has no note; more than max(10, 10 %) removals at once are **held back** until the owner confirms on the card. Runs from the pg_cron job `lascis-trakt-sync` (:07/:37, `x-sync-secret`), 4 s after a media edit here (`scheduleTraktSync`, silent — errors land on the card), and **Sync now**. One run at a time (`trakt_sync_state.sync_started_at`, stale after 5 min). ## Every watch with its own date, and rewatching (migration 149, 14.10.2026)

**Why.** The app kept ONE date per watched episode/movie (`watched_at` = the latest watch, `repeat_count` = plays − 1) while Trakt keeps every play with its own date. The owner used Spread → Change dates on 73 Game of Thrones episodes; the outbox answered each date change with "remove ALL plays of the episode + add every play at the new date" (120/132), wiping their 2018 first-watch and 2026 third-watch dates on Trakt, and Watched again moved the app's one date to the newest watch. (The owner repaired those 73 episodes on Trakt with a one-off SQL; the first history pull after 149 links the watches here to those real plays.) Trakt's API as used here: `docs/integrations/trakt.md`.

**The model.** `media_watches` = one row per watch: `kind` (episode | movie), the item (an episode names `tv_series_id` + `season_number` + `episode_number`, and `episode_id` is filled by the database; a movie names its `movie_entry_id`), `watched_at` (unknown date: the epoch for an episode, NULL for a movie — the 117 rule), `trakt_history_id` (Trakt's id of that one play, unique per user, set only by the sync) and `source` (`app` | `trakt` | `backfill`). Owner RLS + owner lock; `media_watches` is `rw` in `ai-proxy`'s `DB_CATALOG` (the owner may say "I watched it again on …"; `trakt_history_id` is in `AI_NO_WRITE`). `trg_audit` logs the app's own writes only — a Trakt pull is bulk-synced (like `hevy_*`), so Undo this save can't rewrite Trakt from a pull and the first pull doesn't log tens of thousands of rows. Every existing play became a watch at the kept date (`source = 'backfill'`, a **placeholder**; movies only when Completed — a movie play exists only once it was completed). Nothing was sent to Trakt.

**The cache and the three doors** (rules in the database — `docs/backend/database.md`): `user_tv_episodes.watched_at`/`repeat_count` and `user_movie_entries.watched_at`/`repeat_count` are a CACHE of the watches (latest date, count − 1), kept by `trg_media_watch_cache`, so every reader (progress, next episode, the brief, `get_media`, `phone-gateway`, …) keeps working. A watch for an episode the app has no row for creates that row (first watch = watched); removing the last one sets it to not watched (`watched_at` NULL — the row stays, so an Undo puts the watch back on it). A movie's first watch makes a Wishlist movie Completed, removing its last makes a Completed movie Wishlist (not for the sync, which decides statuses itself). A watch of an episode — a rewatch too — removes its planned block (`trg_media_watch_cleans_planned_block`, 043's rule; 043's own trigger fires only when the episode row is new). Old writers still work: a write to the cache columns (the assistant's `db_update`, `markEpisodeWatched`'s upsert, the Trakt summary writes, SQL) is translated into watches at the end of the transaction (`trg_media_watch_reconcile`, deferred — an Undo that puts back an entry and its watches is seen whole): a watched row with no watches gets 1 + `repeat_count` of them (a movie only when Completed); more plays add watches at the written date; fewer plays remove the most recently added (never the latest); a new date moves the latest watch; not watched (Wishlist, or an episode's `watched_at` set NULL) removes them all. **A sync write only ever adds placeholders** — it never removes or re-dates a watch (a linked one is Trakt's play); the count mismatch makes the pull read that title and remove by id. Only the sync may set `trakt_history_id`/`source` (`media_watch_before`); a new date from anyone else drops the link (the old play is removed on Trakt, the new one added). A watch put back before its episode row (Undo this save runs its steps newest first) raises a foreign-key error that 150 retries — never a second episode row. **Undo this save** (Developer → Activity, migration 150) runs through the same triggers, so undoing a save that touched watches (a Spread re-date, a removed last watch, Not watched, the assistant's old-style rewatch) moves, adds or removes single plays on Trakt — never an episode's whole history; a restored watch comes back unlinked (its old play was removed on Trakt). Scenarios: `scripts/db-tests/media-watches/` (`verify-db-media-watches`, 106 checks on Postgres 16, with the real 144 and 150).

**App → Trakt** (`trakt_outbox_watch`): a new watch → `history_add` at its own date; a removed watch → `history_remove_play` — ONLY that play, **never a guessed one** (`playIdsToRemove` / `playToRemove`): by its `trakt_history_id`, or — not linked yet — a play at that **exact second** when Trakt has more plays there than the watches left here account for. Anything else waits ("waiting for Trakt's play ids" on the Trakt card, retried every 30 minutes; the title's next pull links its watches) and is dropped after 7 days with a message (Trakt may still have that play; the next pull shows it again). Before the first pull has linked the watches (`trakt_sync_state.history_synced_at` NULL) no unlinked remove is sent. A new date on one watch = remove that play + add the new one; **removing an item's last watch is that one play too**. The whole item's `history_remove` is queued only for an explicit unmark — the episode row deleted ("Not watched", or a writer setting it NULL), the movie moved to Wishlist or removed — and its question says it removes every play on Trakt. Cancelled before anything is sent, across every waiting row whatever its `next_retry_at` (`cancelledOutboxRows`): an add not sent yet (or failed and waiting) followed by a remove of that watch; a remove followed by an add of the same watch at the same second (deleted, then Undo before the drain). Item keys are the old ones (`ep:…`, `movie:…`), so a waiting watch change keeps the mirror off that item, and `seq` keeps the order. A `history_remove_play` is queued with `next_retry_at` **7 days** ahead: the trakt-api deployed before 149 deleted ops it didn't know without sending them, and a deploy runs migrations before functions (a failed function deploy can leave the old one live for days). The current trakt-api sends a never-tried one at once (`attempts = 0`), so the hold only hides it from the old function.

**Trakt → app** (`syncWatches` in `trakt-api`, pure `traktWatchPlan.ts` GENERATED by `sync-trakt-shared.mjs`, `verify-trakt-watch-plan`): after the library writes, the titles whose plays here differ from Trakt's watched summary (another count, another latest date — from the cache columns — or a watch not linked to a play yet) are read one by one (`/sync/history/shows/{trakt id}`, `/sync/history/movies/{trakt id}`). A **whole-history read** — the first run after 149 or a reconnect (`history_synced_at` NULL; the run happens even when Trakt reports no change), Sync now, a progress reset, more than 25 differing titles or one without a Trakt id — reads the movies' history at once and the shows title by title, keeping its place in `trakt_sync_state.history_cursor` (the last title done), so it **resumes in the next run** and never depends on one edge-function run's time; `history_synced_at` is stamped when it reaches the end. Each item Trakt's summary lists is matched play by play (`matchItem`): a watch linked to a play Trakt still has keeps it; the rest pair up by the same second, then in date order (Trakt's date wins; placeholders are simply replaced); extra plays come in, extra watches go. Guards: items waiting in the outbox are left alone; items the summary no longer lists stay the summary plan's (with its held-back guard); an item whose history came back empty is left alone; a pull never removes more than max(10, 10 %) of the watches it reads by itself (the rest waits for "Review and apply" on the Trakt card, `watchRemovalsNeedConfirm`); a play another watch still holds (23505) is skipped and counted; more than 200 pages of any list is an error, not partial data. Only the import reads every watch's date (it sends the app-only ones at their dates); a sync reads a title's watches when it reads its plays. Reads are per title rather than by date: Trakt's `start_at` filters by the play's own date, so a backdated play (like the GoT repair) would be missed. Disconnect unlinks every watch and clears the stamp.

**Screens.** An episode row shows one short line — "Watched 08.01.2026" or "3 watches · last 08.01.2026" (`watchesLine`; the whole list is in its sheet) — and "· Trakt dates to come" while its watches are placeholders. The history icon (and **Watches** in the selection bar for one episode) opens the watch list (`WatchesSheet`): every watch with its own date, a pencil to change that one date, a bin to remove that one watch (the one delete flow with Undo), **Add a watch**. **Placeholders** (`isPlaceholder`: `source = 'backfill'`, no Trakt id, Trakt connected) read "waiting for Trakt's dates" and can't be changed or removed until the next sync links them — which Trakt play they stand for isn't known. **Mark watched** gives the first watch, **Watched again** adds one, **Change date** (selection, Dates, the movie's button) asks "Which watch gets the new date?" when there are several — one title lists its watches (latest first; placeholders shown, not choosable), several episodes choose the latest (default) or the first of each — then the when-watched sheet, and moves only that watch; an episode whose watches all wait for Trakt is left out with a note. **Not watched** (episodes and movies) asks first ("removes … EVERY play … on Trakt") and offers "· Undo" (`useUnmarkEpisodes` — the episode rows with their watches through `app_delete_rows`; `useMovieNotWatched` — Undo adds the watches back at their dates). Spread's modes: Mark watched → first watches, Watched again → one more watch each at the planned dates, Change dates → the chosen editable watch (latest by default) of each. Before migration 149 a date change writes nothing and says "Changing a watched date needs migration 149" (the old one-date path re-sent every play); mixed batches send only the watches they can name. Stats (`yearReview.ts`): every watch counts on its own date.

**Rewatching** (owner, 14.10.2026: "have it on watching while it's already completed … it should still follow up my episodes like watching acts"). `rewatch_round` (the round's number, 2 = the second time through) and `rewatch_started_at` (when it started — set by the database, to the second) on `user_tv_entries`/`user_movie_entries`. On a Completed title, **Watch again** starts a round: a show's sits beside its finished date (`SeriesFinishedControls`), a movie's fills the status grid's free cell; the Watching status itself stays plain Watching. **An episode is done for the round once it has a watch since the round started** — dated since then, or added in the app since then (a rewatch logged on an older or unknown date); a pilot watched three times before doesn't count, an episode never watched before counts the same way, an episode that airs mid-round joins once aired (`inRound`, `doneInRound`). Next episode (`useNextEpisode` → Daily's Watch next "Rewatch · round 2 · 2/18", Home's Watched tile and brief, the title's Next episode, the episode list's "Next · round 2") = the first aired regular episode (an episode with no air date isn't aired) not done in the round (`nextInRound`, `airedRegularEpisodes`); marking it adds a watch (`again`), never moves a date. The title page says "Rewatching · round 2 · next S01E03"; season tabs count the episodes done in the round; **Watched up to here** stays one tap on every episode still to watch in the round and gives each one more watch. **The round ends by itself, in the database** (`media_rewatch_finished`, from any writer — a play scrobbled on Trakt too): a show when every aired regular episode by TMDB's data on `tv_series` (seasons + `last_episode_to_air`; else every regular episode watched before) has a watch of the round; a movie with its first watch of the round. Completed picked during a show's rewatch ends the round; during a movie's it adds the watch; leaving Watching/Paused clears the round (`media_rewatch_guard`). The Trakt sync never flips a rewatching title to Completed (`isRewatching` in `traktSyncPlan.ts`; the import too). Trakt's own "reset watched progress" is VIP-only and only changes Trakt's progress view, so the rewatch stays app-side; the sync still follows `reset_at` stamps as before (a full mirror).
