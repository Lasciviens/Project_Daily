# Food

> Moved out of CLAUDE.md on 13.10.2026 (word for word, apart from translated quotes). This file describes how the feature works and why. The rules Claude must follow while changing it are in `.claude/rules/food.md`, which Claude Code loads by itself when a matching file is read or edited.

## Food Feature Detail

User-visible name is **Food** (nav tab, CommandBar, page h1); route stays `/recipes` for deep links. `RecipesPage` has 5 tabs: **Today** (default) · **Library** · **Ingredients** ("Foods" on a phone) · **Meal Plan** ("Plan") · **Insights**. Header (owner, 06.10.2026: fewer rows on the phone): the tabs, then ONE row with the day picker (`FoodDateNav`: ‹ [Today | DD.MM.YYYY → month calendar] ›) and Log food (+ Add recipe on Library); from `sm` all on one row. On a phone that second row exists only on Today and Library. No banner photo (`RecipeBackdrop` was deleted as decoration). Every Food popup opens by id through `useEntityModal` (`food-log`, `food-log-edit`, `meal-plan`, `recipe`, `recipe-view`, `day-targets`); deletes confirm via `modal.confirm`.

**Data model — 4 tables** (after migration `061` unified plan + diary):
- `recipes` — title, description, `servings` (base count), instructions, `macro_mode` `manual`|`from_ingredients`, per-serving `calories`/`protein_g`/`carbs_g`/`fat_g`/`sugar_g`/`fiber_g`, `category` (breakfast/lunch/dinner/snack/supplement), `image_url`, `source_url`, `times_cooked`, `is_temp`.
- `recipe_ingredients` — name, `quantity` (nullable = to-taste), unit, note, sort_order, `library_ingredient_id` (nullable FK). Quantities are stored for the base `servings`; recipe macros are stored **per serving**.
- `recipe_ingredient_library` — reusable ingredient catalog, macros **always per 100g**, unique per `(user_id, name)`, + `fiber_g`, portion presets (`serving_label`/`serving_grams`, e.g. "1 scoop"=30g), `food_group`, `image_url`, and `source`/`source_ref` provenance (`off`, `dsld`, `matvaretabellen`, user's own; user's own wins on name conflict, attribution travels on the row, idempotent refresh).
- **`food_log_entries` — plan AND diary in one table**, discriminated by `status`: `'planned'` (intent; macros computed live on read) vs `'eaten'` (a real at-log-time **snapshot**). Planning → eating is a status flip. Slots: breakfast/lunch/dinner/snack/**supplement**; unlimited rows per slot; exactly one of `recipe_id` / `library_ingredient_id`+qty+unit / `custom_title`.
- **`water_log_entries`** (migration `067`) — one row per logged amount; the day's total = `SUM(amount_ml)`. **Deliberately its own table, never a food slot** — water carries no macros and must never enter the calorie ring. Owner-only RLS, `user_id DEFAULT auth.uid()`, no audit trigger (high-frequency, low audit value — same reasoning as the bulk-sync exemption).

**Load-bearing contracts (do not break):**
- **Totals are DERIVED, never frozen (user decision 26.09.2026 — reverses the old "snapshot at log time" rule).** An eaten row's macros always equal what its source adds up to now: a library item (per-100g × grams) or a recipe (per-serving × servings); a `'from_ingredients'` recipe's totals always equal its ingredients. Any add/edit/delete recalculates — past days included — because the user eats more or less based on these numbers. Migration `106` makes the database enforce it for every writer (web, `phone-gateway`, `ai-proxy`): triggers on `recipe_ingredients`, `recipes`, `recipe_ingredient_library` and a BEFORE trigger on `food_log_entries`. Custom rows (no source) and manual recipes keep their typed values, planned rows stay NULL, and a deleted source (FK `SET NULL`) leaves the last computed values. Until 106 is applied the web app does the same itself (`refreshEatenEntries` in `foodLogApi.ts`, called by `useUpdateRecipe` and `useUpdateIngredientLibraryItem`). Live data was repaired once on 26.09.2026 (4 saved meals, 25 eaten rows — e.g. Sushi 546 → 820 kcal).
- The original `UNIQUE (user_id, date, meal_slot)` on the old plan table **had to die** — it physically forbade "lunch = chicken + rice + broccoli".
- **Planned rows render muted "planned" and are NEVER added to the eaten total** (the ring sums `eaten` only) — counting them was visually contradictory with the ring.
- `dayNutritionApi`'s plan-side query deliberately does **NOT** select `recipes.fiber_g` (a missing column would error the whole plan query on old schema; plan rows don't feed the ring anyway).
- **Pre-migration fallback pattern (reused across the feature):** on a column-missing error (`42703` / `PGRST204`) retry once with the new column dropped — `createRecipe`/`updateRecipe` for `fiber_g` and `is_temp`, `create/updateIngredientLibraryItem` for `image_url`, and `foodLogApi`/`mealPlanApi`/`dayNutritionApi` for `status` (they fall back to the old two-table behaviour). This is what let the frontend deploy before migration 061 was applied.
- **Cache-key bug (real):** food-log hooks invalidated `['day-nutrition']`, which does NOT prefix-match the card's `['meal-plan','day-nutrition',date]` key — the card showed stale totals. Invalidate the actual key.
- **Recipe macros must follow their ingredients (real bug, fixed 26.09.2026).** Two disconnects froze calories: (1) the logger's "Save meal" stored `macro_mode: 'manual'` with a total computed once, so editing that meal's ingredients later never changed its calories — it now saves `'from_ingredients'`, and `RecipeModal` opens any manual recipe whose ingredients are all library-linked by weight (`canComputeFromIngredients`; links are only editable in from-ingredients mode, so only old saved meals look like this) as `'from_ingredients'`; (2) editing a library ingredient never touched the recipes built from it — `useUpdateIngredientLibraryItem` now calls `recomputeRecipesUsingIngredient` (recomputes every `'from_ingredients'` recipe using it, and switches those old manual saved meals over). Eaten diary rows follow too (see the derived-totals rule above). `replaceIngredients` also checks its delete error now (a failed delete + insert duplicated every ingredient).
- `macro_mode: 'from_ingredients'` is computed on save (`computeMacrosFromIngredients` in `recipesApi.ts`): sum each linked library ingredient's per-100g macros × `quantity/100`, ÷ servings. Only rows with a `library_ingredient_id` AND a weight/volume unit contribute; the rest are skipped and surfaced in the UI. `RecipeModal` previews the same math client-side (`previewMacros`). `dayNutritionApi` imports recipesApi's `WEIGHT_UNITS` (a narrower local copy once dropped 'milliliter(s)').

**Components / flows:**
- **`FoodLogModal`** — the build-a-meal logger (`sm:max-w-xl lg:max-w-3xl`, 2-column on `lg`: left = recents / saved meals / search / new ingredient, right = the basket). **Recents-only suggestions** — the alphabetical library dump was removed; ingredient match chips render only while searching. Grams or portion-preset tap; live kcal/protein total; footer shows remaining protein/kcal **after** this meal. "Save meal" is **save-only** (no auto-log) with a "Makes N portions" field, so a batch is stored at correct per-serving macros and you log your portion later. Basket rows are ONE line on every width with an always-typeable amount box (grams/ml); − / + beside it step by one portion when the food has one (owner, 07.10.2026 — a stepper-only row left no input).
- **Ingredients** (`INGREDIENT_BOARD`): the add/edit form is a sticky left rail; the food list spans the rest and splits its rows into 1/2/3 columns by its own width (68/100rem).
- **Favourites + hidden Recents (migration `087`, `food_favorites` + `food_recent_hidden`)** — Recent (`useRecentFoods`) is derived purely from eaten history and can't hold something you haven't logged in a while or want to guarantee stays reachable, so Favourites is a SEPARATE, pinned shortcut list, always rendered first. Both the Recents and Favourites grids are collapsible (chevron header, open by default) and share `FoodTile` (`foodLogKit.tsx`) — a photo tile whose main body is the "add this" tap target, with a ★ favourite-toggle and (Recent only) a ✕ "remove from Recent" corner button as SIBLINGS of the inner button, never nested inside it (a `<button>` inside a `<button>` is invalid HTML and gets silently hoisted out by the parser). Corner buttons are a deliberate 24px exception to the mobile-first 44px rule, matching the pre-existing `onEditRecipe` ✎ button's own precedent on the saved-meals strip — a secondary, occasional action layered on a dense grid, not the tile's primary ≥44px tap target. `FoodThumb` gained an optional `sizeClass` prop (Tailwind width/height utilities) for when a call site needs the thumbnail to shrink on mobile — an inline `size` px value always wins over a class, so the two can't be mixed at one call site; the Recents/Favourites grids use `sizeClass="w-9 h-9 sm:w-11 sm:h-11"` (was a fixed 44px at every breakpoint). Both tables are pre-migration-safe (`fetchHiddenRecentKeys`/`fetchFoodFavorites` degrade to empty; a write throws a named "migration 087 not applied" error).
- **"As meal" — several individually-logged items collapse into ONE compact diary line** (migration `087`, `food_log_entries.meal_group_id`). The real complaint: logging a lunch item-by-item (bread, chicken, onion, rice) turned the day view into a wall of separate rows. A checkbox in the basket header — squeezed into the existing "This meal · N" row, never its own row, default ON, only shown once the basket has 2+ items — tags every item in `handleSave`'s batch insert with one shared `crypto.randomUUID()` `meal_group_id` (a group of one has nothing to compact, so it's only assigned above 1 item). `dayNutritionApi.ts`'s `groupDayMeals()` (pure, order-preserving) collapses same-`meal_group_id` rows back into a `MealGroupRow` (summed macros, "`first item title` +N more") for display; `FoodTodayTab`'s slot list renders that as one row with a chevron — tap to expand into each item's own real row (still individually editable/deletable) via a per-slot-card `expandedGroups` set, collapsed by default. Pre-migration-safe: the query retries without `meal_group_id` on a `42703`/`PGRST204`, and `addFoodLogEntries` does the same on insert — every row then reads as its own ungrouped item, today's behaviour.
- **Meal-slot rows — all macros, aligned columns (real complaint, fixed).** Every logged/planned row used to show only calories + protein (`{protein_g}p`), and the amount was baked straight into the title string ("Chicken · 150g" — "the grams are glued to the name" per the report). `FoodTodayTab`'s `mealLine()` now splits `title` into name + quantity via `splitTitleQty()` (splits on the same " · " separator both `unifiedToMeal` branches already use, only treating the tail as a quantity if it starts with a digit — a name that legitimately contains " · " itself is never garbled) and renders TWO markups: a `hidden sm:grid` desktop row with the amount, kcal, protein, carbs, fat and fiber each in their own aligned `grid-cols-[...]` column (never crammed into the name), and a `sm:hidden` mobile version — the name/kcal/actions row, then a small `text-[11px]` macro-summary line underneath. Sugar is deliberately left out of this dense per-row listing (still visible via ✎ → `EditFoodLogModal`) — a documented simplification, not an oversight.
- **Temp meals (migration `066`, `recipes.is_temp`)** — a saved meal is **temp by default**: hidden from the Library grid (`RecipesPage` filters `!is_temp`) but fully usable — it appears in the logger's "Saved meals" strip, and hover (desktop) / the ✎ editor (mobile, `onEditRecipe` → RecipeModal) reveal its ingredients. An inline "Library" checkbox on the save row promotes it to a permanent Library recipe.
- **`MealPortionPicker`** — tapping a saved meal picks a free **%** of the WHOLE batch (25/50/75/100 chips + free entry, + grams when total weight is computable) → `logRecipe(recipe, servingsEaten)` where `servingsEaten = pct/100 × recipe.servings`. `RecipeDetail`'s "I ate this" is a free-entry portions input with a "% of the batch · logs N kcal" hint.
- **`EditFoodLogModal`** — edit a logged row (was delete-only): kind inferred from the row (library → edit grams + re-snapshot · recipe → edit servings + re-snapshot · custom → edit title+macros), and any of them can move meal slot. Wired to ✎ on every diary row (Daily NutritionCard, FoodTodayTab, MealPlanWeek's eaten chips). `DayMeal` carries a `logEntry` sub-object (raw ids/qty/unit) so the modal knows the row kind.
- **`MealPlanWeek`** — 7-day × slot grid; each cell shows 📋 planned (tap → `AssignMealModal`) + green ✓ eaten chips (tap → edit), because a Today-logged day used to leave the plan grid empty. Empty cell = the whole area is one big centered `+`; filled cell gets a full-width bottom "＋ add" row. Every planned row has a **✓ confirm** (`mealPlanApi.eatPlannedEntry` / `useEatPlannedEntry`) that computes a fresh snapshot and flips planned→eaten so it starts counting in the ring. `AssignMealModal` modes: 🍲 Recipe / 🥚 Ingredient / **✏️ Type it** (free-text one-off).
- **`FoodTodayTab`** — laid out by `FOOD_TODAY_BOARD` (`foodBoards.ts`): on phones/tablets Nutrition (the rings) on top, then the meal slots, everything else below (owner, 07.10.2026); from 1280 Nutrition and Water as a rail on the left (with Last 7 days and Coach at 1280/1469), the meal slots in main, Last 7 days and Coach in their own columns from 1920: calorie (accent) + protein rings (the shared `ProgressRing`), macro chips (one chart colour per macro in `recipes/macroColors.ts` — calories series 2, protein 1, carbs 3 (plum), fat 4, fiber 5; over target = danger), sugar, `WaterTracker`, `GoalSummary` (Edit goal opens the `day-targets` popup), and the coach card. Aligned per-macro columns switch on by the slot card's OWN width (container query ≥40rem). The page header's `FoodDateNav` drives `foodDate`.
- **`useNutritionCoach` → THE goal decision (`health/goal/cutDecision.ts`, 29.09.2026, owner: "same data → one confident answer")** — one pure module every coaching surface renders: the goal editor's coach (`GoalCoachBlock`) and Food · Today's coach card (both via `CoachDecisionView`), Health → Goal progress (`goalPath.applyDecision` sets the path headline + calorie/protein steps; the Pace pill is `paceLabel`). The hook reads the goal report's 28-day window (`useGoalReport(28)`: fitted trend, paired intake/Apple burn, `observedTdee` = the scale burn, latest scale body fat %), Muscle watch's level and the last 7 days' steps. **Protein:** with body fat, 2.8 g/kg lean mass clamped to 1.6–2.2 g/kg BW, range max(1.6 BW, 2.3 FFM)–min(2.4 BW, 3.1 FFM) (83 kg / 24.6 % → "Aim ~175 g (145–195)"); without body fat 2.0 (cut) / 1.8 g/kg (Morton 2018, Helms 2014, Jäger 2017). **Floor (heuristic):** max(1500, 500 + 22 × FFM (Cunningham; 24 × BW without body fat), 75 % of the scale burn); it only limits cutting and never triggers a diet break — that is named only after 12+ weeks of cutting or Muscle watch `likely_loss`. **Precedence (first wins, one headline + ≤ 2 lines):** 1 not enough data (< 4 of the last 7 complete days fully logged, < 10 weigh-ins over 14 days) → what's missing · 2 losing > 1 %/wk or `likely_loss` → eat more · 3 cut < 0.5 %/wk and the needed cut would cross the floor or the diary likely misses food (logged < 85 % of Apple burn − scale deficit) → check logging + add steps toward 10k (~0.0006 kcal/step/kg), no cut · 4 cut < 0.5 %/wk with room → the smallest DAILY cut to 0.5 %/wk (≥ 50, rounded to 50, clamped at the floor, 14-day cooldown) · 5 0.5–1 %/wk → on track; maintain/gain keep `paceAdvice` behind gates 1–2. On a cut 0.35–0.5 %/wk reads "Slow but fine" (neutral), never danger. `verify-cut-decision` (65, incl. the owner's exact gate-3 text). Daily's Nutrition card only takes the per-meal hint from the week's weight (no coach there). **`useDayTargets` (migration `086`, `day_targets` — a singleton row per user, same PK-is-user_id pattern as `athlete_profile`)**: calories/protein/water/goal/`last_calorie_adjust` used to live ONLY in localStorage (`'lasci.dayTargets'`) — a second device or a cleared browser silently reset them to the hardcoded defaults with no way to recover the real numbers. `dayTargetsApi.ts` follows the same pre-migration-safe convention as `athleteProfileApi.ts` (a missing-table READ degrades to the same `DAY_TARGETS_DEFAULTS` the old localStorage version shipped; a missing-table WRITE throws a named "migration 086 not applied" error). The hook keeps its old `{ targets, update }` shape exactly — every one of its 4 consumers (`NutritionCard`, `FoodTodayTab`, `WaterTracker`, `useNutritionCoach`) needed zero changes — but is now a react-query hook with an optimistic `onMutate` (a goal pill tap or a stepper click still feels instant, not gated on a round trip) and `placeholderData: DAY_TARGETS_DEFAULTS` (renders synchronously on first paint, same as before). **Real bug, fixed same day it shipped:** the first version used `initialData` instead of `placeholderData` — `initialData` stamps `dataUpdatedAt` as "now" the instant the hook mounts, so combined with `staleTime: 5min` the query read as already-fresh from the very first render and `fetchDayTargets` never actually ran on a normal page load. Every WRITE still landed in the DB fine, but a plain reload silently kept showing the hardcoded defaults instead of the real saved goal — reading exactly like "saving to the DB doesn't work" (a save's own `onSettled` invalidate was the only thing that ever forced a real fetch, so editing a goal right after loading could look fine while a fresh reload reverted it). `placeholderData` shows the same instant fallback without marking the query as already-fetched, so the real fetch always runs on mount. **Per-goal saved targets + explicit Save (migration `088`, `day_target_profiles` — the user's own explicit correction to the autosave design):** the Goals editor used to write on every tap (goal pill, every stepper click) straight to the single active `day_targets` row — switching Cut→Maintain→Cut lost Cut's own numbers (Maintain's overwrote them), and there was no way to compose several changes before committing. Fixed on two axes: (1) `day_target_profiles` (PK `(user_id, goal)`) keeps one saved `{calories, protein_g, water_ml}` set PER GOAL; `upsertDayTargets` mirrors every write into that goal's own profile row, and tapping a goal pill in the editor recalls that goal's saved profile instead of carrying over whatever the previous goal had. **Real bug, fixed same day it shipped:** a missing `day_target_profiles` table (migration 088 not yet applied) used to degrade SILENTLY — the active row still saved fine, so "Saved ✓" showed every time, but the per-goal memory the whole feature is about never actually persisted, with zero indication why. Now throws a visible `toast.warning(...)` naming migration 088 explicitly instead of swallowing it — a genuine (non-missing-table) error still throws through the mutation's own error toast as before. The mutation's `onMutate` also now optimistically writes the just-saved numbers into the profiles cache (not just the active-row cache) so switching goals immediately after Save can never read stale pre-save data during the brief window before the background refetch lands. **Real bug, fixed same day it shipped:** with NO profile saved yet for a goal (first use, or a goal never tapped before), switching pills only changed the `goal` label — calories/protein sat frozen, reading as "picking Cut/Gain does nothing." `selectGoal()` now falls back to a sensible DIFFERENT starting point per goal when no profile exists: protein scales with bodyweight via `coach.proteinByGoal` (`useNutritionCoach` already computes this for all three goals, not just the active one — cut's higher g/kg was sitting unused), calories step off Maintain's own saved number by the standard ~500 kcal deficit / ~300 kcal surplus a cut/gain implies (clamped to `coach.calorieFloor`). Saving a goal replaces this fallback with its own real profile from then on. (2) **One goal (migration `113`):** `day_targets` holds the phase + `phase_start_date`, daily calories/protein/water and one set of body targets (`goal_weight_kg`, `goal_body_fat_pct`, `goal_muscle_mass_kg`); 111's `athlete_profile` columns are kept but no longer read. ONE editor, **Your goal** (`day-targets` popup, `DayTargetsEditor`: phase with a Since date that becomes today on a phase change, daily targets, body targets, coach; one Save), opened from `GoalSummary` — the shared "Your goal · Cut since 1 Sep · … · Edit goal" line on Food Today, Daily's Nutrition card and Health → Goal progress (Health's phase control is read-only). It is a **local draft** seeded once — pills and steppers only touch the draft, Save writes, Cancel closes without saving; Coach "Apply" inside it feeds the draft, while the Coach card's own "Apply" on FoodTodayTab writes immediately. Pre-113: reads fall back to `athlete_profile` then the device copy; `upsertDayTargets(next, loaded)` puts the daily targets on `day_targets` and writes the body goals to their old place only when they (or the phase start) changed or a device-only copy exists, else `'unchanged'` with no warning (`verify-body-goal`, 184). `day_targets` is `rw` in `DB_CATALOG`: the AI may `db_update` it after an explicit yes (setting `phase_start_date` on a phase change) or point to Your goal → Edit goal.
- **Ingredient sources** (all reviewed before save, per-100g): the user's **library** (search-first) · **barcode → Open Food Facts** (`openFoodFactsApi.lookupBarcode`, free/no-key/CORS-open → no edge function) via `BarcodeScanner` (native `BarcodeDetector` + dynamically-imported `@zxing/browser` fallback for iOS, code-split; manual entry always available) · **online name search** (`openFoodFactsApi.searchFoodsByName`, OFF v2, retries on 503 with an honest "busy" state) merged behind **Kassalapp** results (Norwegian branded groceries + price + nutrition) via the `food-search` edge function; `OnlineFoodSearch` is wired into FoodLogModal's new-ingredient (🔎) and the Ingredients manager (📷 + 🔎). (The NIH DSLD supplement lookup lost its screen with the supplement launcher and its orphaned `supplementDsldApi.ts` was deleted 30.09.2026; old `source='dsld'` library rows stay valid.) **Kassalapp:** the response shape and the nutrition codes are confirmed against Kassalapp's own API page (kassal.app/api, the `/products/ean` example, 07.10.2026): `nutrition: { code, display_name, amount, unit }[]` with `energi_kcal` ("Kalorier") / `energi_kj` ("Energi" — the kJ row, so energy is picked by code/unit, never by that label) / `fett_totalt` / `mettet_fett` / `karbohydrater` / `sukkerarter` / `protein` / `salt` / `kostfiber`; amounts are per 100 g (the page doesn't say so, but its examples are the products' per-100 g label values). Unknown codes fall back to null, never crash.
- **Atwater consistency warning (`macroSanity.ts` + `MacroWarningBadge.tsx`)** — a small orange `!` badge (tap/hover, same `Popover` pattern as the ℹ️ `InfoBubble`) appears next to any calorie/macro entry whose declared kcal doesn't match what its own protein/carbs/fat imply (`4P + 4C + 9F`), flagged when the gap exceeds the LARGER of 50 kcal or 15% of declared calories. Pure, import-free, sucrase-verified (`scripts/verify-macro-sanity.cjs`, 15 assertions) — never auto-corrects anything, since a legitimate product can genuinely deviate (fibre/sugar-alcohol calorie adjustments) and the declared kcal is sometimes the MORE trustworthy number, not the macros. Wired into every place nutrition numbers are entered or reviewed: `IngredientManager`'s add/edit form and "Your foods" list rows, `FoodLogModal`'s new-ingredient form AND its library search-result rows (catches a bad EXISTING library entry at logging time too), `OnlineFoodSearch`'s result rows (catches a bad barcode/Kassalapp/OFF result **before** it's ever saved — the earliest possible point), `RecipeModal`'s manual-macro fields and its `from_ingredients` live preview, `RecipeModal`'s inline `NewIngredientInline`, and `EditFoodLogModal`'s custom-macro fields. Real motivating case: a Kassalapp-sourced "TINE Proteinrik Lettost" declared 157.6 kcal/100g alongside 30g protein/16g fat/1.5g carbs — its own macros imply ~270 kcal, a 42% gap traced to third-party source data, invisible without doing the arithmetic by hand. Several call sites needed a `<div>`+inner-`<button>` restructure (the same fix `FoodTile`'s ★/✕ corner buttons already established) since the badge is itself a Popover button and can't nest inside another `<button>`.
- **A same-session bug sweep across the whole feature found and fixed 7 more real issues** (a dedicated read-only pass, not incidental to the Atwater feature above):
  - **`eatPlannedEntry` (`mealPlanApi.ts`) ignored the weight-unit gate** — every other reader of a planned row (`sumMacros`, `unifiedToMeal`) zeroes an ingredient's contribution when its unit isn't a weight/volume unit (a non-gram quantity like "2 piece" can't be scaled against a per-100g basis), but confirming a planned entry as eaten skipped that check entirely — tapping ✓ on a "2 piece" egg snapshotted `ingredientSnapshot(data, 2)`, i.e. **2 grams**, permanently logging near-zero macros. Now gated identically to the other readers.
  - **"Add missing to Shop" (`RecipeDetail.tsx`) ignored the servings-scale factor** — every ON-SCREEN quantity already scales by `factor = servings / recipe.servings`, but the pushed shopping-list quantities used the recipe's raw, unscaled amounts. Doubling a batch before shopping still pushed the original (half) quantities. Now scales each ingredient's quantity by the same `factor` before building the Shop payload.
  - **`FoodLogModal`'s new-ingredient form had no sugar field at all** — unlike `IngredientManager`'s equivalent form, so any food added via Log Food (including barcode scans and online search — the far more common path) permanently lost its sugar value even when the source API supplied a real one. Added the missing field/state, threaded through `prefillFromProduct`/`handleNewIngredient`.
  - **`RecipeDetail`'s "Eating N of M portions / X% of the batch" text divided by `recipe.servings`** (the base/original yield) instead of the currently-scaled `servings` state — doubling a batch before logging kept showing the un-scaled portion count and roughly doubled the reported "% of the batch". The actual logged calories were unaffected (they're computed from per-serving `recipe.calories`, always correct) — only this descriptive line was wrong.
  - **`NewIngredientInline` (inside `RecipeModal.tsx`) had no error handling** — a `try { await onCreate(...) } finally { ... }` with no `catch`, so a rejected create (RLS, network, duplicate name) left the button silently stopping its spinner with zero feedback, violating the mandatory toast-on-every-async-action rule every sibling save path in this feature already follows.
  - **`EditFoodLogModal` hardcoded `unit: 'g'`** on every save regardless of the library ingredient's own unit (some are `'ml'`) — editing such an entry silently relabelled its stored unit (the macro math itself is unit-agnostic and unaffected, but any UI/export trusting `unit` for display was now wrong). Now uses `lib.unit || 'g'`, both in the saved patch and the displayed suffix.
  - **Two food-logging save paths (`FoodLogModal`/`EditFoodLogModal` `handleSave`) had an unhandled-rejection gap** — `await mutateAsync(...)` with no surrounding try/catch; the mutation's own `useMutationWithFeedback` still toasted the error, but the rejected promise was unhandled at the call site (console noise), unlike `AssignMealModal`'s explicit catch-and-swallow precedent elsewhere in this feature. Wrapped to match.
  - **One finding deliberately left as-is, flagged rather than fixed:** day/group nutrition totals sum already-`Math.round()`-ed per-meal numbers rather than rounding a single raw sum once, which can compound a few kcal/g of rounding drift across many small entries — very likely an intentional WYSIWYG trade-off (so every visible per-item number always adds up to the visible total) rather than a defect; left for a deliberate future call rather than guessed at.
