## Food Feature Detail

User-visible name is **Food** (nav tab, CommandBar, page h1); route stays `/recipes` for deep links. `RecipesPage` has 5 tabs: **Today** (default) · **Library** · **Ingredients** ("Foods" on a phone) · **Meal Plan** ("Plan") · **Insights**. Header (owner, 06.10.2026: fewer rows on the phone): the tabs, then ONE row with the day picker (`FoodDateNav`: ‹ [Today | DD.MM.YYYY → month calendar] ›) and Log food (+ Add recipe on Library); from `sm` all on one row. On a phone that second row exists only on Today and Library. No banner photo (`RecipeBackdrop` was deleted as decoration). Every Food popup opens by id through `useEntityModal` (`food-log`, `food-log-edit`, `meal-plan`, `recipe`, `recipe-view`, `day-targets`); deletes confirm via `modal.confirm`.

**Data model — 4 tables** (after migration `061` unified plan + diary):
- `recipes` — title, description, `servings` (base count), instructions, `macro_mode` `manual`|`from_ingredients`, per-serving `calories`/`protein_g`/`carbs_g`/`fat_g`/`sugar_g`/`fiber_g`, `category` (breakfast/lunch/dinner/snack/supplement), `image_url`, `source_url`, `times_cooked`, `is_temp`; since `157` `serving_label` (what one serving is called — "piece"; empty = "portion") and the batch being eaten (`batch_started_at`, `batch_servings`, `batch_cooked_g`; leftovers are derived, see the Diary round).
- `recipe_ingredients` — name, `quantity` (nullable = to-taste), unit, note, sort_order, `library_ingredient_id` (nullable FK). Quantities are stored for the base `servings`; recipe macros are stored **per serving**.
- `recipe_ingredient_library` — reusable ingredient catalog, macros **always per 100g**, unique per `(user_id, name)`, + `fiber_g`, portion presets (`serving_label`/`serving_grams`, e.g. "1 scoop"=30g), `food_group`, `image_url`, and `source`/`source_ref` provenance (`off`, `dsld`, `matvaretabellen`, user's own; user's own wins on name conflict, attribution travels on the row, idempotent refresh).
- **`food_log_entries` — plan AND diary in one table**, discriminated by `status`: `'planned'` (intent; macros computed live on read) vs `'eaten'` (a real at-log-time **snapshot**). Planning → eating is a status flip. Slots: breakfast/lunch/dinner/snack/**supplement**; unlimited rows per slot; exactly one of `recipe_id` / `library_ingredient_id`+qty+unit / `custom_title`. Rows sharing `meal_group_id` (087) are one dish; `meal_group_title` (158) is its own name, on every row of it.
- **`water_log_entries`** (migration `067`) — one row per logged amount; the day's total = `SUM(amount_ml)`. **Deliberately its own table, never a food slot** — water carries no macros and must never enter the calorie ring. Owner-only RLS, `user_id DEFAULT auth.uid()`, no audit trigger (high-frequency, low audit value — same reasoning as the bulk-sync exemption).
- **`quick_guess_items`** (migration `152`) — the Quick guess presets, the owner's own rows: `name` (the diary title it logs), `icon` (an emoji, content), `portion` (what one portion is), per-portion `calories`/`protein_g`/`carbs_g`/`fat_g`/`sugar_g`, `sort_order`. A preset is a template: a tap writes an ordinary one-off `food_log_entries` line (`custom_title`), never a link, so editing or deleting a preset never touches the diary. Owner-only RLS, `trg_audit`, owner lock; `rw` in `ai-proxy`'s `DB_CATALOG`. `options` (migration `159`, jsonb, default `[]`): up to 3 option groups the card asks about before it logs — see the 16.10.2026 Quick guess round.

**Load-bearing contracts (do not break):**
- **Totals are DERIVED, never frozen (user decision 26.09.2026 — reverses the old "snapshot at log time" rule).** An eaten row's macros always equal what its source adds up to now: a library item (per-100g × grams) or a recipe (per-serving × servings); a `'from_ingredients'` recipe's totals always equal its ingredients. Any add/edit/delete recalculates — past days included — because the user eats more or less based on these numbers. Migration `106` makes the database enforce it for every writer (web, `phone-gateway`, `ai-proxy`): triggers on `recipe_ingredients`, `recipes`, `recipe_ingredient_library` and a BEFORE trigger on `food_log_entries`. Custom rows (no source) and manual recipes keep their typed values, planned rows stay NULL, and a deleted source (FK `SET NULL`) leaves the last computed values. Until 106 is applied the web app does the same itself (`refreshEatenEntries` in `foodLogApi.ts`, called by `useUpdateRecipe` and `useUpdateIngredientLibraryItem`). Live data was repaired once on 26.09.2026 (4 saved meals, 25 eaten rows — e.g. Sushi 546 → 820 kcal).
- The original `UNIQUE (user_id, date, meal_slot)` on the old plan table **had to die** — it physically forbade "lunch = chicken + rice + broccoli".
- **Planned rows render muted "planned" and are NEVER added to the eaten total** (the ring sums `eaten` only) — counting them was visually contradictory with the ring.
- `dayNutritionApi`'s plan-side query deliberately does **NOT** select `recipes.fiber_g` (a missing column would error the whole plan query on old schema; plan rows don't feed the ring anyway).
- **Pre-migration fallback pattern (reused across the feature):** on a column-missing error (`42703` / `PGRST204`) retry once with the new column dropped — `createRecipe`/`updateRecipe` for `fiber_g` and `is_temp`, `create/updateIngredientLibraryItem` for `image_url`, and `foodLogApi`/`mealPlanApi`/`dayNutritionApi` for `status` (they fall back to the old two-table behaviour). This is what let the frontend deploy before migration 061 was applied.
- **Cache-key bug (real):** food-log hooks invalidated `['day-nutrition']`, which does NOT prefix-match the card's `['meal-plan','day-nutrition',date]` key — the card showed stale totals. Invalidate the actual key.
- **Recipe macros must follow their ingredients (real bug, fixed 26.09.2026).** Two disconnects froze calories: (1) the logger's "Save meal" stored `macro_mode: 'manual'` with a total computed once, so editing that meal's ingredients later never changed its calories — it now saves `'from_ingredients'`, and `RecipeModal` opens any manual recipe whose ingredients are all library-linked by weight (`canComputeFromIngredients`; links are only editable in from-ingredients mode, so only old saved meals look like this) as `'from_ingredients'`; (2) editing a library ingredient never touched the recipes built from it — `useUpdateIngredientLibraryItem` now calls `recomputeRecipesUsingIngredient` (recomputes every `'from_ingredients'` recipe using it, and switches those old manual saved meals over). Eaten diary rows follow too (see the derived-totals rule above). `replaceIngredients` also checks its delete error now (a failed delete + insert duplicated every ingredient).
- `macro_mode: 'from_ingredients'` is computed on save (`computeMacrosFromIngredients` in `recipesApi.ts`): sum each linked library ingredient's per-100g macros × `quantity/100`, ÷ servings. Only rows with a `library_ingredient_id` AND a weight/volume unit contribute; the rest are skipped and surfaced in the UI. `RecipeModal` previews the same math client-side (`previewMacros`). `dayNutritionApi` imports recipesApi's `WEIGHT_UNITS` (a narrower local copy once dropped 'milliliter(s)').

- **`useNutritionCoach` → THE goal decision (`health/goal/cutDecision.ts`, 29.09.2026, owner: "same data → one confident answer")** — one pure module every coaching surface renders: the goal editor's coach (`GoalCoachBlock`) and Food · Today's coach card (both via `CoachDecisionView`), Health → Goal progress (`goalPath.applyDecision` sets the path headline + calorie/protein steps; the Pace pill is `paceLabel`). The hook reads the goal report's 28-day window (`useGoalReport(28)`: fitted trend, paired intake/Apple burn, `observedTdee` = the scale burn, latest scale body fat %), Muscle watch's level and the last 7 days' steps. **Protein:** with body fat, 2.8 g/kg lean mass clamped to 1.6–2.2 g/kg BW, range max(1.6 BW, 2.3 FFM)–min(2.4 BW, 3.1 FFM) (77 kg / 23 % → "Aim ~165 g (135–185)"); without body fat 2.0 (cut) / 1.8 g/kg (Morton 2018, Helms 2014, Jäger 2017). **Floor (heuristic):** max(1500, 500 + 22 × FFM (Cunningham; 24 × BW without body fat), 75 % of the scale burn); it only limits cutting and never triggers a diet break — that is named only after 12+ weeks of cutting or Muscle watch `likely_loss`. **Precedence (first wins, one headline + ≤ 2 lines):** 1 not enough data (< 4 of the last 7 complete days fully logged, < 10 weigh-ins over 14 days) → what's missing · 2 losing > 1 %/wk or `likely_loss` → eat more · 3 cut < 0.5 %/wk and the needed cut would cross the floor or the diary likely misses food (logged < 85 % of Apple burn − scale deficit) → check logging + add steps toward 10k (~0.0006 kcal/step/kg), no cut · 4 cut < 0.5 %/wk with room → the smallest DAILY cut to 0.5 %/wk (≥ 50, rounded to 50, clamped at the floor, 14-day cooldown) · 5 0.5–1 %/wk → on track; maintain/gain keep `paceAdvice` behind gates 1–2. On a cut 0.35–0.5 %/wk reads "Slow but fine" (neutral), never danger. `verify-cut-decision` (65, incl. the exact gate-3 text for a worked example). **`useDayTargets` (migration `086`, `day_targets` — a singleton row per user, same PK-is-user_id pattern as `athlete_profile`)**: calories/protein/water/goal/`last_calorie_adjust` used to live ONLY in localStorage (`'lasci.dayTargets'`) — a second device or a cleared browser silently reset them to the hardcoded defaults with no way to recover the real numbers. `dayTargetsApi.ts` follows the same pre-migration-safe convention as `athleteProfileApi.ts` (a missing-table READ degrades to the same `DAY_TARGETS_DEFAULTS` the old localStorage version shipped; a missing-table WRITE throws a named "migration 086 not applied" error). The hook keeps its old `{ targets, update }` shape exactly — every one of its consumers (`FoodTodayTab`, `WaterTracker`, `useNutritionCoach`; Daily's Nutrition card until it left the Personal page, 16.10.2026) needed zero changes — but is now a react-query hook with an optimistic `onMutate` (a goal pill tap or a stepper click still feels instant, not gated on a round trip) and `placeholderData: DAY_TARGETS_DEFAULTS` (renders synchronously on first paint, same as before). **Real bug, fixed same day it shipped:** the first version used `initialData` instead of `placeholderData` — `initialData` stamps `dataUpdatedAt` as "now" the instant the hook mounts, so combined with `staleTime: 5min` the query read as already-fresh from the very first render and `fetchDayTargets` never actually ran on a normal page load. Every WRITE still landed in the DB fine, but a plain reload silently kept showing the hardcoded defaults instead of the real saved goal — reading exactly like "saving to the DB doesn't work" (a save's own `onSettled` invalidate was the only thing that ever forced a real fetch, so editing a goal right after loading could look fine while a fresh reload reverted it). `placeholderData` shows the same instant fallback without marking the query as already-fetched, so the real fetch always runs on mount. **Per-goal saved targets + explicit Save (migration `088`, `day_target_profiles` — the user's own explicit correction to the autosave design):** the Goals editor used to write on every tap (goal pill, every stepper click) straight to the single active `day_targets` row — switching Cut→Maintain→Cut lost Cut's own numbers (Maintain's overwrote them), and there was no way to compose several changes before committing. Fixed on two axes: (1) `day_target_profiles` (PK `(user_id, goal)`) keeps one saved `{calories, protein_g, water_ml}` set PER GOAL (and since `153` its `carbs_g` / `fat_g`); `upsertDayTargets` mirrors every write into that goal's own profile row, and tapping a goal pill in the editor recalls that goal's saved profile instead of carrying over whatever the previous goal had. **Real bug, fixed same day it shipped:** a missing `day_target_profiles` table (migration 088 not yet applied) used to degrade SILENTLY — the active row still saved fine, so "Saved ✓" showed every time, but the per-goal memory the whole feature is about never actually persisted, with zero indication why. Now throws a visible `toast.warning(...)` naming migration 088 explicitly instead of swallowing it — a genuine (non-missing-table) error still throws through the mutation's own error toast as before. The mutation's `onMutate` also now optimistically writes the just-saved numbers into the profiles cache (not just the active-row cache) so switching goals immediately after Save can never read stale pre-save data during the brief window before the background refetch lands. **Real bug, fixed same day it shipped:** with NO profile saved yet for a goal (first use, or a goal never tapped before), switching pills only changed the `goal` label — calories/protein sat frozen, reading as "picking Cut/Gain does nothing." `selectGoal()` now falls back to a sensible DIFFERENT starting point per goal when no profile exists: protein scales with bodyweight via `coach.proteinByGoal` (`useNutritionCoach` already computes this for all three goals, not just the active one — cut's higher g/kg was sitting unused), calories step off Maintain's own saved number by the standard ~500 kcal deficit / ~300 kcal surplus a cut/gain implies (clamped to `coach.calorieFloor`). Saving a goal replaces this fallback with its own real profile from then on. (2) **One goal (migration `113`):** `day_targets` holds the phase + `phase_start_date`, daily calories/protein/water and one set of body targets (`goal_weight_kg`, `goal_body_fat_pct`, `goal_muscle_mass_kg`); 111's `athlete_profile` columns are kept but no longer read. ONE editor, **Your goal** (`day-targets` popup, `DayTargetsEditor`: phase with a Since date that becomes today on a phase change, daily targets, body targets, coach; one Save), opened from `GoalSummary` — the shared "Your goal · Cut since 1 Sep · … · Edit goal" line on Food Today and Health → Goal progress (Health's phase control is read-only). It is a **local draft** seeded once — pills and steppers only touch the draft, Save writes, Cancel closes without saving; Coach "Apply" inside it feeds the draft, while the Coach card's own "Apply" on FoodTodayTab writes immediately. Pre-113: reads fall back to `athlete_profile` then the device copy; `upsertDayTargets(next, loaded)` puts the daily targets on `day_targets` and writes the body goals to their old place only when they (or the phase start) changed or a device-only copy exists, else `'unchanged'` with no warning (`verify-body-goal`, 184). `day_targets` is `rw` in `DB_CATALOG`: the AI may `db_update` it after an explicit yes (setting `phase_start_date` on a phase change) or point to Your goal → Edit goal. **Carb and fat goals (`153`):** before 153 a read gives null (worked out) and a save without them retries without the columns; a save with one set throws a named "migration 153 has not been applied" error (remove the fallback once 153 has run live).

- **Atwater consistency warning (`macroSanity.ts` + `MacroWarningBadge.tsx`)** — a small orange `!` badge (tap/hover, same `Popover` pattern as the ℹ️ `InfoBubble`) appears next to any calorie/macro entry whose declared kcal doesn't match what its own protein/carbs/fat imply (`4P + 4C + 9F`), flagged when the gap exceeds the LARGER of 50 kcal or 15% of declared calories. Pure, import-free, sucrase-verified (`scripts/verify-macro-sanity.cjs`, 15 assertions) — never auto-corrects anything, since a legitimate product can genuinely deviate (fiber/sugar-alcohol calorie adjustments) and the declared kcal is sometimes the MORE trustworthy number, not the macros. Wired into every place nutrition numbers are entered or reviewed: `IngredientManager`'s add/edit form and "Your foods" list rows, `FoodLogModal`'s new-ingredient form AND its library search-result rows (catches a bad EXISTING library entry at logging time too), `OnlineFoodSearch`'s result rows (catches a bad barcode/Kassalapp/OFF result **before** it's ever saved — the earliest possible point), `RecipeModal`'s manual-macro fields and its `from_ingredients` live preview, `RecipeModal`'s inline `NewIngredientInline`, and `EditFoodLogModal`'s custom-macro fields. Real motivating case: a Kassalapp-sourced "TINE Proteinrik Lettost" declared 157.6 kcal/100g alongside 30g protein/16g fat/1.5g carbs — its own macros imply ~270 kcal, a 42% gap traced to third-party source data, invisible without doing the arithmetic by hand.
