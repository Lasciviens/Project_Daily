# Tasks

> Moved out of CLAUDE.md on 13.10.2026 (word for word, apart from translated quotes). This file describes how the feature works and why. The rules Claude must follow while changing it are in `.claude/rules/tasks.md`, which Claude Code loads by itself when a matching file is read or edited.

## One table for every domain

**Tasks — one table for every domain.** `tasks` is the single source of truth for tasks across every page; **never create a per-feature task table.** Enums: `domain` `personal|work|media` · `section` `inbox|today|backlog` (the retired `tomorrow|this_week` are still allowed by the CHECK and held by old rows, never written: a day's section is `taskRules.sectionForDay` — today → Today, any other day → Backlog — writers take `LiveTaskSection`, an old row opens and saves as Backlog through `taskRules.liveSection` with no "(legacy)" pill, and the assistant's writes refuse them; 14.10.2026, `docs/features/daily.md`) · `status` `open|in_progress|waiting|done|cancelled` · `priority` `low|medium|high` · **`source_type` `manual|movie|tv_series|media|calendar|ai|training_session|project_item`** (widened by migrations 039 and 047). Canonical queries: Work board `domain='work' AND status != 'cancelled'` · a day's list = `fetchTasksForDay` + `taskRules.onDay` (One task model below) · media plans `domain='media' AND source_type='media'` · inbox `section='inbox' AND status='open'`.

## completed_at is the "when was it closed" clock

**`tasks.completed_at` is THE "when was it closed" clock (migration `129`).** A BEFORE trigger (`trg_tasks_closed_at`) stamps it whenever a task moves into done or cancelled (a Google pull may send Google's own time) and clears it on reopen — every writer is covered. Never read `updated_at` for "finished": any write moves it (a Google Tasks sync every 20 min, `swapTaskOrder`, the title mirror), which is how Home said "All done for today · 1 task finished" on a day with no task. `taskRules.closedDay`/`closedOn(task, day)`: closed on THAT calendar day, read from `completed_at` only — the one "done" rule of every page (see **One task model** below; the 24-hour rule and the `updated_at` fallback are gone).

## One task model

**One task model (12.10.2026, owner: "the same thing reads differently on every page").** Daily, Home and Work used to count "open", "done today" and "next" and run task actions each their own way. Now:
- **Rules** — `todo/taskRules.ts` (pure, `verify-task-model`, with a guard against hand-written open/done checks): open = open, in progress or **waiting**; done/cancelled **on a day = closed that day** (`completed_at`, migration 129); `onDay` (due that day; closed that day; on today also every open overdue task **whatever its section** — one filed in the Inbox or Backlog used to vanish from Daily and Home while Tasks and Work called it overdue — and undated Today-section rows); `dayTasks` (open: overdue first, then sort order; done, cancelled, counts), `countTasks` (Work), `openOnDay`/`weekCounts` (week strips, week card, month dots), `taskGroups` (the Tasks tab), `isFocusedOpen`.
- **One day read** — `useDayTasks(day)` (`fetchTasksForDay(day, today)`: due that day, closed that day, and on today the open overdue + undated Today rows) is what Daily's day pane, Daily's rail, the week strip's today count, Home's tasks card, overview and brief all read (a failed read says so, never an empty day); `useTodayOverview(day)` adds the schedule.
- **One day schedule** — `daily/daySchedule.ts` (pure): `buildDaySchedule` (one-off blocks + yesterday's tails, weekly plans, unlinked Google events), `aheadOnDay` (not yet over, never a closed task's block; the first is "Next up", "Now" while under way), `plannedMinutes`. DayAgenda's header, Daily's rail and Home's hero all show these (the overview's clock ticks every minute on today). A weekly plan's occurrence is never `closed` (a session trained early still reads "next" until its day becomes a block).
- **One action hook** — `todo/hooks/useTaskActions` (`setDone`, `setStatus`, `cancel`, `reopen`, `toggleFocus`, `remove`, `open`, `edit`, `move`/`skip`): ToDoItem (Daily, Home), Work's cards, list, focus strip and drag, and the Log card's Mark done. A training task routes to the session's own actions (Skip asks why, Delete asks + Undo, they toast); every other delete asks first and offers Undo (`docs/features/delete-undo.md`), and every action says its result. Cancel works on a done task too; Focus shows only on open ones.
- **Migration `143`** clears `is_focused` whenever a task is done or cancelled, for every writer (Daily, Google pull, the assistant), and cleared the ones already closed (`verify-db-task-focus`). Reopening doesn't bring focus back.
- **The Tasks tab reads every task in pages** (`fetchAllTasks`, 13.10.2026): PostgREST returns at most 1,000 rows and done tasks are never cleared, so past 1,000 the cut fell on the rows sorted last — the undated ones, where tasks imported from Google Tasks land (`docs/features/planning-calendar.md` → Google Tasks sync). The pages are keyed on `id` (`.gt('id', last)`), not offsets: a row a sync edits between two pages keeps its place (an offset page on `due_date` could move it across the boundary and skip it); the list is sorted afterwards with `taskRules.compareByDueThenOrder` (due date, undated last; sort order, unset last; id).
- **A Google task without a date is today's (migration `148`, owner 14.10.2026).** It used to be imported into the Inbox and show only under Tasks → No date. Now `upsert_task_from_google` files a new undated import under **Today** (a dated one still goes to the Inbox and is on its day by its date); when Google later takes the date away from a task still in the Inbox it moves to Today, and when Google gives an undated Today task a date it moves back to the Inbox — so a task Google dated for next week leaves today's server-side lists. A section the owner chose (Backlog, or the Inbox for an undated one) stays, and a local edit waiting in the outbox holds the section like the date. It is done **at the import, not in the day read**, on purpose: `google_task_id` is set on every task the app pushes to Google too (`useCreateTask` turns Google sync on whenever Google is connected), so a read rule "undated with a `google_task_id`" would have pulled every undated Backlog task onto Today; only the import knows a task came from Google. Filing it under Today keeps one meaning of Today — the section — so `fetchTasksForDay`/`onDay` and the server-side lists below show it with no query changed (NEVER_HIDES). Tasks imported before 148 stay in the Inbox until the owner runs the one-off SQL in `docs/deploy-checklist.md`. DB scenarios: `verify-db-google-today-series` (145's scenarios re-run against the new function); `verify-task-model` guards the import rule and the `section.eq.today` terms of every today read.
- Ask AI's TODAY'S TASKS context reads the same day list. Not yet on the same rules: the server-side counts in `push-send`, `phone-gateway`'s `tasks_today` and `ai-proxy`'s day summary (open tasks in the Today section or due today — they leave out an overdue task filed elsewhere and keep a dated Today-section one before its day). They do agree on undated Google tasks: those are in the Today section (148).

## start_date opens a window

**`tasks.start_date` (migration `069`) is `due_date`'s OPENING edge**, not a second deadline: `start_date=A` + `due_date=B` means "do this between A and B", and `due_date` stays the **sole** deadline representation — so overdue, the brief, the push, `phone-gateway` and `workMeta.ts` learn no new concept. `ToDoItem` renders **one** range chip *instead of* the due chip (never both — that row's own comment records a real 136px-of-393px title-starvation bug) and still takes its colour and ⚠ from `due_date`. `TasksPanel` gains an **"Open now"** group (`start_date ≤ today < due_date`), computed client-side off `fetchAllTasks`' existing `select('*')`, so before 069 `start_date` simply reads `undefined` and the group stays empty — no probe, no query. The window's last day belongs to Today (on `due_date` the deadline is what matters), and Open now only ever takes rows *from* Upcoming, so nothing renders twice. **A window predicate is NEVER added to `fetchTasksForDay`** — a `42703` there takes down Daily's day list (`DayAgenda`), `DayQuickRail`, `HomePage` and Home's `TodaySummary` at once. Written from the Add sheet's "+ Deadline" row via `TaskWindowField` (season chips reusing `windowChips`' math; since one item, 155, it rides on the save as `startDate`), and `tasksApi` retries the write without `start_date` on `42703`/`PGRST204` (the `recipes.fiber_g` precedent) while create omits the key entirely when unset. Fixed in the same pass: `CreateTaskInput` had no `description`, so the Notes textarea was **silently dropped on create** while edit persisted it.

## One item: the Add sheet and quick add (owner, 15.10.2026; migration 155)

**One thing to add.** A task, its time slot and its repeat are one item: one **Add** (Daily's "Add task" and "Add" merge — Daily's day view, `docs/features/daily.md`), and the same sheet edits (`UnifiedPlanModal`, `docs/features/planning-calendar.md` → the one Add sheet). The data stays where it was (`tasks` is the item, `time_blocks` its optional slot, `schedule_blocks` its optional repeat — same ids, same Google links); the merge is in the concept, one save (`useSaveItem`, one RPC) and one Google choice. Existing rows are untouched until they are next saved.
- **Inbox / Today / Backlog are not picked in the sheet** — they follow the date (`sheetRules.sectionForItem`: no date → Inbox, today → Today, another day → Backlog, never a retired section). The Tasks tab keeps its sections. A new item's date defaults to today or the caller's day, so it files under Today like the old `section: 'today'` default did.
- **A time without a length** means "do it at 14:00" and doesn't block time; "+ Blocks time" gives it a length. **"+ Deadline"** (due by) sits behind a tap, with the "do it between" window under it.
- **Quick add** (`src/features/items/quickAdd.ts`, pure, `scripts/verify-quick-add.cjs`): rule-based, English words and digits, no AI. It reads a time (17:30, 7:05, at 17:30, 5pm, 5:30 pm, 17:30-18:30, from 9:00 to 10:30), a length (1h, 1.5h, 90m, 1h30, 45 min, 2 hours, with or without "for"), a date (today, tomorrow, a weekday — the next one, today included; "next fri" = after today — 15.10 this year or next once passed, 15.10.2026, with or without on / from) and a repeat (every day, daily, weekdays, every weekend, every week, weekly, every Mon Wed Fri, every 2 weeks [on Tue Thu], every other week, every 3 days, every month, monthly, every 2 months). **A bare number is never read** ("Buy 3 eggs", "Call 112", "at 5"); neither are "1.2" (a one-digit month), "sun" / "sat" / "wed" alone (words — "on sat" reads) and "daily" / "weekly" / "monthly" as the first word ("Weekly report" is a title). Each part is read once, the first one wins; the read words leave the title. The sheet's title and **Home's quick add** (`TodayTasksCard`) use it: a **Read as** line shows what was read (`ReadAsLine`), **Keep text** turns it off for that entry. Home saves through the same `useSaveItem` (`sheetRules.itemFromQuickAdd`): on today when the text names no day, Google by the default (none without a connection on this device).


## One item (155): how it is stored and saved

The data layer behind the one Add sheet (`src/features/items/`: `itemTypes.ts` the contract, `itemRules.ts` the pure rules — the ONE home of `defaultGoogleTarget`, `googleTargetProblem`, `sectionForItem`, `itemFromRows`, `describeSaved`, re-exported by the sheet's `sheetRules.ts` — `itemApi.ts` the calls, `useItems.ts` the hooks; `scripts/verify-item-rules.cjs`). Google's side (targets, all-day and Free events, "✓ ", the read-back): `docs/features/planning-calendar.md` → One item (155).

- **Where each fact lives** (owner's reading, agreed with the sheet and Daily): the **task** is the item — title, notes (`description`), domain, priority, section (follows the day), the window's start (`start_date`) and **`due_date` / `due_time`: the deadline when the item has one ("+ Deadline", due by), otherwise its own day and time**. The item's own day and time ("do it at") live on its **slot** (`time_blocks`, `task_id`): made for a time, for a day shown on Google Calendar, and for a day whose deadline is elsewhere — Daily places a task with no slot at its `due_time`, so a deadline never lands there as a do-time. `start_time` null = a day with no time; `busy` false = a time with no length (`duration_minutes` then holds a nominal 15, never shown). A **repeat** is a rule (`schedule_blocks`): kind, days, start (`effective_from`), `start_time`/`end_time` (both null = a repeat with no time), `busy`, `google_target`, and the `domain` / `priority` / `notes` its days get. **One day of a repeat** that was acted on is a slot marked with the rule and the day (`schedule_block_id` + `occurrence_date`, 142) and its task.
- **Reading it back** (`itemRules.itemFromRows(task, block, plan)`): the slot's day and time are the item's; the task's due is a deadline only when it differs from the slot's (another day, or another time); a task with no slot is on its due day and time; a rule opens as scope `all`; a day that is its own item opens as that item (scope `item` — its save never touches the rule). An old row's Google choice is where it IS (`presentGoogleTarget`: its Calendar event, its Google Task, both, none) — never a default, so saving an old item never moves it on Google by itself. A training session never has a deadline (its day and time are one fact with its slot, 142).
- **One save** — `app_save_item(item)` (one transaction → one Activity Undo; `useSaveItem`): the rule for a repeat (a one-off given a repeat becomes the rule, its task and slot go with their Google copies), that day for scope `day` (it becomes its own item first — 142's path, once: a double tap gets the same rows), else the task and its slot. A rule becomes a one-off only on an explicit "no repeat" save of the rule itself (scope `all`, no task or slot in the save) — never because a save left the repeat out. It takes the sheet's extras (category, colour, the window's start, the slot's own source with a TV episode's numbers). It writes rows only: the Google Calendar calls follow in the browser (in the background — the save says its result as soon as the database answers: "Added · 15.10.2026 17:30–18:30 · on Google Calendar"). A database without 155 answers "migration 155 not applied".
- **One day of any repeat** — `app_repeat_day(rule, day, action)` (`useRepeatDay`): **done** ticks the day's task (156: made on its day, or now — with no slot, so the series keeps the day) and **skip** makes the day its own item (142's split, reusing the day's task) and cancels it (a training day's skip gets 142's "Cancelled — no reason given" row; Training's own Skip asks why), each says its result with **Undo** ("Done for 15.10.2026 · Undo"); **undo** opens it again. A missed day stays on its day — nothing moves it. "Delete only this day" (`useDeleteItem({ scope: 'day' })`): a day that is its own item goes like an item (the day stays out of the repeat); otherwise the day leaves the repeat (`remove`, an EXDATE on Google) and Undo puts it back (`restore`).
- **One delete** — `useDeleteItem().run(target, { scope })`: `item` (the task — its slot goes with it, 077 — or a slot of its own), `all` (the rule, every day it repeats; its series goes), `day` (above). All through the one delete flow (question, "Item deleted · Undo"); the sheet's `useSheetDelete` adapts its call to it.
- **Convert old items** (Settings → Subscriptions → Google; `app_convert_preview` / `app_convert_apply` / `app_convert_undo`, `useConvertPreview` / `useConvertOldItems`): every FUTURE standalone slot gets a task (`google_sync_enabled` false; Google target `calendar` when the slot has an event — that event stays the item's one Google entry — else `none`; source carried over, `tv_episode` → `tv_series`, none → `manual`), and the slot points at it. A past slot gets no made-up status; a planned episode (season + episode) is left as it is (watching it removes its slot — 043/149 — which would leave its task behind). Nothing goes to Google. Its own **Undo** (on the result toast) unlinks each slot FIRST and only then deletes the task it made (a task closed since is kept), so an original slot or its event is never touched. Developer → Activity's "Undo this save" refuses a conversion (`item_conversions`' row can't be deleted — deleting its tasks would cascade into the original slots through `time_blocks.task_id ON DELETE CASCADE`).
- **A task and its slot, for every writer** (155, in the database): a slot moved by anyone — the assistant, a sync, plain SQL — takes its task's due along when that due WAS its day (and time, or no time); a deadline elsewhere stays (`item_slot_moves_due`; a training session keeps 142's own pair). Watching a planned episode removes its slot (149) and now marks its task **done**; deleting a project item removes its slots (043) and now closes their open tasks — done when the item was done, cancelled otherwise — and its Undo puts the tasks' status back (`app_delete_rows` holds them). Without that, every planned episode or project step saved as an item would leave an open task behind to go overdue.
- **Migration 155** is additive: it changes, moves and queues nothing (asserted in the migration: both outboxes hold what they held), never touches a Google id, `google_calendar_from`, horizon or zone; `schedule_blocks` gets `trg_audit`. DB scenarios: `scripts/verify-db-one-item.mjs` (the owner's data before / after, the save, a repeat's day, the conversion and both Undos, the calendar outbox's upsert, the read-back).

## A repeat's day is a task on its day (owner, 15.10.2026; migration 156)

Owner: "A repeated task should be created on its day. That would be smart. So a training should be a task as well." Before, a day of a repeat was only a projection until it was ticked, skipped or moved: today's training showed in Home's "Next up" but not under "Today's tasks", and counted nowhere.

- **Made on its day.** Every repeating item's day (`schedule_blocks`, training plans included) becomes a real `tasks` row on that day: the hourly pg_cron job `lascis-repeat-days` (`repeat_days_run()`, a SQL function called directly — no secret; Europe/Oslo's today, every account the owner lock lets in), the app's own call when it opens or comes back to the front (`app_repeat_days_today`, `useRepeatDaysOnOpen` in `useAppBootstrap` — the fallback), and a repeat saved today gets today's task in the same save (`app_save_item` → `repeat_days_follow_rule`). Never a past day (no backfill — the first run makes only today's), never a day ahead (future days stay projections). Its title, notes, domain and priority come from the repeat; the section is Today, `due_date` the day, `due_time` the repeat's time. It is linked by `tasks.schedule_block_id` + `occurrence_date`, unique together (`tasks_occurrence_key`): one task per day of a repeat, whoever runs first.
- **No slot.** The day's task has no `time_blocks` row: the repeat's time stays on the repeat, so its Google Calendar series keeps the day — no EXDATE and no extra event per day. The day becomes a slot of its own only when it is edited on its own (142's split, `item_occurrence`): This day in the sheet, a move, a skip, the read-back of a day moved in Google, any training action (below) — and the split **reuses** the day's task. A day's task opened from a plain list and saved (Home, the Tasks tab) is saved as that day of its repeat (`app_save_item` routes it to scope `day`).
- **Never twice, never again.** A day acted on (142's slot), taken out ("Only this day", `except_dates`), whose task was deleted, or whose task was moved to another day is never made again. For every writer, in the database: deleting a day's task takes its day out of the repeat (`trg_repeat_day_task_deleted`) and Undo reverts that change itself (`app_delete_rows` holds the repeat as a touched row; Activity's Undo reverts the audited update), so a day that was out before stays out; moving a day's task with no slot to another day takes its own day out for good (`trg_repeat_day_task_moved` — it was acted on) — the browser then pushes the series (`refreshSeriesSoon`, from `useDeleteTask` / `useUpdateTask`). **Untouched** (`repeat_day_untouched`) = still to do, on its own day, no slot, and its day still in the repeat: a day edited on its own ("This day" — even with no time, when its slot goes again) is never untouched. Deleting a repeat takes its untouched days with it (`trg_repeat_drops_open_days`; `app_delete_rows` holds them for Undo); days done, skipped, missed, edited or split off stay as tasks, their link gone (ON DELETE SET NULL). Editing a repeat (All days) brings its untouched days from today on along (title, notes, domain, priority, time, Google); an untouched day it no longer has goes.
- **Its sheet.** A day's task opened from a list (Home, the Tasks tab) that is still its repeat's day opens as that day of its repeat with **This day** picked (`PlanEntityModals.useRepeatDayOf`); a Repeat sent with a day's task applies to its own repeat (All days, its start kept) — never a second repeat (`app_save_item`). "Only 15.10.2026" on a day that is a task (open, ticked, skipped or missed) deletes that task (`useDeleteItem` → `fetchRepeatDayTaskId`) with its own Undo; a day with no task leaves the repeat (`app_repeat_day 'remove'`).
- **Missed days stay missed** (owner: never carried over). When a day has passed, its unticked task is closed as missed: status `cancelled`, `closed_reason = 'missed'`, `completed_at` the last second of ITS day (so it shows as **Missed** on its day and never on Today's lists, as overdue or as cancelled). The job does it at the start of the next day (and the app's call); a day moved forward is judged on its new day, and one moved to "no date" is never closed (it has no day that could pass). A missed day can still be ticked done; reopened, it is closed again by the next run. `closed_reason` is cleared whenever the task is no longer cancelled (`trg_tasks_closed_reason`). A missed training day gets no skip row (`training_task_cancel_skip` leaves it: it wasn't skipped), and a Hevy workout logged late — within 141's six days — still completes it (`training_plan_candidates` takes it). A training day's task takes its routine the app's way (`repeat_day_routine`, `nextSession.matchRoutineToPlan`'s rule: the exact title, else the longest routine name inside the plan's title; the current program's of two of one name); a day split from a view keeps the routine that view read (`trainingPlanApi.keepRoutine`).
- **One row everywhere.** It is a task, so Home's "Today's tasks", the brief, `phone-gateway`, `push-send` and `ai-proxy` list it with no query changed (NEVER_HIDES); none of them reads `schedule_blocks`, so nothing counts twice. Daily shows the projection and its day's task as ONE row (`dayItems`); Home's "Next up" never shows a ticked day (`daySchedule.buildDaySchedule` takes the day's tasks); the week strip, week card, month and the day header count a day that is a task with the tasks (`repeatDayKeys`).
- **Google, per repeat** (`schedule_blocks.google_target`): `calendar` — the series, the day's task is not on Google Tasks; `tasks` — **"Google Tasks · one per day"**: no series, each day's task goes to Google Tasks (due = its day) through 071's outbox as it is made, and ticking it in Google ticks the day (the pull); a switch to Google Tasks waits only for today's day that is still to do and on Google Tasks (`dayTaskId`) — a ticked one has nothing to wait for; `both` — the series and the day's Google Task ("Shows twice in Google Calendar"); `none`. A missed day's Google Task is removed (cancelled = deleted on Google, 071), so the widget never carries a day over either. Moving between them is 155's rule (the new copy first, confirmed, then the old one). A repeat's Google Tasks list is the default list (the plan stores none yet).
- **Audit.** The job's writes are audited like every automatic writer (actor `service`); undoing such an entry in Developer → Activity deletes those days' tasks but never takes a day out of its repeat (the delete rule stands aside inside `app_undo_transaction`, read from the call stack), so the next run makes them again.
- **Migration 156** creates, changes and queues nothing (asserted). DB scenarios: `scripts/verify-db-repeat-days.mjs` (the job twice a day, three days in a row, skipped / deleted / moved / taken-out days, training with 141 and 142, missed days and a late workout, each Google choice, the item save, deleting a repeat, the app's call; and the SQL repeat rule `repeat_occurs_on` compared with `daily/recurrence.ts` day by day over two years).
