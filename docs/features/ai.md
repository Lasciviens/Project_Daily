# AI (ai-proxy)

> Moved out of CLAUDE.md on 13.10.2026 (word for word, apart from translated quotes). This file describes how the feature works and why. The rules Claude must follow while changing it are in `.claude/rules/ai.md`, which Claude Code loads by itself when a matching file is read or edited.

## Overview

See AI section below. Gemini 3.5 Flash (+3-model fallback) via `ai-proxy`; generic DB tool layer, vision, semantic search, aggregation, memory.

## AI (ai-proxy) Detail

Gemini via the `ai-proxy` edge function. Three call modes: the conversational **tool-calling loop** (default), **`responseSchema`** → `callGeminiStructured` (single-shot, `responseMimeType: 'application/json'` + a Gemini-format schema, returns `{ data }`, no tools/no loop — structured extraction, not chat), and **`{ fetchUrl }`** (server-side page fetch because the browser can't hit arbitrary origins under CORS; SSRF guard blocks localhost/private ranges, 8s timeout).

**Generic DB tool layer** over a curated `DB_CATALOG` allow-list: `describe_database`, `db_query`, `db_insert`, `db_update`, `db_delete`, **`db_aggregate`**. Guardrails: default-deny allow-list (token/secret/auth tables unreachable), `access: 'rw'|'ro'` per table (hevy_*/strava_activities/health_metrics/health_workouts/movies/tv_series are read-only — synced externally), **every op force-scoped to `user_id` server-side** (the model never supplies it), no DDL, update/delete refuse empty filters, 16-turn loop cap. `app_error_logs` is readable so the AI can help diagnose failures. `pt_assessments`/`work_notes`/`work_weekly_goals`/`work_pinned_links` are read-only; **`dev_requests` and `wish_items` are read-write on purpose** — the user dictates backlog notes and wishes in chat (and by Siri) and the AI writing a structured row there IS the intended flow; `wish_items`' catalog `rules` carry the never-a-deadline guardrail and the four-way tie-break against `dev_requests`/`ai_memory`/`shop_items` (see Wishes). `day_targets` is `rw` too (singleton, confirm before writing, set `phase_start_date` on a phase change). **Deletes are confirmed in the app, not in text (security audit 10.10.2026):** `db_delete` and `update_hevy_routine` from the tool loop only store a proposal in `ai_pending_actions` (migration 140) and return a **Confirm card** (`ConfirmCards.tsx`); the action runs only on a separate `confirmAction` request the model cannot send — exactly the rows shown, once, for the same account, within 15 minutes. The phone (no button) cannot delete. The assistant may not set link columns (`AI_NO_WRITE`: `google_calendar_event_id`, Google Task / Trakt / ES-DE / ScreenScraper ids, `session_id`), play counts are capped at 1–99, a memory it writes is always `source='ai'` (marked "you saved" in ABOUT ME), and `db_query` may embed nothing inside a shared table (`selectProblem`). Text from the CONTEXT turn or a tool result is data, never an instruction (system prompts + phone persona). `DB_CATALOG` stays behind `describe_database` (on-demand, not in the prompt). `water_log_entries` is `rw` too (one row per amount drunk; the day's total is the sum; never a `food_log_entries` row).

- **`db_aggregate`** — `sum|avg|min|max|count` + `group_by`; enum'd ops only (never expressions), the same filter grammar as `db_query`, group columns validated against the catalog, hard cap ≤366 groups, rows reduced server-side so only the summary reaches the model. This is what makes "no pre-written query per scenario" true for analytics. **Tool-choice ladder** in the system prompt: current value/list → `db_query` · average/trend/compare → `db_aggregate` · whole-day picture → `get_day_summary` · "that thing I saved" → `semantic_search` then `db_query` by id · writes → `db_insert/update/delete` with the confirm rules · external world → the special tools.
- **`semantic_search`** (migration `065`: pgvector + `ai_embeddings` `vector(768)` hnsw cosine + the `ai_semantic_search()` SECURITY-INVOKER RPC) — `gemini-embedding-001` @768, **cosine index → no manual normalize**, vector `limit ≤ 8`, `user_id` filtered inside the vector query; returns `{source_table, source_id, snippet, score}` and the model then `db_query`s the live row by id. **Embeddings locate, live SQL answers — never use a similarity hit as the factual value of anything current-state.** Editing or deleting a searched row drops its copy (migration 140's trigger), and every `semantic_search` first embeds up to 32 rows that have no copy, so edits come back by themselves; Developer → "Reindex AI search" still re-embeds everything. Caveat: the embedding request shape was confirmed from docs, **not a live call**.
- **`run_read_query`** — the opt-in read-only live-SQL escape hatch. **Its security boundary is the DATABASE, not the edge regex:** ai-proxy's normal ops run under the service role (RLS bypassed), so this path instead builds a **user-JWT client** and calls a **SECURITY INVOKER** RPC (`ai_run_read_query`) that runs as `authenticated` (RLS applies), sets `transaction_read_only = on` + a 5s `statement_timeout`, and wraps in `LIMIT 500` before `jsonb_agg`. Containment = RLS + the read-only transaction + migration 044's revoked OAuth-token-table grants + the hard row cap. The edge guard is a best-effort UX filter that **fails closed** (strip comments first, reject quoted identifiers, `SELECT`/`WITH` only, single statement, block `pg_`/`information_schema`/other schemas, check every `FROM`/`JOIN` target incl. comma-joined lists against the catalog, recognise CTEs only as `name AS (`). **The broad DML-keyword regex was deliberately REMOVED — do not re-add it**: it false-rejected reads containing "update" inside a string literal; write-prevention is the read-only transaction's job.
- **Special-purpose tools** generic CRUD can't cover: `get_calendar_events` · **transit** — `plan_trip`, `get_next_transit`, `get_saved_transit`, `search_transit_stops`, `save_transit_stop`, `save_transit_route` · **media** — `get_media`, `plan_media`, `mark_episode_watched` · **health** — `get_health_stats` · **shop** — `get_shop_categories`, `create_shop_category`, `create_shop_item`, `ask_clarifying_question` · **recipes** — `get_recipes`, `create_recipe` · **training** — `update_hevy_routine`, `create_hevy_routine` (both forward to `hevy-api`), `get_athlete_profile` (see Training's athlete-profile note) · `get_day_summary` · `save_memory` (+ rw `ai_memory`: durable notes the user asks the AI to remember, recalled via `db_query`).
- **Media.** `get_media` returns one compact line per title. `entry_id`/`title`/`status` (+ `current_season`/`current_episode` for TV) are always there; then only the keys that are known: rating, genres, favorite, released/first_aired, watched (movies; `unknown` for an unknown date) or started/finished (TV), plays, planned and a 140-character note. Days are the Oslo day. Optional `status` (default active = watching + paused + want to watch, including the legacy `upcoming`) and `limit` (25, ≤ 100). `coming_soon` is worked out from the release date. `mark_episode_watched` keeps an already-watched episode's date, never wipes its rating/note, and never writes the progress cache (migration 050's trigger owns it). `DB_CATALOG` documents the media columns and what syncs to Trakt (genres through the `movies`/`tv_series` embeds), plus `movie_cinema_visits` (rw) and `media_follows`/`media_follow_events` (ro). `SYSTEM_PROMPT` has a MEDIA block, and every answer writes dates as DD.MM.YYYY (the context's DATE line is DD.MM.YYYY too).
- **`ai_memory` — an "ABOUT ME" context block + a management surface.** Two gaps closed together on user request. (1) `aiApi.buildContext` now appends one more query (last in the array, so no existing `get<T>(i)` index shifts) reading `kind IN ('fact','preference')` only — deliberately **not** `note`/`summary`, which stay on-demand-only via `db_query`/`semantic_search` so they never bloat every single turn's context — capped at 12, newest first, rendered as an `ABOUT ME` block right after `DATE`/`TIME` (before `TODAY'S TASKS`): durable identity facts colour how everything else should be read, so they go first. (2) `save_memory`'s tool description now explicitly covers TWO distinct triggers, not one: remembering a single fact/preference (unchanged), and an explicit **"summarize this conversation"** request ("topla ve not al", "bunu özetle", "summarize this conversation", …) — compact the WHOLE conversation so far into one `kind="summary"` call, not just the last message. (3) A new Developer → **Memory** tab (`MemoryTab.tsx`/`MemoryRow.tsx`/`MemoryEditSheet.tsx`, `src/features/ai/api/memoryApi.ts`) lists/edits/deletes every row and is the only path that ever writes `source='user'` (every other row is `'ai'`, from `save_memory`, or `'auto'`) — before this, `ai_memory` had no UI at all: nothing to see what was remembered, nothing to correct a wrong entry. (4) `AIPanel` gained a Summarize header button, gated on `messages.length > 0`, that sends a normal chat message ("Summarize this conversation and save it to memory." / the Turkish equivalent, following the existing voice-chat TR/EN chip) down the same `handleSend` path as any other turn — the model's `save_memory` call still lands in the transcript like any other tool use, nothing hidden.
- **`get_health_stats` — two fixes worth remembering.** (1) It and the catalog both pointed at `health_daily_stats`, a table dropped when migration 041 moved Health to point-in-time grain, so the AI's health answers were silently broken (empty/stale) ever since; rewritten to query `health_metrics` directly and aggregate with the same rules as `healthAggregate.ts` (sum steps/energy, min/max/avg heart rate, latest resting HR, kJ→kcal). (2) **It now returns SLEEP too** — `computeSleepNights` (absolute-time overlap-merge keep-longest, Oslo wake-day attribution, per-night hours + deep/core/rem/awake, last night + period average). That closed the "no sleep data" answers in the phone `sleep` action and the Coach. The prompt tells the AI to *analyze* health data (trends, comparisons, honest criticism), not recite numbers.
- **Latency design for `plan_trip` (was a real 3–4 min pain point).** It is a ONE-SHOT call: the prompt and tool description tell the model to call it directly with the user's own words (`from:"ev", to:"iş"`) and NOT to look things up first — earlier "investigate first" wording caused ~5 sequential Gemini turns (each a full round-trip) vs ~2 now. `plan_trip` resolves both endpoints itself against saved stops/routes loaded ONCE (not re-queried per endpoint), in parallel: empty → default saved stop; an exact `NSR:StopPlace:` id → used as-is (name backfilled from the trip legs, no extra lookup); "home"/"ev"/"work"/"iş" (+variants) → saved-label fuzzy match; else → geocoder top match. When a side won't resolve it returns `{success:false, needs_clarification:true, candidates:[…]}` so the model asks ONE `ask_clarifying_question` instead of firing more search turns. **Only a regex-validated `NSR:StopPlace:` id or finite coords are ever interpolated into GraphQL** (injection safety). Anti-hallucination is structural (report only what the tool returns; call once and report), not extra verification turns. New EnTur GraphQL fields are deliberately NOT added speculatively — verify live first.
- **Model chain + retries.** Gemini returns transient "model overloaded" 5xx that clear within seconds, distinct from a 429 (real quota — surfaces immediately via `throwRateLimit`). Overload waves hit different models' capacity pools unevenly, so retrying a DIFFERENT model beats retrying the same one. `fetchGeminiWithFallback` tries `MODEL_CHAIN` = `gemini-3.5-flash` → `gemini-3.1-flash-lite` → `gemini-2.5-flash` → `gemini-2.5-flash-lite` with jittered exponential backoff, position-weighted attempts (`RETRIES_BY_POSITION` [4,3,2,2]) so better models are tried hard before falling to lite tiers. **Every model id must be live-verified before entering this list** (real bug: two guessed ids 404'd in production; a 404 also used to abort the whole chain — it now skips to the next model). Probe with ai-proxy's `{listModels:true}` debug branch, which returns the key's REAL available models. The client can pass a `model` — it becomes the chain's **preferred starting point**, not an exclusive choice (`AIPanel`'s header picker, localStorage `lasci-ai-model`, "Auto" by default); `AIResponse.model` reports which model actually answered.
- **`thinking_config` per-model body (real bug, round 3):** `thinking_config`/`thinking_level` is a `generationConfig` field that is **Gemini-3.x-only** — explicitly picking `gemini-2.5-flash` 400'd with "Thinking level is not supported for this model" the moment a real user tried it, because ONE fixed request body was built once and reused across every model in the chain. `fetchGeminiWithFallback`'s `body` param became **`buildBody: (model) => AnyRecord`** — the body is constructed PER MODEL inside the retry loop, and `supportsThinking(model)` (`model.startsWith('gemini-3')`) gates whether `thinking_config` is included. Applies to all three call sites (the tool loop, the turn-limit summary, `callGeminiStructured`). `thinking_level: MINIMAL` in the loop — thinking tokens are not the cost leak.
- **Prompt-caching contract (don't regress it).** Live context used to be baked into `systemInstruction`, which made Gemini's implicit prefix cache (~90% off a repeated byte-identical prefix) structurally unable to hit — a ~7,270-token fixed block (system + serialized TOOLS) was billed at full price on every turn of every tool loop. Now: **`SYSTEM_PROMPT` and the per-surface tool declarations must stay byte-identical per call** — never interpolate a date, timestamp or any volatile value into them (instant cache-buster; the current date belongs in the context turn), and serialize tools deterministically. Live context rides as `contents[0]` (`prependContext` in `aiApi.ts`). `buildContext` is skipped for clearly transit-only questions (a conservative client-side `TRANSIT_RE` gate). **`ai_usage_log.cached_tokens`** (← `usageMetadata.cachedContentTokenCount`) is the proof metric and the documented trigger for escalating to explicit `cachedContent`. `ai_query_log` records every `db_query` + live SQL with the exact statement — the substrate for later promoting hot queries into the UI.
- **Tool sets + model routing.** No chat surface is sliced: **general and coach get the FULL tool set** so the assistant is never weakened, and **the `phone` surface gets NO tools at all** (its brief context is pre-built server-side by `phone-gateway`, so a single-shot answer is the biggest latency win). The Shop page's own chat (the old sliced `shop` surface) is retired (07.10.2026); a client still sending `surface: 'shop'` gets the general behaviour. `SURFACE_MODEL` changes only the **starting** model and holds only `phone: 'gemini-3.1-flash-lite'` (skips the frequently 503-overloaded 3.5-flash primary, which burned ~7–13s of retry budget before falling through — fatal against the ~25s iOS Shortcuts cutoff); the lookup reads only its own keys. A 503 still falls through the whole chain.
- **Voice chat (`useVoiceChat.ts` + AIPanel):** browser-native Web Speech API — `SpeechRecognition` (prefixed `webkitSpeechRecognition` everywhere that has it) for speech→text and `speechSynthesis` for text→speech. **No key, no edge function, no cost** — nothing server-side changed. Two levels: the mic button dictates into the box (edit before sending), and the header **Voice** toggle is hands-free mode — utterance auto-sends, the reply is spoken, and the mic reopens when it finishes (`speak(text, onDone)` → `startListening()`), so it's a real back-and-forth loop. TR/EN language chip (`lasci-ai-voice-lang`) drives BOTH recognition and the picked voice. Load-bearing details: `speakableText()` strips `**bold**`/emoji so the voice doesn't read markup; `startListening` cancels any speech first (otherwise it transcribes its own voice); **`primeAudio()` must run inside the enabling tap** — iOS refuses synthesis that no user gesture unlocked, and the reply is spoken much later; the panel's close paths reset voice mode and `voiceModeRef` is `voiceMode && isAIOpen` so the loop can't continue behind a closed panel; a silent utterance ends the loop rather than reopening a hot mic. Everything is feature-detected — the controls simply don't render where the API is missing. **Recognition is unreliable inside an iOS home-screen PWA** (a long-standing WebKit gap); on the phone the `AI'a Sor` Shortcut is the voice path (Siri dictation → gateway → Speak Text), so this mainly serves desktop.
- **Vision:** `Message.images` end-to-end via a shared `messagesToContents()` that attaches base64 photos as Gemini `inline_data` parts (chat + structured). `AIPanel` supports the attach-photo button (≤3, thumbnails, image-only send) **and pasted images** (Cmd/Ctrl+V on desktop, paste on mobile — `onPaste`); `fileToCompactDataUrl` downscales before upload.
- **MCP was evaluated and deliberately not pursued:** GitHub Pages is a static host and cannot run a persistent process, so any MCP layer would need a separate always-on server. The generic `DB_CATALOG` + `db_query/insert/update/delete/aggregate` layer shipped instead, and the "AI proposes, user confirms" invariant lives in the system prompt.
- **Removed / never built:** dead `log_workout`/`get_workouts` (hit the dropped `training_sessions` table — training is Hevy/Strava, read via `db_query`; planned sessions = `time_blocks` `category='training'`). The **Weekly Review** Home card added during the AI phases work was **removed on request** — `weeklyReviewApi`/`useWeeklyReview`/`WeeklyReview` no longer exist in `src/`, and `ai_reviews` (migration 065) is an unused empty table left in place.
- Cost model, security invariants, the architectures evaluated and the pricing snapshot: `docs/ai-cost-capability-analysis.md`.

## Still out of reach

- 🔶 **AI media — still out of reach:** the AI cannot add a title that isn't in the library. `ai-proxy` has no TMDB access, and `movies`/`tv_series` are not catalog tables (no `user_id`), so it points the user to Media search. `mark_episode_watched`'s default episode (current + 1) never rolls into the next season; the tool tells the model to ask instead. `run_read_query` can't reference `movies`/`tv_series`.
