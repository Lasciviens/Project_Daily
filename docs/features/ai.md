# AI

> Moved out of CLAUDE.md on 13.10.2026 (word for word, apart from translated quotes). This file describes how the feature works and why. The rules Claude must follow while changing it are in `.claude/rules/ai.md`, which Claude Code loads by itself when a matching file is read or edited.

## The Claude layer, app side (phase 1, 21.11.2026)

The AI rebuild's first phase (plan: `ai-plan.md`, contract: `ai-phase1-contract.md`) adds the `claude` edge function and, in the app, the code under `src/features/ai/claude/`. Phase 2a (22.11.2026) moved the recipe editor's and Food's quick-guess calls to the same function (section below). Everything after that describes the old assistant (`ai-proxy`: Ask AI, the coach), which stays until phase 4.

- **Words.** A *ledger* is the table `ai_calls`: one row for every call, with its tokens, cost and how it ended. A *job* is one named task the function can do; there are `item_fill`, the five jobs of phase 2a, the five of phase 2b–2d (the PT assessment, the Kobo's and the phone's, the Test bench; below) and the tiny `diagnose` (see Diagnose below). An *outcome* is how a call ended (answered, refused, cut off, over budget …).
- **Files.** `claudeApi.ts` (`runClaudeJob`, `describeClaude`, `diagnoseClaude`, `ClaudeJobError`) is the only code that talks to the function. `ledgerApi.ts` reads `ai_usage` (a database function: the month summed per Oslo day, job, mode and model), the `ai_calls` pages (never the text columns; a call's text is read when it is opened) and reads and writes `ai_settings` and `ai_job_settings`. `ledgerRules.ts` holds the pure rules (reading values where they enter, money, the Oslo month, totals, budget tones); `scripts/verify-ai-ledger-ui.cjs` checks it. `hooks/useClaude.ts` has one hook per read and per write.
- **✨ on the item screen** calls `runClaudeJob('item_fill', { text })`. A stopped run shows the function's own sentence for every reason (`off`, `budget`, `busy`, `not_configured`, `refused`, `cut_off`, `invalid`, `error`); only an answer with no sentence says "Couldn't fill the fields — try again in a moment".
- **Money** is USD: two decimals from a dollar up and for whole cents, four below a dollar, six in a call's detail. The budget counts a calendar month on Oslo's clock.
- **Safety.** A call's text is drawn as a text node in a `<pre>`, never as HTML or a link. The price source is a link only for an https address on one of Anthropic's own hosts (exact host match); source files link to GitHub only for a plain repo path. The calls' query is never kept on the device. The app can read the ledger and cannot write it; only the function does.
- **The page** is Developer → AI (`developer.md`). The harness plays the function in `scripts/harness/claude.cjs` (`scripts/harness/README.md`).

### Recipes and quick guess on Claude (phase 2a, 22.11.2026)

The recipe editor's and Food's quick-guess calls used to be `ai-proxy`'s `responseSchema` and `fetchUrl` modes (Gemini); both are gone from `ai-proxy`, with `callGeminiStructured`, its private-address code and `aiApi.ts`'s structured calls. They were rebuilt from scratch as five jobs of the `claude` function (all one-shot, app only, Haiku 5.5, low effort, no tools, no data, review-first: each only fills a form and nothing is saved or logged by it). The app side is `src/features/ai/claude/recipeJobs.ts` (the calls), `recipeAnswers.ts` (the recipe answers read again where they enter the browser; `verify-ai-ledger-ui`), and the screens' own existing checks (`readGuessEstimate`, `parseGuessOptions`) stay.

| Job | Where | In | Out (the shape the screen already used) |
|---|---|---|---|
| `recipe_from_text` | Recipe editor → Paste recipe → Paste text | the text, 10–6000 characters | `title`, `servings`, `instructions` (one step a line), `ingredients[{ name, quantity, unit, note }]`, `macro_estimate` (per serving, or null), `usedAi: true` |
| `recipe_from_link` | the same, From URL (also sets the recipe's source link) | an https link | the same; `usedAi: false` when the page's own data was read |
| `recipe_macros` | Recipe editor → Estimate | `servings`, up to 80 ingredients | `calories`, `protein_g`, `carbs_g`, `fat_g`, `sugar_g`, all five |
| `quick_guess` | Food → Quick guess → Describe it | up to 500 characters | `title` (≤ 40 asked, ≤ 60 held), `portion`, the five numbers, 1–4 `assumptions` |
| `quick_guess_options` | Settings → Food → Suggest options | a preset: name, portion, one portion's five values | `groups` (≤ 3) of `choices` (≤ 6): pick `one`/`any` add the five values, `size` has a `factor` |

- **AI last: `recipe_from_link`.** The function fetches the page with code (`page-fetch.ts`), then looks for a schema.org `Recipe` in the page's ld+json (`recipe-page.ts`); when there is a usable one (a title and an ingredient) code alone builds the recipe, quantities and units split from the ingredient lines, nutrition from `nutrition` (kilojoules are not calories). **No model is asked** — it is not an AI call: nothing is reserved, but a finished zero-cost ledger row is written (provider `page`, model `none`; Developer → AI → Calls shows it as "Read by code, no AI", and the link is kept in it only while the text log is on); the reply says `source: 'page'` and the app tells the owner "Read from the page, no AI used". Only a page with no usable Recipe sends its visible text (scripts, styles and comments out, 12,000 characters at most) to the model. Because it costs nothing, a spent budget does not stop a page the code can read; a switched-off job or a missing key does (the page is not fetched then). Because the row exists, the rate caps count each read; the caller is an owner-list account and each read is capped at 10 s and 2 MB.
- **AI last in the app (review fixes, 22.11.2026).** *Estimate* in the recipe editor first computes every ingredient that is linked to your library (or whose name is exactly one library food's name, case and spacing ignored; a name two foods share is left out) and has a weight or volume amount, from the library's per-100 g values (`macroEstimate.ts`); only the rest goes to `recipe_macros`, and when nothing is left the model is not asked. The toast says how much was computed and how much estimated. *Describe it* answers with no AI when the text is exactly one of your presets or the title of an earlier one-off diary line (30-day recents): the sheet says "From your preset — no AI used" or "From your earlier entry — no AI used". Not done: Kassalapp or Open Food Facts lookups for unlinked names (a later step).
- **Time limits and the answer reader.** A job's request limit follows its longest answer: 30 s up to 2000 tokens (✨), 50 s for a 4000-token recipe, at most 100 s. A model answer that is JSON followed by a note, a note and the object on one line, or a note and a code fence is read (the last top-level object that parses; an array is still refused). ✨ is handed the next 14 days (weekday and date) and next week's Monday, worked out by code in Europe/Oslo, instead of counting weekdays itself. (That 14-day list matches the old assistant's idea; it is kept because code works out the dates, which the model counts badly, not because the old prompt had it.)
- **The fetch is the SSRF wall** (docs/backend/edge-functions.md; `verify-ssrf-guard`): https only, no user name or port, private addresses in any spelling and names that resolve to one refused (`isPrivateHost` + `resolvesToPrivate`), every redirect re-checked (by hand, at most 4), 10 s, 2 MB, `text/html` only, fixed headers only. The address code is news-article's, line for line; the DNS question is handed in by `main.ts` (only it touches `Deno`).
- **Language: everything saved is English** (owner, 22.11.2026: "all the data that will be saved should be English; the assistant answers in the language of the question"). The first recipe prompt forced Turkish, the second kept the recipe's own language; now the model **translates** a recipe into English (title, ingredient names and notes, steps; a brand or a dish's own name stays): one sentence, `RECIPE_LANGUAGE_RULE` in `recipe-rules.ts`; change it there (and the jobs' version pins). The same rule holds for what the other jobs write that the app stores: ✨'s title and notes (a place stays as typed), the quick guess line's title, portion and assumptions and the options' names, the PT assessment, and the Kobo's saved answer. What is only shown follows the asker: the phone's question is answered in its own language, the phone's brief (no question) in English.
- **A recipe read from a page by code keeps the page's language.** There is no model call there (AI last), so nothing translates it: the result says `language: 'source'` (a model's recipe says `'english'`), and the app offers nothing new for it. An English rewrite of such a recipe would be an AI call; it is **not built**, listed for later.
- **No enforced answer shape** (`anthropic.md` trap 16): each job writes its JSON Schema into its instructions and our code checks every field (`answer-reader.ts`, `recipe-rules.ts`, `job-quick-guess.ts`): a wrong type, a number outside its range, a text over its limit or an unknown key is dropped, never repaired; a list over its limit keeps its first entries. A recipe with no title or no ingredient is invalid, so text that is not a recipe says so (the old prompt guessed a recipe anyway). `quick_guess` needs all five numbers (a missing one would show as a plain 0 on a line about to be logged). The reader finds the JSON object plain, in a code fence, or after a note on its own line (shared with ✨).
- **Limits.** A request is at most 16 KB, so a pasted recipe is at most 6000 characters (the app says so before sending).

### The PT assessment, the Kobo, the phone and the Test bench (phase 2b–2d, 22.11.2026)

Built from scratch on the `claude` function, like 2a; each old Gemini path is gone (`ptCoachApi.ts`'s `invokeAI` call and its Turkish `PT_SYSTEM_PROMPT`, `kobo-sync`'s `ASK_MODELS`/`GEMINI_API_KEY`, `phone-gateway`'s `FAST_MODEL`/`askAi` and the phone's secret path into `ai-proxy`). Five new jobs, all one-shot, Haiku 5.5, low effort, no tools, no enforced answer shape:

| Job | Callers | Where | In | Out | Time limit |
|---|---|---|---|---|---|
| `coach_assessment` | app | Training → Coach → Assess | feeling (one of four fixed English words: undertrained, normal, tired, very tired; the old Turkish ones are read as these), a note ≤ 300, the verdicts ≤ 1500, the snapshot ≤ 8000, the previous assessment ≤ 2000 | `{ text }`: four bold-headed English parts (Assessment, Recovery, The ONE priority for the next workout, Closing), ≤ 3000 characters | 40 s (2500 tokens) |
| `kobo_ask` | kobo | the Kobo's "Ask Lasci's AI" on a selected passage | `cleanAsk`'s fields: the kind, the selection ≤ 1500, context ≤ 600 each side, a question ≤ 500, title, author, language, percent, the answer language | `{ answer, answer_en }`: the answer in the language the reader chose, for the screen, and an English copy for the notes (empty for an English screen, where `answer` is saved), each ≤ 1200 characters, asked for ≤ 80 words (the Kobo's screen holds about that; the limit is twice the ask) | 20 s (the Kobo function waits 24 s) |
| `phone_brief` | phone | the shortcut "Sabah Brief" | `context` ≤ 4000 characters, built by the gateway's code (English labels, dates DD.MM.YYYY) | `{ text }` ≤ 1500 characters | 18 s |
| `phone_ask` | phone | "AI'a Sor" and "Uyku Özeti" | `question` ≤ 1000, optional `context` ≤ 4000 | `{ text }` ≤ 1500 characters | 18 s |
| `test_bench` | app | Developer → AI → Test bench | `text` ≤ 2000 characters, optional `model`, `effort`, `thinking` | `{ text, thinking, served_model }` | 40 s (2000 tokens) |

- **AI last, 2b.** The PT assessment's decisions are code (`src/features/training/coach/coachFacts.ts`): the recovery gate (sleep under 6 h trims the session, under 5 h two nights running is a rest day, "very tired" with a night under the average trims it), the deload cue (a muscle at its ceiling, the program's workload review, two lifts down while very tired), the one lift (the first READY_TO_INCREASE, else the first watch flag, with the progress engine's own target), the muscles under their weekly minimum and the push-/quad-heavy flags. They go to the job as a `<verdicts>` block beside the snapshot (`formatPtSnapshot`, still the app's own pre-aggregated figures); the model explains them, reads the owner's own words (pain) and writes the note. That is why the effort is low, not medium. The saved `pt_assessments.model` is the model that answered (`CallSummary.served_model`; new on every run answer), shown as "Haiku 5.5" on the tab. The coach's language is one sentence (`COACH_LANGUAGE_RULE`): the owner reads Turkish there; the feeling words stay Turkish because they are stored.
- **AI last, 2c.** The phone's context (tasks, schedule, training; or the last nights' sleep from `computeSleepNightsGw`) is looked up by the gateway's code and handed over as data; the old `ask` could call database tools, the new one cannot until Ask AI is rebuilt (phase 4), and gets the day's context instead.
- **How a device reaches `claude`.** Only `claude` holds `ANTHROPIC_API_KEY`. `kobo-sync` and `phone-gateway`, after checking their own device secret in constant time, call `POST /functions/v1/claude` with `x-claude-server-key: <HMAC-SHA256(service key, "claude-device-v1") as hex>`, never the service key itself (security review, 22.11.2026: a header can reach a log or a gateway, and the credential opens only `claude`'s device path, not the database; the service key is read through their `<supabase-keys>` block, so the new `sb_secret_` key and the legacy JWT key both work, and `claude` derives the same value itself) and a body of exactly `{ action: 'run', caller: 'kobo' | 'phone', job, input }`. `claude` is `verify_jwt = false` (an `sb_secret_` key is not a JWT, so platform verification would refuse it; this follows the documentation and has **not been tried on the real platform**), and authenticates both callers in code before it reads the body. See `ai-plan.md` §5 (phase 2 rows) for what an attacker controlling each input can do. The account is never sent: `claude` acts as `HEVY_USER_ID` from its own environment. The ledger row says `caller` kobo or phone, so Developer → AI → Calls shows them; each device has 100 calls in 24 hours (counted from the ledger by `caller`) on top of the ledger's 20 a minute and 600 a day, the Kobo keeps its own 100 in `kobo-sync`, and the monthly and per-job budgets bind a device like the app. A device run has no sign-in token, so `ai_gate` (which asks who is signed in) cannot answer it: the early rate-cap read counts the owner's `ai_calls` rows with the service client (three count queries); the real wall is `ai_reserve`, which counts and holds the budget in SQL under a lock and, since migration 195, this caller's own 24 hours too (`p_caller_per_day`: 100 for a device), so a burst cannot overshoot the cap.
- **The phone's `ask`/`brief`/`sleep` response** is the old `{ ok, text, model }` (model now the served Claude model) or `{ ok: false, error }`; the Kobo's `/ask` answers `{ ok, answer, model, saved }` or `{ error, message }` with the codes `rate_limited` (busy, over budget), `not_configured` (no key, switched off), `invalid`, `no_answer`, which the plugin already read.
- **`ai-proxy` no longer accepts the phone's secret** (its `viaPhone` branch and its copy of `sameSecret` are gone): a stolen phone secret reaches `phone-gateway`'s actions and the phone jobs, never the old assistant's tools.

**The Test bench** (Developer → AI → Learn → Test bench; `AiTestBench.tsx`, `benchJobs.ts`, `useBenchCount` / `useBenchRun`). A page of its own inside Learn, not a card in How it works: it is a thing the owner uses, with a form and its own results, unlike Diagnose, which only reads. The owner types a question (≤ 2000 characters), picks a model, an effort (both from `describe`'s lists) and thinking Adaptive or Off, and:
- **Count tokens** (free, `{ action: 'count', input }`): Anthropic's `count_tokens` on the request exactly as a run would build it (`buildRequest`), shown as the prompt's tokens, the input cost at the picked model's price and the answer's token ceiling. It writes nothing and reserves nothing; it is refused while the account is at a rate cap and for an account off the owner list.
- **Ask** (a real call): reserved, ledgered, in Calls as `test_bench`. Shows the answer, the model that answered, tokens (prompt, output, thinking, cache reads), cost, time and the thinking summary.
- **Compare thinking**: two real calls, Adaptive then Off, side by side, to read what thinking costs and how long it takes. `thinking: 'off'` is `{ type: 'disabled' }` in the provider (the SDK's `ThinkingConfigDisabled`; no `display`); with it Haiku 5.5 reports 0 thinking tokens and no summary. That it is accepted together with `effort` at low, medium and high on Haiku 5.5 is taken from the task brief and **not confirmed by a live call**: the Test bench is where to try it. This is the first step of "thinking off where measured safe" (`ai-plan.md`, Next): no job turns it off yet.
- The pick still goes through the code's lists twice (`prepare`, then `checkedChoice` in `run.ts`); a pick wins over the job's stored model and effort, and the stored job switch, budgets and longest answer still apply. The question travels in its own escaped tag; the job has no tools and no data of the owner's.

### Controls, numbers and what is saved (owner-critic and security round, 22.11.2026, migration 195)

Reviewed after 2b–2d; every item below is in the same PR.

- **Two controls** (migration 195). *All AI*: `ai_settings.ai_enabled` (default on), the first card in Settings. Off stops every job at once, the Kobo's and the phone's too: the function answers reason `off` ("All AI is switched off"), writes a ledger row and calls nothing; the Overview says so. *Thinking per job*: `ai_job_settings.thinking` (null = default, `adaptive`, `off`), a Thinking field on each job's card. The default stays adaptive **until a job's answers are measured to be as good without thinking** (a form fill probably needs none: less cost and time); nothing has been measured live yet. Both are input to the function like every setting: only `true` keeps AI on, only the word `off` turns thinking off; the app reads both with the 42703 fallback the database rules require (a database from before 195 reads them as on and adaptive; saving the defaults still works, saving a change names migration 195). Remove the fallbacks once 195 is live.
- **The cost of one call, in the call's detail**: each kind of token times its price (the prices of `describe`; the same sum the function made), then ×5 for a long prompt or ×0.5 for a batch. A call whose bill is unknown (a timeout: Anthropic may have billed it) has no token behind its cost: it is shown as **"Held at worst case — the real bill is unknown"**, and the Overview shows that amount separately ("$0.0019 of this is held at worst case for 1 call"). The rule is `heldAtWorstCase` in `ledgerRules.ts`: outcome `error` or `pending`, a cost, no token.
- **What was sent**: the provider part returns the request as it built it (`ModelAnswer.sent`, never a key: that is in a header), and the text log keeps it as `request.sent_to_provider` (the cache mark, the thinking setting, the effort and answer shape, the time limit); the instructions and the text are named by their length there, since the log holds them. The detail labels the parts by what they are billed as: the instructions are *cached input*, your text is *input*, the thinking and the answer are *output*. (A job's instructions under the model's minimum cacheable length are billed as plain input: the cache mark costs about $0.00003 a call when unused, so there is no per-job switch.)
- **The Overview's numbers** (from `ai_usage`, which 195 extended at its end: the average and the slowest time of the calls that ran, how many ran, and the held calls and their cost): the month's average time and cache hit %, thinking tokens, and per job the average and slowest time, the average real cost (held calls left out of both sides), the cache hit %, the thinking tokens and the split between models. The average of a job is weighted by its calls that ran; a stop before sending has no time.
- **Views**: Overview · Calls · Settings · **Learn** (How it works, Prices, Test bench, in a switcher under the bar, only inside Learn; `?view=learn&learn=prices`; the older `?view=how|prices|bench` links still land there). Four labels fit a phone without scrolling, and the bar never changes shape. A new explanation goes into Learn, never into a fifth tab. How it works has Diagnose under the path of a request, and a "Still on Gemini" card.
- **Caps that are walls.** The 100-a-day cap of each device is counted inside `ai_reserve` under the account's advisory lock (migration 195 added `p_caller_per_day`; a changed signature, so the old function is dropped), not only by the early read. The Test bench's free token count is a request to Anthropic too: it is capped at 10 a minute, counted from the ledger, and each count leaves a zero-cost row (stop reason `count_tokens`, shown in Calls as "token count, free") that the account's own caps count like any call (so "Calls" in the Overview includes free counts). Two counts at the same instant may both pass: the cap is small and the count free, so it is read without a lock.
- **The phone and the coach, from the same review**: the gateway keeps the brief's context under 3900 characters in whole lines (the function takes 4000), a phone question over 1000 characters says "too long" instead of "Ask something first", and the coach's request is cut by **bytes** before it is sent (`fitRequestBytes`: the function takes 16 KB for a request and an accent takes two bytes; the snapshot loses its last lines first, then the previous assessment; the verdicts and the note are never cut).
- **Not built, on purpose**: a retry of a refusal on Sonnet (no real refusal to look at yet; Settings does not offer it); a code-first reader of ✨'s sentence and an input fingerprint (phase 4 with `ai-plan.md` §8: a rule reader is not reliable across languages, and ✨ costs under $0.0001 and about a second); an English rewrite of a recipe read from a page by code (an AI call, for later); streaming (answers are short).

**Quick guess, written from its purpose (not from an earlier prompt).** The review said the two quick-guess instructions still read like the old ones. They were rewritten from what each screen is for; the **answer shapes stay**: they are the app's stored data contract (a diary line's fields, `quick_guess_items.options`), like `cleanItemFill` for ✨.
- *Describe it* serves someone who ate something they could not weigh and needs the one diary line they would otherwise work out by hand, and who reviews it before logging. So the instructions put the portion first among the assumptions (the amount is the biggest error), ask for kcal to the nearest 5 (a guess must not look exact), keep alcohol in the calories but out of the macros, and ask for 1–3 short assumptions (each under 100 characters; held at 4 and 200: asked below the hold, so a slightly long answer is not thrown away). The title is at most 40 characters asked (the card appends " ×2"), 60 held (the preset name's own limit); the portion under 60 asked, 120 held (the column's limit).
- *Suggest options* serves a preset that logs in one tap: each group is one more question before that tap. So it asks for the one or two groups that move the numbers most (held at 3, the table's limit), 4 or 5 choices each (held at 6), names under 20 characters (held at 30), and a size group only between 0.5 and 2 portions, because the card already has its own ½–2 switch (held at 10, the table's limit); no size for a fixed unit.
- Both write their texts in English (everything saved is English) and keep the injection rules (the text in its own escaped tag, never an instruction).

### Diagnose (22.11.2026)

**Why.** On 22.11.2026 every ✨ call waited exactly 30 s and got nothing back from Anthropic (no request id, 0 tokens), then the function gave up (`APIConnectionTimeoutError`); the Supabase log showed only a POST 200 after about 30 s. Two causes fit: the request never reached Anthropic (the network or the SDK between Supabase's edge runtime and `api.anthropic.com`), or Anthropic got it and was slow (most likely the one-time compile of ✨'s answer shape: 21 optional fields; Anthropic says a new schema is compiled once and then cached for 24 hours). Diagnose tells the two apart from production, with one tap.

**Where.** Developer → AI → Learn → How it works, the card under "The path of one request" (it follows the path, since it is for when the path misbehaves), titled "Check the connection to Anthropic" (`AiDiagnose.tsx`; the button says "Check the connection"). It is on How it works, not a view of its own, because it is a question about how the function works and it shares the page's "read only, nothing to set" nature; a sixth tab would be one card on a page of its own. While it runs the card says "Checking… this can take up to 2 minutes." The result is four rows (a tick or a cross, the time, the function's own sentence) under one verdict line worked out from them (`diagnoseVerdict` in `ledgerRules.ts`, checked by `verify-ai-ledger-ui`). The card stays when the description of the function can't be read, since Diagnose doesn't need it.

**The four checks** (`{ action: 'diagnose' }` → `{ ok: true, steps: [{ name, title, ok, ms, detail }] }`, `supabase/claude-src/diagnose.ts`):
1. *Network and key* — lists the models (free, 20 s). Says how long, how many models, and whether `claude-haiku-5-5` is in the list; or the error kind and HTTP status. **Only this check stops the others:** with no connection nothing after it tells us anything.
2. *Request shape* — counts the tokens of ✨'s real request (its instructions, answer shape and a made-up sentence; free, 20 s). A 400 here would show Anthropic refuses the answer shape.
3. *Tiny answer* — "Reply with the word OK.", no answer shape, effort low, 512 tokens at most (20 s), through the normal run path: reserved against the budget, sent, written to the ledger as the job `diagnose` (a real, tiny call; it shows in Calls and in How it works → Jobs).
4. *✨'s real request* — the `item_fill` job with the same made-up sentence through the normal run path (reserved, ledger row), with **90 s** instead of 30 s, so its true time shows.

The whole action stays under Supabase's 150 s limit: step 4 gets at most 90 s and at most what is left of 140 s; if less than 10 s is left it is skipped and says so. A step that throws is a failed step, never a crashed function. Each `detail` is one plain sentence with numbers, through `hideSecrets`, at most 400 characters; never the key, never a raw SDK object.

**Reading it.** Tiny answer fast and ✨ slow means the answer form is the slow part (run it again: the first call with a new form compiles it once). Step 1 failing means the server can't reach Anthropic or the key is refused. Both slow means Anthropic is slow overall.

**Rate cap: one a minute per account.** The function reads the ledger with the owner's own client: a `diagnose` row written in the last 60 s means "busy" (a plain sentence, nothing sent). Step 3's reservation writes that row even when the budget refuses it, so the ledger is the clock and no new table or column is needed. A read that fails answers an error and runs nothing (fail closed). Not counted: a Diagnose that stopped at step 1, which sends only the free list request. Two taps in the same instant can both pass the check; the database's own rate caps and budget wall in `ai_reserve` still bound them. The tiny job can also be started by a plain `run` from the app (it is tiny and capped like any job).

**Cost.** Steps 1 and 2 are free. Steps 3 and 4 cost a fraction of a cent (the ✨ call is about $0.0002 once the instructions are cached); each holds its worst-case cost against the budget first, like every call.

**Trade-off for this test.** The provider's time limit is a per-request option (`ModelRequest.timeoutMs`, default 30 s), not a second client; only Diagnose sets it. The message for a timeout names the limit that was used ("within 90 seconds").

## AI (ai-proxy) Detail

Gemini via the `ai-proxy` edge function. Call modes: the conversational **tool-calling loop** (default) and **`{ itemFill: { text } }`** (11.11.2026, the item screen's ✨ — `docs/features/planning-calendar.md` → The item screen): a narrow action that reads nothing else of the body. The sentence (checked first: 1–500 characters, one line, no control or direction characters — `itemFillTextProblem`, else 400) goes to the model with today's date in Oslo, the next 14 days by weekday and the time zone, in the user turn as a JSON string the prompt calls data, never instructions; the prompt (`ITEM_FILL_PROMPT`) and the schema stay fixed, so they cache. One single-shot call (`gemini-3.1-flash-lite` first, the answer capped at 2,048 tokens; this branch has since moved to the `claude` function, `item_fill`, and this text is history), **no tools and no data**; nothing is read from or written to the database. The answer goes through `cleanItemFill` — `src/features/items/itemFill.ts`, GENERATED into the function between `// <item-fill-shared>` markers by `scripts/sync-item-fill-shared.mjs` — which keeps only the item screen's own fields, each checked (allow-lists, real days and times in range, capped text with no control, direction or invisible characters — the astral ones too, by a `u`-flag class) and drops any other key. The model is never asked for a link or the area: the link is the one https:// address written in the sentence (`linkOfSentence`; the model's `url` is never read — a piece of a link, `https://den` from "Dentist", `https://router` or `localhost` can't come back), and the area picks the item's Apple calendar, so it is never guessed (guardian, 11.11.2026); an answer that isn't JSON fills nothing. The browser runs the same check again. The phone's secret can't call it ("Fill in the app."); a stolen session could only spend the AI quota, as with chat (`scripts/verify-item-fill.cjs`).

**Generic DB tool layer** over a curated `DB_CATALOG` allow-list: `describe_database`, `db_query`, `db_insert`, `db_update`, `db_delete`, **`db_aggregate`**. Guardrails: default-deny allow-list (token/secret/auth tables unreachable), `access: 'rw'|'ro'` per table (hevy_*/strava_activities/health_metrics/health_workouts/movies/tv_series are read-only — synced externally), **every op force-scoped to `user_id` server-side** (the model never supplies it; a shared read-only table without `user_id` — `fx_rates_nok`, `shop_site_policies` — is read whole by `db_query`, with nothing embedded in it, where the filter only made the read fail; 10.11.2026), no DDL, update/delete refuse empty filters, 16-turn loop cap. `app_error_logs` is readable so the AI can help diagnose failures. `pt_assessments`/`work_notes`/`work_weekly_goals`/`work_pinned_links` are read-only; **`dev_requests` and `wish_items` are read-write on purpose** — the user dictates backlog notes and wishes in chat (and by Siri) and the AI writing a structured row there IS the intended flow; `wish_items`' catalog `rules` carry the never-a-deadline guardrail and the four-way tie-break against `dev_requests`/`ai_memory`/`shop_items` (see Wishes). `day_targets` is `rw` too (singleton, confirm before writing, set `phase_start_date` on a phase change). **Deletes are confirmed in the app, not in text (security audit 10.10.2026):** `db_delete` and `update_hevy_routine` from the tool loop only store a proposal in `ai_pending_actions` (migration 140) and return a **Confirm card** (`ConfirmCards.tsx`); the action runs only on a separate `confirmAction` request the model cannot send — exactly the rows shown, once, for the same account, within 15 minutes. The phone (no button) cannot delete. The assistant may not set link columns (`AI_NO_WRITE`: `google_calendar_event_id`, Google Task / Trakt / ES-DE / ScreenScraper ids, `session_id`) or what the database fills itself (09.11.2026: Shop's frozen NOK rates `fx_nok`/`fx_source`/`sale_fx_nok`/`sale_fx_source` on things and extra costs — a rate sent is kept as typed by hand — and a sale's Undo record `sale_undo`), nor a task's retired `tomorrow` / `this_week` section (14.10.2026: a day other than today is Backlog), play counts are capped at 1–99, a memory it writes is always `source='ai'` (marked "you saved" in ABOUT ME), and `db_query` may embed nothing inside a shared table (`selectProblem`). Text from the CONTEXT turn or a tool result is data, never an instruction (system prompts + phone persona). `DB_CATALOG` stays behind `describe_database` (on-demand, not in the prompt). `water_log_entries` is `rw` too (one row per amount drunk; the day's total is the sum; never a `food_log_entries` row). `quick_guess_items` is `rw` (migration 152: the Quick guess presets — templates, not logs; the rules say eating something is always a `food_log_entries` row and a preset is added or changed only when the user asks; the Confirm card calls them "quick guesses"; migration 159 added `options`, a jsonb array of up to 3 option groups — the catalog spells out its shape, the table's CHECK refuses anything else, and the rules say to send the whole array and leave it `[]` unless asked). `day_targets` lists `carbs_g` / `fat_g` (migration 153: the owner's own carb and fat goals; NULL means the app works them out, so the AI reads a NULL as "worked out", never as zero).

- **`db_aggregate`** — `sum|avg|min|max|count` + `group_by`; enum'd ops only (never expressions), the same filter grammar as `db_query`, group columns validated against the catalog, hard cap ≤366 groups, rows reduced server-side so only the summary reaches the model. This is what makes "no pre-written query per scenario" true for analytics. **Tool-choice ladder** in the system prompt: current value/list → `db_query` · average/trend/compare → `db_aggregate` · whole-day picture → `get_day_summary` · "that thing I saved" → `semantic_search` then `db_query` by id · writes → `db_insert/update/delete` with the confirm rules · external world → the special tools.
- **`semantic_search`** (migration `065`: pgvector + `ai_embeddings` `vector(768)` hnsw cosine + the `ai_semantic_search()` SECURITY-INVOKER RPC) — `gemini-embedding-001` @768, **cosine index → no manual normalize**, vector `limit ≤ 8`, `user_id` filtered inside the vector query; returns `{source_table, source_id, snippet, score}` and the model then `db_query`s the live row by id. **Embeddings locate, live SQL answers — never use a similarity hit as the factual value of anything current-state.** Editing or deleting a searched row drops its copy (migration 140's trigger), and every `semantic_search` first embeds up to 32 rows that have no copy, so edits come back by themselves; Developer → "Reindex AI search" still re-embeds everything. Caveat: the embedding request shape was confirmed from docs, **not a live call**.
- **`run_read_query`** — the opt-in read-only live-SQL escape hatch. **Its security boundary is the DATABASE, not the edge regex:** ai-proxy's normal ops run under the service role (RLS bypassed), so this path instead builds a **user-JWT client** and calls an RPC (`ai_run_read_query`) that runs with exactly the caller's rights as `authenticated` (RLS applies), sets `transaction_read_only = on`, and wraps in `LIMIT 500` before `jsonb_agg` (a row count, not a size cap; the time limit is the role's own statement timeout — the function's 5 s setting can't shorten a running statement). Containment = RLS + the read-only transaction + migration 044's revoked OAuth-token-table grants + the row cap + **185**: (1) only an app user (`is_app_user()`) may call it; (2) **Postgres's own wall** — the function is SECURITY DEFINER *owned by `authenticated`*, so it has the caller's rights and Postgres refuses any change of `role` or `session_authorization` inside it, whatever runs the SQL (an extension included); where the platform won't let the migration hand it to `authenticated`, the deploy log says so and it stays SECURITY INVOKER; (3) name checks, fail closed: comments, quoted names, `;`, SET/RESET/DISCARD, `set_config`, `current_setting` (it would read the request's own headers — the caller's sign-in token), `set_limit`, `setseed`, built-ins that run SQL text (`*_to_xml*`, `ts_stat`, `ts_rewrite`, `dblink*`), itself, `pg_` names and system schemas (an alias or CTE may not be named like one either); (4) a last line: a query that changed the role, the claims or a flag the database's own code reads (its `watched` list; 189 added 187's `app.shop_restored`) returns nothing and the change is undone (it can't see a change the query restores itself). Why (guardian, 02.11.2026): 140's `set_config` pattern could be stepped around with a comment or a call built inside a string `query_to_xml` runs, and a query that changes the `role` setting becomes the service role (PostgREST's login may become it) — past the 044 grants, reading every token; any signed-in session could call the RPC straight from the browser; an extension that runs SQL text (tablefunc, pgTAP, pgRouting) would reopen it without (2). `verify-db-read-query` reproduces 140's hole first, then checks every bypass is refused, with the wall and without it (tested on a database built like Supabase's, not yet on the live project). The edge guard is a best-effort UX filter that **fails closed** (strip comments first, reject quoted identifiers, `SELECT`/`WITH` only, single statement, block `pg_`/`information_schema`/other schemas, check every `FROM`/`JOIN` target incl. comma-joined lists against the catalog, recognise CTEs only as `name AS (`). **The broad DML-keyword regex was deliberately REMOVED — do not re-add it**: it false-rejected reads containing "update" inside a string literal; write-prevention is the read-only transaction's job.
- **Special-purpose tools** generic CRUD can't cover: `get_calendar_events` · **transit** — `plan_trip`, `get_next_transit`, `get_saved_transit`, `search_transit_stops`, `save_transit_stop`, `save_transit_route` · **media** — `get_media`, `plan_media`, `mark_episode_watched` · **health** — `get_health_stats` · **shop** — `get_shop_categories`, `create_shop_category`, `create_shop_item`, `ask_clarifying_question` · **training** — `update_hevy_routine`, `create_hevy_routine` (both forward to `hevy-api`), `get_athlete_profile` (see Training's athlete-profile note) · `get_day_summary` · `save_memory` (+ rw `ai_memory`: durable notes the user asks the AI to remember, recalled via `db_query`).
- **Media.** `get_media` returns one compact line per title. `entry_id`/`title`/`status` (+ `current_season`/`current_episode` for TV) are always there; then only the keys that are known: rating, genres, favorite, released/first_aired, watched (movies; `unknown` for an unknown date) or started/finished (TV), plays, planned and a 140-character note. Days are the Oslo day. Optional `status` (default active = watching + paused + want to watch, including the legacy `upcoming`) and `limit` (25, ≤ 100). `coming_soon` is worked out from the release date. `mark_episode_watched` keeps an already-watched episode's date, never wipes its rating/note, and never writes the progress cache (migration 050's trigger owns it). `DB_CATALOG` documents the media columns and what syncs to Trakt (genres through the `movies`/`tv_series` embeds), plus `movie_cinema_visits` (rw), `media_watches` (rw — every watch with its own date, migration 149; `trakt_history_id` is in `AI_NO_WRITE`) and `media_follows`/`media_follow_events` (ro). - **`ai_memory` — an "ABOUT ME" context block + a management surface.** Two gaps closed together on user request. (1) `aiApi.buildContext` now appends one more query (last in the array, so no existing `get<T>(i)` index shifts) reading `kind IN ('fact','preference')` only — deliberately **not** `note`/`summary`, which stay on-demand-only via `db_query`/`semantic_search` so they never bloat every single turn's context — capped at 12, newest first, rendered as an `ABOUT ME` block right after `DATE`/`TIME` (before `TODAY'S TASKS`): durable identity facts colour how everything else should be read, so they go first. (2) `save_memory`'s tool description now explicitly covers TWO distinct triggers, not one: remembering a single fact/preference (unchanged), and an explicit **"summarize this conversation"** request ("topla ve not al", "bunu özetle", "summarize this conversation", …) — compact the WHOLE conversation so far into one `kind="summary"` call, not just the last message. (3) A new Developer → **Memory** tab (`MemoryTab.tsx`/`MemoryRow.tsx`/`MemoryEditSheet.tsx`, `src/features/ai/api/memoryApi.ts`) lists/edits/deletes every row and is the only path that ever writes `source='user'` (every other row is `'ai'`, from `save_memory`, or `'auto'`) — before this, `ai_memory` had no UI at all: nothing to see what was remembered, nothing to correct a wrong entry. (4) `AIPanel` gained a Summarize header button, gated on `messages.length > 0`, that sends a normal chat message ("Summarize this conversation and save it to memory." / the Turkish equivalent, following the existing voice-chat TR/EN chip) down the same `handleSend` path as any other turn — the model's `save_memory` call still lands in the transcript like any other tool use, nothing hidden.
- **`get_health_stats` — two fixes worth remembering.** (1) It and the catalog both pointed at `health_daily_stats`, a table dropped when migration 041 moved Health to point-in-time grain, so the AI's health answers were silently broken (empty/stale) ever since; rewritten to query `health_metrics` directly and aggregate with the same rules as `healthAggregate.ts` (sum steps/energy, min/max/avg heart rate, latest resting HR, kJ→kcal). That closed the "no sleep data" answers in the phone `sleep` action and the Coach. The prompt tells the AI to *analyze* health data (trends, comparisons, honest criticism), not recite numbers.
- **Latency design for `plan_trip` (was a real 3–4 min pain point).** It is a ONE-SHOT call: the prompt and tool description tell the model to call it directly with the user's own words (`from:"ev", to:"iş"`) and NOT to look things up first — earlier "investigate first" wording caused ~5 sequential Gemini turns (each a full round-trip) vs ~2 now. `plan_trip` resolves both endpoints itself against saved stops/routes loaded ONCE (not re-queried per endpoint), in parallel: empty → default saved stop; an exact `NSR:StopPlace:` id → used as-is (name backfilled from the trip legs, no extra lookup); "home"/"ev"/"work"/"iş" (+variants) → saved-label fuzzy match; else → geocoder top match. When a side won't resolve it returns `{success:false, needs_clarification:true, candidates:[…]}` so the model asks ONE `ask_clarifying_question` instead of firing more search turns. **Only a regex-validated `NSR:StopPlace:` id or finite coords are ever interpolated into GraphQL** (injection safety). Anti-hallucination is structural (report only what the tool returns; call once and report), not extra verification turns. New EnTur GraphQL fields are deliberately NOT added speculatively — verify live first.
- **Model chain + retries.** Gemini returns transient "model overloaded" 5xx that clear within seconds, distinct from a 429 (real quota — surfaces immediately via `throwRateLimit`). Overload waves hit different models' capacity pools unevenly, so retrying a DIFFERENT model beats retrying the same one. `fetchGeminiWithFallback` tries `MODEL_CHAIN` = `gemini-3.5-flash` → `gemini-3.1-flash-lite` → `gemini-2.5-flash` → `gemini-2.5-flash-lite` with jittered exponential backoff, position-weighted attempts (`RETRIES_BY_POSITION` [4,3,2,2]) so better models are tried hard before falling to lite tiers. Each attempt has 20 s (`GEMINI_ATTEMPT_TIMEOUT_MS`, `AbortSignal.timeout`): a timed-out attempt moves on to the next model, and when the last one times out the answer is a 500 "Gemini timed out: …" (through `hideSecrets`); any other network error still ends the chain. The limit was promised on 22.07.2026 but only wired on 07.11.2026 — until then a hung connection held the request until the platform ended it (`verify-secret-errors`). The same day every other outside **read** got one (`fetchWithin`, the answer included): Gemini embeddings 20 s, the model list 10 s, Google's token 10 s and each Calendar page 15 s, EnTur 10 s (a trip 15 s); a read that runs out fails as "<service> did not answer within N s". The two Hevy routine **writes** (`hevyRoutineWrite`) wait up to 60 s; with no answer, or a hevy-api failure that can come after Hevy took the write (a 5xx that is not Hevy's own 4xx), the result is `outcome_unknown` and tells the model not to send it again and to have the user check Hevy — a plain failure invited a retry and a second routine Undo can't remove (guardian, 07.11.2026). A tool that throws is one failed step the model is told about (`{ success: false, error }`, through `hideSecrets`, logged), never the end of the reply; a network error names the service, never the URL (which held the search's words). A confirmed action's error is scrubbed the same way before its text and step reach the browser. A confirmed routine change with no answer reads "Hevy didn't confirm the change. It may have gone through: check the routine in Hevy before trying again." (its step: "? update_hevy_routine — not confirmed"), never the model's own instruction. **Every model id must be live-verified before entering this list** (real bug: two guessed ids 404'd in production; a 404 also used to abort the whole chain — it now skips to the next model). Probe with ai-proxy's `{listModels:true}` debug branch, which returns the key's REAL available models. The client can pass a `model` — it becomes the chain's **preferred starting point**, not an exclusive choice (`AIPanel`'s header picker, localStorage `lasci-ai-model`, "Auto" by default); `AIResponse.model` reports which model actually answered.
- **`thinking_config` per-model body (real bug, round 3):** `thinking_config`/`thinking_level` is a `generationConfig` field that is **Gemini-3.x-only** — explicitly picking `gemini-2.5-flash` 400'd with "Thinking level is not supported for this model" the moment a real user tried it, because ONE fixed request body was built once and reused across every model in the chain. `fetchGeminiWithFallback`'s `body` param became **`buildBody: (model) => AnyRecord`** — the body is constructed PER MODEL inside the retry loop, and `supportsThinking(model)` (`model.startsWith('gemini-3')`) gates whether `thinking_config` is included. Applies to all three call sites (the tool loop, the turn-limit summary, `callGeminiStructured`). `thinking_level: MINIMAL` in the loop — thinking tokens are not the cost leak.
- **Prompt-caching contract (don't regress it).** Live context used to be baked into `systemInstruction`, which made Gemini's implicit prefix cache (~90% off a repeated byte-identical prefix) structurally unable to hit — a ~7,270-token fixed block (system + serialized TOOLS) was billed at full price on every turn of every tool loop. Now: **`SYSTEM_PROMPT` and the per-surface tool declarations must stay byte-identical per call** — never interpolate a date, timestamp or any volatile value into them (instant cache-buster; the current date belongs in the context turn), and serialize tools deterministically. Live context rides as `contents[0]` (`prependContext` in `aiApi.ts`). `buildContext` is skipped for clearly transit-only questions (a conservative client-side `TRANSIT_RE` gate). **`ai_usage_log.cached_tokens`** (← `usageMetadata.cachedContentTokenCount`) is the proof metric and the documented trigger for escalating to explicit `cachedContent`. `ai_query_log` records every `db_query` + live SQL with the exact statement — the substrate for later promoting hot queries into the UI.
- **Tool sets + model routing.** No chat surface is sliced: **general and coach get the FULL tool set** so the assistant is never weakened, and **the `phone` surface gets NO tools at all** (its brief context is pre-built server-side by `phone-gateway`, so a single-shot answer is the biggest latency win). The Shop page's own chat (the old sliced `shop` surface) is retired (07.10.2026); a client still sending `surface: 'shop'` gets the general behaviour. `SURFACE_MODEL` changes only the **starting** model and holds only `phone: 'gemini-3.1-flash-lite'` (skips the frequently 503-overloaded 3.5-flash primary, which burned ~7–13s of retry budget before falling through — fatal against the ~25s iOS Shortcuts cutoff); the lookup reads only its own keys. A 503 still falls through the whole chain.
- **Voice chat (`useVoiceChat.ts` + AIPanel):** browser-native Web Speech API — `SpeechRecognition` (prefixed `webkitSpeechRecognition` everywhere that has it) for speech→text and `speechSynthesis` for text→speech. **No key, no edge function, no cost** — nothing server-side changed. Two levels: the mic button dictates into the box (edit before sending), and the header **Voice** toggle is hands-free mode — utterance auto-sends, the reply is spoken, and the mic reopens when it finishes (`speak(text, onDone)` → `startListening()`), so it's a real back-and-forth loop. TR/EN language chip (`lasci-ai-voice-lang`) drives BOTH recognition and the picked voice.
