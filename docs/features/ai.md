## The Claude layer, app side (phase 1, 21.11.2026)

The AI rebuild's first phase (plan: `ai-plan.md`, contract: `ai-phase1-contract.md`) adds the `claude` edge function and, in the app, the code under `src/features/ai/claude/`. Phase 2a (22.11.2026) moved the recipe editor's and Food's quick-guess calls to the same function (section below). Everything after that describes the old assistant (`ai-proxy`: Ask AI, the coach), which stays until phase 4.

- **Instructions are short and written for a model (owner, 23.11.2026).** The owner's words: "Your pre-prompts for ai is too long and detailed! Keep it simple and be aware that it is an ai not human." Every job's instructions (and the two chats') now hold the task in a sentence or two, short bullet rules that change the answer, and the answer shape; no background stories or reasons meant for a person, and code checks the rest. Each job's version string was bumped (`2026-11-23.x`) and its pin in `verify-claude-function` updated; the chat's version is `2026-11-23.4`, so a chat opened before it asks for a new one.
- **Read a receipt (owner, 23.11.2026).** The owner's words: "add a function in shop page to read from receipt. Either to sell or save a purchase. Both, physical receipt and digital receipt/PDF. AI can read and search web for this function." It is the same job as "From a receipt" (`receipt_read`), no second copy. The popup (`shop-receipt`, lazy, `ShopReceiptModal`) reads up to 5 files, one call each and one after another (see "Several receipts at once" below), presets a Bought | Sold switch from `kind` (the owner can change it), and lists the product lines: Bought → a line that is one of the owner's wishes says "Bought" (the wish becomes bought through the one Bought every screen uses, with its Undo, and Just bought opens with the receipt's values, the channel included), any other line has a tick, and "Next" opens the ticked ones as drafts in the Shop's create popup ("1 of 3", saved one by one) with the line's name (the product name when there is one), brand and model, condition, price, currency, day, the store matched to the owner's own and the category; Sold → each line is matched by code to one of the owner's things still theirs (`thingForLine`: equal folded name, a name that holds the other, then `matchLine`; two equal matches are not guessed between) with a picker to change it, and "Sell" opens Sell with the amount, the day and the buyer (the receipt's store when it is one of the owner's own stores). A line saved shows ✓. **The category (owner, 23.11.2026: the PDF was read but "did not fill in category").** `receipt_read` used to get only the file, so it could not name the owner's category. It now works as `shop_tidy` does: the app sends the owner's own categories (`tidyCategories(categories, 200)`: "Top" and "Top / Sub", paths cut to 60, tops first, at most 200 — the ids are not in the prompt, the body stays inside the 1.5 MB wall beside a PDF at its limit: tested at the worst size), the function numbers them "number | Top / Sub" in an escaped `<categories>` tag, each line may answer one number (the subcategory when one fits, else a top one, or none), and code maps the number back to the id that was sent — a number off the list is dropped, a model-written id is never read. The app checks again (`readReceipt` keeps only an id it sent) and shows it as a "check" fact from "the receipt" in the popup's "Filled in for you" list, never over a category the owner chose. With no list sent (or a category deleted meanwhile) the fill works as before. Version 2026-11-23.5 (the owner's best sites as a hint; a product page link from the search, a discount with its reason and the normal price, the receipt's extra costs). The instructions tell the model the Norwegian labels, the number forms ("4490,-"), to skip shipping, pick-up and 0,01 lines, to take the order day and not the payment day, and what an Outlet mark means. An Outlet line has no condition fact (the app holds none for it): it goes in the receipt note.
- **Several receipts at once (owner, 23.11.2026: "add option to add multiple pdf reading"):** the same job, called once per file by the app (`useReceiptRun`, one at a time, at most 5 files a pick, each file read at its turn; no function change). The worst case is shown before the queue starts (`receiptWorstCost`). Attacker notes for it: *files* — each is the attacker's input as before (checked again by the function; the browser's type and size check only saves a call); a hostile name never leaves the screen (shown as text through `shownName`, never sent, stored or logged); a file that fails or is a repeat costs one call and changes nothing. *Answers* — each is checked field by field twice as before; two reads of one receipt are called the same only by code (store, day, total). *Link targets* — a money link's two ends are ids of the owner's own items or rows this session's writes answered with; the suggestion is code and never reads an id from an answer; a model-written id cannot become a link. *Undo all* — acts only on ids this popup wrote, asks first, skips what is no longer sold or no longer there. *The queue* — it can never spend more than the budget wall and the per-minute and per-day caps allow, since every call is reserved like any other; it stops on the first off / budget / billing reason.
- **Attackers and the receipt** (guardian notes): a PDF or photo is the attacker's input: its words are data (the instructions say so, the answer is only a JSON object that code checks field by field, no link is followed, no HTML is rendered, a brand or model with a link is dropped); a huge or many-page PDF is refused by size (1 MB), by Anthropic's own count (16,000 tokens) and by the reservation held at that count; a file that is not a PDF is refused by its bytes, one with a password by its `/Encrypt` entry, one Anthropic cannot read by its 400 at the count; web search results are data, at most 2 searches, and only the checked answer leaves; the body is capped (1.5 MB, 16 KB for every other job); `auth.getUser`, `isAppUser`, the ledger, `ai_reserve` before the call and `hideSecrets` apply as for every job; the function has no PDF library.
- **A receipt's page link, costs and discounts (owner, 23.11.2026: "Shop AI don't bring picture link"; "2 items on a PDF does not work as it should"; "the discounted or additional costs do not come as separate").** `receipt_read` (and `shop_tidy`) may name the product's own page, never a picture address: the function keeps a link only when it is an address that call's own web search returned (the provider part reads each `web_search_result.url`; exact match, https, ≤ 2 048, no user, password or port) and adds up to two more results on other hosts as candidates; the app reads them through shop-price's `read` (see `docs/features/shop.md`). Each line also returns, apart: `price` (paid), `before` (the normal price, only when printed), `discount` and a `discount_reason` (points, member, campaign, coupon, staff, other); the receipt returns `costs` (shipping, fee, service, warranty, insurance, deposit, discount: kind, short name, positive amount, a discount's reason, at most 8). Code checks every value (the normal price above the paid one, the discount below the normal price, else both are dropped; 0,01 and absurd amounts dropped; a link as a name loses its name) and the app checks them again; none is ever worked out by code from another.
- **Tidy up info (owner, 23.11.2026).** The owner's words: "an additional function to tidy up the existing products info". The job `shop_tidy` (Haiku 5.5, low effort, web search at most 2, app only) suggests, for one thing, a cleaner name ("Brand Model variant, colour"), a brand, a model and one of the owner's own categories. **The exception to "saved data is English" (owner, 23.11.2026): it keeps the store's words** — no translation — like the owner's own typed words. It may also name the product page (only addresses its search returned): the app reads it for a picture and offers it as a ticked **Picture** field (`docs/features/shop.md`). It is in Shop (the header's ⋯ → "Tidy up product info" for all wishes and things you own; a record's ⋯ → "Tidy up info" for one) and is documented in `docs/features/shop.md`. Code decides everything but the words: the category list is the owner's own and is sent by code, numbered; the answer's name must share a word with the old one; no link, path or over-long value passes; a category must be one that was sent. Attackers (guardian notes): a thing's name is data and may be hostile (it can come from a page read) — it is escaped in its own tag, the model's answer is a JSON object with four keys and nothing else can be saved, so no link, picture, price or date can be changed; a name that tries to steer the model into another name is dropped by the shared-word rule; the category can only be one of the owner's own; "all" is one call at a time, each reserved (`ai_reserve`) and ledgered, with the per-minute cap waited out (three tries) and the budget or switch ending the run with the function's own sentence.
- **Sort out a list — attackers (guardian review, 23.11.2026).** The typed text may be pasted from a hostile page, and the model's answer is input too. (1) *Instructions in the text:* it is data in its own escaped tag; a closing tag cannot end it. (2) *A name the text never held:* every name is checked against the text's own words (typos only), every number in it is a number the text wrote and every single letter an exact token of it — so no digits, no "a b c d" filler, no brand can be added; a quantity and a unit likewise; anything else is dropped and counted, never repaired. (3) *Symbols and markup:* a name may hold only letters, marks, numbers, spaces and `. , ' & ( ) % / + -`. (4) *Hidden characters:* the text is refused, and a name is cleaned, with the whole `FILL_NOT_TEXT` set (tag characters, U+2060–206F, soft hyphen, line separators, C1 controls, variation selectors, lone surrogates); the zero-width joiner is also stripped before the address check. (5) *Addresses:* looked for after NFKC (full-width letters) and without invisible characters: schemes, `www.`, `@`-addresses and real top-level domains from a short list, in the text (refused before any call) and in every name (dropped). (6) *Writing:* the job writes nothing; the review's Add is the batch add of plain titles and notes the owner has just seen and may have edited — no link, id or key from the model reaches a write. (7) *Cost:* the text is capped at 1 000 characters and 30 items, refused before the call, and the call is reserved and ledgered like any job. Tests: `verify-quick-list-ai`, `verify-claude-function` (quick_list_parse).
- **Sort out a list (owner, 23.11.2026).** The owner's words: "ai list for quick list. I should be able to write things there and the ai will resolve and polish it to separate items or just fix it whatever that means to ai." The job `quick_list_parse` (Haiku 5.5, low effort, no tools, app only, 1 500 tokens) splits a typed or pasted text into items: a name, and a quantity and unit only when written. **The owner's own typed words: not translated, saved as typed** (the exception to "saved data is English"). **AI last:** the app splits a text that already has commas or lines by code and never sends it (`planQuickText`); only the rest is sent. **Nothing invented:** a name must be made of words the text holds (typos allowed), a quantity a number the text wrote, a unit a word it wrote, at most 30 items, no link; the text (≤ 1 000 characters, no link, no hidden character) is refused before a call, the answer is checked in the function and again in the app. Nothing is written by the job; the review's Add goes through `useAddBatchToQuickList`. Details: `docs/features/shop.md` → "Sort out a list with AI".
- **Words.** A *ledger* is the table `ai_calls`: one row for every call, with its tokens, cost and how it ended. A *job* is one named task the function can do; there are `item_fill`, the five jobs of phase 2a, the five of phase 2b–2d (the PT assessment, the Kobo's and the phone's, the Test bench; below) and the tiny `diagnose` (see Diagnose below). An *outcome* is how a call ended (answered, refused, cut off, over budget …).
- **Files.** `claudeApi.ts` (`runClaudeJob`, `describeClaude`, `diagnoseClaude`, `ClaudeJobError`) is the only code that talks to the function. `ledgerApi.ts` reads `ai_usage` (a database function: the month summed per Oslo day, job, mode and model), the `ai_calls` pages (never the text columns; a call's text is read when it is opened) and reads and writes `ai_settings` and `ai_job_settings`. `ledgerRules.ts` holds the pure rules (reading values where they enter, money, the Oslo month, totals, budget tones); `scripts/verify-ai-ledger-ui.cjs` checks it. `hooks/useClaude.ts` has one hook per read and per write.
- **✨ on the item screen** calls `runClaudeJob('item_fill', { text })`. A stopped run shows the function's own sentence for every reason (`off`, `budget`, `busy`, `not_configured`, `refused`, `cut_off`, `invalid`, `error`); only an answer with no sentence says "Couldn't fill the fields — try again in a moment".
- **Money** is USD: two decimals from a dollar up and for whole cents, four below a dollar, six in a call's detail. The budget counts a calendar month on Oslo's clock.
- **Safety.** A call's text is drawn as a text node in a `<pre>`, never as HTML or a link. The price source is a link only for an https address on one of Anthropic's own hosts (exact host match); source files link to GitHub only for a plain repo path. The calls' query is never kept on the device. The app can read the ledger and cannot write it; only the function does.
- **The page** is Developer → AI (`developer.md`). The harness plays the function in `scripts/harness/claude.cjs` (`scripts/harness/README.md`).

### Recipes and quick guess on Claude (phase 2a, 22.11.2026)

The recipe editor's and Food's quick-guess calls used to be `ai-proxy`'s `responseSchema` and `fetchUrl` modes (Gemini); both are gone from `ai-proxy`, with `callGeminiStructured`, its private-address code and `aiApi.ts`'s structured calls. They were rebuilt from scratch as five jobs of the `claude` function (all one-shot, app only, Haiku 5.5, low effort, no tools, no data, review-first: each only fills a form and nothing is saved or logged by it). The app side is `src/features/ai/claude/recipeJobs.ts` (the calls), `recipeAnswers.ts` (the recipe answers read again where they enter the browser; `verify-ai-ledger-ui`), and the screens' own existing checks (`readGuessEstimate`, `parseGuessOptions`) stay.

| Job | Where | In | Out (the shape the screen already used) |
|---|---|---|---|
| `recipe_from_text` | Recipe editor → Paste recipe → Paste text | the text, 10–6000 characters | `title`, `servings`, `instructions` (one step a line), `ingredients[{ name, quantity, unit, note }]`, `macro_estimate` (per serving, or null), `usedAi: true` |
| `recipe_from_link` | the same, From URL (also sets the recipe's source link) | an https link | the same; `usedAi: false` when the page's own data was read |
| `recipe_macros` | Recipe editor → Estimate | `servings`, up to 80 ingredients | `calories`, `protein_g`, `carbs_g`, `fat_g`, `sugar_g`, all five |
| `quick_guess` | Food → Quick guess → Describe it | up to 500 characters | `title` (≤ 40 asked, ≤ 60 held), `portion`, the five numbers, 1–4 `assumptions` |
| `quick_guess_options` | Settings → Food → Suggest options | a preset: name, portion, one portion's five values | `groups` (≤ 3) of `choices` (≤ 6): pick `one`/`any` add the five values, `size` has a `factor` |

- **AI last: `recipe_from_link`.** The function fetches the page with code (`page-fetch.ts`), then looks for a schema.org `Recipe` in the page's ld+json (`recipe-page.ts`); when there is a usable one (a title and an ingredient) code alone builds the recipe, quantities and units split from the ingredient lines, nutrition from `nutrition` (kilojoules are not calories). **No model is asked** — it is not an AI call: nothing is reserved, but a finished zero-cost ledger row is written (provider `page`, model `none`; Developer → AI → Calls shows it as "Read by code, no AI", and the link is kept in it only while the text log is on); the reply says `source: 'page'` and the app tells the owner "Read from the page, no AI used". Only a page with no usable Recipe sends its visible text (scripts, styles and comments out, 12,000 characters at most) to the model. Because it costs nothing, a spent budget does not stop a page the code can read; a switched-off job or a missing key does (the page is not fetched then). Because the row exists, the rate caps count each read; the caller is an owner-list account and each read is capped at 10 s and 2 MB.
- **AI last in the app (review fixes, 22.11.2026).** *Estimate* in the recipe editor first computes every ingredient that is linked to your library (or whose name is exactly one library food's name, case and spacing ignored; a name two foods share is left out) and has a weight or volume amount, from the library's per-100 g values (`macroEstimate.ts`); only the rest goes to `recipe_macros`, and when nothing is left the model is not asked. The toast says how much was computed and how much estimated. *Describe it* answers with no AI when the text is exactly one of your presets or the title of an earlier one-off diary line (30-day recents): the sheet says "From your preset — no AI used" or "From your earlier entry — no AI used". Not done: Kassalapp or Open Food Facts lookups for unlinked names (a later step).
- **Time limits and the answer reader.** A job's request limit follows its longest answer: 30 s up to 2000 tokens (✨), 50 s for a 4000-token recipe, at most 100 s. A model answer that is JSON followed by a note, a note and the object on one line, or a note and a code fence is read (the last top-level object that parses; an array is still refused). ✨ is handed the next 14 days (weekday and date) and next week's Monday, worked out by code in Europe/Oslo, instead of counting weekdays itself. (That 14-day list matches the old assistant's idea; it is kept because code works out the dates, which the model counts badly, not because the old prompt had it.)
- **The fetch is the SSRF wall** (docs/backend/edge-functions.md; `verify-ssrf-guard`): https only, no user name or port, private addresses in any spelling and names that resolve to one refused (`isPrivateHost` + `resolvesToPrivate`), every redirect re-checked (by hand, at most 4), 10 s, 2 MB, `text/html` only, fixed headers only. The address code is news-article's, line for line; the DNS question is handed in by `main.ts` (only it touches `Deno`).
- **Language: everything saved is English** (owner, 22.11.2026: "all the data that will be saved should be English; the assistant answers in the language of the question"). The first recipe prompt forced Turkish, the second kept the recipe's own language; now the model **translates** a recipe into English (title, ingredient names and notes, steps; a brand or a dish's own name stays): one sentence, `RECIPE_LANGUAGE_RULE` in `recipe-rules.ts`; change it there (and the jobs' version pins). The same rule holds for what the other jobs write that the app stores: ✨'s title and notes (a place stays as typed), the quick guess line's title, portion and assumptions and the options' names, the PT assessment, and the Kobo's saved answer. What is only shown follows the asker: the phone's question is answered in its own language, the phone's brief (no question) in English.
- **A recipe read from a page by code keeps the page's language.** There is no model call there (AI last), so nothing translates it: the result says `language: 'source'` (a model's recipe says `'english'`), and the app offers nothing new for it. An English rewrite of such a recipe would be an AI call; it is **not built**, listed for later.
- **No enforced answer shape** (`anthropic.md` trap 16): each job writes its JSON Schema into its instructions and our code checks every field (`answer-reader.ts`, `recipe-rules.ts`, `job-quick-guess.ts`): a wrong type, a number outside its range, a text over its limit or an unknown key is dropped, never repaired; a list over its limit keeps its first entries. A recipe with no title or no ingredient is invalid, so text that is not a recipe says so (the old prompt guessed a recipe anyway). `quick_guess` needs all five numbers (a missing one would show as a plain 0 on a line about to be logged). The reader finds the JSON object plain, in a code fence, or after a note on its own line (shared with ✨).
- **Limits.** A request is at most 16 KB, so a pasted recipe is at most 6000 characters (the app says so before sending).

### The PT assessment, the Kobo, the phone and the Test bench (phase 2b–2d, 22.11.2026)

Built from scratch on the `claude` function, like 2a; each old Gemini path is gone (`ptCoachApi.ts`'s `invokeAI` call and its Turkish `PT_SYSTEM_PROMPT`, `kobo-sync`'s `ASK_MODELS`/`GEMINI_API_KEY`, `phone-gateway`'s `FAST_MODEL`/`askAi` and the phone's secret path into `ai-proxy`). Five new jobs (four after 22.11.2026: `phone_brief` was removed, see below), all one-shot, Haiku 5.5, low effort, no tools, no enforced answer shape:

| Job | Callers | Where | In | Out | Time limit |
|---|---|---|---|---|---|
| `coach_assessment` | app | Training → Coach → Assess | feeling (one of four fixed English words: undertrained, normal, tired, very tired; the old Turkish ones are read as these), a note ≤ 300, the verdicts ≤ 1500, the snapshot ≤ 8000, the previous assessment ≤ 2000 | `{ text }`: four bold-headed English parts (Assessment, Recovery, The ONE priority for the next workout, Closing), ≤ 3000 characters | 40 s (2500 tokens) |
| `kobo_ask` | kobo | the Kobo's "Ask Lasci's AI" on a selected passage | `cleanAsk`'s fields: the kind, the selection ≤ 1500, context ≤ 600 each side, a question ≤ 500, title, author, language, percent, the answer language | `{ answer, answer_en }`: the answer in the language the reader chose, for the screen, and an English copy for the notes (empty for an English screen, where `answer` is saved), each ≤ 1200 characters, asked for ≤ 80 words (the Kobo's screen holds about that; the limit is twice the ask) | 20 s (the Kobo function waits 24 s) |
| `phone_ask` | phone | "AI'a Sor" and "Uyku Özeti" | `question` ≤ 1000, optional `context` ≤ 4000 | `{ text }` ≤ 1500 characters | 18 s |
| `test_bench` | app | Developer → AI → Test bench | `text` ≤ 2000 characters, optional `model`, `effort`, `thinking` | `{ text, thinking, served_model }` | 40 s (2000 tokens) |

- **AI last, 2b.** The PT assessment's decisions are code (`src/features/training/coach/coachFacts.ts`): the recovery gate (sleep under 6 h trims the session, under 5 h two nights running is a rest day, "very tired" with a night under the average trims it), the deload cue (a muscle at its ceiling, the program's workload review, two lifts down while very tired), the one lift (the first READY_TO_INCREASE, else the first watch flag, with the progress engine's own target), the muscles under their weekly minimum and the push-/quad-heavy flags. They go to the job as a `<verdicts>` block beside the snapshot (`formatPtSnapshot`, still the app's own pre-aggregated figures); the model explains them, reads the owner's own words (pain) and writes the note. That is why the effort is low, not medium. The saved `pt_assessments.model` is the model that answered (`CallSummary.served_model`; new on every run answer), shown as "Haiku 5.5" on the tab. The coach's language is one sentence (`COACH_LANGUAGE_RULE`): the owner reads Turkish there; the feeling words stay Turkish because they are stored.
- **AI last, 2c.** The phone's context (tasks, schedule, training; or the last nights' sleep from `computeSleepNightsGw`) is looked up by the gateway's code and handed over as data; the old `ask` could call database tools, the new one cannot until Ask AI is rebuilt (phase 4), and gets the day's context instead.
- **How a device reaches `claude`.** Only `claude` holds `ANTHROPIC_API_KEY`. `kobo-sync` and `phone-gateway`, after checking their own device secret in constant time, call `POST /functions/v1/claude` with `x-claude-server-key: <HMAC-SHA256(service key, "claude-device-v1") as hex>`, never the service key itself (security review, 22.11.2026: a header can reach a log or a gateway, and the credential opens only `claude`'s device path, not the database; the service key is read through their `<supabase-keys>` block, so the new `sb_secret_` key and the legacy JWT key both work, and `claude` derives the same value itself) and a body of exactly `{ action: 'run', caller: 'kobo' | 'phone', job, input }`. `claude` is `verify_jwt = false` (an `sb_secret_` key is not a JWT, so platform verification would refuse it; this follows the documentation and has **not been tried on the real platform**), and authenticates both callers in code before it reads the body. See `ai-plan.md` §5 (phase 2 rows) for what an attacker controlling each input can do. The account is never sent: `claude` acts as `HEVY_USER_ID` from its own environment. The ledger row says `caller` kobo or phone, so Developer → AI → Calls shows them; each device has 100 calls in 24 hours (counted from the ledger by `caller`) on top of the ledger's 20 a minute and 600 a day, the Kobo keeps its own 100 in `kobo-sync`, and the monthly and per-job budgets bind a device like the app. A device run has no sign-in token, so `ai_gate` (which asks who is signed in) cannot answer it: the early rate-cap read counts the owner's `ai_calls` rows with the service client (three count queries); the real wall is `ai_reserve`, which counts and holds the budget in SQL under a lock and, since migration 195, this caller's own 24 hours too (`p_caller_per_day`: 100 for a device), so a burst cannot overshoot the cap.
- **The phone's brief is no AI job (owner, 22.11.2026).** `phone-gateway`'s `brief` action builds its text with the same fixed rules as Home's daily brief — `src/features/home/briefRules.ts`, copied into the gateway between `// <brief-shared>` markers by `scripts/sync-brief-shared.mjs` (`verify-brief-shared` checks the copy is current, that `brief` never calls `askClaude`, and that copy and source write the same brief for the same inputs). It reads today's open tasks (overdue by `due_date`; closed today by `completed_at`), the schedule, the training and the food against the targets, each best-effort; the phone has no weather, rates or Watch source, so those sections are left out. The answer is `{ ok, text, source: 'rules' }`, with no model and no cost, and the `phone_brief` job, its tests, pin and Describe entry are gone. `ask` and `sleep` stay AI.
- **The phone's `ask`/`sleep` response** is the old `{ ok, text, model }` (model now the served Claude model) or `{ ok: false, error }`; the Kobo's `/ask` answers `{ ok, answer, model, saved }` or `{ error, message }` with the codes `rate_limited` (busy, over budget), `not_configured` (no key, switched off), `invalid`, `no_answer`, which the plugin already read.
- **`ai-proxy` no longer accepts the phone's secret** (its `viaPhone` branch and its copy of `sameSecret` are gone): a stolen phone secret reaches `phone-gateway`'s actions and the phone jobs, never the old assistant's tools.

**The Test bench** (Developer → AI → Learn → Test bench; `AiTestBench.tsx`, `benchJobs.ts`, `useBenchCount` / `useBenchRun`). A page of its own inside Learn, not a card in How it works: it is a thing the owner uses, with a form and its own results, unlike Diagnose, which only reads. The owner types a question (≤ 2000 characters), picks a model, an effort (both from `describe`'s lists) and thinking Adaptive or Off, and:
- **Count tokens** (free, `{ action: 'count', input }`): Anthropic's `count_tokens` on the request exactly as a run would build it (`buildRequest`), shown as the prompt's tokens, the input cost at the picked model's price and the answer's token ceiling. It writes nothing and reserves nothing; it is refused while the account is at a rate cap and for an account off the owner list.
- **Ask** (a real call): reserved, ledgered, in Calls as `test_bench`. Shows the answer, the model that answered, tokens (prompt, output, thinking, cache reads), cost, time and the thinking summary.
- **Compare thinking**: two real calls, Adaptive then Off, side by side, to read what thinking costs and how long it takes. `thinking: 'off'` is `{ type: 'disabled' }` in the provider (the SDK's `ThinkingConfigDisabled`; no `display`); with it Haiku 5.5 reports 0 thinking tokens and no summary. That it is accepted together with `effort` at low, medium and high on Haiku 5.5 is taken from the task brief and **not confirmed by a live call**: the Test bench is where to try it. ### The weekly report (phase 3, 22.11.2026, migration 196)

The owner's decisions (22.11.2026): it covers **Training, Health, Food and Tasks & time**; it is ready **Monday morning** (made at 05:00, announced at 07:00, Europe/Oslo); it shows as **a card on Home and a push notification** that opens it. It is the first **batch job** (Anthropic's Message Batches API: the answer comes within hours, usually one, at **half the price**).

- **AI last.** Code works out every number (`supabase/claude-src/week-facts.ts`, read by `week-data.ts` with the service client, every query naming the user id): the week is **Monday to Sunday in Europe/Oslo** (a session at 00:30 on a Monday is Monday's; the week of a clock change is 167 or 169 hours long); training sessions, working sets and volume against the average of the four weeks before, credited sets per muscle (primary 1, secondary 0.5, warm-ups out) and the top set of the three biggest lifts against the best before; sleep per night by the sleep contract (the day you woke up, sessions merged, manual wins; the fourth hand-mirrored copy, `verify-ai-sleep-merge`), steps and active energy by the Health tab's hour-level collapse, resting heart rate, weight (the newest reading of each day, from Hevy, the scale's report and Apple Health); food days, averages and days on target; tasks done (by `completed_at`), slipped (due this week, still open), older open ones, and the busy time scheduled per area. A section with no data says `NO DATA THIS WEEK` and the model skips it; one that could not be read says so. The model only says what the figures mean in four short sections and **Next week** (1–3 suggestions). It has no tools and writes nothing but this text.
- **Job `weekly_report`**: `mode: 'batch'`, callers `schedule` and `app` (the button needs the app), Haiku 5.5, medium effort, 3000 tokens, no enforced shape (its answer shape is in its instructions and `readWeeklyReport` holds it: length, **only the five known headings**, no link or markup, never repaired). A normal `run` of it is refused.
- **Flow.** `pg_cron` (migration 196) calls `claude` on Mondays at 03:00 and 04:00 UTC; only a run that lands from **05:00 to 07:00 Oslo time** acts (so Sunday is complete, winter or summer: the earlier winter run is "not the time", a second run in the window finds the report made), and one report per (user, week, maker) is ever made (a unique key). `report_make` reads the figures, **reserves the worst case at the batch price** (half of the live worst case) in `ai_reserve` (mode `batch`), inserts the report row (`queued`), submits one batch with one request and stores the batch id. The request's `custom_id` is **the ledger row's id** (unique per submission), so a report made again can never be answered by an earlier batch's line. A second timer runs every 15 minutes but calls only while a report is queued or a push is owed; `report_check` asks whether the batch ended and, when it did, reads the one result line **by `custom_id`** (exact match, any order), checks the text, writes the report (`ready`) and **corrects the ledger row to the real cost at the batch price**. The push is a separate step: the real report is then **owed a push** (`push_due`), and the first check from **07:00 to 22:00 Oslo time** sends it, once (a report that ends at 05:30 is saved at once and announced at 07:00).
- **Which report is the real one.** The timer's report (`made_by = 'schedule'`) is the real one: only it shows on Home and only it is pushed. **Make this week's report now** makes the last full week's real report again when it is missing or failed (the same row, a fresh batch, the push owed); when last week's report is ready it makes a **test copy** of last week on Monday and Tuesday and the **week so far** later in the week, as the button's own row (`made_by = 'app'`), labelled as a test in Batches, never replacing the real one and never pushed. A failed row has **Try again** (the same button's logic). Only the owner's phone is pushed to: `claude` gets a push sender only when the verified account is `HEVY_USER_ID`, so a second allowed account's report is saved and never announced there.
- **Every difference and duration is code** (owner-critic, 22.11.2026): the figures say "+3 286 steps a day, +55 %", "6 h 47 min", "-12 min", "-0.5 kg within the week", "against the target: -267 kcal, -12 %" (`week-facts.ts`: `grp`, `dur`, `sdur`, `sgn`, `pctChange`); the instructions tell the model to copy them and never add, subtract, convert or round.
- **Failures never loop and never lose money.** Batch errored / expired / cancelled / no result line / not ended after 26 hours / never registered: the report is `failed` with a plain sentence, its batch is deleted at Anthropic (cancelled first when it has not ended; one whose id could not be saved is cancelled at once, and a finished report that could not be saved fails rather than waiting for a batch that is gone), the ledger row **keeps the worst case** (outcome `error`, stop reason `batch_<kind>`: the safe side), and one short push says "This week's report could not be made" (a scheduled week the owner expects; the sentence is fixed text, never the model's). An answer that came back but fails the check, was refused or cut off is billed (the real cost at the batch price) and fails the same way. A scheduled week that failed is not tried again by the timer (the row stops the second run); the button can redo it. Switched off (all AI or the job), no key, over the budget wall, a rate cap, no data: nothing is queued, the week is recorded as failed with the reason, **no push** (the owner chose it or there is nothing to say). A submit that failed keeps the worst case only when the request may have reached Anthropic (a timeout, a network error, a 5xx), else it costs nothing.
- **Once.** A check **claims** the report (`claimed_at`; a claim older than ten minutes is taken over), and every claim and write of a check is **tied to the report it read** (`created_at`: a report made again gets a new one, so a stale check can never write into it, security review 22.11.2026). The push is **stamped before it is sent** (`pushed_at`), so two overlapping checks read one result and send one push; a push that reaches no phone is not repeated.
- **How the timer proves itself** (the schedule's own door, see `.claude/rules/ai.md`): the header `x-claude-schedule-key` carries `HMAC-SHA256(PUSH_CRON_SECRET, "claude-schedule-v1")` as hex, computed in SQL by pgcrypto from the Vault secret the other timers already use; `claude` derives the same value from its environment and compares with `sameSecret`. The schedule may only ask for `report_make` and `report_check` and acts as `HEVY_USER_ID`. Why not the service key: pg_cron cannot read it (it is not in Vault, and putting it there would hand the database the key to itself); a dedicated secret would mean an owner step in two places for no gain over the one the timers already share. A leaked header opens only these two actions (and `push-send` is not reachable with it).
- **The push** goes through `push-send` (`x-cron-secret` = `PUSH_CRON_SECRET`, an explicit `{ title, body, url }`): "Weekly report" / "Your report for 16.11.2026 – 22.11.2026 is ready." and the link `#/home?report=<id>`; a failed real report gets "This week's report could not be made." The words are built by code, never from the model. Tapping it opens Home with the report's popup.
- **App.** A Home card "Weekly report" (`WeeklyReportCard`): shown only for the **real (scheduled) report, in the week after its week (Monday to Sunday)**, with a short summary **built by code from the saved figures** ("3 sessions · 9 286 steps a day · 1 933 of 2 200 kcal · 3 tasks done", cut with `<Truncate>`); it opens `WeeklyReportSheet` (a `ModalShell`, lazy-loaded; plain text in headed sections, its cost at the batch price in the footer). The card is one PageBoard section (`report`, under the brief on every step), keeps the room it took last time (`KeepRoom`, nothing jumps), and a failed read leaves no card. **Developer → AI → Learn → Batches** (`AiBatches`): a one-line intro; each report with its week, its kind (Monday timer, made again by the button, Test copy, Test · week so far), status, its cost at the batch price (a waiting one is held; a failed one that holds the worst case says "held, likely $0": Anthropic bills nothing for a failed batch) and, opened, the report or the reason, **Try again** on a failed one, and **Figures sent** (the exact text the model read, saved with the report); **Make this week's report now** and **Check now**.

### Diagnose (22.11.2026)

**Why.** On 22.11.2026 every ✨ call waited exactly 30 s and got nothing back from Anthropic (no request id, 0 tokens), then the function gave up (`APIConnectionTimeoutError`); the Supabase log showed only a POST 200 after about 30 s. Two causes fit: the request never reached Anthropic (the network or the SDK between Supabase's edge runtime and `api.anthropic.com`), or Anthropic got it and was slow (most likely the one-time compile of ✨'s answer shape: 21 optional fields; Anthropic says a new schema is compiled once and then cached for 24 hours). Diagnose tells the two apart from production, with one tap.

**Where.** Developer → AI → Learn → How it works, the card under "The path of one request" (it follows the path, since it is for when the path misbehaves), titled "Check the connection to Anthropic" (`AiDiagnose.tsx`; the button says "Check the connection"). It is on How it works, not a view of its own, because it is a question about how the function works and it shares the page's "read only, nothing to set" nature; a sixth tab would be one card on a page of its own. While it runs the card says "Checking… this can take up to 2 minutes." The result is four rows (a tick or a cross, the time, the function's own sentence) under one verdict line worked out from them (`diagnoseVerdict` in `ledgerRules.ts`, checked by `verify-ai-ledger-ui`). The card stays when the description of the function can't be read, since Diagnose doesn't need it.

**The four checks** (`{ action: 'diagnose' }` → `{ ok: true, steps: [{ name, title, ok, ms, detail }] }`, `supabase/claude-src/diagnose.ts`):
1. *Network and key* — lists the models (free, 20 s). Says how long, how many models, and whether `claude-haiku-5-5` is in the list; or the error kind and HTTP status. **Only this check stops the others:** with no connection nothing after it tells us anything.
2. *Request shape* — counts the tokens of ✨'s real request (its instructions, answer shape and a made-up sentence; free, 20 s). A 400 here would show Anthropic refuses the answer shape.
3. *Tiny answer* — "Reply with the word OK.", no answer shape, effort low, 512 tokens at most (20 s), through the normal run path: reserved against the budget, sent, written to the ledger as the job `diagnose` (a real, tiny call; it shows in Calls and in How it works → Jobs).
4. *✨'s real request* — the `item_fill` job with the same made-up sentence through the normal run path (reserved, ledger row), with **90 s** instead of 30 s, so its true time shows.

The whole action stays under Supabase's 150 s limit: step 4 gets at most 90 s and at most what is left of 140 s; if less than 10 s is left it is skipped and says so. A step that throws is a failed step, never a crashed function. Each `detail` is one plain sentence with numbers, through `hideSecrets`, at most 400 characters; never the key, never a raw SDK object.

**Reading it.** Tiny answer fast and ✨ slow means the answer form is the slow part (run it again: the first call with a new form compiles it once). Step 1 failing means the server can't reach Anthropic or the key is refused. Both slow means Anthropic is slow overall.

**Rate cap: one a minute per account.** The function reads the ledger with the owner's own client: a `diagnose` row written in the last 60 s means "busy" (a plain sentence, nothing sent). Step 3's reservation writes that row even when the budget refuses it, so the ledger is the clock and no new table or column is needed. A read that fails answers an error and runs nothing (fail closed). Not counted: a Diagnose that stopped at step 1, which sends only the free list request. Two taps in the same instant can both pass the check; the database's own rate caps and budget wall in `ai_reserve` still bound them. The tiny job can also be started by a plain `run` from the app (it is tiny and capped like any job).

**Cost.** Steps 1 and 2 are free. Steps 3 and 4 cost a fraction of a cent (the ✨ call is about $0.0002 once the instructions are cached); each holds its worst-case cost against the budget first, like every call.

**Trade-off for this test.** The provider's time limit is a per-request option (`ModelRequest.timeoutMs`, default 30 s), not a second client; only Diagnose sets it. The message for a timeout names the limit that was used ("within 90 seconds").

**The chat step (22.11.2026, second Diagnose).** After the four checks the app asks for a fifth with `{ action: 'diagnose', part: 'chat' }`: the chat's real first request (its real eight tools and instructions, the date line and the made-up question "What is on my plan today?") sent once with a 120 s limit. It reports the time to the first stream event and the total, what the model did (asked for a tool, which is not run, or answered), the tokens and the cost. It is a call of its own because the four checks (up to 140 s) plus 120 s would pass Supabase's 150 s. It has the same one-a-minute pause as Diagnose. It is one real call: reserved, written to Calls as step 1 of the job `chat` (its request text says Diagnose), nothing stored in a chat. When it cannot run (budget, busy), the card shows a failed fifth step with the reason. It exists because `count_tokens` cannot show a slow first request (anthropic.md traps 16 and 29).

**The chat's deadline (22.11.2026).** The chat is not strict (anthropic.md trap 29) and has its own clocks: no stream event within 45 s, or a stream silent for 30 s once it has started (a long answer that keeps streaming is not cut), is stopped, and a whole answer ends by 110 s at the latest. A stopped round finishes its ledger row as an error with the worst case held, stores nothing of the round (the question and earlier rounds stay), and the app shows "No answer — Anthropic took too long. Try again." A call row still reserved after 150 s (older than the function can live; the live case of 22.11.2026 at 22:45) shows in Calls as "Stopped" (its detail says no answer, held at worst case) instead of "In flight"; the Outcome filter has "In flight" (young rows) and "Stopped" (old ones) apart (worked out from its age on the client; the stored row is not changed, and its worst case stays counted).

**The chat's sign-in.** The chat's stream is a manual `fetch` (supabase.functions.invoke cannot stream), so `chatApi.ts` reads the session right before each request (`getSession()` refreshes an expired token) and on a 401 refreshes once and sends once more (`sendWithSession` in `chatRules.ts`); only a second refusal shows the session message. Every other call to the function uses `supabase.functions.invoke`, which refreshes by itself.

## Ask AI on Claude (phase 4a, 22.11.2026)

Ask AI was rebuilt from scratch on the `claude` function (job `chat`, Claude Haiku 5.5). Nothing of the old Gemini assistant is carried over (no prompt, tool, loop or helper); the old `ai-proxy`, `AIPanel.tsx` and `aiApi.ts` were read only to learn what Ask AI does for the owner. The prompt is laid out tools → fixed instructions → (the owner's instructions, 4b) → the messages, with cache marks on the last tool, the instructions and the messages. The date line is its own block in the user message and is repeated only on a new Oslo day or after two hours. Context editing clears old tool results from 40 000 tokens. Cache diagnostics' miss reasons and the cleared amounts are stored with the answer (Developer → AI → Calls).
- **Streaming.** The app calls the function with `stream: true` and reads server-sent events: `start`, `text`, `step`, `detail` (a lookup's checked inputs), `retract`, `proposal`, `done` (with the cost, the run, the prompt size and the reasoning summary), `error` (only these; never a raw provider event, never the thinking text as a stream). A refusal or an error in the middle of the stream takes the streamed text back (`retract`) and stores nothing of that round. One try only (`maxRetries` 0).
- **Citations.** `find_text` results are `search_result` blocks; a citation is shown only if its source was returned by a tool in that chat and the row is one of the owner's (read again with the owner's token); the title is the row's own. They are kept with the answer, so a reopened chat shows them.
- **Developer → AI.** Calls groups the requests of one answer (steps under each other), the call detail shows the cache-miss reason and what context editing cleared, and How it works lists the chat job with its eight tools (from `describe`). The tools' shape (name, fields used, rows, bytes, time; for the database tool a fingerprint) is in each ledger row's `tools`, for the "using AI for less" suggestions (ai-plan §8, step A).
- **Deleting a chat, and how long chats are kept.** The history's trash button asks (`confirmDelete`), the function sets `deleted_at` (a *soft* delete: nothing is removed, the chat leaves the list and cannot be continued) and the toast says "Chat deleted · Undo"; Undo (`chat_restore`) clears it. I chose a soft delete because a chat is append-only and hash-chained: a hard delete could not be undone. `ai_chats_purge()` (daily timer `lascis-ai-chat-purge`) removes for good the chats deleted more than 7 days ago **and every chat whose last message is older than the AI log's retention** (`ai_settings.log_days`, 30 by default, 1 to 90): a conversation's text cannot be trimmed (it is replayed unchanged), so retention removes whole chats, with their messages and proposals (the append-only guard lets that cascade pass). So a chat lives at most as long as the owner keeps the AI text log.

## AI (ai-proxy) Detail

Gemini via the `ai-proxy` edge function. Call modes: the conversational **tool-calling loop** (default) and **`{ itemFill: { text } }`** (11.11.2026, the item screen's ✨ — `docs/features/planning-calendar.md` → The item screen): a narrow action that reads nothing else of the body. The sentence (checked first: 1–500 characters, one line, no control or direction characters — `itemFillTextProblem`, else 400) goes to the model with today's date in Oslo, the next 14 days by weekday and the time zone, in the user turn as a JSON string the prompt calls data, never instructions; the prompt (`ITEM_FILL_PROMPT`) and the schema stay fixed, so they cache. One single-shot call (`gemini-3.1-flash-lite` first, the answer capped at 2,048 tokens; this branch has since moved to the `claude` function, `item_fill`, and this text is history), **no tools and no data**; nothing is read from or written to the database. The answer goes through `cleanItemFill` — `src/features/items/itemFill.ts`, GENERATED into the function between `// <item-fill-shared>` markers by `scripts/sync-item-fill-shared.mjs` — which keeps only the item screen's own fields, each checked (allow-lists, real days and times in range, capped text with no control, direction or invisible characters — the astral ones too, by a `u`-flag class) and drops any other key. The model is never asked for a link or the area: the link is the one https:// address written in the sentence (`linkOfSentence`; the model's `url` is never read — a piece of a link, `https://den` from "Dentist", `https://router` or `localhost` can't come back), and the area picks the item's Apple calendar, so it is never guessed (guardian, 11.11.2026); an answer that isn't JSON fills nothing. The browser runs the same check again. The phone's secret can't call it ("Fill in the app."); a stolen session could only spend the AI quota, as with chat (`scripts/verify-item-fill.cjs`).

**Generic DB tool layer** over a curated `DB_CATALOG` allow-list: `describe_database`, `db_query`, `db_insert`, `db_update`, `db_delete`, **`db_aggregate`**. - **`db_aggregate`** — `sum|avg|min|max|count` + `group_by`; enum'd ops only (never expressions), the same filter grammar as `db_query`, group columns validated against the catalog, hard cap ≤366 groups, rows reduced server-side so only the summary reaches the model. - **`semantic_search`** (migration `065`: pgvector + `ai_embeddings` `vector(768)` hnsw cosine + the `ai_semantic_search()` SECURITY-INVOKER RPC) — `gemini-embedding-001` @768, **cosine index → no manual normalize**, vector `limit ≤ 8`, `user_id` filtered inside the vector query; returns `{source_table, source_id, snippet, score}` and the model then `db_query`s the live row by id. **Embeddings locate, live SQL answers — never use a similarity hit as the factual value of anything current-state.** Editing or deleting a searched row drops its copy (migration 140's trigger), and every `semantic_search` first embeds up to 32 rows that have no copy, so edits come back by themselves; Developer → "Reindex AI search" still re-embeds everything. (2) **It now returns SLEEP too** — `computeSleepNights` (absolute-time overlap-merge keep-longest, Oslo wake-day attribution, per-night hours + deep/core/rem/awake, last night + period average). That closed the "no sleep data" answers in the phone `sleep` action and the Coach. The prompt tells the AI to *analyze* health data (trends, comparisons, honest criticism), not recite numbers.
- **Latency design for `plan_trip` (was a real 3–4 min pain point).** It is a ONE-SHOT call: the prompt and tool description tell the model to call it directly with the user's own words (`from:"ev", to:"iş"`) and NOT to look things up first — earlier "investigate first" wording caused ~5 sequential Gemini turns (each a full round-trip) vs ~2 now. `plan_trip` resolves both endpoints itself against saved stops/routes loaded ONCE (not re-queried per endpoint), in parallel: empty → default saved stop; an exact `NSR:StopPlace:` id → used as-is (name backfilled from the trip legs, no extra lookup); "home"/"ev"/"work"/"iş" (+variants) → saved-label fuzzy match; else → geocoder top match. When a side won't resolve it returns `{success:false, needs_clarification:true, candidates:[…]}` so the model asks ONE `ask_clarifying_question` instead of firing more search turns. **Only a regex-validated `NSR:StopPlace:` id or finite coords are ever interpolated into GraphQL** (injection safety). Anti-hallucination is structural (report only what the tool returns; call once and report), not extra verification turns. New Entur GraphQL fields are deliberately NOT added speculatively — verify live first.
- **Model chain + retries.** Gemini returns transient "model overloaded" 5xx that clear within seconds, distinct from a 429 (real quota — surfaces immediately via `throwRateLimit`). Overload waves hit different models' capacity pools unevenly, so retrying a DIFFERENT model beats retrying the same one. `fetchGeminiWithFallback` tries `MODEL_CHAIN` = `gemini-3.5-flash` → `gemini-3.1-flash-lite` → `gemini-2.5-flash` → `gemini-2.5-flash-lite` with jittered exponential backoff, position-weighted attempts (`RETRIES_BY_POSITION` [4,3,2,2]) so better models are tried hard before falling to lite tiers. Each attempt has 20 s (`GEMINI_ATTEMPT_TIMEOUT_MS`, `AbortSignal.timeout`): a timed-out attempt moves on to the next model, and when the last one times out the answer is a 500 "Gemini timed out: …" (through `hideSecrets`); any other network error still ends the chain. The limit was promised on 22.07.2026 but only wired on 07.11.2026 — until then a hung connection held the request until the platform ended it (`verify-secret-errors`). The same day every other outside **read** got one (`fetchWithin`, the answer included): Gemini embeddings 20 s, the model list 10 s, Google's token 10 s and each Calendar page 15 s, Entur 10 s (a trip 15 s); a read that runs out fails as "<service> did not answer within N s". The two Hevy routine **writes** (`hevyRoutineWrite`) wait up to 60 s; with no answer, or a hevy-api failure that can come after Hevy took the write (a 5xx that is not Hevy's own 4xx), the result is `outcome_unknown` and tells the model not to send it again and to have the user check Hevy — a plain failure invited a retry and a second routine Undo can't remove (guardian, 07.11.2026). A tool that throws is one failed step the model is told about (`{ success: false, error }`, through `hideSecrets`, logged), never the end of the reply; a network error names the service, never the URL (which held the search's words). A confirmed action's error is scrubbed the same way before its text and step reach the browser. A confirmed routine change with no answer reads "Hevy didn't confirm the change. It may have gone through: check the routine in Hevy before trying again." (its step: "? update_hevy_routine — not confirmed"), never the model's own instruction. **Every model id must be live-verified before entering this list** (real bug: two guessed ids 404'd in production; a 404 also used to abort the whole chain — it now skips to the next model). Probe with ai-proxy's `{listModels:true}` debug branch, which returns the key's REAL available models. The client can pass a `model` — it becomes the chain's **preferred starting point**, not an exclusive choice (`AIPanel`'s header picker, localStorage `lasci-ai-model`, "Auto" by default); `AIResponse.model` reports which model actually answered.
- **`thinking_config` per-model body (real bug, round 3):** `thinking_config`/`thinking_level` is a `generationConfig` field that is **Gemini-3.x-only** — explicitly picking `gemini-2.5-flash` 400'd with "Thinking level is not supported for this model" the moment a real user tried it, because ONE fixed request body was built once and reused across every model in the chain. `fetchGeminiWithFallback`'s `body` param became **`buildBody: (model) => AnyRecord`** — the body is constructed PER MODEL inside the retry loop, and `supportsThinking(model)` (`model.startsWith('gemini-3')`) gates whether `thinking_config` is included. Applies to all three call sites (the tool loop, the turn-limit summary, `callGeminiStructured`). `thinking_level: MINIMAL` in the loop — thinking tokens are not the cost leak.
- **Prompt-caching contract (don't regress it).** Live context used to be baked into `systemInstruction`, which made Gemini's implicit prefix cache (~90% off a repeated byte-identical prefix) structurally unable to hit — a ~7,270-token fixed block (system + serialized TOOLS) was billed at full price on every turn of every tool loop. Now: **`SYSTEM_PROMPT` and the per-surface tool declarations must stay byte-identical per call** — never interpolate a date, timestamp or any volatile value into them (instant cache-buster; the current date belongs in the context turn), and serialize tools deterministically. Live context rides as `contents[0]` (`prependContext` in `aiApi.ts`). `buildContext` is skipped for clearly transit-only questions (a conservative client-side `TRANSIT_RE` gate). **`ai_usage_log.cached_tokens`** (← `usageMetadata.cachedContentTokenCount`) is the proof metric and the documented trigger for escalating to explicit `cachedContent`. `ai_query_log` records every `db_query` + live SQL with the exact statement — the substrate for later promoting hot queries into the UI.
- **Tool sets + model routing.** No chat surface is sliced: **general and coach get the FULL tool set** so the assistant is never weakened, and **the `phone` surface gets NO tools at all** (its brief context is pre-built server-side by `phone-gateway`, so a single-shot answer is the biggest latency win). The Shop page's own chat (the old sliced `shop` surface) is retired (07.10.2026); a client still sending `surface: 'shop'` gets the general behaviour. `SURFACE_MODEL` changes only the **starting** model and holds only `phone: 'gemini-3.1-flash-lite'` (skips the frequently 503-overloaded 3.5-flash primary, which burned ~7–13s of retry budget before falling through — fatal against the ~25s iOS Shortcuts cutoff); the lookup reads only its own keys. A 503 still falls through the whole chain.
- **Voice chat (`useVoiceChat.ts` + AIPanel):** browser-native Web Speech API — `SpeechRecognition` (prefixed `webkitSpeechRecognition` everywhere that has it) for speech→text and `speechSynthesis` for text→speech. **No key, no edge function, no cost** — nothing server-side changed. Two levels: the mic button dictates into the box (edit before sending), and the header **Voice** toggle is hands-free mode — utterance auto-sends, the reply is spoken, and the mic reopens when it finishes (`speak(text, onDone)` → `startListening()`), so it's a real back-and-forth loop. TR/EN language chip (`lasci-ai-voice-lang`) drives BOTH recognition and the picked voice. Load-bearing details: `speakableText()` strips `**bold**`/emoji so the voice doesn't read markup; `startListening` cancels any speech first (otherwise it transcribes its own voice); **`primeAudio()` must run inside the enabling tap** — iOS refuses synthesis that no user gesture unlocked, and the reply is spoken much later; the panel's close paths reset voice mode and `voiceModeRef` is `voiceMode && isAIOpen` so the loop can't continue behind a closed panel; a silent utterance ends the loop rather than reopening a hot mic. Everything is feature-detected — the controls simply don't render where the API is missing. **Recognition is unreliable inside an iOS home-screen PWA** (a long-standing WebKit gap); on the phone the `AI'a Sor` Shortcut is the voice path (Siri dictation → gateway → Speak Text), so this mainly serves desktop.
- **Vision:** `Message.images` end-to-end via a shared `messagesToContents()` that attaches base64 photos as Gemini `inline_data` parts (chat). `AIPanel` supports the attach-photo button (≤3, thumbnails, image-only send) **and pasted images** (Cmd/Ctrl+V on desktop, paste on mobile — `onPaste`); `fileToCompactDataUrl` downscales before upload.
- **Retry and refresh (28.10.2026):** Retry after a failed turn sends the question once, with its photos, and leaves the box alone (before, the question went out and was stored twice and its photos were dropped). After every turn the `aiWrite` group refreshes a screen key for every table the assistant can write — Books' library and settings, training skips, sleep confirmations, Health's goal diary, Home's recently watched and the saved transit stops/routes were missing; `verify-ai-confirm` maps each `rw` table to a key and fails on a new one until it is mapped.
- **MCP was evaluated and deliberately not pursued:** GitHub Pages is a static host and cannot run a persistent process, so any MCP layer would need a separate always-on server. The generic `DB_CATALOG` + `db_query/insert/update/delete/aggregate` layer shipped instead, and the "AI proposes, user confirms" invariant lives in the system prompt.
- **Removed / never built:** dead `log_workout`/`get_workouts` (hit the dropped `training_sessions` table — training is Hevy/Strava, read via `db_query`; planned sessions = `time_blocks` `category='training'`). The **Weekly Review** Home card added during the AI phases work was **removed on request** — `weeklyReviewApi`/`useWeeklyReview`/`WeeklyReview` no longer exist in `src/`, and `ai_reviews` (migration 065) is an unused empty table left in place.
