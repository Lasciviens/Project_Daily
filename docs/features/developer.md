# Developer page

> Moved out of CLAUDE.md on 13.10.2026.

## Overview

Standalone `/developer` (sidebar footer, More sheet, Settings ⚙), pill tabs synced to `?tab=`. Tabs: **Connections** (see Connections below), **Memory** (see AI), **Activity** (CRUD audit trail — `audit_logs`, written by DB triggers, migration `037`; filters by table/op/actor/days, 30-day retention swept probabilistically inside the trigger) and **Errors** (`app_error_logs`), plus a "Reindex AI search" button. Activity, Errors and Memory are list + detail (`developerBoards.ts` → `LIST_DETAIL_BOARD`): phones and tablets open a row in place (Memory: its edit sheet); from the laptop toolbar + list sit in main and the picked row opens in a sticky pane beside them (two tracks from 1920; it stops at three). `paneSelection` keeps the picked row, else the first listed row; Activity shows no pane for an empty list; Memory asks before discarding an unsaved pane edit. The pane is `ActivityLogDetail` (the diff), `ErrorLogRows`' `ErrorDetail` (message + context with copy buttons) or `MemoryDetail` (an inline editor sharing `MemoryFields` with the sheet); the picked row is `bg-accent-50` + `aria-current`. The header stops over the tab's board. Audit triggers cover user-authored tables only — bulk-synced tables (hevy_*/health_*/strava) are deliberately excluded to avoid sync-spam; `actor` distinguishes 'web' (browser session) from 'service' (AI/webhooks, service-role writes). Activity is a **timeline** (`ActivityLogRows.tsx`, tones for created/updated/deleted): a plain-language sentence per change, same-transaction cascades grouped, a readable diff on expand. Both log tabs read through `developer/hooks/useLogs.ts` and confirm "Clear all" first. A group of changes is labelled "Same save · N changes" (one database transaction, `tx_id`); stored timestamps and dates in the diff read `DD.MM.YYYY HH:MM`. The exact window's ends are a `DateInput` and, once a day is set, a 24-hour time chip (the supplements' `TimeChip` — the Add sheet's `Time24Field`); a day alone runs from 00:00 / to 23:59 (28.10.2026 — before, native `datetime-local` fields showed the browser's own date format).

## Undo this save (migrations 150, 151)

Owner, 14.10.2026: a save changed 73 TV episodes and had to be taken back by hand with SQL from this log — "it should be safe to do… it should not miss anything while undoing it." 151 (same day, after two reviews) makes the preview show everything the undo sets off, not only the rows it writes.

- **Where:** "Undo this save" on a group's header, under a lone change's diff (phones) and in the detail pane (laptop). It always undoes the whole save (the transaction), whatever the filters show. It opens the `undo-save` entity popup (`openUndoSave(txId)` → the shell's `ModalHost`), so it works from any screen — the result toast's Undo too, after you've left Activity.
- **Preview first** (`UndoSaveSheet` in `ModalShell`, adapter `modals/UndoSaveEntityModal.tsx`): the database's own plan, in plain words (`undoPlanText.ts`, `verify-undo-plan-text`). Top to bottom:
  - for a save of media rows, a one-line, tappable **hint** when other saves by the same actor sit within 10 seconds on the same media tables (undos left out): "2 more saves seconds later (one Spread?) — if they belong together, undo them too, newest first · Open the newest" — the tap opens that save's own preview above this one;
  - **Changed again later** ("TV episode «S01E03» — changed again later at 10:45 (watched date) · Undo would overwrite it", with the value now and the one Undo puts back);
  - **Not exactly as before** — a database rule changes a step's row right after Undo: a column put back, or a column outside the step (143: putting `done` back clears `is_focused` — "Task «Ship it» — a database rule changes is focused right after Undo"), or a row put back has a column a rule rewrote;
  - **Outside the app** — one danger line per service: the outbox rows the trial run queued plus the Google Calendar events the browser makes or moves right after ("Trakt: 3 plays removed and 3 added at the restored dates", "Google Tasks: 2 tasks changed", "Google Calendar: 1 event removed · 1 event added · 2 events changed"); a whole-item Trakt remove says "every play of 1 item («Undo movie») is removed there — this can't be undone on Trakt". Outside links Undo leaves as they are ("Google Calendar: 1 schedule block keeps its current event link — Undo doesn't put the old one back"). For a save made by AI / a sync, a service that gets nothing from the undo: "This save came from AI / sync. Trakt still has it — the next sync may bring it back" (left out when the outbox lines already name that service);
  - **Can't be undone** — blocked changes (no account, table gone, no key, no access, unreadable, **order unknown**) and tables outside the log ("Task tags of a deleted task aren't in the log — if it had any, they can't come back"; SET NULL children "…stay unlinked");
  - **What Undo changes** ("73 TV episodes: watched date put back"), **Also affected** (rows Undo's deletes take with them that the save didn't make, and rows a database rule changes besides: "Also deleted by a database rule: 1 schedule block («Watch S01E05»)");
  - quiet notes: edits of other fields kept (only columns the undo doesn't change itself), generated/dropped columns.
  Undo / Cancel; the button says **Undo anyway** (danger, `text-on-danger`) when anything is listed to confirm, and is off when there is nothing to do or the trial run failed. Result: "Save undone · 73 changes put back · Undo" — its Undo opens the same preview for the undo's own save (`result.undo_tx`), so the way back is checked the same way.
- **Database** — `app_undo_transaction(tx_id, apply, confirm, overrides)` (SECURITY INVOKER: row level security and the owner lock apply):
  - Folds each row's changes in the order they happened (`audit_logs.seq`, added by 150 — `created_at` is the same for a whole transaction): its state before the save and after it. UPDATE → the changed columns get their old values (only those); INSERT → the row is deleted through `app_delete_rows` (144), runs of one table in one call; DELETE → the full old row goes back with the same id (the overrides reset Google ids, as the delete flow's Undo does). A row's key is `id`, or `user_id` for a one-row-per-account settings table (`games_prefs`, `screenscraper_prefs`, `reading_settings`, `kobo_device_config`, `athlete_profile`, `day_targets` — their audit rows carry no row id, so the account is the key).
  - **Order unknown (151):** rows logged before 150 got `seq` in storage order, which may not be the real one. A row changed more than once in a save must chain up **column by column** — each change's old value of a column equals the previous change of that column's new value (bookkeeping aside); an INSERT only after a DELETE, nothing after a DELETE but an INSERT — or the row is blocked as `order_unknown` and left alone; it is never folded in a guessed order nor counted as unchanged. (Title a→b, status open→done, title b→c stored backwards shares no column between neighbours: only the per-column check sees it.)
  - **Bookkeeping** (`app_undo_bookkeeping`): clocks and the state of the outside copy — `updated_at`, `synced_at`, `google_local_edit_at` (071), a task's `google_etag` / `google_position` / `google_updated_at` / `google_web_view_link` / `google_links` / `google_hidden` / `google_deleted`, a plan's `google_calendar_horizon`, a title's `trakt_note_text`, a watch's `trakt_history_id` / `source` (149: a watch the undo re-dates loses its Trakt play id by design) — are never put back and never compared.
  - **Outside links** (`app_undo_links`): a task's `google_task_id`, `google_tasklist_id` and `google_calendar_event_id`, a slot's or plan's `google_calendar_event_id`, a title's or episode's `trakt_note_id`. **Never put back** — chosen over putting them back with a warning, because the link must name what exists on that service now: an old event or task id names one deleted or replaced there, and an old list may be gone. When the save changed one and it isn't back as before, the plan says so (`links_kept`, per table and column) and needs confirming; a save that changed only a link is never "already as before".
  - Compares each row now with what the save left: changed since → a **conflict** (with the later saves' times and columns from the log, bookkeeping aside); already as before → nothing to do; a later edit of other columns → **kept** — unless the undo itself changes that column (then it is drift). Changes it can't see or address are **blocked**: written for no account (`app_undo_hidden_changes` counts them), a table gone, without a usable key, one the caller may not read, or in an unknown order. Columns a value can't go back into (generated, identity, dropped since) are named. Tables outside the log a put-back row's foreign keys reach are named (`not_logged`) — only for rows put back they could point at (a non-null referenced value), with how many and whether such rows were deleted with it or only unlinked; a SET NULL table only while it holds a row with an empty link (the link the delete emptied is still empty — none means nothing pointed at the row). A CASCADE table can't be checked: its rows are gone, so it is named whenever the key could match.
  - **The trial run** (`apply = false`) runs the whole undo and rolls it back. At the end of the steps it fires the deferred triggers (`SET CONSTRAINTS ALL IMMEDIATE` — 149's watch reconcile), then reads back: what deletes took with them (`collateral`); every step row again (`drift`: a column put back changed again; a column outside the step that changed on that row while the undo ran — from the undo's own audit rows, before vs after, bookkeeping and generated columns aside; a row put back with any column rewritten — override keys, generated/always-identity columns, the key, bookkeeping and links aside; a deleted row still there; a put-back row gone again); the undo's **own audit rows** for rows outside its steps (`side_effects`: a rule between tables, e.g. 043 deleting a watched episode's plan; `side_hidden` counts those the caller's log doesn't show); and the **outbox rows** it queued (`outbox`, per service and kind: `trakt_outbox`, `google_tasks_outbox`, `calendar_outbox`, via the count-only SECURITY DEFINER `app_undo_outbox`; Trakt's are read after a mark taken before the steps, so a whole-item `history_remove` names only what the undo queued). To `outbox` it adds the browser's Google Calendar writes, worked out from the steps: `create` for a slot or plan put back that had an event, `update` for a slot whose day, time, length or title goes back (a plan: any change) while it has one. Whether it can run at all is `error` (e.g. a parent deleted since). It changes nothing and leaves no log rows. Collateral and side effects sort by their text, so a preview and its apply give the same fingerprint.
  - `sync_save`: a save made by AI / a sync (actor `service`) whose undo touches a synced table (`app_undo_synced`, kept in step with `SYNCED` in `undoPlanText.ts` — the verify script compares them). It needs confirming; the sheet names only services the undo sends nothing to (they still have the save's change). 149 doesn't audit the Trakt pull's writes to `media_watches`, so this concerns episodes, movies, shows and Google tasks.
  - `apply = true` first locks the save's rows (`FOR UPDATE`) and then reads them, so a save committing at that moment is either seen (and the fingerprint refuses) or waits for the undo — at most `lock_timeout` (4 s, set by the function for preview and apply), then `55P03` "Another save is writing these rows — try again in a moment". It runs the same steps in ONE transaction (all or nothing) and must pass the plan's `confirm` fingerprint when it listed anything to confirm — conflicts, blocked, `not_logged`, collateral, drift, side effects, outside writes, links kept or a sync's save (`UD001` otherwise); a fingerprint that no longer matches — anything changed since the preview — is refused (`UD002`), and the sheet reads the plan again. The browser always passes it. An applied undo is noted in `audit_undos` (its transaction and the save it took back; 30 days), so the hint leaves undos out; `nearby` is outside the fingerprint.
  - **Undoing the same save twice is a no-op** (every row already as before: no steps, applying changes nothing). The undo is itself audited, so it can be undone too.
  - After the undo the browser does what the delete flow's Undo does (`useUndoSave` → `followUndo`): slots and plans it deleted leave Google Calendar, those it put back get an event again, slots whose time or title went back move their event (all listed in the preview), Google Tasks delivers at once, and an undo that touched movies, shows or watches starts a Trakt sync (`scheduleTraktSync`); a step that fails is a warning, the undo stands.
  - Fast enough for big saves: rows of one table with the same action go in one statement, and JIT is off inside the functions (the planner takes jsonb set functions for a million rows) — 73 rows ≈ 40 ms, 2,000 ≈ 0.7 s on the test database. Only the request's own time limit gives "This save is too big to undo here" (`57014`); an apply's other known errors read like the preview's ("Undo can't run: another row has taken its place since"), from one table (`undoErrorText.ts`).
  - Only audited tables can be undone — bulk-synced data (`hevy_*`, `health_*`, `strava_*`) is not in the log. Repeating plans (`schedule_blocks`) have no audit trigger either, so their edits can't be undone here (their one-off slots, `time_blocks`, can).
  - Scenarios: `verify-db-undo-save` (PR check), two databases. The undo-save base: the 73-episode update, a second undo (no-op), the undo of the undo, a mixed insert + update + delete, a cascade delete, a conflict refused then confirmed, a stale confirm, collateral, generated/dropped columns, blocked changes (hidden, no key, no access), a parent deleted since, order inside a save, a batch of 30, row level security, a rule that fights back (drift), another account; and (151) Google Tasks updates counted, a slot put back with its event (Calendar `create`), 043 deleting a later plan with its Calendar event (side effect + outbox), a row put back that a rule rewrites, a settings row keyed by user_id (update, delete, insert), changes in an unknown order (per row and the per-column probe, with the same changes in their real order folded), 143 clearing focus on a row the undo writes (drift, not kept), an outside link left as it is (also when it is all the save changed), a sync's save, `not_logged` only for a non-null key and an emptied SET NULL link, media saves seconds apart (a wish save and an undo left out), and two races with dblink (a save committing while the undo waits: `UD002`; a save holding the row: `55P03` for preview and apply). The 149 base (`undo-save/watches.sql`): a pre-149 re-date undone after 149 — the deferred reconcile's watch moves and Trakt plays are in the preview and the cache columns end right — a re-dated watch undone with no drift, a first watch's undo as one play, a preview's `SET CONSTRAINTS` not leaking into the rest of the transaction, and a whole-item Trakt remove naming only the undo's own item.
- **Client:** `api/undoSaveApi.ts` (types, `fetchUndoPlan`, `applyUndo`, plain messages for `UD001`–`UD003`, `55P03` and `57014`, the preview's words for other known codes), `hooks/useUndoSave.ts` (`openUndoSave`; `useUndoPlan(txId)` — `qk.logs.undoPlan`, read fresh each time; `useUndoSave({ onApplied })` — `useMutationWithFeedback`, says the result itself (the Undo toast); on success the sheet closes and its plan leaves the cache before `saveUndone` refreshes every query, so no second trial run and no "Nothing to undo" flash).
- The other Undo — the toast after a delete (`docs/features/delete-undo.md`) — puts back one delete right away; this one takes back any save from the last 30 days.
