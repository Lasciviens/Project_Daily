# Developer page

> Moved out of CLAUDE.md on 13.10.2026.

## Overview

Standalone `/developer` (sidebar footer, More sheet, Settings ⚙), pill tabs synced to `?tab=`. Tabs: **Connections** (see Connections below), **Memory** (see AI), **Activity** (CRUD audit trail — `audit_logs`, written by DB triggers, migration `037`; filters by table/op/actor/days, 30-day retention swept probabilistically inside the trigger) and **Errors** (`app_error_logs`), plus a "Reindex AI search" button. Activity, Errors and Memory are list + detail (`developerBoards.ts` → `LIST_DETAIL_BOARD`): phones and tablets open a row in place (Memory: its edit sheet); from the laptop toolbar + list sit in main and the picked row opens in a sticky pane beside them (two tracks from 1920; it stops at three). `paneSelection` keeps the picked row, else the first listed row; Activity shows no pane for an empty list; Memory asks before discarding an unsaved pane edit. The pane is `ActivityLogDetail` (the diff), `ErrorLogRows`' `ErrorDetail` (message + context with copy buttons) or `MemoryDetail` (an inline editor sharing `MemoryFields` with the sheet); the picked row is `bg-accent-50` + `aria-current`. The header stops over the tab's board. Audit triggers cover user-authored tables only — bulk-synced tables (hevy_*/health_*/strava) are deliberately excluded to avoid sync-spam; `actor` distinguishes 'web' (browser session) from 'service' (AI/webhooks, service-role writes). Activity is a **timeline** (`ActivityLogRows.tsx`, tones for created/updated/deleted): a plain-language sentence per change, same-transaction cascades grouped, a readable diff on expand. Both log tabs read through `developer/hooks/useLogs.ts` and confirm "Clear all" first. A group of changes is labelled "Same save · N changes" (one database transaction, `tx_id`); stored timestamps and dates in the diff read `DD.MM.YYYY HH:MM`.

## Undo this save (migration 150)

Owner, 14.10.2026: a save changed 73 TV episodes and had to be taken back by hand with SQL from this log — "it should be safe to do… it should not miss anything while undoing it."

- **Where:** "Undo this save" on a group's header, under a lone change's diff (phones) and in the detail pane (laptop). It always undoes the whole save (the transaction), whatever the filters show.
- **Preview first** (`UndoSaveSheet`, a `ModalShell` sheet): the database's own plan, in plain words (`undoPlanText.ts`, `verify-undo-plan-text`): **Changed again later** first ("TV episode «S01E03» — changed again later at 10:45 (watched date) · Undo would overwrite it", with the value now and the one Undo puts back), **Not exactly as before** (a database rule changes a row again right after Undo), then **Can't be undone**, **What Undo changes** ("73 TV episodes: watched date put back"), **Also affected** (rows Undo's deletes take with them that the save didn't make), then notes (edits of other fields kept, generated/dropped columns, which services get the reverse change). Undo / Cancel; the button says **Undo anyway** (danger) when anything is listed to confirm, and is off when there is nothing to do or the trial run failed. Result: "Save undone · 73 changes put back · Undo" — its Undo opens the same preview for the undo's own save (`result.undo_tx`), so the way back is checked the same way.
- **Database** — `app_undo_transaction(tx_id, apply, confirm, overrides)` (SECURITY INVOKER: row level security and the owner lock apply):
  - Folds each row's changes in the order they happened (`audit_logs.seq`, added by 150 — `created_at` is the same for a whole transaction): its state before the save and after it. UPDATE → the changed columns get their old values (only those); INSERT → the row is deleted through `app_delete_rows` (144), runs of one table in one call; DELETE → the full old row goes back with the same id (the overrides reset Google ids, as the delete flow's Undo does).
  - Compares each row now with what the save left: changed since → a **conflict** (with the later saves' times and columns from the log); already as before → nothing to do; a later edit of other columns → **kept**. Changes it can't see or address are **blocked**: written for no account (`app_undo_hidden_changes` counts them), a table gone, without a single `id` key, or one the caller may not read. Columns a value can't go back into (generated, identity, dropped since) are named; tables outside the log a put-back row's foreign keys reach are named (`not_logged`).
  - `apply = false` runs the whole undo and rolls it back: the plan says what deletes take with them (`collateral`), whether it can run at all (`error`, e.g. a parent deleted since), and — after reading every touched row again — which rows a trigger changed again (`drift`), so it never claims "as before" for a row that isn't. It changes nothing and leaves no log rows.
  - Fast enough for big saves: rows of one table with the same action go in one statement, and JIT is off inside the functions (the planner takes jsonb set functions for a million rows) — 73 rows ≈ 40 ms, 2,000 ≈ 0.5 s on the test database.
  - `apply = true` runs the same steps in ONE transaction (all or nothing) and must pass the plan's `confirm` fingerprint when it listed conflicts, blocked changes, collateral or drift (`UD001` otherwise); a fingerprint that no longer matches — anything changed since the preview — is refused (`UD002`), and the sheet reads the plan again. The browser always passes it.
  - **Undoing the same save twice is a no-op** (every row already as before: no steps, applying changes nothing). The undo is itself audited, so it can be undone too.
  - Everything goes through the tables' normal triggers, so linked systems follow: **an undo of a synced change sends the reverse change to that service** — the Google Tasks outbox, the Calendar outbox (135/147) for deleted slots and plans, the Trakt outbox for movies/shows/episodes. After the undo the browser does what the delete flow's Undo does (`useUndoSave` → `followUndo`): slots and plans it deleted leave Google Calendar, those it put back get an event again, slots whose time or title went back move their event, Google Tasks delivers at once; a step that fails is a warning, the undo stands.
  - Only audited tables can be undone — bulk-synced data (`hevy_*`, `health_*`, `strava_*`) is not in the log, and the sheet says so. Repeating plans (`schedule_blocks`) have no audit trigger either, so their edits can't be undone here (their one-off slots, `time_blocks`, can).
  - Scenarios: `verify-db-undo-save` (85, PR check): the 73-episode update, a second undo (no-op), the undo of the undo, a mixed insert + update + delete, a cascade delete, a conflict refused then confirmed, a stale confirm, collateral, generated/dropped columns, blocked changes (hidden, no key, no access), a parent deleted since, order inside a save, a batch of 30, row level security, a rule that fights back (drift), another account.
- **Client:** `api/undoSaveApi.ts` (types, `fetchUndoPlan`, `applyUndo`), `hooks/useUndoSave.ts` (`useUndoPlan` — `qk.logs.undoPlan`, read fresh each time; `useUndoSave(onUndoAgain)` — `useMutationWithFeedback`, says the result itself (the Undo toast), invalidates `saveUndone`: every query, since any table may have changed).
- The other Undo — the toast after a delete (`docs/features/delete-undo.md`) — puts back one delete right away; this one takes back any save from the last 30 days.
