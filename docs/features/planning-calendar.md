## One item (155): Google Calendar and Google Tasks

The data layer of one item (how it is stored, the one save, a repeat's day, the conversion): `docs/features/tasks.md` → One item (155). Google's own rules for what follows (checked 15.10.2026 against its reference): `docs/integrations/google-calendar.md`.

- **The choice** (owner, 15.10.2026; `tasks.google_target` / `schedule_blocks.google_target`, NULL on rows from before 155 = where they are now): a time → **Google Calendar**, Busy with a length and **Free** without one (`transparency`: a nominal 15-minute end, `NOMINAL_EVENT_MINUTES`); no time → **Google Tasks**, or **All day** (the time chip) / Google Calendar → an **all-day** event (`start.date` → the next day; Google's end is exclusive); a repeat → one **series** on Calendar (an **all-day series** when it has no time: `RDATE;VALUE=DATE`, `EXDATE;VALUE=DATE`); **Both** only when picked ("Shows twice in Google Calendar"); **Not on Google**. Google Tasks can't repeat through its API, so a repeat on Google Tasks (156) is **one Google Task per day**: each day's task (made on its day — `docs/features/tasks.md` → A repeat's day is a task) goes through 071's outbox with its day as `due`, and ticking it in Google ticks that day; `both` is the series plus the day's Google Task. The owner reads to-dos in the Google Tasks widget on the iPhone and sees Google Calendar through Apple Calendar.
- **All-day ↔ timed reaches Google** (20.10.2026): Google merges a PATCH's objects, so an item turned all-day kept its old `dateTime` and a timed one its old `date`, and the change never took (owner: an all-day event "can't be edited"). Every PATCH of a start/end now sends the unused form as null (`calendarEventRules.timePatch` — a slot's push, the server's outbox, a series). **Events made in Google itself** open in the event editor (`EditCalendarEventModal`, `calendar/eventEditRules.ts`, `verify-calendar-event-edit`): **At a time | All day**, an all-day event's first and last day (Google's end is the day after the last), a timed one's day and 24 h time (`DateInput` + `Time24Field`, no `datetime-local`), the same nulls; a repeating event's change applies to that day only. One the app may not change — a calendar you can only view (its `accessRole`), an invitation whose guests can't modify it, a birthday, a Gmail event, a working location, a locked copy — shows its day and why, with **Open in Google Calendar**.
- **After the save** (`calendar/api/itemCalendar.ts`, `settleItemGoogle`, in the background — a save never waits for Google and a Google failure never undoes it): a slot that should be on Calendar is linked (`linkBlockCalendarEvent`, which now builds the event from the slot as it is — all-day, Free, "✓ " — `calendarEventRules.blockEventBody`) or brought up to date (`pushBlockCalendarEvent`); a rule's series follows `syncScheduleSeriesAfterSave` — and its days on Google Tasks (156): → Calendar only, the days still to do leave Google Tasks once the series answered `'linked'` (`app_repeat_days_google_tasks`); → Tasks, the series goes only once today's day task has its Google Task id (no day today: nothing to wait for); a day of a repeat is carried the 142 way (the series' EXDATE first, then the day's own event). **Moving between Tasks and Calendar never loses the item on Google:** the new copy is made and confirmed first and only then the old one goes — → Calendar: Google Tasks is turned off only once the event answered `'linked'`; → Tasks: the database turns Google Tasks on, the outbox is drained and the task read again, and only with its Google Task id there does the event go (then an all-day presence slot, `app_item_drop_block`). `'unknown'` removes nothing (the item shows in both until a later save finishes it; said once).
- **"✓ " when done** (`calendarEventRules.calendarTitle`): a done item's event title starts with "✓ "; reopening takes it off. A day of a repeat ticked through its day's task (156) — not split off — gets no "✓ " on its series' instance: that needs a PATCH of one instance, which `docs/integrations/google-calendar.md` hasn't confirmed (its Log says so); the series keeps the day as it is. A day split off (142) has its own event and gets the "✓ ". The browser pushes it right away (`refreshTaskEventSoon` after a tick, Training's done / reopen, a repeat's day); every other writer is covered by the calendar outbox's upsert. A done / reopen push sends the title ONLY (`eventPatchFor(body, 'title')`; the outbox row says `fields: 'title'`, and merged with a slot change it becomes `'all'`), so ticking an item never sends its old day back over a move made in Google.
- **The calendar outbox's upsert** (155, `calendar_outbox.operation 'upsert'`): a linked slot changed on the SERVER — the assistant, a Google Tasks pull renaming its task, Hevy closing a session, a task ticked anywhere — is queued by a trigger and `google-tasks-sync` PATCHes the event from the row as it is when the run reaches it (Oslo's wall clock: `time_blocks` keeps no zone); a renamed plan's series gets its new title. A delete always wins over a waiting upsert; a new request moves `requested_at`, and a run removes a row only while it still holds the request it read. A link made or cleared (the browser's own call) and a change the read-back applies queue nothing.
- **Changes made in Google Calendar come back** (`google-tasks-sync`, every run, BEFORE the outbox drain — a move made in Google reaches the slot before the drain pushes it; `google_calendar_sync_state`, the Google card's line): a sync-token read of `primary` (the first run and the run after a 410 only take a token — nothing before them is applied); only events a slot or plan stores are looked at (`apply_calendar_readback`): a one-off **moved / renamed** → its slot and task follow (a deadline elsewhere stays; a change older than the slot's own `updated_at` is skipped — the app's save wins); **deleted** → the link goes and the item's Calendar presence turns off — the item stays (never deleted or cancelled; an all-day slot goes only when it held nothing else: not a day split off a repeat, and the task's due is that very day — a slot holding the day of an item due elsewhere stays); **one day of a series moved** → that day becomes the plan's own one-off day holding the moved instance (the 142 path; the series push never EXDATEs that day — `keepDays` — or Google would cancel the instance); one day **deleted** → that day becomes its own item, off Google; a **series deleted** → the plan's link goes (its zone stays); a series renamed → the plan follows. Editing the series' rule in Google (other days, a new time for every day) is not followed: the next push from the app sends its own rule again. The token moves only when every change was applied. What a database rule decides because of such a move — a training session moved 7 or more days is skipped in its week and that week's session moves there, 166's recheck reopens or completes a session — is the app's own change and goes back to Google through the outbox; the move itself does not (169, 28.10.2026: `training_task_moved` turns `app.calendar_readback` off for its own writes).

## Task and schedule model (migration 077)

**Task ↔ Schedule model (migration `077`, root-cause fix — read before touching either table):** A Task (deadline: `due_date`/`due_time`) and its optional one-off schedule slot (`time_blocks`, a specific date/time to actually do it) are **independent facts**, never kept in sync by a DB trigger any more. **Exception since 142: a training task's day/time and its block move together** (Training → One planned session, one model). `time_blocks.task_id` (a real FK, `ON DELETE CASCADE`, DB-enforced at-most-one-per-task via a partial unique index) is the **ONLY** representation of "this block belongs to a Task" — `time_blocks.source_type` never equals `'task'` again (that CHECK value was removed). `source_type`/`source_id` on a task-linked block instead carry the block's REAL originating entity (`training_session`/`movie`/`tv_episode`/`project_item`/`calendar`/`manual`), independent of `task_id` and never overwritten by it — the actual bug this migration fixes (creating a task+schedule together used to silently discard the real source by overwriting it with `{source_type:'task', source_id:<task id>}`). The old bidirectional due-date↔block-date/time sync triggers and the "deleting/unscheduling a block soft-cancels its Task" trigger are **retired** (dropped, not disabled — their `link_rules` config rows are marked disabled + re-described instead of deleted). The one remaining cross-table effect is one-directional: a Task title edit mirrors onto its linked block's title via a DB trigger (`sync_time_block_title_from_task`, fires from every write door — browser, `ai-proxy`, Google Tasks pull — not just the modal). Tapping a `DayAgenda` row opens the correct editor for whatever was actually clicked, directly — no select-then-✎ second step (a small always-visible ⋯ toggle is the only way to reach the postpone/delete quick actions instead): a recurring row opens `scheduleBlock`, a task-linked one-off row opens the Task itself (`task`), a standalone one-off row opens `timeBlock` directly; there is no "which tab" decision anywhere in that flow. **This routing now lives only in `PlanBlockEntityModal`/`TimeBlockEntityModal` (`PlanEntityModals.tsx`)** — callers just open `time-block` with the block id (or `plan-block`). It exists because `TrainingCalendar`'s own plan-block click handler once got it wrong (opened via `timeBlock` unconditionally, which seeded `alsoCreateTask=true` since `buildInitialForm` had no idea a task already existed, and Save then minted a SECOND task and re-pointed the block at it). `saveSchedule`'s "Also add to Tasks" branch also gained a defensive `shouldCreateLinkedTask` guard (`planModal.config.ts`) that refuses to create a task at all when the `timeBlock` passed in already has one — `timeBlock` is contractually standalone-only, so this should be unreachable, but it's the last line of defense against exactly the TrainingCalendar-class bug. When writing `time_blocks` from a new call site (edge function or client), always set `task_id` for task-linkage and never write `source_type: 'task'` — and remember the two tables use DIFFERENT TV vocabulary (tasks: `tv_series`; time_blocks: `tv_episode` — mixing them up 400s on the CHECK, a real bug `ai-proxy`'s `planMedia` shipped with; `planMedia` now also stamps `season_number`/`episode_number` when the AI was given a specific episode, matching `EpisodesPanel`'s own single-episode rule, so `cleanup_block_on_episode_watched` can actually match the row). A caller with no `source` prop editing an EXISTING task/timeBlock falls back to that entity's own `source_type`/`source_id` (via `blockSourceTypeForTask`/`taskSourceTypeForBlock` in `planModal.config.ts`) — except `tasks.source_type='tv_series'` deliberately does NOT fall back to a block's `tv_episode` (no season/episode numbers to back that up; overclaiming episode identity generically was reconsidered and dropped). "One task = one Google entry" (see the Google Calendar + Tasks section below) is enforced on BOTH the create path and now every edit that newly makes a task calendar-linked or newly links a calendar-linked block to a task (`needsGoogleTaskDedupe`) — the create-only version of this check was a real gap.

## Calendar status is typed

**Calendar-status is a TYPED, tri-state contract — never a message-string guess.** `calendarApi.ts`'s `CalendarApiError` carries the real HTTP status (`isCalendarNotFound(error)` checks `error.status === 404`, never `message.includes('404')` — a Google error body can legally carry only a human message like `"Not Found"` with no digits in it at all). `scheduleApi.ts`'s `updateTimeBlock` and `UnifiedPlanModal`'s `linkCalendarEvent` both return a `TimeBlockCalendarStatus` (`scheduleSyncRules.ts`): `'linked'` (confirmed live this call), `'not_linked'` (confirmed gone — a real 404 whose local-id-clear write ALSO succeeded, or an explicit unlink that completed), or `'unknown'` (no token, a network/401/403/429/5xx failure, or the local clear/persist step itself failed — genuinely unconfirmed either way). The policy this feeds: `needsGoogleTaskDedupe`/`needsGoogleTasksFallback` (`planModal.config.ts`) only ever act on a CONFIRMED status — `'unknown'` triggers neither a dedupe-delete of the Google Task nor a create-time Google Tasks fallback, so an unconfirmed calendar failure can never cost the user their ONLY remaining Google representation of a task. `linkCalendarEvent` also compensates for the split-brain case where the remote Calendar event was created successfully but persisting its id locally then failed: it deletes the orphan it just created (reporting `'not_linked'` on success, `'unknown'` if even that compensation can't be confirmed) rather than leaving a real, untracked event behind. `useUpdateTask`'s own Task-title→Calendar-event push (a DB trigger keeps the block's title in sync, but has no OAuth token to reach Google with) is routed through the SAME `updateTimeBlock` call — not a second, independent `updateCalendarEvent` call with its own inconsistent swallow-everything error handling — so every calendar push in the app shares one lifecycle. An explicit unlink (`google_calendar_event_id: null`) with no Calendar token connected no longer silently drops the local link either — every OTHER patch field still applies, but the id itself is left alone (reported `'unknown'`) since nothing here could act on the remote side to justify clearing it.

## Google Tasks sync

How it works now (13.10.2026). The API itself — endpoints, fields, what we use and what we don't: `docs/integrations/google-tasks.md`.

- **App → Google: the outbox.** A task write queues a row in `google_tasks_outbox` (071's triggers, in the same transaction). The browser drains it right after the save (`syncGoogleTasksSoon` → `googleTasksOutbox.ts`) with a token from `ensureValidCalendarToken()` — the stored one used to be sent even when it was past its hour, so a phone back from the background got 401 on every send. That drain respects each row's backoff (a fresh row is due at once); only Push forces. `google-tasks-sync` drains it too.
- **Google → app: one pull, on the server.** `google-tasks-sync` mirrors the lists (`google_task_lists`), then reads each list: in full once a day, on Sync now and for a list new to the mirror; otherwise only what Google changed since the last clean run minus 60 s (`googleTasksPullPlan`). Each task goes through `upsert_task_from_google` (145, 148); a training rule a pulled move sets off (a move of 7 or more days, 166's recheck) is queued back to Google Tasks like a change made in the app, the pulled move itself is not (169, 28.10.2026). It runs every 20 minutes (cron, 072), when the app opens or comes back to the front if the last run is over 10 minutes old (`useGoogleTasksBackgroundSync`, mounted in `useAppBootstrap`), and on **Sync now** (Settings → Subscriptions → Google; a full run that also forces the outbox). The browser's own copy of the pull (the old Import button) is gone: it had drifted from the server's (dates, errors) and broke on duplicate list names. A failed run is never silent: after a background run, a failure this device hasn't been warned about yet shows one warning toast pointing to Settings → Subscriptions (the same error repeating stays quiet; a good run resets it — `lasci.googleTasks.warnedError`).
- **Visible outcome.** Each run writes `google_tasks_sync_state` (last attempt, last clean run, last full read, a readable `last_error`); the Google card shows it under the buttons ("synced 13.10.2026 11:00", or "sync failed …: Google refused the stored sign-in"). A new problem also goes to Developer → Errors once, not every 20 minutes.
- **Isolation.** A list that can't be mirrored or read is reported and holds the watermark back; one task whose write fails is reported but lets its list (and the watermark) go on — the daily full read retries it.
- **Where imported tasks show.** A new Google task is created as `personal`. With a due date it goes to section `inbox` and is on that day in Daily (overdue ones on Today); **without one it goes to section `today` (migration 148, owner 14.10.2026) and is on Today** — in Daily, Home and the brief, and in the server-side today lists (`phone-gateway`, `push-send`, `ai-proxy` read `section = 'today'`). Google taking the date away from an Inbox task moves it to Today; Google dating an undated Today task moves it to the Inbox; a section the owner chose stays (`docs/features/tasks.md` → One task model). Tasks imported before 148 stay in the Inbox until the owner runs the one-off SQL in `docs/deploy-checklist.md`. `fetchAllTasks` reads in pages: past 1,000 rows PostgREST's cap cut the undated rows first.
- **Dates.** Google's `due` is a date (the time is dropped): read its date part, write midnight UTC (`googleTasksRules.ts`, mirrored in the function, `verify-google-tasks`).
- **Links.** Google's `links` (a task made from Gmail links to the email) are kept in `tasks.google_links` (145) and shown with "Open in Google Tasks" in the row's ⋯ menu and hover strip (`GoogleTaskLinks.tsx`).
- **Migration 145.** Drops 076's unique list-title index (Google allows two lists of one name; the pull failed on it — Import with a duplicate-key error, the cron by silently skipping that list); `upsert_task_from_google` keeps links, keeps a task cancelled on every re-read of its tombstone and reopens one Google restored, keeps an opt-out (and the local edit) while an outbox row waits, keeps a local close time, accepts a task without a title, and fails loudly without a user; two runs inserting the same new task at once no longer clash (`on conflict … do nothing`); `set_task_parent_from_google` leaves a task with a waiting outbox row alone. Both run only as the service role (the sync function): the browser's pull is gone, and a SECURITY DEFINER write open to any signed-in account would step past the owner lock. DB scenarios: `verify-db-google-tasks-pull`.

## Google Tasks outbox

**Google Tasks outbox — per-task FIFO + typed 404s (migration `079`).** `claim_google_tasks_outbox` (migration 073's `FOR UPDATE SKIP LOCKED`) now ALSO only ever claims the OLDEST outstanding row per `(user_id, task_id)` — a newer row for the same task can never be claimed while an older one is still outstanding, even mid-backoff or mid-claim by another worker. Real race this closes: an opt-out `'delete'` and a later Reopen `'force_recreate'` `'create'` for the SAME task, processed out of order, could let the stale delete's unconditional id-clear wipe the BRAND NEW `google_task_id` the create just wrote. `clear_google_task_id_if_matches` (new RPC) is the belt-and-suspenders half of that fix: `processDelete` (both `googleTasksOutbox.ts`'s browser drain and `google-tasks-sync`'s cron mirror) now only clears `tasks.google_task_id` when it STILL equals the id THIS delete targeted, instead of the old unconditional `apply_google_task_snapshot(p_clear_google_task_id=true)`. `GoogleTasksApiError`/`isGoogleTaskNotFound` (`googleTasksApi.ts`, mirrored by hand in the edge function) replace every `message.includes('404')` check on the Tasks API side too. `processCreate` also re-checks the LIVE task row after the Google `POST` returns (a real network round trip the user can act during) — if the task opted out/cancelled/hard-deleted while the create was in flight, the just-created remote task is deleted rather than adopted, and a failed compensation delete enqueues a durable retry `'delete'` outbox row (never just a log line) so a later drain finishes the cleanup.
- **The claim query above didn't actually lock anything — a second review pass caught this against a live `EXPLAIN`, before either migration ever went live.** The original `claim_google_tasks_outbox` computed the per-task `rn=1` filter in a `ranked` CTE (a `row_number()` window function over the base table), then applied `FOR UPDATE SKIP LOCKED` in a SEPARATE `claimable` CTE that selected only `id FROM ranked` — not directly from the base table. This is documented Postgres behavior, not a fluke: a locking clause on a query does **not** propagate into a WITH query that it merely selects from; the clause has to be attached to the individual `SELECT` INSIDE the WITH query to have any effect. The live `EXPLAIN` plan for the broken version confirmed it directly — no `LockRows` node anywhere — meaning the whole claim had silently stopped providing ANY concurrency guarantee: two workers could both believe `SKIP LOCKED` protected them while claiming the identical row, reintroducing the exact migration-073 duplicate this function exists to prevent. Fixed by moving `FOR UPDATE OF o SKIP LOCKED` onto a CTE that selects directly from the base table, with the per-task ordering expressed as a `NOT EXISTS` anti-join (`older.task_id = o.task_id AND (older.created_at, older.id) < (o.created_at, o.id)`) instead of a window function in the same query block as the lock clause — the same shape migration 073's own (correct) query already used, just with the anti-join added. A supporting `(task_id, created_at, id)` index ships alongside it.
- **The opt-in trigger branch (migration `078`) had its own real race, found reviewing that migration a second time.** `enqueue_google_tasks_outbox()`'s opt-in branch required `NEW.google_task_id IS NULL` before enqueueing a fresh `'create'` — but a row that was JUST opted out (the very next branch enqueues a `'delete'` for its CURRENT `google_task_id` WITHOUT clearing that column locally; only the drain's own `clear_google_task_id_if_matches` does that, once the delete actually runs) still HAS a non-null `google_task_id` until that delete drains. Re-opting in before it drains hit the `IS NULL` guard and enqueued **nothing at all** — the task ended up `google_sync_enabled=true` with a stale (or soon-to-be-cleared) id and no create ever queued to replace it. Fixed: the opt-in branch now enqueues a `'create'` on EVERY opt-in transition, stamping `force_recreate: true` whenever a `google_task_id` is still present — migration 079's per-task FIFO claim (fixed in the same review pass) guarantees the earlier pending `'delete'` for the SAME task drains first, so `force_recreate` is what lets this create proceed the moment that delete has cleared the id.

## Repeat kinds (migration 146)

**How a recurring plan repeats (owner, 13.10.2026).** The planner's Repeat is ONE line at every width: a select with **No repeat · Every day · Weekdays · Weekly · Monthly · Custom** (`RECURRENCE_OPTIONS`; `RECURRING_EDIT_OPTIONS` drops No repeat when editing a saved plan), followed by the **M T W T F S S day circles** (Monday first — `DAY_ORDER`; `days_of_week` keeps 0 = Sunday; hover shows the full day name) whenever days matter. On a 402px phone the select and the seven 30px circles share one line. Every day / Weekdays light their circles; a tap turns the choice into the set it now is (`toggleRepeatDay`: all seven = Every day, Mon–Fri = Weekdays, any other set = Weekly — the same reading as opening a saved plan). Picking Weekly (or Custom) with no set of its own starts from the plan's own weekday. Below Monthly and Custom: a one-line summary ("Every month, the Saturday nearest the 13th", "Every 2 weeks on Tue and Thu") and the next three dates (DD.MM.YYYY), computed by the same rule the agenda projects. Every day / Weekdays / Weekly get no such line — the select and the circles already say it, and it cost the phone a line.

| Choice | Stored (`schedule_blocks`) | Occurs on |
|---|---|---|
| Every day / Weekdays / Weekly | `repeat_kind 'weekly'`, `days_of_week` | those weekdays every week (every row from before 146) |
| Monthly | `'monthly'`, `days_of_week` = one weekday or none | every month: the chosen weekday **nearest** the start's day of the month (13.10 + Saturday → the Saturday closest to the 13th), or that same date (clamped to the month's last day) with no weekday |
| Custom → Every N days | `'interval'`, `repeat_interval` N, `repeat_unit 'day'` | every N days from the start |
| Custom → Every N weeks | `'interval'`, N, `'week'`, `days_of_week` ≥ 1 | the chosen weekdays in every Nth Monday-first week, counted from the start's week |
| Custom → Every N months | `'interval'`, N, `'month'`, one weekday or none | the monthly rule every N months |
| Custom → Dates | `'dates'`, `repeat_dates` | exactly the picked days (picked on `DateCalendar`) |

- **The start** is `effective_from` (081): the planner's date ("Starts"; a new repeat no longer always starts today), the anchor of the monthly and every-N kinds; nothing occurs before it. Picked dates start at the earliest pick when it is earlier. Editing keeps the saved start (only an earlier picked date moves it), except for a choice that counts from it (see Recurring editor above). `except_dates` (142) leaves single days out of every kind.
- **Nearest never ties.** The seven days from 3 before to 3 after a date hold each weekday once, so the nearest is at most 3 days away and unique; it may land in the neighbouring month (the Saturday nearest the 1st can be the 30th before) and is still that month's occurrence. Before the start it is skipped (13.10 + Saturday → 10.10 is skipped; the first is 14.11).
- **One shape per meaning:** `repeatRowFromForm` stores "every 1 week" as weekly, "every 1 month" as monthly, "every 1 day" as every day. `repeatFormFromRow` is its inverse; a CHECK (`schedule_blocks_repeat_check`) keeps each kind's columns consistent (weekly rows keep no new rule, so no old row can fail).
- **The one reader is `src/features/daily/recurrence.ts`:** `occursOn(rule, day)`, `occurrencesBetween`, `nextOccurrences`, `weeklyDaysOf`, `repeatSummary` — day math on `yyyy-MM-dd` day numbers (no time zone, no DST drift). `projectRecurringBlocksForDay(dateStr, templates)` asks it for the day and for the previous day (the cross-midnight tail), and every other projection goes through that: Daily's agenda (`daySchedule.ts`), Home, Daily's training card, the Training calendar (`calendarPlans.ts`), next session (`trainingPlanModel.ts`), plan twins. The weekly views that lay plans out by weekday (Training's Weekly schedule card) use `weeklyDaysOf`; the coach's and the Program tab's scheduled training days a week use `weeklyDaysPerWeek` (every N weeks counts 1/N) — a monthly or picked-dates plan has no fixed weekday and is listed under the card by its summary. `scripts/verify-recurrence.cjs` covers month ends, leap years, every N, picked dates, `effective_from`, `except_dates` and the spillover.
- **Before 146 is applied** a weekly-style save still works (the write drops the new columns); a monthly / every-N / dates save fails with "migration 146 not applied" (`scheduleApi.ts`). The assistant has no `schedule_blocks` entry in `DB_CATALOG`, so it cannot write repeating plans.
- **Google Calendar (147).** A plan can be ONE repeating event — see Repeating plans on Google Calendar below.
- **Words.** A plan may be monthly, every N or on picked dates, so the app says "repeating plan" (Daily's and Training's delete: "Repeating plan deleted"; Training's "Change / Delete repeating plan"), and a workout's plan note reads the plan's own repeat ("Planned every 2 weeks on Tue and Thu, 16:45" — `repeatSummary`). The coach and Training's Program tab count an every-N-weeks plan's weekdays as 1/N of a training day a week (`weeklyDaysPerWeek`; a weekday covered weekly by another plan counts 1).

## Repeating plans on Google Calendar (migration 147)

**Owner, 13.10.2026: a repeating plan appears in Google Calendar as ONE repeating event, and moving or skipping one day changes only that day there.** Before, only one-off slots (`time_blocks`) reached Google. The API side (fields, syntax, traps, checked against Google's docs): `docs/integrations/google-calendar.md`.

- **Where.** The planner's "Add to Google Calendar" now shows for a repeat too: when creating (Add → a Repeat picked) and in the repeating-plan editor, where it reads "Added to Google Calendar" once linked. Unticking it removes the event; the plan stays. An existing plan is added the same way: tap it in Daily's agenda (or Training's ⋯ → Change repeating plan), tick the box, Save — or **all of them in one tap (148, owner 14.10.2026): Settings → Subscriptions → Google, "Add N plans to Calendar"**. That button shows only while Google is connected and some plan isn't on Google Calendar yet with a day left to show (`plansToAddToCalendar`); it links them one after another with the planner's own code (`addPlansToCalendar` → `linkScheduleSeries`, quiet per plan), shows "Adding 6 repeating plans to Google Calendar…" while it runs and then one result ("Added 6 repeating plans to Google Calendar · 1 failed — the app tries again the next time it opens"; an error toast when none went). A plan Google didn't take goes on the retry list as a re-link, so the next app open adds it (`useAddPlansToCalendar`, `AddPlansToCalendarButton`).
- **Stored.** `schedule_blocks.google_calendar_event_id` (the series, in `'primary'`), `google_calendar_horizon` (how far a monthly kind's RDATE list reaches; null when the event carries every occurrence) and `google_calendar_time_zone` (the zone it is expanded in) and, since 148, `google_calendar_from` (the day it was added to Google — the series' start, below; cleared with the link, kept by Undo's reset so a plan put back starts where it did). The link is written only while the plan has no series or this one, and cleared only while it still names this one (`setScheduleBlockCalendarLink` / `clearScheduleBlockCalendarLink` — the `clear_google_task_id_if_matches` rule): a second tab's link or a stale clear never overwrites a newer one; a series made by the losing tab is deleted again. Before 147 is applied, ticking the box says "migration 147 not applied" and the plan still saves.
- **The mapping** (`src/features/calendar/calendarSeries.ts`, pure, `verify-calendar-recurrence`): weekly → `RRULE:FREQ=WEEKLY;WKST=MO;BYDAY=…` (every day: `FREQ=DAILY`), every N days → `FREQ=DAILY;INTERVAL=N`, every N weeks → `FREQ=WEEKLY;INTERVAL=N;WKST=MO;BYDAY=…`; monthly, every N months and picked dates → an `RDATE;TZID=…` list from `occurrencesBetween` (no RRULE says "the Saturday nearest the 13th"); `except_dates` → `EXDATE;TZID=…` (only days the rule really has). The event's start is the rule's **first real day** on or after the later of `effective_from` and **the day the plan was added to Google** (`google_calendar_from`, 148 — owner, 14.10.2026: an old plan added today used to fill Google with all its past weeks; the app's own projection still starts at `effective_from`, and a start that doesn't fit the rule would add a stray day in Google). The day is stored with the link and every later push keeps it, so the series never creeps forward; a series linked before 148 has none and is pushed once when the app opens (`needsSeriesFromDay`), starting from that day. A day before Google's start was never on Google, so done / move / skip / Undo skip on it leave Google alone (`isBeforeSeriesStart`). The series is at the plan's wall-clock time in the series' zone — Google expands the repeat in that zone, so 16:30 stays 16:30 across daylight saving. **The zone** is the device's when the series is created or the plan is saved in the planner (Europe/Oslo when the device names none) and is stored; every other push (a day carried over, the horizon, Undo, a retry) reuses the stored zone (`seriesPushZone`), so opening the app abroad never re-zones a plan. A plan crossing midnight ends the next day. The verify script expands what we send the way Google does and compares it, day by day over two years, with `occurrencesBetween` for every kind.
- **Horizon (a year, chosen with 147).** The monthly kinds list their days to a year past the later of today and the first day; `useCalendarSeriesTopUp` (mounted in `useAppBootstrap`) pushes the list again once per app open when fewer than 90 days of it remain — after it has retried the pushes Google didn't take (below). Picked dates are all listed (no horizon). Past days stay on Google.
- **Lifecycle** (`src/features/calendar/api/scheduleSeriesCalendar.ts`, the same rules as a slot's event): token from `ensureValidCalendarToken()`; the typed `'linked' | 'not_linked' | 'unknown'` status from the real HTTP status; a deterministic id (`blockEventId(planId, n)` — a retry after a lost answer adopts the series it made, a `cancelled` one is skipped); a Calendar failure is reported once ("Saved locally, Google Calendar sync failed: …") and never undoes the save. The save hooks carry it: `useCreateScheduleBlock` / `useUpdateScheduleBlock` take `gcal` (ticked → added or brought up to date with one PATCH of title, times and the whole `recurrence`; unticked → deleted on Google first, then unlinked; no Google connection → left as it is) and answer `{ block, calendarStatus }`. A PATCH answering 404/410 (deleted in Google Calendar) forgets the link and, with the box ticked, makes a new one. A plan whose every day was taken out has no event left: its series is removed.
- **Delete and Undo.** `useDeleteScheduleBlock` (Daily, the planner, Training) removes the series right after the delete (best effort); Undo puts the plan back with no link (`SERIES_EVENT_RESET`; its zone stays) and makes a new series (`<hex>v1` — Google keeps the deleted one under `<hex>`); when Google doesn't take that now, it goes on the retry list (no note on the Undo toast — the retry says so once). A plan deleted on the server queues its event in `calendar_outbox` (147's `trg_enqueue_calendar_series_delete`, like 135's for slots).
- **One day changed (142).** Done, move or skip on a day of a plan turns that day into a one-off slot (`trainingPlanApi.ensurePlanTask`; the database adds the day to `except_dates`). When the plan is on Google, `carryOccurrenceToCalendar` runs **in the background, after** the task and its link are written — Done / Move / Skip never wait for Google, and a Calendar failure never blocks or undoes them. It pushes the series with that day's EXDATE and, **only once Google took it** ('linked'), gives the slot its own event — read fresh from the slot, so a move that already ran is respected (and one that lands while the event is made is pushed right after). Moving that day then moves only that event; deleting it removes only that event. The same runs for a day that was turned into a slot earlier but never got its event.
  - **Skip** takes the day off Google: the slot's own event is removed (`takeSkippedDayOffCalendar`, the `updateTimeBlock(…, { google_calendar_event_id: null })` path) while the series keeps its EXDATE, so Google shows nothing that day. **Undo skip** gives the slot its event back (`putSkippedDayBackOnCalendar` → `linkBlockCalendarEvent`). Only days of a plan that is on Google; a skipped one-off session keeps its event as before.
  - **Retry.** When the EXDATE push answers 'unknown' (no connection, a network or 5xx failure), the day gets no event of its own (Google would show the session twice); the plan and the day are remembered on this device (`SERIES_PENDING_KEY` in localStorage, cleared on sign-out by `security/accountState.ts`) with one warning ("Google Calendar didn't take that change yet — the app tries again the next time it opens"), and `useCalendarSeriesTopUp` pushes those plans (any kind) when the app next opens, then links their days.
- **Read side.** Google returns a series as instances (`singleEvents=true`), each with its own id and the series' id as `recurringEventId`. The agenda (`daySchedule.buildDaySchedule`, Daily and Home) hides every event whose id or `recurringEventId` is a linked slot's or plan's (`linkedCalendarEventIds` / `isLinkedCalendarEvent`), so a linked plan shows once — its own row, including yesterday's cross-midnight tail. The week and month "on Google" dots leave a linked plan's instances out too. Every events list follows `nextPageToken` (Google may answer a short page while more remain; a daily plan alone is 30 instances a month) — the browser's (`calendarApi.listAllEvents`) and the assistant's `get_calendar_events` (`ai-proxy`, which used to stop at 20 events for the week).

## Recurring templates and effective_from

**Recurring templates rendered into the PAST — real bug, fixed (migration `081`).** `schedule_blocks` (migration 004) carried `days_of_week` + `start_time` + `end_time` and **no date bounds of any kind**, so `projectRecurringBlocksForDay` matched a template on every calendar day whose weekday was in `days_of_week`, in BOTH directions, forever — creating a "weekdays 16:30" template on a Wednesday instantly back-filled every Mon-Fri in recorded history with a block that never happened. Fixed with one lower bound: `effective_from DATE NOT NULL` (existing rows backfilled from `created_at::date` — the honest start date for a row that never recorded one, so every day between a template's creation and today keeps rendering exactly as before and only the fabricated pre-creation history stops). `projectRecurringBlocksForDay` now takes `dateStr` as its first argument (since 146 its only other argument is the templates — the day's weekday comes from `recurrence.occursOn`) and gates BOTH branches; the spillover branch is gated on the **previous** day (the day that occurrence actually starts on), so a template effective from today never leaks a "continued from yesterday" tail onto its own first day. `createScheduleBlock` stamps `effective_from: todayStr()` **at the API layer, not any call site** (it's a property of the entity, so `UnifiedPlanModal.saveRecurring` needed no change) and sends the client's own LOCAL today rather than relying on the column's `CURRENT_DATE` default — that default is the SERVER's UTC day, which is yesterday for Oslo between 00:00 and 02:00; it remains the fallback for a writer that sends nothing, e.g. `ai-proxy`'s generic `db_insert`. A row with no `effective_from` (pre-081) is treated as unbounded, i.e. exactly the old behaviour, so the UI degrades instead of hiding every recurring block. **`effective_until` was deliberately NOT added** — the report is one-directional and an end date is a real feature with its own UI and its own "did this routine end?" semantics; adding the column now with no reader and no writer would be the speculative schema this repo's rules forbid. 9 assertions in `scripts/verify-plan-modal-helpers.cjs` §17 (inclusive boundary, the reported past-day case, the pre-migration fallback, and all three cross-midnight spillover cases).

## DayAgenda across midnight

**DayAgenda cross-midnight projection + task-linked click (real bugs, fixed).** A one-off block or recurring template that crosses midnight used to be attributed ENTIRELY to the day it starts on — the after-midnight portion never appeared on the next day's agenda at all, and that day's own booked-minutes/overlap math counted the FULL cross-midnight duration as if it all happened that day. `dayAgendaProjection.ts`'s `projectOneOffBlocksForDay`/`projectRecurringBlocksForDay` (pure, tested) now project every block/template onto EVERY day it actually occupies, each showing only its own `[0,24)` portion — a spillover row (↳ badge, "Continued from yesterday") on the next day for whatever crossed over, with its own synthetic id (never colliding with the canonical row) that still edits/deletes/postpones through the REAL `canonicalId`. Separately: a task-linked row's ✎ used to look the task up in a client-side preloaded map (`linkedTaskMap`) that could still be loading (or briefly stale) when tapped — a lookup miss silently did nothing. It now opens the `task` popup by id, which loads the row itself (loading and not-found states inside the popup) — no tap is ever a silent no-op.

## Server-side deletes and the calendar outbox

**Server-side deletes remove their Google Calendar event — the calendar outbox (migration `135`).** `time_blocks.google_calendar_event_id` is the only pointer to a block's event. The browser removes a deleted block's event right after the delete when Google is connected (`calendar/api/deletedBlockEvents.ts`, best effort — this outbox is its safety net), but a block deleted on the server — `ai-proxy`'s `db_delete`, the Hevy functions closing a planned-session task, the `tasks → time_blocks` `ON DELETE CASCADE`, migration 043's cleanup triggers (episode watched, project item deleted), plain SQL — has no OAuth token and used to orphan the event forever. Now an `AFTER DELETE` row trigger on `time_blocks` (`trg_enqueue_calendar_event_delete`, SECURITY DEFINER; row triggers also fire for cascaded rows) queues the event in `calendar_outbox` (one row per user + calendar + event, `ON CONFLICT DO NOTHING`; owner read-only RLS, no browser writes, no `trg_audit`; skipped while the account itself is being deleted, or the queue's own FK would abort the account deletion). `google-tasks-sync` (cron every 20 min; the same unified refresh token, whose consent includes `calendar.events`) drains it as its last step: 2xx = deleted, 404/410 = already gone (where the browser already removed it — the trigger can't tell), 401/403/429 = back that row off and stop the run, anything else = back off on the Tasks outbox's curve (60 s doubling, 1 h cap); after 8 failures a row is parked and tried once a day. A stop (once per new message) and a newly parked row are written to `app_error_logs` (Developer → Errors). An event a live block — or, since 147, a live repeating plan — still points at is never deleted (only the queue row goes). Since 147 a deleted repeating plan queues its series the same way (`trg_enqueue_calendar_series_delete` on `schedule_blocks`; `time_block_id` stays null, the payload names the plan; DB scenarios `verify-db-calendar-series`). ≤ 50 rows and a 25 s budget per run; the response carries a `calendar` summary (`deleted/already_gone/kept/failed/left/stopped`), and Calendar trouble lands in `partial_errors.calendar` / `last_error` but never holds back the Tasks `last_success_at` watermark. Every linked event lives in `'primary'` (`time_blocks` has no calendar column) — a path that links an event in another calendar must store that calendar on `time_blocks` and have the trigger read it (`verify-calendar-outbox` fails while they disagree). Pure rules + the drain loop: `src/features/calendar/calendarOutboxRules.ts`, hand-mirrored into the function between `<calendar-outbox-rules>` markers; `scripts/verify-calendar-outbox.cjs` (126). Not covered, by design: a server-side UPDATE that clears `google_calendar_event_id` (only `ai-proxy`'s `db_update` or SQL could; the browser's own unlink deletes remotely first). Events orphaned before 135 was applied stay (nothing recorded them). **Two browser fixes found with it (07.10.2026):** `isCalendarNotFound` also accepts **410** (Google answers a delete of an already-deleted event with 410 "Gone"; an event deleted in Google Calendar first used to make the app refuse to delete its block until Google purged it), and **re-linking after an unlink** no longer adopts the block's own deleted event: Google keeps a deleted event (status `cancelled`) under its id and answers a new insert with 409, so `linkCalendarEvent` walks the block's id sequence (`blockEventId`: `<hex>`, `<hex>v1`, `<hex>v2`…) past cancelled ones, and after five lets Google pick the id (`verify-plan-modal-helpers` §11).

## Google Calendar and Tasks

**Google Calendar + Tasks:** ONE unified "Connect Google" consent — the scope list (`GOOGLE_SCOPES` in `calendar/googleScopes.ts`) is `calendar.events` (read + write), `calendar.calendarlist.readonly`, and `tasks`, on one refresh token. Token stored in `useCalendarStore`; a reconnect is required if previously connected with a narrower scope set.
- **Subscribed/secondary calendars never appeared in the agenda — real bug, fixed in TWO rounds.** Round 1: (1) the scope list had no `calendarList`-reading permission at all, so `fetchCalendarList`'s `GET /users/me/calendarList` (`calendarApi.ts`) 403'd — `calendar.events` only grants read/write on *events*, never on calendar list/metadata; fixed by adding the narrowest scope that covers it, `calendar.calendarlist.readonly`, rather than the much broader `calendar`/`calendar.readonly`. (2) Even where the calendar picker already existed and worked (`WeekWidget`'s "⊞ Filter calendars", backed by `useCalendarList()` and persisted to `useCalendarStore`'s `selectedCalendarIds`), only the week/month grid's own dot indicators (`useCalendarEventDatesForRange`) actually looped over every selected calendar — `useCalendarEventsForDay`/`useCalendarEventsForRange` (the hooks `DayAgenda` actually reads for the real agenda list) were hardcoded to `calendarApi.ts`'s `calendarId = 'primary'` default and never looked at `selectedCalendarIds` at all. **Round 2 (still broken after reconnecting + regranting the new scope):** `selectedCalendarIds: null` meant two DIFFERENT things in two places — `WeekWidget`'s own `isCalSelected` treats null as "every calendar is selected" (every checkbox renders green/checked with zero action taken, since opening "⊞ Filter calendars" at all is undiscoverable and never required), but all THREE fetch hooks fell back to `selectedCalendarIds ?? ['primary']` — the same null read as "only primary". A user who never explicitly toggled a checkbox (the overwhelmingly common case) stayed primary-only forever regardless of the OAuth scope fix. Fixed with one shared `useSelectedCalendarIds()` (`useCalendar.ts`) that resolves null to every id from the SAME `useCalendarList()` query the picker already uses, falling back to `['primary']` only while that list genuinely hasn't loaded yet — used by both fetch hooks (`useCalendarEventsForDay`/`useCalendarEventDatesForRange`), merged and sorted chronologically via a shared `sortEvents` helper. **Existing connected users must reconnect once** to pick up the new scope — there is no way to silently widen an already-granted consent.
- **Two-way block ↔ event link (migration `038`):** (a repeating plan's series works the same way since 147 — see Repeating plans on Google Calendar) `time_blocks.google_calendar_event_id` stores the created event id; `scheduleApi.updateTimeBlock` (at the API layer, so every edit path is covered) moves the event with its block; a deleted block's event is removed right after the delete (`deletedBlockEvents.ts`, best effort) and the calendar outbox (135) finishes what the browser couldn't — Undo makes a new event. A calendar failure never blocks the local write, except an unlink, which removes the remote event first.
- **One task = ONE Google entry.** A task that will also become a calendar event used to produce a Google **Task** *and* an event — two things in Google for one thing here. Fixed: `useCreateTask` takes `skipGoogleTasks`, which `UnifiedPlanModal` passes whenever the task will be linked to an event; `linkCalendarEvent` is **idempotent** (re-reads the block and early-returns when `google_calendar_event_id` already exists, so no orphaned/duplicate events). "Add to Google Calendar" now also appears in **edit** mode, rendered as a disabled "Added ✓" readout when already linked. **Don't "simplify away" the `skipGoogleTasks` branch in `useTodos.ts`** — it's what prevents the duplicate on CREATE.
  - **The dedupe used to be CREATE-only — real gap, fixed.** Editing an ALREADY Google-synced task into a calendar-linked schedule (or checking "Also add to Tasks" on an already-calendar-linked standalone block) skipped the dedupe entirely, since it only ever ran at create time — the task ended up on Google twice. `saveTask`'s edit branch now computes `needsGoogleTaskDedupe(willBeCalendarEvent, googleSyncEnabled)` (`planModal.config.ts`) and, when true, patches `google_sync_enabled: false` — that re-fires migration 071's opt-out trigger branch, which enqueues the outbox `'delete'` that removes the now-redundant Google Task. `saveSchedule`'s `timeBlock` + "Also add to Tasks" branch got the matching `skipGoogleTasks` fix.
  - **Ordering matters — a second real bug found reviewing the fix above.** The dedupe patch (`google_sync_enabled: false`) must NOT be applied before the calendar link is CONFIRMED to have actually succeeded: `useUpdateTask` drains the outbox (deleting the Google Task) synchronously inside its own mutation, so patching the flag first and only then attempting `linkCalendarEvent` meant a failed calendar link (expired token, missing scope, …) left the task with NEITHER Google representation. Fixed: `saveTask`'s edit branch now updates content fields first (no `google_sync_enabled` in that patch), awaits `syncTaskSchedule`'s REAL, confirmed outcome (`linkCalendarEvent` now returns a boolean instead of swallowing everything), and only then — in a second, separate mutation — applies the dedupe if the link actually landed. `needsGoogleTaskDedupe`'s signature dropped its `googleTaskId` parameter for a second, related reason: a task can be `google_sync_enabled=true` with `google_task_id` still NULL (a `'create'` outbox row enqueued but not yet drained) — requiring a real id meant that pending create was never cancelled, and would still fire later and put the task back on Google as a duplicate. `shouldSkipPendingCreate` (`src/features/todo/api/googleTasksOutboxRules.ts`, a deliberately import-free pure module so it's testable without a live Supabase client) is the other half of that fix — both `processCreate` implementations (the browser drain in `googleTasksOutbox.ts`, and the `google-tasks-sync` edge function's hand-mirrored duplicate, since Deno can't import that file) now skip a `'create'` outright when the task has since opted back out (`google_sync_enabled=false`), treating it as a clean no-op rather than a failure.
  - **The SAME ordering hazard also existed on every CREATE path** (`saveTask`'s plain create, and both of `saveSchedule`'s "Also add to Tasks" branches) — each passes `skipGoogleTasks: willBeCalendarEvent` to `useCreateTask` speculatively, before the calendar link is even attempted; a failed link left the task with neither representation, same as the edit-path bug. `needsGoogleTasksFallback(skippedGoogleTasks, calendarLinked)` (`planModal.config.ts`) is the CREATE-side mirror of `needsGoogleTaskDedupe`, and all three create paths now call `reenableGoogleTasksIfCalendarFailed` after the real outcome is known — re-enabling `google_sync_enabled` (which re-fires migration 071's opt-in branch and pushes the task to Google Tasks) exactly when the calendar bet didn't pay off.
  - **`force_recreate` must never bypass the opt-out guard — a real regression caught reviewing the Reopen fix itself.** `shouldSkipPendingCreate`'s two guards originally shared one `!forceRecreate` condition, so a `force_recreate` row (Reopen) also bypassed the "task has since opted out" guard — a real sequence (Reopen enqueues a `force_recreate` `'create'`, then before it drains the task gains a calendar-linked schedule and opts out) could still put an unwanted Google Task back. Fixed: the opt-out check (`!task.google_sync_enabled`) is now unconditional in both `processCreate` implementations; `forceRecreate` bypasses ONLY the "already has an id" guard, which is all it was ever meant to do.
  - **`updateTimeBlock` used to swallow EVERY calendar-push failure the same way — a real gap the dedupe-ordering fixes above didn't close.** Even with the correct ORDER (confirm the calendar link before touching `google_sync_enabled`), the "confirmation" itself was worthless if the remote event had been deleted directly in Google Calendar (outside this app): the push 404s, `updateTimeBlock` only logged it, and the caller — reading the block's own still-non-null `google_calendar_event_id` column — reported "confirmed linked" anyway, so `needsGoogleTaskDedupe` deleted the task's real Google Task, leaving NEITHER Google representation. Fixed: `updateTimeBlock` now returns a real `calendarStatus` (`'linked' | 'not_linked' | 'unknown'`, `scheduleSyncRules.ts`'s `classifyCalendarPushFailure` is the pure 404-vs-everything-else classification, deliberately import-free so it's testable without a live Supabase client) — a CONFIRMED 404 clears the stale local id and reports `'not_linked'` (safe to recreate a fresh event); any OTHER failure (network, rate limit, an expired token, …) reports `'unknown'` WITHOUT touching the local id, since the event is presumably still fine and an unconfirmed failure must never be the reason a task's Google Task gets deleted. Both `syncTaskSchedule` and `saveSchedule`'s `timeBlock` branch now read THIS call's own confirmed status instead of the pre-call block snapshot.
  - **Reopen (↺) never actually recreated the task on Google — real bug, fixed (migration `078`).** Migration 071's "un-cancelled" trigger branch correctly enqueues a fresh `'create'` outbox row (Google Tasks has no undelete), but both drain implementations' `processCreate` (`googleTasksOutbox.ts`'s browser drain AND `google-tasks-sync`'s cron poller) guard `if (task.google_task_id) return` — a guard that's CORRECT for its original purpose (skip re-creating a task whose create already succeeded, e.g. a partial earlier failure) but can't tell that apart from "this id is a known-dead leftover from before the cancel." Fixed: the un-cancelled branch now stamps the payload with `force_recreate: true`, and both `processCreate`s bypass the guard specifically for that flag — every other `create` row keeps the exact same idempotency check as before.
  - **The CRON drain's stale-delete guard was silently dead — real bug, fixed.** `clear_google_task_id_if_matches` (migration 079) resolves its scope via `effective_user_id(p_user_id)`, which for a `service_role` caller returns `p_user_id` **verbatim** (never `auth.uid()` — there is no JWT on this path at all). `google-tasks-sync`'s edge-function helper called the RPC without `p_user_id`, so on the cron path `v_user_id` resolved to `NULL` and `UPDATE … WHERE user_id = NULL` matched zero rows every single time — 079's whole stale-delete-vs-Reopen race protection was live from the browser drain and a complete no-op from the cron drain. Fixed: `clearGoogleTaskIdIfMatches` now takes and forwards a `userId` parameter (`processDelete`'s own `userId`, already available — it's the outbox row's owner), threaded through on both call sites. The browser drain (`googleTasksOutbox.ts`) never had this bug — its RPC call is a real user JWT, so `effective_user_id` uses `auth.uid()` regardless of what's passed — but it wasn't touched, since the fix is edge-function-only.
  - **`applySnapshot` failure after a successful remote create could still duplicate the Google Task — real bug, fixed, then the fix ITSELF found broken by a second review pass.** `processCreate` POSTs to Google first, then calls `applySnapshot` to persist the returned id locally; if that persist step throws — a risk `migration 075`'s own header comment already flagged — a naive retry with `google_task_id` still NULL would call `createGoogleTask` again. The FIRST fix (compensate by deleting the orphan, or — if that delete also failed — durably `enqueueOrphanCleanup` a brand-new `'delete'` outbox row) was itself a real bug once migration 079's per-task FIFO claim landed IN THE SAME REVIEW PASS: a new row for the SAME task_id always sorts AFTER the original (still-outstanding, still-retrying) `'create'` row, and FIFO means the newer row can never be claimed while the older one is outstanding — the stale create would keep retrying (spawning a fresh orphan on every attempt) while its own cleanup queued uselessly behind it, forever. **Rewritten to checkpoint in-place, never a second row:** `processCreate` (`googleTasksOutbox.ts` / `google-tasks-sync`) stashes every state transition into THIS row's own `payload` — `created_remote_task` (the POSTed remote object, once known — reused on retry instead of re-POSTing) and `created_remote_tasklist` (the list it was created into, fixed at creation time so a later list-change on the task can't misdirect a retry's delete/adopt) and `abandon` (set when the remote task must be deleted rather than adopted — opted out mid-flight, or the checkpoint write itself failed) — via `patchPayload`/`patchOutboxPayload`. A retry of the SAME row resumes from whichever state its own payload records; no second outbox row is ever created for this. Closed the SAME day it was introduced, before either shipped independently.
  - **In-flight-edit gap, closed by the same rewrite.** A title/notes/due edit landing strictly between the original POST (fields now frozen/stale) and a LATER retry finally persisting the id would previously never reach Google at all — the DB trigger only enqueues an `'update'` row once `google_task_id` is actually set, which is exactly what the retry loop hasn't managed yet. Fixed: whenever a retry REUSES a checkpointed `created_remote_task` (as opposed to a fresh POST, which already carries current fields), it pushes one more `updateGoogleTask` PATCH with the task's live fields before `applySnapshot` — idempotent (PATCH always sends the full field set, never a diff), so it's free to run on every such retry.
  - **Every Supabase read/write inside the outbox drain now checks its own `{error}` — a real gap across `resolveGoogleListId`/`resolveGoogleParentId`/the task fetches/the row's own final delete.** All of these used to destructure only `{ data }`, so a transient DB failure was indistinguishable from a legitimate "no row" — silently misresolving a task's real list/parent, or (worse) the drain loop's own final `google_tasks_outbox` row delete: a failure there used to still increment `drained`, hiding that the row (and any checkpoint state on it) was still sitting there. Every one of these now throws on its own `error`, which routes into the SAME backoff/retry path a Google API failure already takes.
  - **`tasks.move` retried unconditionally on every retry of an update, even once an earlier attempt's move had already landed and only a LATER step failed — real gap, fixed.** The Tasks API has no documented no-op guarantee for moving a task to a parent/list it's already at; a reordering side effect on a redundant move is plausible, not just theoretical. `processUpdate` now fetches the task's current remote state first (`getGoogleTask`) and skips the `moveGoogleTask` call entirely once it's confirmed already at the target parent (list moves are always attempted — a single-list GET gives no cheap "already there" signal for that case).
  - **The Calendar→Google-Tasks fallback was one-directional in the edit path — real bug, fixed.** `saveTask`'s edit branch already ran `needsGoogleTaskDedupe` (gained a calendar link → turn Google Tasks OFF) but never its mirror: if an already-`google_sync_enabled=false` task's schedule was later unlinked from Calendar (block deleted, or GCal disconnected) so `syncTaskSchedule` now returns `'not_linked'`, nothing ever turned Google Tasks back on — the task silently ended up with **neither** Google representation. Fixed by capturing `wasCalendarLinked` (from the pre-sync snapshot of the linked block) and adding an `else if (!task.google_sync_enabled && needsGoogleTasksFallback(wasCalendarLinked, calendarStatus))` branch that re-enables `google_sync_enabled` — reusing the SAME pure `needsGoogleTasksFallback` function the create paths already use, no new predicate needed. `needsGoogleTaskDedupe`/`needsGoogleTasksFallback` are mutually exclusive (one requires `calendarStatus==='linked'`, the other `'not_linked'`), so the `else if` can never race against the dedupe branch above it.
  - **A second review pass found the write side had NO token refresh at all — real gap, closed by `calendarTokenSync.ts`.** Every Calendar WRITE path (`linkCalendarEvent`, `updateTimeBlock`, removing a deleted block's event) used to read `useCalendarStore.getState().accessToken` raw — the store's own `expiresAt` was never consulted, unlike the READ-side query hooks (`useCalendar.ts`'s `ensureToken`), which already refresh proactively on a timer. A token could sit expired-but-still-present in the store between refreshes and every write would 401, indistinguishable from "not connected". `ensureValidCalendarToken()` (new file, `calendarTokenSync.ts` — deliberately SEPARATE from `calendarApi.ts`, which stays import-free of the live supabase client/store singleton so `CalendarApiError`/`isCalendarNotFound` stay requirable as pure code by `scripts/verify-plan-modal-helpers.cjs`) mirrors `ensureToken`'s refresh-if-needed logic for use outside a component; `ensureLinkedCalendarEventRemoved(eventId)` (same file) removes one event (an unlink, and `deletedBlockEvents.ts` after a delete).
  - **`linkCalendarEvent`'s own "does a block already have an event?" lookup never checked its read's `{error}` — real bug, fixed.** A DB read failure there (network, RLS, …) looked identical to "no event linked yet," letting the function go on to create a SECOND Calendar event for a block that already had one. The lookup now throws on its own `error` instead of silently falling through.
  - **Calendar event creation gained a deterministic, client-supplied id — closes the one Calendar-side gap Google's OWN Tasks API can't (a genuine, documented Tasks API limitation, not something app code can fix: `tasks.insert` accepts no client id or `requestId` at all, unlike Calendar's `events.insert`).** `linkCalendarEvent` now POSTs with `id: blockId.replace(/-/g, '')` (a uuid's hex characters are a valid subset of Calendar's own base32hex id charset) — if a PRIOR attempt's POST actually landed on Google but its response never reached us (a network timeout), retrying with the SAME id 409s (`isCalendarConflict`) instead of silently minting a second event; the 409 is caught and the existing event is adopted via the new `getCalendarEvent`.
  - **`fetchEventsForDay`'s `timeMax` was `date+"T23:59:59"` — one second short of the correct EXCLUSIVE boundary** per Google's own documented `events.list` semantics (a match requires `event.end > timeMin AND event.start < timeMax`). Fixed to next-day local midnight; `useCalendarEventDatesForRange`'s own range query had the identical off-by-one and got the same fix.

## DayAgenda Calendar-event rendering

**DayAgenda's Calendar-event rendering, fixed on TWO fronts (a second review pass, after the local-block cross-midnight projection above had already shipped).**
- **A linked block's spillover row and its OWN Calendar event could both render on the SAME day.** `linkedGCalIds` (the de-dupe set — "this event id already has a `time_blocks` row representing it, don't also render the raw Calendar-API result") was built from `timeBlocks` alone. A block whose OWN `date` is YESTERDAY but crosses midnight into TODAY renders its spillover tail from `prevTimeBlocks` — and per Google's own `events.list` window semantics (a cross-midnight event matches whenever `event.end > timeMin`), that SAME linked event is ALSO returned by TODAY's own Calendar fetch. Without `prevTimeBlocks` in the de-dupe set, it rendered twice: once as the spillover row, once as a separate 'calendar' row. Fixed: `linkedGCalIds` now unions `timeBlocks` and `prevTimeBlocks`.
- **A linked repeating plan (147) comes back as its instances**, each with its own id and `recurringEventId` = the series' id; the de-dupe (`linkedCalendarEventIds` + `isLinkedCalendarEvent` in `daySchedule.ts`) takes the plans' event ids too and matches an instance by `recurringEventId`.
- **A cross-midnight Calendar event's own startHour/endHour were computed straight from each instant's `.getHours()`**, correct per-instant but assembled into a single startHour=23/endHour=1 pair for a 23:00→01:00 event — a nonsensical (negative-duration) range that broke the overlap check and the booked-minutes sum the moment a Calendar event crossed midnight, mirroring the exact bug the one-off/recurring block projection fix (`dayAgendaProjection.ts`) had already closed for local blocks. Fixed with a new pure helper, `projectCalendarEventForDay(dateStr, event)`, clipping the event onto ONE day exactly like `projectOneOffBlocksForDay` already does for a same-shape local block — 5 new assertions in `scripts/verify-plan-modal-helpers.cjs` (§15) cover the cross-midnight clip, the spillover flag, an unrelated day returning `null`, a normal same-day event, and an all-day event.

**Duration bounds — `time_blocks.duration_minutes` had no real upper (or DB-enforced lower) bound.** The custom-duration input (`DurationField`, `fields.tsx`) had `min={1}` and no `max` at all, and — critically — an HTML `min`/`max` attribute doesn't block a form submit regardless; nothing downstream re-validated the parsed value either (`Number(form.customMin) || 60` lets a negative string like `"-30"` through unchanged, since a nonzero negative number is still truthy). This matters because `dayAgendaProjection.ts`'s whole cross-midnight model assumes a block occupies at most its own start day plus a SINGLE spillover day — a >1440-minute (>24h) block would need a third day's worth of spillover nothing in that file (or `TrainingCalendar`'s dot-per-day rendering, or Home's next-session lookup) was ever built to represent; it wouldn't crash, it would just silently vanish past its second day. Fixed with `clampDurationMinutes` (`planModal.config.ts`, pure, `Math.min(1440, Math.max(1, Math.round(raw)))`, falls back to 60 on a non-finite input) applied at all three `effDuration` computations in `UnifiedPlanModal.tsx` (schedule create/edit, recurring create/edit), the input's own `max={1440}` as a visible hint, and migration `080` (`time_blocks_duration_minutes_range` CHECK constraint, clamping any pre-existing out-of-range rows first so the `ADD CONSTRAINT` itself can't fail) as the real enforcement layer — the client clamp alone doesn't cover `ai-proxy`'s generic `db_insert`/`db_update` tool, which writes `time_blocks` directly with no knowledge of this app-layer clamp at all.
- **Google Tasks field coverage (audited + fixed 20.08.2026).** Per-task real-time sync covers create (title/notes/due), toggle-done (complete/reopen via `status`, `completed:null` to clear on reopen), delete, and — **the one real gap found** — edit: `useUpdateTask` used to be a bare passthrough with zero Google sync, so rescheduling a due date or fixing a typo left the Google-side copy silently stale forever. Fixed: it now PATCHes title/notes/due to Google whenever one of those three fields is actually in the patch (a priority/section-only edit doesn't touch Google — nothing there to update). All sync is soft-fail (`logError`, never blocks the Supabase write), matching the create/toggle/delete precedent. `useSyncFromGoogleTasks`/`usePushToGoogleTasks` (previously dead code, no UI trigger) are now reachable via `GoogleTasksSyncButtons` in Developer → Connections, on `useMutationWithFeedback`. The pull direction (`useSyncFromGoogleTasks`) also gained a fix: it read `rt.notes` from the Google Tasks API response but never carried it into the imported row — a task's detail written in the Google Tasks app used to vanish on import.
  - *(Superseded by migration 071 and later: task lists, subtasks via `parent_task_id` and Google's order via `google_position` are built — `GoogleTaskListsSheet`, `MoveToListSheet`, `SetParentTaskSheet`. Only `links` is still not used.)* **Deliberately NOT built** (real Google Tasks fields with no equivalent here, verified via the Tasks API's real resource shape — not guessed): **multiple task lists** (everything reads/writes `/lists/@default/tasks` only; our own `domain`/`section` categorization doesn't map 1:1 onto Google's flat named-list structure, and building that mapping is a real feature, not a wiring fix); **subtasks** (`parent`/indentation — our `tasks` table has no parent-task concept at all, a data-model change, not a sync gap); **manual ordering** (`position` — our own `sort_order` is independent and un-synced either direction); **`links`** (e.g. an attached email) — no use case for a personal task app.

- **Wall-clock hours (28.10.2026).** `projectCalendarEventForDay` places an event by its local clock time, not by the time elapsed since midnight: on the days the clocks change (25.10.2026, 28.03.2027) an event sat an hour off (a 10:00 event at 11:00 or 09:00, Home's "Next" with it; a 23:30 event ended at 25). `hourLabel` rounds hours and minutes together (09:59:45 reads 10:00, never 09:60).
