## Training Feature Detail

**Structure (27.09.2026 overhaul).** `TrainingPage` has six tabs kept in `?tab=` (`pages/trainingTabs.ts`): **Next** (default — the next planned session from `useNextTrainingSession`, or the current program's least-recently-trained routine; every exercise with the progress engine's per-set target incl. backoff weights, last session and GIF, a recovery line from Health (last night's sleep, resting HR vs your own baseline — no score) and engine alerts; the warm-up ramp and the routine's exercise notes were removed on the owner's call — notes stay in Library → Routines, collapsed by default) · **Program** (current-program picker — pre-ticks routines actually trained in the last 28 days via `suggestCurrentProgramRoutineIds` —, weekly schedule from recurring training blocks, each routine's prescription (stacked under the schedule in main, 42rem; per-muscle and balance in the side tracks), an `exercise_target_overrides` editor, planned weekly sets per muscle graded against Pelland 2025 and the 10–20 sets range with MEV–MAV labelled as heuristic, push:pull / hamstring:quad balance; limitations and muscle preferences are applied) · **Progress** (4/12/26-week improvement card, the decision table, the weekly-volume body map open by default, a days-since-trained list per muscle, the older charts collapsed) · **Log** (`?view=hevy|strava`, switched at the right end of the page tab row; default Hevy: a month calendar — `calendar/TrainingMonthCalendar`, sticky left from `lg` — beside the workout cards; Strava: its activities. Hevy body measurements live on Health → Body, and an old `?tab=log&view=body` link redirects there) · **Library** (`?view=routines|exercises`, same place: routines, exercises + GIF fixer) · **Coach** (PT coach + profile with the Training focus, limitations, preferences). The progress engine runs ONCE per page (`TrainingProgressProvider` → `progressModel.ts`, a pure function; `useProgressData` is a thin wrapper). Pure plan logic lives in `src/features/training/plan/` (`verify-training-plan.cjs`, 104 assertions); every science citation with its URL is in `plan/sources.ts`, and the fact-checked research behind it is kept in `docs/training-health/research/` (a `verify-*.json` correction wins over its `research-*.json`). **One source per concept:** bodyweight = `useBodyweightSeries` (Health; Hevy > smart scale > Apple), next session = `useNextTrainingSession`/`pickNextTrainingSession` (Training, Daily, Home), sessions per week = `sessionsThisWeek`, est. 1RM = `est1RM` (`progressAggregate`), and ONE AI coach context (`training/coach/`: `coachData` → `coachFormat`, which holds the Turkish snapshot, the Coach JSON and `PT_SYSTEM_PROMPT` together) fed by the same engine run, so the coach cannot contradict Progress. Free-text limitations resolve through `muscleMap.resolveMovementPattern`; a 'monitor' limitation no longer paints a muscle. `WorkedMuscles`/`TrainingCalendar` are split into `components/muscles/` and `components/calendar/`. **Round 3 (27.09.2026):** **RPE** (`hevy_sets.rpe`, synced all along) shows wherever a logged set does — one formatter, `setFormat.ts::rpeSuffix` (" @ RPE 8/9/10"); the Next card adds an informational "near your limit" (avg ≥ 9.5) / "room to push" (≤ 7) note that never changes the target, and the coach snapshot carries it. **Missed sessions** (migration `112`, `training_skips`; `plan/skippedRoutines.ts`, `verify-skipped-routines`): a current-program routine not done for more than 7 days with no one-off plan ahead (recurring templates deliberately don't count) shows a warning on Program and Next — Plan it (or **Move it** when the routine has an open past plan: never a second plan beside it), or Skip with a required reason (the shared `training-plan-skip` sheet; covers the week it was due; undoable). **Session popup:** every session opens ONE popup, `training-session` (`{ workoutId?, plan?: { kind: 'block'|'recurring', id, date } }`, `components/session/TrainingSessionView`) — from the Log calendar rows and workout cards, Next's ⋯, Daily's Training card and agenda training blocks, Home's Next up/Later rows (`NextUpItem.category`/`planDate`), the Home Training tile and widget, and Health → Workouts. It is compact: a workout shows one stats row (duration · working sets · volume · avg HR from the matched Apple Watch workout, or the exercise count without one), an RPE line when a set was rated ("Avg RPE · N of M working sets rated"), one collapsed line per exercise (with `rpeSuffix`) that expands to its set table, and a collapsed "Heart rate & energy" section; a planned session shows the progress engine's targets, the same rows as Next (`useRoutineSessionPlan`, its own `TrainingProgressProvider`); a plan a workout covered opens as that workout ("Planned for 18:00" / "In place of ⟳ Upper B" — `sessionRef.resolveTrainingSession`, pairing via `calendarSessions.matchDaySessions`; the Log calendar rows use the same words via `sessionRef.coveredPlanNote`); a plan's actions are the ONE session action list (see **One planned session, one model** below). `training-session` is the only session popup kind (the `hevy-workout` alias was deleted). `training/sessionLinks.ts` records which workout a popup shows, keyed by the request object, so Health's `isTrainingSessionRequest` treats a popup opened from a covered plan as "back" from the Apple workout popup. Verified by `verify-training-log` (122). **Push:pull / quad:ham** come from ONE module, `plan/muscleBalance.ts` (push = chest+shoulders+triceps, pull = back+traps+biceps, shown "a : 1", heavy above 1.5×), used by the Program card (planned), the Muscles card (done, last 30 days — each shows the other's number and a "why they differ" line) and the coach; `muscleMap.templateMuscleCredit` credits each muscle once per set (Hevy's lats + upper_back used to double-count Back, which is why "balanced" showed against a planned 1.77). **Personal records are gone from every screen (owner's call, 27.09.2026):** the Library's Records tab (`HevyPRList`, `BestLiftsCard`, `fetchHevyPRs`, `personalRecords.ts`), the Improvement card's record timeline and the decision table's "6-month best" chips. The engine still emits its record events (they count as evidence for the program verdict); `progress-engine/copy.ts::visibleEvents` keeps them off screen. The notes below describe how the individual pieces were built; where they mention the old Hevy/Strava/Health/Coach tabs or records, read them against this structure.

Page layout: `PageContainer` + the tab row; each tab is a PageBoard (`trainingBoards.ts`): Next (session + context rail left, exercise cards `minmax(22rem,1fr)` across the rest) · Program (main 42rem; current program/schedule | planned sets | balance) · Progress (decisions + body map in main, improvement/verdict/recency rail, charts below in 1–3 columns) · Log (sticky calendar rail left) · Coach (main 42rem; coach | profile | history). - **AI PT Coach** (`PTCoachTab.tsx` + `api/ptCoachApi.ts`): user-initiated (NEVER auto-runs) daily assessment acting as a decisive personal trainer. **Token-minimal BY CONSTRUCTION** — `buildTrainingSnapshot()` pre-aggregates everything client-side (latest workout's per-exercise set summaries with previous-same-exercise comparison from up to 10 sessions back, weekly hard-sets-per-muscle vs `MUSCLE_LANDMARKS`, last-night + 7d-avg sleep, steps/active energy, 30d weight trend) into ONE compact text block → a single one-shot `invokeAI` call, zero tool loop (same pattern as the daily briefing). The coaching brain (recovery gate on <6h sleep, MRV deload cues, double-progression +2.5/+5kg engine, volume steering vs MEV) was distilled by the `strength-coach` agent and bounded by the `sports-scientist` agent's evidence guardrails — **the snapshot line formats are a CONTRACT with that prompt; change them together.** Input: feeling chips + optional free text. Every assessment is saved to `pt_assessments` (migration `051`: date, feeling, note, the exact snapshot the coach saw, the reply, which model served it); the next run feeds the previous one back in and the prompt's FOLLOW-UP rule makes the coach open with whether its last advice was applied. History is browsable in the tab; a localStorage fallback still displays results if the migration isn't applied.
- **Coach mode in the main chat** (`AIPanel`'s Coach toggle → `sendCoachMessage`/`buildCoachContext`): a SEPARATE surface from the daily assessment — open conversation over a prepared last-30-days compact JSON (workouts w/ sets, current routines incl. ids, sleep, steps, active kcal, weight/body-fat, the diary's logged nutrition, the coach's own past assessments, the athlete profile + active limitations below; ~7k chars measured live), blunt science-over-feelings persona, and REAL program edits via `update_hevy_routine` plus new-routine creation via `create_hevy_routine`. Both forward to `hevy-api` so every documented Hevy payload trap stays handled in one place and **Hevy stays the source of truth** (the local mirror is upserted by hevy-api, never written directly); both confirm first, and create requires resolving real `exercise_template_id`s via `db_query` on `hevy_exercise_templates`. The general Ask AI chat also carries a TRAINING QUESTIONS persona block (client-side in `aiApi.ts`'s `SYSTEM_PROMPT`, no edge deploy needed), which now tells the model to check the `get_athlete_profile` tool before giving programming advice.
- **Athlete profile** (migration `070`: `athlete_profile` + `athlete_limitations`) — a second strength-coach/sports-scientist design pairing, this time over durable facts about the person rather than volume math. **Two tables, not one `text[]` column**, because the repo's real convention for a one-to-many attribute list is a child table (`recipe_ingredients`, `hevy_exercise_template_muscles`), and a limitation needs its own identity/`created_at`/CHECK that an array element can't carry. `athlete_profile` is a true **singleton** — `user_id` is the PRIMARY KEY (no `id` column) — holding `goal` = the **Training focus** (strength/hypertrophy/general — a stored `fat_loss` reads as general via `trainingFocusOf` and migration 113 rewrites it, since losing fat is the Cut phase on `day_targets`; read-only metadata for the coach's tone that never forks the volume algorithm; the coach snapshot/JSON carry `Odak`/`focus` plus the phase `Faz`/`phase`, and `get_athlete_profile` maps it too and omits the superseded goal columns), `experience_level` (novice/intermediate/advanced), `training_age_years`, `training_days_per_week`, `equipment_access`, `notes`. `athlete_limitations` is a normal list: `movement_pattern` + `severity` (`avoid`/`limit`/`monitor`, **defaults to `monitor`** — escalating to avoid/limit is always an explicit, separate update, never automatic on log) + `note` + `active`.
  - **`movement_pattern`, never a muscle slug.** A physical limitation is almost always movement-shaped, not muscle-shaped — a shoulder issue rules out overhead pressing, but flat press/flyes are frequently still safe despite training the same chest muscle; flagging at the muscle level would suppress a still-safe stimulus. `muscleMap.ts`'s `MovementPattern` (9 values: squat/hinge/horizontal_press/vertical_press/horizontal_pull/vertical_pull/lunge/carry/isolation — a standard S&C taxonomy, not exotic) is free text on the DB side (no CHECK enum — a fixed value list would force an `ai-proxy` redeploy for every new phrasing a real conversation surfaces, the same reasoning `069`'s rejected season-CHECK already established).
  - **`PATTERN_AFFECTED_SLUGS`** (`muscleMap.ts`) is the derivation seam: which `Slug`s a pattern restriction realistically touches, and how hard (`'avoid'` = no comparable substitute at heavy load; `'limit'` = other patterns/isolation work still train it safely). This is what lets `WorkedMuscles.tsx` — a pipeline keyed entirely by muscle `Slug`, with zero pattern dimension of its own — render a per-muscle flag without the DB ever storing a muscle slug directly. A flagged muscle is a **third visual state** (violet, `FLAG_META`), deliberately never green or red: most flagged muscles are still safely trainable through a non-conflicting exercise, so a danger colour would overstate the restriction. Shown even at 0 logged sets (the flag is the point, not the volume).
  - **Experience-scaled landmarks** (`scaleLandmarksForExperience`, `EXPERIENCE_MULTIPLIER`): novice ×0.85 / intermediate ×1 / advanced ×1.15, applied to **MEV and MRV only** — MV and MAV are deliberately left unscaled, a cross-examined agreement (RP framework: training age shifts MEV/MRV; scaling the WHOLE landmark set would overclaim precision on a table that's already a heuristic, not a measurement). Every `InfoBubble` showing an adjusted landmark says so explicitly: *"Adjusted ±15% for your experience level — an unvalidated adjustment on top of an already-heuristic baseline, not a measured number."*
  - **`ptCoachApi.ts`'s snapshot** gets one new block — a `PROFİL:` line (goal/experience/equipment/days, only the fields actually set) + one `Kısıtlama:` line per active limitation — inserted before the workout lines, respecting the file's snapshot-line-format contract; `PT_SYSTEM_PROMPT`'s rule 1 (safety) was extended to ground `avoid`/`limit`/`monitor` into concrete behaviour. Absent entirely when the user has never touched the profile — zero snapshot-line change for anyone who doesn't use this feature.
  - **`ai-proxy`**: `athlete_profile`/`athlete_limitations` are `rw` `DB_CATALOG` entries (per the user's explicit instruction to give the AI authority here) plus a new single-shot tool, `get_athlete_profile` — returns both tables in ONE call (mirroring `get_day_summary`'s shape) instead of two separate `db_query` round trips, because token efficiency was an explicit requirement. `athlete_profile` being a singleton keyed by `user_id` (no `id` column) means `db_update` needs a non-empty `filters` object even though the function already scopes to `user_id` internally — the catalog's `rules` text spells out the exact `filters={"user_id":...}` shape to use. Not added to `EMBED_SOURCES` (semantic search) — this is structured settings data consulted deterministically, not free text worth fuzzy-recalling.
  - **Settings UI**: `PTCoachTab.tsx` gained a slim summary strip (`🎯 hypertrophy · intermediate · gym · 2 limitations` + a ⚙ button) opening `AthleteProfileSheet.tsx` (pills/stepper autosave on tap, `notes` autosaves on blur — matching Media's `personal_note` convention, no Save/Cancel footer) and `LimitationsList.tsx` (every limitation stays visible even when inactive — muted, one tap to reactivate; deleting is a separate confirmed action, never implied by "inactive"). Pre-migration-safe throughout: every new read degrades to `null`/`[]` on a missing table, every write throws a named "migration 070 not applied" error rather than failing silently.
- **Progress sub-tab** (`ProgressTab.tsx` + `progressAggregate.ts`) — three charts answering "how am I actually changing over time", added from an explicit `strength-coach` (what metric per exercise type) + `sports-scientist` (which other charts are evidence-worthy) agent consultation (28.08.2026), the same pairing behind Muscles/athlete-profile. **Data:** `hevyApi.fetchTrainingHistory(fromISO,toISO)` fetches the last 182 days of `hevy_workouts` → `hevy_workout_exercises` → PAGINATED `hevy_sets` (1000-row chunks) → `hevy_exercise_templates`, joined client-side (the `fetchMuscleVolume` precedent), via `useTrainingHistory()` (10-min `staleTime`). All three charts share this one fetch.
  - **Exercise Progress** (`ExerciseProgressChart.tsx`) — the user picks ONE exercise (mandatory `Combobox`/`ComboboxInput`/`ComboboxOptions`; **`immediate` goes on the root `<Combobox>`, not `<ComboboxOptions>`** — a real bug this session: `immediate` on the wrong element type-errored AND left the picker showing zero options on focus) and sees its own progression across every session it appears in. **The metric plotted is NOT one universal formula** — `metricKindForExerciseType(type)` dispatches on the exercise's own Hevy `CustomExerciseType`: `weight_reps`/`short_distance_weight` → **Est. 1RM** (Epley, the one `est1RM()` in `progressAggregate.ts` — never a second formula for the same number), `bodyweight_reps`/`reps_only` → top-set reps, `bodyweight_weighted` → added weight, `bodyweight_assisted` → **assistance, inverted** (less assistance over time = the improvement, so the line trending down is the win), `duration`/`weight_duration` → top-set duration, `distance_duration`/`floors_duration`/`steps_duration` → top-set distance; an unrecognized/future type falls back to `est1rm` rather than crashing. `computeExerciseProgression` groups sets by `date|workout_id`, excludes `type==='warmup'` entirely, and picks the SINGLE BEST set per session (never an average) — a `dropset` can never win (lighter by construction), a `failure` set legitimately can (a real top effort). An `est1rm`/`addedWeight` exercise gets a toggle to **Session Volume** (Σ weight×reps that session, warm-ups excluded) — never offered for a rep/duration/distance exercise, which has no weight-based "volume" to switch to. Guardrail copy (always visible, never buried in an ℹ️, matching the Muscles feature's tone) covers: the Epley ±10%-at-low-reps caveat and its 12-rep cutoff (`est1RM` returns `null` above 12 reps — those sets are excluded from the estimate), volume-vs-strength, added-weight understating true load, the assisted-exercise inversion, a rep-range-swing warning (`repRangeVariedSignificantly`, triggers at a ≥4-rep swing across the period), "read the trend over sessions, not day to day," and an explicit disambiguation from the Muscles body map (a muscle's total weekly dose) — this chart is not that.
  - **Weekly Training Volume** (`WeeklyVolumeChart.tsx`) — the sports-scientist agent's #1-priority chart: total weekly tonnage (Σ weight×reps, warm-ups excluded, weight-based exercise types only via `computeWeeklyVolumeTrend`) as a **trend**, not the Muscles feature's current-window snapshot, with a 4-week rolling average line (`rollingAverage`) overlaid. Uses its own `ComposedChart` (bar + line, two independent series) rather than the shared `BarLineChart` (which only supports one dataKey driving both a bar and a line). Guardrail: tonnage is a training INPUT, not a stimulus or outcome — it conflates load and reps freely (100kg×5 and 50kg×10 tally identically) and shifts with exercise-mix changes; read it over months, not weeks.
  - **Training Consistency** (`TrainingConsistencyCalendar.tsx`) — a diverging-colour week-cell calendar (`computeConsistencyByWeek`) plus a current-streak readout (`currentStreakWeeks`), grounded in the sports-scientist finding that frequency is largely a volume-equating variable, not an independent driver — the guardrail copy says so explicitly, framing this as an adherence view rather than a second "more is better" signal. **`computeConsistencyByWeek` builds a DENSE week series** (every Monday from the earliest to the latest logged week, explicit `sessionCount: 0` for an untrained gap week) — a real bug caught in test-writing: the original sparse version only returned weeks with data, which silently glued two non-consecutive trained weeks into one fake unbroken streak.
  - **Follow-up review (31.08.2026)** implemented the three originally-deferred items plus each agent's own top "extra" recommendation, reconciling two independent agent passes (a sports-scientist review superseded the strength-coach's initial bucket/threshold proposals where the two disagreed — see each file's own header comment for the reasoning):
    - **`RelativeStrengthChart.tsx`** — bodyweight-normalized strength trend, **`est1rm`-type exercises only** (a ratio built from reps/added-weight/assistance/duration/distance has no interpretable meaning normalized by bodyweight — the strength-coach's separate "total load" formula for `bodyweight_weighted` lifts was considered and dropped, since two different ratio formulas on one chart is exactly the kind of silent misread this feature exists to prevent). `resolveBodyweightForDate` (`progressAggregate.ts`) is a 3-rung ladder — exact same-day match → linear interpolation between two anchors ≤21 days apart → nearest single anchor within ±14 days → otherwise **no point at all** — deliberately never an indefinite carry-forward, which would flatten the denominator across a cut/bulk and make the ratio lie about which side (strength or bodyweight) actually moved. `computeRelativeStrengthTrend` combines this with `computeExerciseProgression(sets, id, 'est1rm')`'s own session points — reusing that function rather than a parallel one. `hevyApi.fetchBodyweightHistory` unions `hevy_body_measurements.weight_kg` (the user's own manual log) with `health_metrics.weight_body_mass` (an automated scale synced through Apple Health), same-day conflicts resolved manual-wins. The chart always plots BOTH lines (ratio + a muted dashed bodyweight line) — never just the ratio — specifically so a rising number during a cut is visibly attributable to the denominator, not silently read as new strength. Estimated (non-same-day) points render as a hollow dot. **No strength-standard reference lines** (1×/1.5×/2×BW-style bands) — what counts as strong varies by height, limb length, age and sex, none of which this app knows.
    - **`RepRangeDistributionChart.tsx`** — a set-count histogram by rep bucket, **boundaries `1–5 / 6–12 / 13–20 / 21–30 / 31+`** (`REP_BUCKETS`, `computeRepRangeDistribution`) — the sports-scientist review's call, not the strength-coach's originally-proposed `6-8/9-12` split: Schoenfeld et al. 2017 (JSCR 31(12):3508-3523) and Morton et al. 2016 (J Appl Physiol 121(1):129-138) found hypertrophy roughly equivalent from ~5 to ~30 reps taken near failure, so there's no evidence for a boundary at rep 8, and the chart deliberately does NOT frame any bucket as "the hypertrophy range." Warmups excluded, dropsets/failure sets counted (each drop its own set, matching `computeExerciseProgression`'s own eligibility). Period toggle 30/90/182 days (default 90) + an optional muscle-group filter (primary-attribution only — deliberately NOT the Muscles tab's fractional secondary credit, since a histogram counts whole sets and crediting half a set to a second bar would double-count it). No target-distribution overlay.
    - **`WeeklySetsPerMuscleChart.tsx`** — the sports-scientist review's top-priority "what else": the SAME currency the Muscles tab already uses (hard sets/muscle/week vs `MUSCLE_LANDMARKS`' MEV-MAV) — the one training measure in this app with an actual dose-response meta-analysis behind it (Schoenfeld 2017; Pelland 2025) — but as a per-week **trend** rather than a single rolling-window snapshot. `computeWeeklySetsPerMuscleTrend` reuses `muscleMap.ts`'s `contribution()`/`HEVY_TO_SLUG` exactly (primary 1.0, secondary 0.5), no parallel volume model; `fetchTrainingHistory` was extended to also join `hevy_exercise_template_muscles` (the same query `fetchHevyExerciseTemplates` already does) so `TrainingExerciseTemplate` carries `secondary_muscle_groups` for free. A muscle chip row (reusing `MAJOR_MUSCLES`/`labelForSlug`) picks one muscle at a time; the chart shades the MEV–MAV band and an MRV reference line, scaled by `scaleLandmarksForExperience` when an athlete profile exists.
    - **`WeeklyChangesPanel.tsx`** ("Big Changes This Week") — ships **instead of** an acute:chronic workload ratio (ACWR), which the strength-coach review explicitly advised against: ACWR's injury-prediction evidence is team-sport running/GPS load, it has drawn sustained statistical criticism (mathematical coupling between the acute and chronic windows it computes from, unstable "sweet spot" thresholds), and this app's OWN Weekly Volume guardrail already documents tonnage as conflating load and reps — a risk flag can't be built on a quantity already flagged as ambiguous, and a solo lifter's log has none of the sample size the original research relied on. `computeWeeklyChangeFlags` is a plain per-exercise change detector: a top-set-load jump ≥10% or a set-count jump ≥30% vs the **median** of up to the 4 preceding weeks (median, not mean, so one deload week can't manufacture a flag on the return; requires ≥3 prior weeks of history), plus an unconditional `'new'` flag for any exercise not trained in the last 8 weeks (or ever) — unfamiliar-movement soreness is real and otherwise invisible in this data. No score, no colour-coded "risk," no threshold band.
    - **`RecoveryLoadPanel.tsx`** ("Recovery Inputs Alongside Load") — sleep and resting-heart-rate trends alongside weekly tonnage, as **three stacked lanes sharing one weekly X axis**, deliberately NOT a dual-axis overlay (which lets two arbitrary scales be tuned until any two series look coupled — a causality claim made with a scale factor instead of words) and NOT a computed composite "readiness" score (this app's own house rule forbids synthetic derived metrics — see Health's "no derived sleep metrics" precedent). `recoveryAggregate.ts` (new, pure, import-free of runtime deps) computes weekly sleep (mean nightly hours from `computeSleepSummary`) and weekly resting HR (median from `computeDailySeries('resting_heart_rate', ...)`), both keyed to the SAME `mondayOf` weeks `progressAggregate.ts`'s tonnage trend uses — one definition of "a week" for the whole panel — and both gated at **≥4 tracked nights/days per week**, else null (a broken line is more honest than an imputed one). **An HRV lane was deliberately left out**: different HRV measures (e.g. SDNN vs RMSSD) must never share a line or an average, and this app's own rule is to verify an external field's exact shape live before shipping copy that names it — add it once that's confirmed against a real payload.
    - **Deliberately still not built**: a "Stalled & Progressing" exercise roll-up table (the strength-coach's other "extra" suggestion — real value, but a genuinely new UI surface, an OLS-slope-over-time helper plus a sortable table, rather than an extension of what's here; tracked as a fast-follow, not silently dropped).
    - **Verified:** `scripts/verify-training-progress.cjs` — 63 assertions against the real un-mocked `progressAggregate.ts`/`recoveryAggregate.ts` (Epley cutoff, per-type dispatch, warmup exclusion, best-set-not-average selection incl. the dropset/failure-set distinction, the assisted-exercise inversion, the dense-week-series fix, streak termination at a real gap, the bodyweight-resolution ladder's every branch, rep-bucket boundaries and filtering, weekly-change-flag detection incl. the new-exercise/insufficient-history/no-change cases, primary+secondary muscle credit, and the sleep/RHR minimum-tracked-days gate).
  - **Exercise pickers sort by recency, not alphabetically** (`ExerciseProgressChart.tsx`/`RelativeStrengthChart.tsx`, 01.09.2026) — both compute a `lastUsed` date per exercise from the fetched sets and sort descending, so the lift you just did is at the top instead of buried among 40+ alphabetical names.
  - **`TrainingInsightsPanel.tsx` ("Training Analysis")** — a third sports-scientist agent review (01.09.2026), this time answering the user's explicit ask to actually READ what they're doing well/poorly, not just look at more charts. Rendered FIRST in `ProgressTab`, above every chart it summarizes. **Deliberately a fixed rules engine (`trainingInsights.ts`), never an AI call** — the agent's own explicit call: PT Coach is a dated, one-shot, snapshot-archived opinion where non-reproducibility is bounded and auditable, but this is a *standing* view the user re-opens repeatedly and reads as the app's canonical verdict on their log — two loads of the same data producing two different verdicts would be the app contradicting itself about a fact, not a tone difference, and an LLM reliably launders a heuristic threshold ("MEV") into a paraphrased "scientific minimum" over enough renders. The same log always produces the same text.
    - **Every `Finding`** (`{id, tier, positive, text}`) carries an exact number traceable to the user's own log and one of three tiers, rendered as a coloured pill so a heuristic can never read as a measurement: **Measured** (arithmetic on the log, no interpretation) · **Evidence-based** (an interpretation backed by cited meta-analytic work, inline citation in the sentence) · **Heuristic** (a practitioner convention with no trial support for the exact number — every MEV/MAV/MRV-based finding is this tier). `sortFindings` renders measured → evidence-based → heuristic. **NEVER_HIDES applies to absence of data too**: a rule that can't fire due to insufficient history renders an explicit "can't assess this yet, because X" line (the rep-range-varied skip in `computeExerciseTrendFindings`, the relative-strength null case) rather than the section silently vanishing.

A training day that passed with no workout and no tick is closed by the database as missed (`cancelled` + `closed_reason 'missed'`), never as a skip: no skip row, and `sessionState` reads it as a past open plan (`taskMissed`: "Not logged yet" while 141's six days run, then Missed); a workout of its routine logged late within those six days still completes it (`training_plan_candidates` takes a missed day). Training's calendar and next-session cards read blocks and projections: a day ticked only through its task without a split (Google Tasks, a Hevy workout) shows there through the day's workout pairing, as a projection day always did.

DB (Hevy): `hevy_workouts`/`_exercises`/`hevy_sets`, `hevy_routines`/`_exercises`/`hevy_routine_sets` (routine sets also have `rep_range_start/end`), `hevy_exercise_templates`(+`_muscles`; `thumbnail_url` since 154), `hevy_routine_folders`, `hevy_body_measurements`, `hevy_workout_events_cursor`, `hevy_account` (154, read-only for the app).

## Training session never planned twice

**A training session is never planned twice on one day without asking** (`training/plan/planTwins.ts`, `verify-training-plan`): saving a one-off training block (time-block / task popups) on a day that already has the same session — the weekly ⟳ template by name, or the same routine (`source_id`) or name as another block — asks "Plan this session twice?" first (`UnifiedPlanModal.confirmNoTwin`; a failed read never blocks). Before this, Missed sessions → Plan it, Routines → Plan, Next and Daily could add a second copy on the template's day, and every page then listed the session twice.
