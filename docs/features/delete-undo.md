## One delete, with Undo (migration 144)

**One delete, with Undo (migration `144`, 13.10.2026; owner: every delete asks first, says what happened, and can be undone).** Before, each feature deleted its own way — some asked, some had Undo, most neither, and an Undo brought back only the row you tapped, never what went with it.
- **Database:** `app_delete_rows(table, ids)` (SECURITY INVOKER — RLS and the owner lock apply) deletes and, in the same transaction, returns what went with the rows: every row a single-column foreign key deletes with them (CASCADE, all levels, parents first), the rows whose link it empties (SET NULL), and rows the two rules without a foreign key change (043: a project item's slots, while that rule is on; 123: recipes built from a deleted food) — those two kinds with their values before and after the delete. NULL = nothing was deleted (the write's own answer is the result — no second read); over 10,000 rows it still deletes but returns `too_big` and no rows. `app_restore_rows(snapshot, overrides)` puts it all back with the same ids (a GENERATED ALWAYS identity, `reading_page_events`, gets new ones), all or nothing (a group whose parent isn't back yet waits a round; `ON CONFLICT DO NOTHING`, `restored` counts what came back); a link (only while still empty) or a rule-changed row gets back only the columns still holding what the delete left, so an edit made since is kept; it names what it may not write (`skipped`, also a link row level security wouldn't update). The client's own Undo copy follows the counts: "Restored", "Restored · 1 already there", or "Not restored — it's already there again" (`restoreAnswer`); a step after the delete that fails (`afterDelete`) is warned about and Undo is still offered. 144 also lets the owner write back reading history and Kobo questions (insert/update policies). Scenarios: `verify-db-delete-undo` (56, PR check).
- **Client:** `shared/utils/deletedRows.ts` (`deleteRows`, `restoreRows`, `rowsOf`, `restoreAnswer`, `notRestoredNote`), `shared/hooks/useRowsDelete.ts` (`run(ids, { title, message?, done })`: the question, the delete, the rows leave every cached list, "Wish deleted · Undo"), `shared/modals/deleteFlow.ts` + pure `deleteFlowCore.ts` (`confirmDelete` for anything else; with no `restore` the question adds "This can't be undone."; `ask: false` when the screen's own dialog asked — Games' Hide instead / Delete anyway). Slots deleted with something lose their Google Calendar event right after (`calendar/api/deletedBlockEvents.ts`, best effort — the 135 outbox is the safety net) and Undo makes a new one; a task put back gets a new Google Task (`TASK_GOOGLE_RESET`: its Google ids null, `google_hidden`/`google_deleted` false — they are NOT NULL); a movie/show put back makes its Trakt note anew.
- **Covers:** tasks (incl. training sessions — `trainingPlanApi`'s own snapshot is gone), slots, weekly plans, projects/phases/items, wishes, Work links/goals, diary rows, recipes, foods, shop items (their own RPC, 137 — the thing and the accessories bought for it, `shopModel.deleteScope`, the same from every screen), shop costs/links, transit stops (the default moves and comes back)/routes, subscriptions, dev requests (one or many), AI memory, movies/shows (Trakt removal, then re-add on Undo), cinema visits, follow rules, games/platforms (ScreenScraper history can't come back — Undo says so), books (with reading history), Kobo questions, training limitations/preferences/targets/GIF fixes. **No Undo, and the question says so:** what lives outside the app — a Google Tasks list, a Calendar event, a Trakt list, a paused playback, Kobo files — and clearing the logs. Toggles are not deletes (star, queue, follow, reminder bell); "Not watched" gets its Undo with step 5.
- **Guard:** `verify-delete-flow` (88) counts every raw `.delete()` left in `src/` per file, with its reason — a new one fails until it goes through the flow or is listed.
