# Edge functions and deploy

> Moved out of CLAUDE.md on 13.10.2026.

## Edge Functions (Supabase)

**Deploy is automatic on merge (11.10.2026, `.github/workflows/deploy.yml`; setup runbook `docs/deploy-setup.md`).** Job `secrets-guard` ("Deploy secrets are environment-only") fails while the deploy secrets — or the old `SUPABASE_DB_PASSWORD` — exist as repository secrets. Job `backend` runs only from `main` and always deploys **main's newest commit** (looked up at start; a run whose own `deploy.yml` is older than main's deploys nothing, and the website job re-checks before publishing, so a re-run or queued older run can't put older code back): it tries the Supabase token (read only), checks that 139 and 140 ran, runs every migration numbered **above 140** that has not run yet, in number order, each once (`scripts/deploy/run-migrations.mjs`: the file is sent as ONE query together with its row in `deploy.applied_migrations`, so a failing file keeps nothing; a file with its own `BEGIN`/`COMMIT` is refused by the PR check), then deploys **every** edge function (`supabase functions deploy --use-api`, CLI and action pinned). Only then does the website build and deploy. A failing migration stops the run with functions and website unchanged; a failing function deploy leaves the database migrated and the website old (fix and merge again). The secrets `SUPABASE_ACCESS_TOKEN` (a personal `sbp_` token) and `SUPABASE_DB_URL` (the **Session pooler** address of this project — the direct `db.<ref>.supabase.co` is IPv6-only and GitHub cannot reach it) live in the GitHub environment **`production`**, limited to `main`; without them the job deploys nothing, warns about migrations waiting, and the website deploys as before. **Actions → Deploy → Run workflow → Dry run** checks both secrets and lists what would run, changing nothing. The log is public: the runner prints file names, line numbers and error codes, a message only when its class cannot quote row data (`publicError`), never NOTICE texts; the full error goes to `deploy.migration_errors`. Migrations `001`–`140` were applied by hand and are never run by the workflow. **Never run a migration numbered above 140 by hand, never `supabase db push`, and never deploy a function by hand** — the next merge would run the migration again and replace the function. Earlier attempts failed: a `supabase db push` job (06.06.2026–21.06.2026) tried to apply the whole history, and a functions job (14.07.2026) had a wrong token (401). Functions stay self-contained (no `_shared/` imports) so a Dashboard deploy still works in an emergency. PR check: `run-migrations.mjs --check` and `verify-deploy-migrations.mjs` against a throwaway Postgres service.

**`supabase/config.toml` is THE list of functions with platform JWT verification OFF** (14 since 23.11.2026, when `ai-proxy` left the file; 15 since 22.11.2026 with `claude`, which authenticates both of its callers in code; 14 since 11.10.2026: the 13 below plus **`news-proxy`**, whose feed fetch and `<img>` pictures send no JWT — it was deployed by hand with `--no-verify-jwt` and missing from the file, so the first CLI deploy would have switched it on). A function not in the file gets verification ON at every deploy. `scripts/verify-deploy-migrations.mjs` fails when a browser call without a JWT targets a function not in the file. The others: **`hevy-sync`, `health-export-webhook`, `google-tasks-sync`, `claude`, `phone-gateway`, `push-send`, `esde-sync`, `esde-media-sync`, `esde-content-sync`, `screenscraper-media`, `trakt-api`, `kobo-sync`, `shop-price`.** Every one of them authenticates with its own Bearer/custom secret (or, for `screenscraper-media`, a per-game HMAC signature) rather than a Supabase JWT (checked in-code), so leaving platform verification ON makes Supabase reject the call **before our code runs**. This is a real production gotcha, hit three times.

**Correct-in-the-repo = deployed** (the deploy secrets exist since 12.10.2026; first dry run green). Anything outside this repo — Vault secrets, dashboard switches, devices — is still a manual step below. The order inside one merge is always migrations → functions → website; when a function must be live BEFORE a migration, ship two PRs (the function first).

**Type-checking a function** (`deno check` reads the code and reports type mistakes without running it; no workflow runs it): `deno check --node-modules-dir=none --no-lock supabase/functions/<name>/index.ts` — all 31 functions pass (07.11.2026). Why the flags: the website's `package.json` at the repo root makes Deno 2 take npm packages only from the root `node_modules` folder (its "manual" mode), so an `npm:` import resolves only when the website installs that exact version. `@supabase/supabase-js@2.118.0` does today, so the plain command passes for 29 functions; `web-push` (`push-send`) and `psn-api` are never installed there, so those two fail with "Could not find a matching package", and every function would fail the day the website moves to another supabase-js. `--node-modules-dir=none` uses Deno's own package cache instead; `--no-lock` stops it writing a `deno.lock` at the root. A root `deno.json` with `"nodeModulesDir": "none"` would make the plain command work, but VS Code's Deno extension switches itself on for the whole repo when it finds one, the React code included — so there is none. Six functions still read outside JSON through one loose alias each (`AnyRecord` in `ai-proxy`, `google-tasks-sync`, `phone-gateway`; `AnyRec` in `psn-api`, `igdb-api`; `Db = any` in `trakt-api`): they pass, but the check sees less there.

| `screenscraper-media` | Streams one ScreenScraper file (image, manual PDF, video) to an `<img>`/`<video>`/link without the browser ever seeing a ScreenScraper URL: `?j=<game>&s=<system>&m=<their media token>&x=<expiry>&k=<sig>` (+`w`/`f` for a resized image, `e` for video/manual). **JWT verification OFF** (an `<img>` cannot send a header) — every request instead carries an HMAC-SHA256 signature over `jeu|system|expiry` issued by `screenscraper-sync` (key `SCREENSCRAPER_MEDIA_KEY`, else derived from the service-role key), binding ONE game on ONE system until the end of next week, so a leaked link can only fetch that game's own media for a few days. Only fixed widths (120/200/360/640/1280), whitelisted params, whitelisted content types and response headers (+ `nosniff`, a sandbox CSP, inline disposition), browser-cached only until the signature's expiry, their plain-text errors mapped to 404/503 (never echoed), one retry when they say busy, one bare redirect hop. Nothing is stored — this is what makes "Online" cost no Storage. |
