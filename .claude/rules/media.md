# Media and Trakt rules

Trakt is the online service that keeps the owner's film and series history; the app syncs with it both ways. Background: `docs/features/media.md`, API facts: `docs/trakt/REFERENCE.md`.

- TV progress has one source: `user_tv_episodes`. The `current_season`/`current_episode` cache columns are written only by their trigger (050).
- Marking an episode watched has one write path (`useMarkEpisodeWatched`, `again` = one more watch) and never overwrites an existing watch date.
- Every watch is a `media_watches` row with its own date (149). `watched_at`/`repeat_count` on episodes and movies are a cache the database keeps — new code writes watches, never the cache; a date change names the one watch it moves (`WatchPickSheet` when there are several); only the sync sets `trakt_history_id`/`source`.
- Trakt gets one play per watch change (`history_add` / `history_remove_play`); a whole item's `history_remove` only for an explicit unmark — never "remove all + re-add" for a date, never for removing a last watch.
- A done movie or episode plan is a watch (216): the database writes it (`trg_tasks_link_effects`) and 149's outbox sends it — no app or edge-function code writes a watch for a tick. Before sending a tick's add the drain checks Trakt's history for a play that day (`tickAddsOnTrakt` → `tickPlayOnTrakt`), knowing a tick's add only from the ledger `task_link_effects`, never from the payload.
- Never guess which Trakt play to remove: by its history id, or an exact-second match no remaining watch accounts for; otherwise it waits for the title to be linked. Placeholders (`source='backfill'`, unlinked) are locked in the database while Trakt is connected and its whole history isn't read yet — screens leave them (and Not watched / Remove of their title) alone and say "waits for Trakt's dates"; the read's end makes the rest ordinary watches. A link by the sync keeps an `app` watch `app`.
- A sync write never removes or re-dates a watch through the cache columns; the pull removes by play id. Whole-history reads resume through `history_cursor`, never one run's clock.
- A rewatch is `rewatch_round` + `rewatch_started_at` (Watching); an episode is done for the round once it has a watch since the start (`watches.ts`); the database ends the round from any writer, and the sync never flips it to Completed. Watching = rewatching (161): Completed → Watching starts the round in the database (any writer but the sync; a show only when its stored TMDB status is Ended/Canceled and every aired episode has a watch — stored TMDB data is never refreshed, so a running show is never guessed at), and the app starts one only through `app_start_rewatch` (`useStartRewatch`) — never its own round number.
- Removing every watch ("Not watched") asks and offers Undo; Trakt facts we rely on are in `docs/integrations/trakt.md`.
- A watch count on screen is every watch ever, read from the watch list through `watches.ts` (`watchMark` for an episode row or a movie, `rewatchTotals`/`watchCounts` for a show) — never `repeat_count` arithmetic; from 2 watches it is the neutral ×N counter (`WatchHistoryButton`) that opens the watch list, and during a round only the round's ✓ is green.
- "When watched?" is one sheet (`WatchedWhenSheet`), asked only through `useWatchedWhenPrompt`; for more than one episode use `askMany`, whose 5th option opens `SpreadWatchedSheet` — never a copy of either (`verify-watched-when`).
- Trakt is the source of truth for what it holds (watched + plays, ratings, watchlist, favorites, dropped shows, notes). App-only facts (Paused, priority, plans) stay local. When unsure whether something is only on screen or also stored: the data is one, and Trakt sees what the app shows.
- Changes reach Trakt through the outbox triggers; the sync's own writes carry `x-trakt-sync: 1` so nothing loops — counted only on a service-role request (184, `trakt_sync_writing()`): never trust a request header a browser can send.
- Lists are Trakt lists; an automatic list keeps only its rule in `media_follows`.
- The Queue is never deleted (owner, 24.11.2026; 207): it is known by its Trakt list id in `trakt_queue_lists` (written only by `trakt-api`, never by name alone); no Delete on screen, `deleteTraktList` refuses the flagged Queue, `list_delete` takes only one of the account's own lists by a strict numeric id and refuses every marked one, the database refuses deleting or changing a mark; a change of the rule is a migration. The name "Queue" is the Queue's own: only "+ Queue" (`list_create` with `queue: true`) makes it; New list and ✦ rules by that name are refused, and no ✦ rule fills it (`fill: true`, `checkFollows`). Titles leave it by the owner's hand (✕, Remove N watched) or by `sweepQueue` at each sync (every Completed film, `queueMoviesCompleted`; a failure goes to the Trakt card's last error) — never by touching watches; a rewatch is Watching, so it stays. Every way a title goes into it (`QueueButton`, `AddToListMenu`) runs `useQueueAddCheck`: a Completed film asks to start a rewatch first, Cancel adds nothing.
- The Queue's order has one save path: every move (drop, ↑ ↓, Top, Up, Down, Alt+↑/↓) is one `useReorderQueue().save` (`list_reorder`, on the shared `useOrderSave`): shown at once; moves during a save go on from the shown order and only the newest order is sent when the save in flight is done (never two calls racing); a refused save puts back the last order Trakt took; rows Trakt skipped are said (a warning, never a plain "saved"). The drag is the shared `src/shared/ui/dragReorder/` (THEME §5, `.claude/rules/ui.md`; `verify-drag-reorder`, `verify-media-queue`).
- "Coming soon" is derived from the release date, never a stored status.
- An unknown watch date is NULL for movies and the epoch for episodes; screens show "date unknown". Without TMDB data, never guess a show's status.
- The import and sync plans are GENERATED into `trakt-api` by `scripts/sync-trakt-shared.mjs`.
- Notes sync is a three-way comparison through `trakt_note_text`; an edit is never lost to a delete.
- A Trakt title with no TMDB id is matched by the owner (Settings → Subscriptions → Trakt, `TraktMatchList`), stored in `trakt_manual_matches` (200). The rows are input: `trakt-api` loads them right after `snapshot()` (`applyPicks`), keeps only a movie/show with two positive integers, fills only an id Trakt did not give, skips a pick whose TMDB id Trakt gives to another item, and a per-title history read gets the id from the used picks (`traktManualMatch.ts`, GENERATED into the function). A failed read of the table stops the run (a matched title would look gone from Trakt); a missing table means no picks. The table is not in `DB_CATALOG`: the assistant never reads or writes it. The picks are loaded before `drainOutbox` (a play removal of a matched title reads history with them, the `item_key` filter stays); `trakt_sync_state.matches_fingerprint` makes a changed set pull even when Trakt is unchanged; a refused pick is written to `trakt_unmatched` as `PICK_NOT_USED`. Never steer an outbox write with an id read from this table (changes to a matched title don't reach Trakt yet — shown on the row). Remove goes through `useRowsDelete`, a save has "Sync now · Undo" (`verify-trakt-manual-match`, `verify-db-trakt-manual-matches`).
