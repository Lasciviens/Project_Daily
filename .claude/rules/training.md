# Training rules

Background: `docs/features/training.md`.

- For training science questions, call `training-scientist`; it reads `docs/training/science.md`.
- One source per concept: bodyweight `useBodyweightSeries`, next session `useNextTrainingSession` (this week's first still to do, `sessionState.planWeek`; else `pickNextTrainingSession`), sessions per week `sessionsThisWeek`, est. 1RM `est1RM`, one coach context (`training/coach/`). Never a second formula for the same number.
- The progress engine (`progress-engine/`) is pure, versioned (`ALGORITHM_VERSION`) and runs once per page (`TrainingProgressProvider`). RPE is shown but never gates a decision — and not on "Last time" on the Next card or in the planned-session popup (owner, 27.11.2026: "dont show RPE here", the popup too; `sessionPlan.lastSets`; "Yes, RPE stays a note"); the effort note keeps its RPE wording.
- Progression (owner, 27.11.2026: "this page forces me always to go up in weight asap... It does not feel right"; "Scientific results … but not confusing"): Add weight only after 2 sessions in a row at the top of the range at one load, never after a session worse than the last (S3/S10); the step is a % of the load rounded to the equipment (S4); a smallest step over 10 % is "Almost" — reps first (top + 2 at most) or jump, both progress (S5); matching last time is on track, the line reads "Repeat 10/10/9 = good · +1 rep anywhere = progress" (S12/S14/S16); below the minimum twice after a jump, the second no better, is "Step back" with a target at the previous load (S6). One action per card, a 1–2-word pill from `actionLabel(action, metricKind)` ("Less assist" for an assisted lift); alerts follow the card's action, never a trend read; never "must", "failed" or "behind". Every screen (Next, session rows, Progress table, coach) reads the same `ExerciseProgressResult`; tones come only from `plan/actionTone.ts`.
- e1RM is shown only from sets of ≤ 10 reps (S15, `est1RM`); a high-rep set still counts for progression. A plateau needs ≥ 4 sessions and ≥ 21 days (S13); "flat" is within ±3 % (S16). Never claim a fixed e1RM error ("±10 %").
- The coach snapshot line formats are a contract with the `coach_assessment` job's instructions (`supabase/claude-src/job-coach.ts`): change them together, bump its version and regenerate (`node scripts/build-claude-function.mjs`). The assessment's decisions (rest day, deload cue, the one lift) are code (`coach/coachFacts.ts`); the model only explains them. A deload cue follows S31 (weeks without an easy week, stalled lifts, reported fatigue) — high weekly volume alone is never one (S18).
- A planned session's status comes only from `plan/sessionState.ts`; `training_skips` is written only by the two training APIs (`verify-training-session`).
- Sessions done early, late or swapped (213; owner, 27.11.2026: "Missed sessions, sessions I did but in different days.. What I actually should do"): a workout completes its OWN routine's session from 2 days before its day (S20) to 6 days after, inside that session's week (167 — the owner's rule is the outer limit; S20's ±2 only sets the early side): the session's own day first, then one already due before one ahead (a make-up workout closes the missed one), then the nearest; a swap (done on another program routine's day still to do) completes its own session 3–6 days later and leaves the other to do. One workout, one session; a session's workout is its own account's (`trg_tasks_workout_owner`). A sync writing a workout again unchanged matches nothing — old rows change only through the owner's reviewed one-off. The app's windows (`EARLY_WINDOW_DAYS`, `LATE_WINDOW_DAYS`) equal the database's — change them together (`verify-training-session`).
- One truth (owner, 27.11.2026: "One truth! Thats the rule. So if its moved it is moved! It has to stick to the real data!"): every screen reads sessions on their stored days — never a day of its own, never "moves to" on screen. Next is one rule (`plan/nextRule.ts`: a missed session still counting before today's, in the program's order — the weekly schedule's day order, S22/S23 — then by day; today's stays next all day) for the app, `phone-gateway` and `push-send` (`sync-training-next-shared.mjs`, `verify-training-next-mirror`).
- Move / Pull is the owner's tap, never automatic (owner: "It should be an option not must/night job"): the strip offers it (`shiftOffer`) when a program session's day passed undone or one was done early; ONE call (`training_shift_sessions`, SECURITY INVOKER, an advisory lock per account) moves the cycle in the data, gaps kept, never two on one day (a Pull takes the early one to its workout's day), never 7+ days from a session's first day (refused); the toast names what the database answered, with Undo (`training_shift_undo`, only rows still on the moved day holding the same workout, never onto a taken day). No scheduled job moves sessions.
- This week (`planWeek`, one `ThisWeekStrip` on Next, Log and Daily's Training card — every way in; Daily's count is the strip's); break notes only after 14 days (S27–S29). Missed or still open never takes a warn or danger tone. Today's call starts with a verb and leaves the day and time to the header. The coach's MISSED line reads the same week (`weekInputs.weekMissed`).
- A skip with a task covers only that session; an older routine-week skip (no task — none is written since 213) covers a weekly day with no task only before today (`skipForPlan`). A skip whose week is over (`weekIsOver`) offers Move, never Undo skip — the hourly job would skip it again.
- The database completes a planned session when its workout syncs (141): edge functions never close or delete training tasks.
- A training plan's day is a task on its day (156, no block): every training action splits it the 142 way first (`ensurePlanTask` → `item_occurrence`, the same task, keeping the view's routine) so the block-reading views see it; its routine is matched the app's way in SQL too (`repeat_day_routine` mirrors `matchRoutineToPlan` — change them together); a day closed as missed (`closed_reason 'missed'`) is read as a past open plan (`taskMissed`), never a skip — every view passes it (`calendarSessions.planTaskOf`); a weekly day is read with its day's task (`buildPlansByDate`'s `dayTasks`).
- A moved session is moved (166): a training task whose day changes is checked again in the database (`trg_training_task_recheck` → `training_task_recheck`: a workout that no longer fits is unlinked — the session it closed is to do again, a hand tick stays done; a workout of its OWN routine on its new day completes it; a missed day moved to today or later is to do; a repeat's day moved without its slot is split) — never a client-side relink.
- A workout represents itself (167): it completes only its own routine's session — a stand-in only where a routine is missing (the workout's or the session's), in the database and in the calendar's pairing. A session's week is its first day (`tasks.first_plan_date`, never moved) and the next six: a workout counts only inside it; skipped then done inside it → done; skipped and moved to today or later inside it → to do; moved 7+ days after its first day → skipped there and that week's session of the same plan moves instead (`training_move_past_week`); not done by its week's end → skipped on its first day ("Not done within 7 days", `training_weeks_close` in the hourly job). Never a second implementation in the browser — the Move popup only says it (`movesPastWeek`).
- A session is never planned twice on one day without asking (`plan/planTwins.ts`); "Plan it" goes through `usePlanThis` (its training step `planTraining.planRoutine` asks to move a routine's open past plan first).
- One training identity (211): an Apple Health row is a Hevy workout only by `health_workouts.hevy_workout_id`, worked out by the database (Hevy-written, or an older "Traditional Strength Training", within 2 minutes) — readers take it first (`workoutHealthMatch.appleWorkoutOfSession` / `hevySessionOfWorkout` / `isTrainingSessionRow`), so a session shows and counts once; a Watch-only workout is never linked and never closes a plan; never store or show the Watch's device name (`raw.source.name` is dropped on write).
- A routine or a workout with its exercises and sets is ONE linked request (`hevyApi.ts` → `linkedOr`: PostgREST follows 024's foreign keys), rebuilt in the order the level-by-level read gave; that read stays as the fallback, and `verify-hevy-linked-reads` compares the two field for field. Never add a level as a second request that waits for the first (owner, 16.11.2026: Training's first read took seven rounds). Reads a line needs that don't depend on the plan start while the plan loads (`NextReadsAhead`).
- The current program is explicit (`current_program_routines`), never inferred from recency.
- Hevy payloads match the OpenAPI schema exactly: omit `rep_range` instead of sending null; no `folder_id` on PUT; omit empty body-measurement fields and merge with the stored day before writing (a partial save once wiped a day).
- A free-text limitation resolves through `muscleMap.resolveMovementPattern`; a `monitor` limitation never paints a muscle.
- The body map uses the fixed `BODY_MAP_COLORS` palette (it sits on a dark stage), not theme tokens.
- An exercise GIF override is keyed by `exercise_template_id`, never by title.
- Exercise pictures: thumbnails show Hevy's `thumbnail_url` first, the GIF as fallback — one chooser, `chooseExerciseMedia` (owner, 14.10.2026). The exercise popup puts the GIF big on top and Hevy's still small below ("Picture from Hevy"); no GIF → Hevy's still on top. Reduce Motion: no autoplay — Hevy's still (or only the caption) on top with "Play animation", not repeated below. One chooser, `chooseExercisePopupPictures` (owner, 25.10.2026).
- Every Hevy endpoint, field and trap is in `docs/integrations/hevy.md`: a Hevy change adds a dated entry to its Log. Hevy's create enums live in `hevyEnums.ts`, mirrored in `hevy-api` (`verify-hevy-api`).
- Personal records stay off every screen (owner's call); the engine may still use them as evidence.
- A template's rule draws training days only from today on (`buildPlansByDate`'s `today`): a past day shows what was stored for it, never today's rule drawn back onto it — a schedule edited later would put sessions on days that never had one.
