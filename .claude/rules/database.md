# Database rules

Full background and history: `docs/backend/database.md`.

## Migrations
- Name `NNN_short_description.sql`, numbered above the highest file (`ls supabase/migrations | sort | tail -1`). `056` does not exist and `058` is a deliberate no-op — never reuse those numbers.
- A merge runs each new file once, as ONE transaction together with its row in `deploy.applied_migrations`: no top-level `BEGIN`/`COMMIT`/`ROLLBACK`/`SAVEPOINT`, nothing that can't run in a transaction (`CREATE INDEX CONCURRENTLY`, `VACUUM`). Never edit or rename a migration that ran — write a new one. The Actions log is public: no personal data in `raise` texts.
- Idempotent: `IF NOT EXISTS`, `DROP … IF EXISTS` before `CREATE TRIGGER`, the `pg_policies` guard for policies. It must survive a re-run.
- Every table: RLS on right after `CREATE TABLE`; owner policy `USING ((select auth.uid()) = user_id) WITH CHECK (…)` — `(select auth.uid())`, never bare `auth.uid()` (046); `user_id uuid NOT NULL DEFAULT auth.uid() REFERENCES auth.users(id) ON DELETE CASCADE` (the default is load-bearing — the client and the assistant insert without it); `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at` when rows change; `text CHECK (col IN (…))` instead of enum types; an index on `(user_id, <the column you filter or sort by>)`. A text bound counts every character and needs one that is not a space — `char_length(x) <= N and x ~ '\S'`, never `char_length(btrim(x))` (a megabyte of spaces around one letter passes that); an amount gets an upper bound too, not only `< 'Infinity'` (192).
- End every table-creating migration with `select public.owner_lock_apply('public.<table>');` (139).
- Every new table grants its roles in the same migration — from 30.10.2026 Supabase gives a new table no API access by itself: `service_role` gets `select, insert, update, delete` (edge functions), `authenticated` what the app does with it, `anon` nothing (owner lock); a token table grants `service_role` only. A `serial` column's sequence gets `grant usage` too (`verify-table-grants`).
- A user-authored table gets `trg_audit` (`log_audit()`) in the same migration, or a one-line reason in the header why not (bulk-synced `hevy_*`/`health_*`/`strava_*`, high-frequency append-only tables).
- An audited table is undoable from Developer → Activity (150/151, `app_undo_transaction`, through the table's own triggers): give it a single `id` primary key (a one-row-per-account settings table may use `user_id`), or Undo lists its changes as blocked. `audit_logs.seq` is the order of changes inside a save — never drop it.
- A new outbox table (a queue for an outside service) goes into `app_undo_outbox` (151) with `user_id` and `created_at default now()`, or Undo's preview won't say what it sends there. A new sync clock or outside-copy state column goes into `app_undo_bookkeeping` (or every undo of it reads "not exactly as before"); a new link to an outside copy (an event, task or note id) into `app_undo_links` (or Undo puts an old id back that names nothing there).
- `GRANT EXECUTE` on every new function. Token tables: `REVOKE ALL … FROM anon, authenticated`, no browser policy, never readable by an assistant tool.
- A trigger that inserts a row tied to a user (audit, outbox, queue) skips a user that no longer exists, or deleting the account aborts.
- Dropping a table or column: grep the hard-coded name lists first (037's audit array, 046's policy list).
- A SECURITY DEFINER helper meant for one RPC (the browser can still call it): act only on what that RPC hands it in a transaction-local setting stamped with the transaction's own `txid_current()` + `now()`, and add the setting to the read query's `watched` list (187's `app.shop_restored`, 189; `docs/backend/database.md` point 15).
- A new table pointing at `shop_items` is put back by Shop's Undo as the caller: give the browser the write it needs (INSERT for CASCADE, UPDATE of the column for SET NULL), or Delete names it in `hidden` and its rows don't come back — or give it its own restore (point 16). A new column on `shop_price_watch` / `shop_price_points` joins `shop_restore_price_history` in the same migration (188, 190), or Undo drops it.
- A new foreign key decides what a delete takes with it and what Undo brings back (`app_delete_rows`, 144, follows single-column FKs: CASCADE rows are deleted and restored, SET NULL links are restored). A rule that deletes or changes rows without a foreign key must be added to `app_delete_rows` too, or Undo misses it.
- Seeded data the owner edits is per account and keeps its source on the row (`source_facts`); its trigger derives `owner_edited` on every write (made by the owner, or facts ≠ source) and a seed writes facts only where it is false — never a flag a writer sets (191, point 17). Tell writers apart by `current_user` (`authenticated` = the owner, `service_role` = the assistant), never by what the row claims.
- Migration 195 changed `ai_usage` (a function's result columns cannot change with `create or replace`: dropped and created again, same rights, new columns at the end) and `ai_reserve` (a 14th argument, `p_caller_per_day`, counted under the same advisory lock; the old 13-argument function is dropped so the cap cannot be skipped). Both keep their refusals; `verify-db-ai-ledger` lints 194 and 195.
- `notifications` (211/212) is written only by `notify_row()` (SECURITY DEFINER, service role only — 211's `notify()` goes through it), the triggers, the nightly job and `notify_service_problem()`; the browser reads it and updates only `read_at` and `acted_at`; it never gets a URL or free-text column (the screen and the push build the words and the way from its kind: `notificationKinds.ts`, mirrored in `push-send`). A new kind changes four lists together: the `notifications_kind_check` and `notifications_shape` checks, `notification_prefs`' check, `notification_default_channel` and the registry (`verify-db-notifications`). A trigger that makes a notice from a table the browser can write acts only on the server's writes (212's follow events). `task_link_effects` is the plan-effect trigger's alone (no browser write, no audit: Undo of the tick undoes it).
- `ai_calls` (194) is written only by the service role (the `claude` function); the browser reads it — the monthly budget wall and the rate limits are worked out from it, so a forged or deleted row would move them. No write grant, no write policy and no audit trigger on it, ever; `app_delete_rows`, `app_restore_rows`, `app_undo_steps` and `app_undo_transaction` stay SECURITY INVOKER, or they would write it for the browser (`verify-db-ai-ledger`; `docs/backend/database.md` point 19).
- The learning tables (204: `ai_learn_answers`, `ai_corrections`, `ai_rules`, `ai_cases`, `ai_lessons`, `ai_job_learning`, `ai_eval_runs`, `ai_source_stats`) are written by the service role; the browser changes only `state` (column grant + `ai_learn_guard` + policy), never reads `ai_learn_answers`, `ai_cases.input` or `ai_eval_runs.batch_id`/`plan`/`claimed_at`. The guard refuses the service role turning on a rule or a note that needs the owner; keep it (`verify-db-ai-learning`).
- AI prices are code in the `claude` function, never a table — the budget wall is worked out from them, and a price row the browser could write would switch it off.
- Ask the owner before `DROP TABLE`, `DROP COLUMN`, `TRUNCATE`, removing a policy or a grant. Never `DELETE FROM` without `WHERE`. Prefer additive changes.

## Client code against the schema
- The website can meet an older schema (a failed migration, a revert): a read/write of a new column catches `42703`/`PGRST204` and retries once without it; a new table gets a missing-table guard that renders empty; a write that needs it throws a named "migration NNN not applied" error. Note the fallback's removal condition.
- Types are written by hand next to the api/hooks that use them; update every select that should return a new column.
- Mutations scope explicitly with `.eq('user_id', userId)` even with RLS; `requireUser()` gives the id from the local session. Destructure `{ data, error }` and throw on `error`.
- PostgREST returns at most 1,000 rows: page open-ended reads with `.range()` until a page comes back short.

## Cross-entity rules live in the database
- The app writes through three doors (web, the assistant's db tools, edge functions/webhooks), so a rule that must always hold is a trigger, not app code (043 `link_rules`, 077, 141, 142, 143, 149's watch cache).
- Outside calls never run in a trigger (no token there): a trigger only queues (Apple Calendar: `icloud_outbox`; Google Tasks: `google_tasks_outbox`). Google Calendar's `calendar_outbox` (135) is empty and unwritten since 208 — never queue into it again.
- A claim query with per-row ordering uses a `NOT EXISTS` anti-join inside the CTE that carries `FOR UPDATE … SKIP LOCKED` — never a window function upstream of the lock (079; check `EXPLAIN` shows `LockRows`).
- A foreign key from one user's row to another table admits ANY account's id (the check bypasses row security): a link the browser or the assistant can write gets an owner check in a trigger for every writer (210's `trg_tasks_links` → `task_link_ok`, IT011), not only in the RPC. `app_save_item` has two signatures since 210: change the save itself in `app_save_item(jsonb)`; `app_save_item(jsonb, jsonb)` only adds the link.
- An RPC scoped through `effective_user_id(p_user_id)` needs `p_user_id` at every service-role call site (a service role has no `auth.uid()`).
- A new uniqueness constraint over old data: backfill and de-duplicate first, then create the index.
- A trigger that keeps another audited table in step fires after `trg_audit` and checks the state between the tables when the transaction ends (a deferred constraint trigger) — Activity's Undo puts rows back newest first; a row it derives from a new parent is written deferred with `ON CONFLICT DO NOTHING`; an ownership check refuses with 23503, so a restore retries the row once its parent is back (192; `docs/backend/database.md` point 17).

## The assistant and cron
- The Claude assistant has no table catalogue (`ai-proxy`'s `DB_CATALOG` went in phase 5): its reads are fixed tools and `ask_database` (a read-only RPC with the owner's rights, `ai_run_read_query`); its writes are two confirmed proposals. A new table is out of its reach until a reviewed tool names it.
- pg_cron: idempotent `cron.unschedule` + `cron.schedule`; read secrets from Vault inside the job, never inline; pg_cron runs in UTC.
