# Planning, schedule, Apple Calendar and Google Tasks rules

Background: `docs/features/planning-calendar.md`.

- **Google Calendar is gone (owner, 25.11.2026: "Google calendar can be removed"; "Calendar only" — Google Tasks stays; "Leave them in Google").** Apple Calendar is the only calendar: never add a Google Calendar call, read, outbox row or event link again, and never delete or change anything in Google Calendar (208 stopped the database side; `docs/integrations/google-calendar.md` is retired). `google_target` keeps its name: `calendar` is Apple Calendar through the item's area. The retired columns (`google_calendar_event_id`, `_from`, `_horizon`) stay null; Undo never brings an old value back (`restoreResets.ts`).

- `UnifiedPlanModal` is the one Add sheet (one item, 155), drawn as the item screen ("New Item" / "Edit Item" wherever it opens): one form (`ItemForm.tsx`), one save (`useSaveItem`), one delete (`items/useSheetDelete`, the stand-in for `useDeleteItem`) — never a table write in the sheet. A new item has Add; an edit saves by itself through `useItemAutosave` — one save at a time, each later save naming the slot and task the first one answered with (never a second slot), what waits sent before closing and before a delete; a change that takes the slot away, and a new list's name being typed, wait for the screen to close (`itemScreenRules.heldChange`); a failed save before closing asks, never traps. `task`, `time-block`, `schedule-block`, `plan-block` are aliases that open it through `useEntityModal`; `PlanEntityModals.tsx` loads the item's rows by id and holds the one routing rule (a block with a `task_id` opens as its task). Log every logic change in the CHANGELOG at the top of `UnifiedPlanModal.tsx`.
- The Category is the title card's row, for every item (owner, 27.11.2026: "bring category to top on the task screen"); its add-on fields come right after it, drawn only from the registry `items/categoryDetails.ts` by `DetailsSection.tsx` — one section for every way the screen opens (owner: "Category decides how the task's add-on fields would show up. Since we use only one (I HOPE!!) task screen"); a mode may hide a field, never copy it. The thing is the task's link (`form.link` → `p_link`; × or a category / type that can't hold it sends "none"), a TMDB title added to the library only inside the save (never on pick); a cinema trip's Cinema is the item's one place (the slot's; by name in the details without one); the rest goes only as the one save's `p_details` (215), never a second write; values stay on the form across a category change and the save keeps what fits; "On" suggests only the owner's earlier values (no seeded list). `verify-item-screen` §11, `verify-item-details`.
- Nobody mounts `UnifiedPlanModal` outside `plan-modal/` (every caller opens it through `useEntityModal`; `verify-item-screen`). Inside another popup only through `itemScreenEmbed` (the training session's Edit tab: the host closes it through the handle, what waits saved first). Waiting for and Parent are rows that save through their own actions (`TaskRows.tsx`), never through the item save.
- The section follows the date (no date → Inbox, today → Today, another day → Backlog); a new item's date defaults to today or the caller's day — never undated by default (`.claude/rules/tasks.md`).
- The Calendar row (the old Google chip) shows the actual target, never "Auto" — Apple Calendar, Google Tasks, both, or Only in this app — with Apple's or Google's mark always and a red dot only when Apple doesn't have the item, its reason read from the queue's own answer for the row (`itemScreenRules.appleDot`, `useAppleItemSend` — the row named, never an address); its default and problems come only from `items/sheetRules.ts` (or the data layer's copy of the same rules, once it lands): a time or a repeat → Calendar, no time → Tasks, Both only when picked; a calendar choice in an area that is off says so ("Its area has no calendar"); a repeat on Tasks is "Google Tasks · one per day" (156: each day's task is a Google Task, never a Tasks-side repeat).
- Quick add has one parser (`items/quickAdd.ts`) and one save (`items/useQuickAdd.ts` → `useSaveItem`; Home's builds the same input) for the sheet's title, Work's quick add, the search bar's "add …" and Home's quick add; a bare number is never read; a new reading gets its cases in `verify-quick-add`.
- ✨ on the item screen (step 4) changes the form only through `itemFillForm.fillForm` (the helpers a tap uses, rows the screen shows) after the browser's own `cleanItemFill`; nothing saves by itself — an edit's autosave keeps the screen as it was before ✨ until **Use these**, and Cancel / Undo put back exactly that (`useItemFill`).
- A task and its one-off slot are independent facts. `time_blocks.task_id` is the only link; `time_blocks.source_type` is never `'task'` (it names the block's real origin). TV vocabulary differs: tasks use `tv_series`, time_blocks `tv_episode`. A training task's day/time and block move together (142).
- Calendar status is typed: `'linked' | 'not_linked' | 'unknown'` from what the server confirms (Apple: the row's `icloud_area` after the queue was sent) — never a message-string guess. `'unknown'` never deletes a Google Task copy and never creates a fallback.
- Google Tasks outbox: per-task FIFO claim (079); a delete clears `google_task_id` only if it still matches (`clear_google_task_id_if_matches`); a create checkpoints its progress in its own row's payload, never a second row; the opt-out check is never bypassed by `force_recreate`.
- `GOOGLE_SCOPES` (`calendar/googleScopes.ts`) is the one consent list — `tasks` only since 25.11.2026; never add a Calendar scope back. Every browser Google Tasks call goes through `ensureValidCalendarToken()` — never the stored token as is.
- Google Tasks → app runs only in `google-tasks-sync` (cron, Sync now, the background run): never add a second pull in the browser. Its pure rules live in `todo/api/googleTasksRules.ts` between `<google-tasks-rules>` markers, copied verbatim into the function (`verify-google-tasks`).
- Google's `due` is a date: read its date part, write midnight UTC (`googleDueToDate`/`dateToGoogleDue`) — never through a local time.
- The mirror takes Google's data as it is: two lists may share a name (145 dropped 076's index); a failing list or task is reported, never skipped silently.
- A repeating plan is ONE calendar event: its mapping only in `calendar/calendarSeries.ts` (start = the rule's first real day on or after the later of `effective_from` and the day its series starts from — `series_from`, Apple's `icloud_from`, never moved by a later write; wall-clock time + zone, EXDATE only for real occurrences — `verify-calendar-recurrence`); Apple's series is built from it (`icloudEvents.planEvent`). Every write uses the plan's own zone (`calendarSeries.planTimeZone`, 183), never the device's. A skipped day of a plan comes off Apple Calendar; Undo skip puts it back.
- Duration is 1–1440 minutes (`clampDurationMinutes`, CHECK in 080). Recurring templates start at `effective_from` (081) and never render before it. Blocks crossing midnight project onto both days (`dayAgendaProjection.ts`).
- Whether a recurring plan occurs on a day is answered only by `daily/recurrence.ts` (`occursOn` / `occurrencesBetween`; weekday layouts use `weeklyDaysOf`) — never a `days_of_week` test of its own: since 146 a plan may repeat monthly, every N days/weeks/months or on picked dates (`verify-recurrence`). On the server only by `repeat_rule_occurs_on` (160; 156's `repeat_occurs_on` and the supplement schedules call it), its SQL copy — change the two together (`verify-db-repeat-days` compares them day by day).
- A repeat's day is a task on its day (156), made only by `repeat_day_task` (the hourly job `repeat_days_run`, `app_repeat_days_today` when the app opens, a repeat's save): never a past day, never a day ahead, never with a slot (the series keeps the day: no EXDATE or extra event per day). 142's split (`item_occurrence`) reuses that task — never a second one; a training action splits it first (`ensurePlanTask`). Deleting or moving a day's task takes its day out of the repeat (triggers; Undo reverts the change itself — never a rule that puts a day back); the browser then pushes the series (`refreshSeriesSoon`). Only an untouched day (`repeat_day_untouched`: open, on its day, no slot, its day still in the repeat) follows a rule edit, a repeat's delete or a Google Tasks switch — a "This day" edit never. A day's task opens as its repeat's day (This day); a Repeat sent with a day's task is its repeat's All days, never a second repeat. A day ticked without a split gets no "✓ " on the series.
- An incomplete repeat can't be saved (`recurrenceProblem`, which runs `hasValidRecurrenceSelection` for weekly, and caps picked dates at 366); editing a recurring template never silently turns it into a one-off. The Repeat choice stays one line (a select) at every width.
- Editing a plan keeps its `effective_from`, except for a choice that counts from it (Monthly, every N): "Starts" shows and is saved (`editedRepeatStart`).
- Schedule writes invalidate the whole `schedule`/`taskGraph` groups; never give a schedule view its own private query key.
- The app's iCloud calendars (Phase 2, story in `docs/features/calendar-plan.md`): one per area at a fixed place (`calendarAreas.areaSlug`); their settings only from `calendar_prefs` through `readCalendarPrefs` (mirrored into `icloud-calendar` between `<calendar-areas>` markers, `verify-calendar-areas`) — every value is the owner's setting, never a constant. The app-specific password is stored only sealed (`ICLOUD_ENC_KEY`); `connect` needs a password sign-in in the last 10 minutes (`amr`, password entry only) and another Apple ID only after Disconnect (a stolen session must not redirect the calendars); a renewal keeps the calendars.
- An item's Apple event is built only by `areas/icloudEvents.ts` (generated into the function by `scripts/sync-icloud-shared.mjs`) and written only by the function's `drain` from `icloud_outbox` — triggers queue, never iCloud from a trigger — the new copy before the old, with If-Match (`icloud_etag`). A row stores only its area key (`icloud_area`), never an address: the address is built server-side at the moment of use (`ownEventUrl`; the warning in `AGENTS.md`). No assistant tool writes an `icloud_*` column (a confirmed proposal's columns are fixed). Every write and remove reads the event first and goes only over the version read; an event with invitees is never rewritten or removed (iCloud would email them); an item's failure shows on the iCloud card (`notSent`).
- Per area, in use or off (`onApple` = in use; the saved `app` key is not read since 208): an item in an area in use goes to its Apple calendar, one in an area that is off is only in the app (an event made earlier stays); its save sends the queue and confirms by `icloud_area` (`settleItemApple`) before a Google Task goes; its line says "sending to Apple Calendar", never that it is there. The save names its rows (`drain`'s `items`, browser input: 1–3 distinct rows, each an allow-listed kind and a strict uuid, else 400; the item last, what goes away first — `appleRowsOf`): they only pick which of the caller's own queued rows go first — never an address, calendar or area — within the run's 25 rows and lease, a row in backoff at most every 10 s (`itemRowMayGo`); a save's run sends the backlog for 8 s at most. A failure in the app's own code says so (`sendFailureText`, `stepFailureText`), never "iCloud did not answer"; a warning is one short line for 8 s, a retry promised only where one helps (`appleSendRules`). `drainStep`: put; keep an Apple copy while its area is off or its Google Task isn't there yet; else remove — never a Google Calendar hand-over (gone with `icloud_hand_over`, 208). A skipped day of a repeat is off Apple (a missed day stays).
- Apple → app only in the drain's read-back (176/177), before anything is sent: only the app's own events (file name + exact server-built address + uid) through `apply_icloud_readback`. An iPhone change counts when stamped `LAST-MODIFIED` or a version the app didn't write, unless the app's own change of the item waits (`icloud_outbox.changed_at`, never `requested_at`); a deletion lets go, never deletes; the token moves only when every change was handled. Limits: a repeat's days from today, ≤ 31; a one-off within a year; > 20 removals of still-linked events never applied.
- The invite test (209, Settings → Subscriptions, a one-off): its one event's UID and file are fixed constants in the Personal area calendar from `area_calendars` (`inviteEventUrl`), its organizer read from iCloud's `calendar-user-address-set` at the moment of use, its guests allow-listed and every line under `inviteGuard`; Send / Rewrite / Remove guest need a password sign-in in the last 10 minutes (`connect`'s check) and are reserved by `icloud_invite_test_reserve` (5 a day) before the PUT; Rewrite / Remove guest only over the ETag the card showed; nothing but Delete after 31.12.2026. It never joins the queue, the read-back or the item rules; the drain's INVITED guard stays (`verify-icloud-invite-test`).
- A Hevy workout's event (179, Training calendar) is named only by `hevy_workouts.icloud_key` (a uuid from Hevy's id), never Hevy's id itself; a workout shown by its planned session's event gets none of its own; it is never read back. An item's area comes from its category and origin (`itemArea`, six areas with Games) — the Add sheet's chip asks the same rule with the same inputs.
- What the read-back applies is not queued back (`app.icloud_readback`); a trigger rule that decides something of its own inside it turns that flag off for its own writes and back on after (177 D), so its answer reaches Apple.
- An event's look comes only from the settings (2b-3a): no alert ("None", or a Default whose area has none) writes Apple's no-alert marker (`icloudEvents.NO_ALERT`) on every event, never an empty alert list (iCloud and the iPhone add the account's default to an event with no `VALARM`; `verify-icloud-events` sweeps every builder); the read-back leaves out a default-marked alarm (`X-APPLE-DEFAULT-ALARM:TRUE`), never the item's own alert; a settings change re-queues the events it alters as a re-send (`app.icloud_look` keeps `changed_at`), never as a change of the item. Undo resets the Apple link and the retired Google one (`restoreResets.BLOCK_EVENT_RESET`, `SERIES_EVENT_RESET`). Across features: `verify-db-icloud-cross`.
- One item (155): the choice is stored per item (`google_target`; NULL = an old row, read as where it IS, `itemRules.presentGoogleTarget` — never a default, so a save never moves an old item by itself). The item rules live once, in `items/itemRules.ts` (`sheetRules.ts` re-exports them) — never a second implementation.
- A Google Task's list is a row (`OptionsSection.GoogleListRow`: the Google lists and New list…); a task's labels are `LabelsRow` (Headless UI Combobox, no box, Enter adds), shown only for a task — never a repeat's rule.
- "All-day" on the item screen is no time and no length; an item on a calendar stays there as an all-day event (`planForm.withAllDaySwitch` → `withAllDay`) — never a stored flag of its own.
- Starts / Ends are drawn from the stored day, start and length (`itemScreenRules`): an end picked there becomes the length — the next day too, at most 24 hours (080); one before the start or longer is held (`badEnd`) and nothing saves. Moving the start keeps the length.
- The screen's look on a phone (owner, 27.11.2026: "Real visual issues as you can see.. Work until it is perfect! Things dont stand where they have to, either not fitting or scaling issues. Also flaws like attached screenshot"): nothing cut, overlapping, covered (the marks' peeking banner excepted: it peeks by design) or outside the screen at 375, 402, 430, sideways and on the laptop, at Display scale 80, 100 and 125 % (THEME §3) — `scripts/audit-item-screen.mjs` measures it on the harness, `verify-item-screen` §12 keeps its rules. A length that must match rows is measured, never a pixel constant (the time wheel's rows: `wheelGeometry`); a Starts / Ends pill grows for its text; a timeline hour label shows only whole, its tick with it; a field's list on this screen is a `FieldOptions` (under its field, sized above the keyboard — the field scrolled up first when three rows don't fit — never into the status bar); every typed field takes `typingHints` (iOS guesses contact fields from a field's attributes and words — untested on a device) and a placeholder that fits.
- Every choice on the item screen is the shared field list (owner, 28.11.2026, of the Show / Movie search's list: "I almodt want everything to use that type dropdown.. We will do that an other time for now apply that to all dropdowns in task screen."): a row whose value is one of a list is a `SelectRow` (`FieldSelect` — Category, Travel Time, Alert, Second Alert, Calendar, List, Time Zone, End Repeat), a choice inside an editor a `SelectChip` (Repeat's kind and unit, Currency), a search's matches `FieldOptions` (the thing, On, With, Location / Cinema, Labels, Parent) — never a list of its own in the group, a raw Headless UI list or a native select (`verify-item-screen` §13; THEME §8 makes it the app-wide default).
- A show's episode is filled with its next one by default (owner, 28.11.2026: "when I select the tv serie it should by default bring next episode"): only from `useNextEpisode` (the app's one rule), only when `items/episodeDefault` says it is one (not all watched, aired, TMDB's data there), once per show and only while no episode is set; one the owner clears stays cleared (for a saved item too, remembered per item and show, cleared at sign-out). It saves like a picked episode: the plan becomes that episode's plan — an edit's autosave sends it as the screen opens.
- Each row's mark says where its field goes only through `itemScreenRules.fieldGoes`, shown while `calendar_prefs.prefs.showMarks` is on (`readCalendarSettings`; outside the `<calendar-areas>` block, so the server's copy never sees it). Inside a titled card the marks are its banner (`Section` → `FieldMark.CardBanner`: each place once, tucked behind the card's top-right after its heading in the DOM, adding no height, motion only under `useMotion()`; a tap names the rows, `cardMarksText`); the untitled title card passes its mark to the next card (`marksTo` → `carried`) — only a mark that is the row's value (the Calendar row's, its red dot) stays in the row.
- An item's place (186: `time_blocks.place`, `schedule_blocks.place`, `{name, locality?, lat?, lon?, id?}`) comes from EnTur's search (`useStopSearch`), Home/Work or typed text, only through `items/itemPlace` — the sheet sends it through `cleanPlace`, whose answer `place_ok` always takes (`isStorablePlace` = its rule; `verify-item-places`). An edit sends it only when the sheet knew it or the owner changed it — never a null over a place it wasn't told about. Writers read it through `calendarEventRules.eventPlace`; Apple's pin only through `icloudEvents.locationLines` (allow-listed parameters, exact-shape guard). A day split off a plan takes the plan's (`'{}'` = not given; an explicit null stays); a one-off turned into a repeat (or back) keeps its own.
- An item's calendar fields (193: `alerts`, `show_as`, `url`, `travel_minutes` on `time_blocks` and `schedule_blocks`; `repeat_until` / `repeat_count` on a repeat) are input: each column has a CHECK (`item_alerts_ok`, `item_url_ok`, the lists), the save checks the same and refuses with a message, the writers read a row only through `calendarEventRules.eventAlerts` / `eventShowAs` / `eventUrl` / `eventTravel`, and Apple's lines keep their last guards (`ITEM_TRIGGERS`, the travel line, `ITEM_URL`, the `RRULE` shape) — an allow-list, never escaping alone. The lists live once in `calendarEventRules.ts` and match 193's SQL (`verify-db-item-calendar-fields`); the sheet sends a link only through `itemCalendarFields.cleanItemUrl` and a field only when it knew it or the owner changed it (`calendarTouched`). With a count the database keeps `repeat_until` at the Nth day (`repeat_count_end` = `recurrence.countEndDay`, change the two together); no day of a repeat after its end, in `occursOn` and `repeat_occurs_on` alike. A read-back takes a field only when the event differs from what the app writes now (`fieldsChangeOf`), Show As only for an item whose Show As is set, and never a repeat's End Repeat.
- The screen's rows for them (step 2: `CalendarFieldRows.tsx`, `EndRepeatRows.tsx`) show only where a slot or a repeat keeps them (`itemScreenRules.screenParts().slotFields`, the Location row's rule; End Repeat only under a repeat, never "This day"); every choice comes from `itemCalendarFields` and changes the form only through `withCalendarField`; a link that isn't https or an End Repeat that can't be saved stops Add and the autosave and says why (`urlProblem`, `repeatEndIssue` — the database refuses the same). The URL row opens only `itemScreenRules.openableUrl` (cleaned, then `eventUrl`: a link may come from the iPhone), after showing its address (the host first), in one anchor with `rel="noopener noreferrer"` and no referrer — never a link built or opened from the raw text (`verify-item-screen`).
- An item's times are a wall clock in its own zone (183: `time_blocks.time_zone`, `schedule_blocks.time_zone`; none = Europe/Oslo). The sheet saves the zone it shows (a new item's the phone's, a saved one's its own, or one picked with the chip); a writer that leaves the column out (default `''`) gets the plan's for a day split off it, else the request's `x-time-zone`; an explicit null stays null (Undo) — never re-zone an item by itself. Every calendar writer uses `itemTimeZone` / `planTimeZone` (never the device's zone at write time, never a stored value unchecked: it lands in TZID lines); the read-back reads a change on the item's clock. `x-time-zone` goes to the data API only (edge functions' CORS lists fixed headers).
- An item moving between Google Tasks and Apple Calendar: the new copy first, confirmed, then the old one goes (`calendar/api/itemCalendar.settleItemGoogle` → `settleItemApple`); `'unknown'` removes nothing. `app_save_item` never turns Google Tasks off for a move to Calendar (the browser does, after `'linked'`) and keeps a slot whose calendar presence must go (`blockToDrop`; dropped at once when no calendar holds it).
- A slot's event is built only by `calendarEventRules.blockEventBody` (all-day for no time, Free for no length, "✓ " when its task is done; generated into `icloud-calendar` with `icloudEvents.ts`); a repeat with no time is an all-day series (`VALUE=DATE` lines). Writes read the row as it is, never the caller's copy; a change made on the server reaches Apple through `icloud_outbox` (its triggers), never a call from a trigger.
