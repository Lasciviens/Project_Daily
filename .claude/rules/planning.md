# Planning, schedule and Google rules

Background: `docs/features/planning-calendar.md`.

- `UnifiedPlanModal` is the one Add sheet (one item, 155): one form (`ItemForm.tsx`), one save (`useSaveItem`), one delete (`items/useSheetDelete`, the stand-in for `useDeleteItem`) — never a table write in the sheet. `task`, `time-block`, `schedule-block`, `plan-block` are aliases that open it through `useEntityModal`; `PlanEntityModals.tsx` loads the item's rows by id and holds the one routing rule (a block with a `task_id` opens as its task). Log every logic change in the CHANGELOG at the top of `UnifiedPlanModal.tsx`.
- The section follows the date (no date → Inbox, today → Today, another day → Backlog); a new item's date defaults to today or the caller's day — never undated by default (`.claude/rules/tasks.md`).
- The Google chip shows the actual target, never "Auto"; its default and problems come only from `items/sheetRules.ts` (or the data layer's copy of the same rules, once it lands): a time or a repeat → Calendar, no time → Tasks, Both only when picked and with "Shows twice in Google Calendar"; a repeat on Tasks is "Google Tasks · one per day" (156: each day's task is a Google Task, never a Tasks-side repeat).
- Quick add has one parser (`items/quickAdd.ts`) for the sheet's title and Home's quick add; a bare number is never read; a new reading gets its cases in `verify-quick-add`.
- A task and its one-off slot are independent facts. `time_blocks.task_id` is the only link; `time_blocks.source_type` is never `'task'` (it names the block's real origin). TV vocabulary differs: tasks use `tv_series`, time_blocks `tv_episode`. A training task's day/time and block move together (142).
- Calendar status is typed: `'linked' | 'not_linked' | 'unknown'` from the real HTTP status (`isCalendarNotFound` accepts 404 and 410) — never a message-string guess. `'unknown'` never deletes a Google Task copy and never creates a fallback.
- One task = one Google entry: a task linked to a Calendar event skips Google Tasks. Don't simplify away `skipGoogleTasks` in `useTodos.ts`; apply the dedupe only after the Calendar link is confirmed.
- Google Tasks outbox: per-task FIFO claim (079); a delete clears `google_task_id` only if it still matches (`clear_google_task_id_if_matches`); a create checkpoints its progress in its own row's payload, never a second row; the opt-out check is never bypassed by `force_recreate`.
- `GOOGLE_SCOPES` (`calendar/googleScopes.ts`) is the one consent list. Calendar writes and every browser Google Tasks call go through `ensureValidCalendarToken()` — never the stored token as is.
- Google Tasks → app runs only in `google-tasks-sync` (cron, Sync now, the background run): never add a second pull in the browser. Its pure rules live in `todo/api/googleTasksRules.ts` between `<google-tasks-rules>` markers, copied verbatim into the function (`verify-google-tasks`).
- Google's `due` is a date: read its date part, write midnight UTC (`googleDueToDate`/`dateToGoogleDue`) — never through a local time.
- The mirror takes Google's data as it is: two lists may share a name (145 dropped 076's index); a failing list or task is reported, never skipped silently.
- Every linked Calendar event lives in `'primary'` — a slot's and a repeating plan's series (147); a path that links another calendar must store it on `time_blocks` / `schedule_blocks` and in both outbox triggers (135, 147) (`verify-calendar-outbox`).
- A repeating plan is ONE Google event: its mapping only in `calendar/calendarSeries.ts` (start = the rule's first real day on or after the later of `effective_from` and the day it was added to Google — `google_calendar_from`, 148, stored with the link and never moved by a later push; wall-clock time + zone, EXDATE only for real occurrences — `verify-calendar-recurrence`), its calls only in `calendar/api/scheduleSeriesCalendar.ts` through the schedule save/delete hooks and Settings' "Add plans to Calendar" (`addPlansToCalendar` → `linkScheduleSeries`, never a second copy). The agenda de-dupes a linked event by its id and by `recurringEventId`.
- A plan's link is written only while it has no series or this one and cleared only while it still names this one. Background pushes keep the series' stored zone (only a planner save may change it). A day of a plan carried to Google (142) runs after the plan's own writes, never awaited; its own event is made only once Google took the EXDATE, else it goes on the retry list (`SERIES_PENDING_KEY`, cleared on sign-out). A skipped day of a plan comes off Google; Undo skip puts it back.
- Duration is 1–1440 minutes (`clampDurationMinutes`, CHECK in 080). Recurring templates start at `effective_from` (081) and never render before it. Blocks crossing midnight project onto both days (`dayAgendaProjection.ts`).
- Whether a recurring plan occurs on a day is answered only by `daily/recurrence.ts` (`occursOn` / `occurrencesBetween`; weekday layouts use `weeklyDaysOf`) — never a `days_of_week` test of its own: since 146 a plan may repeat monthly, every N days/weeks/months or on picked dates (`verify-recurrence`). On the server only by `repeat_occurs_on` (156), its SQL copy — change the two together (`verify-db-repeat-days` compares them day by day).
- A repeat's day is a task on its day (156), made only by `repeat_day_task` (the hourly job `repeat_days_run`, `app_repeat_days_today` when the app opens, a repeat's save): never a past day, never a day ahead, never with a slot (the series keeps the day: no EXDATE or extra event per day). 142's split (`item_occurrence`) reuses that task — never a second one; a training action splits it first (`ensurePlanTask`). Deleting or moving a day's task takes its day out of the repeat (triggers; Undo reverts the change itself — never a rule that puts a day back); the browser then pushes the series (`refreshSeriesSoon`). Only an untouched day (`repeat_day_untouched`: open, on its day, no slot, its day still in the repeat) follows a rule edit, a repeat's delete or a Google switch — a "This day" edit never. A day's task opens as its repeat's day (This day); a Repeat sent with a day's task is its repeat's All days, never a second repeat. A day ticked without a split gets no "✓ " on the series (an instance PATCH isn't confirmed in `docs/integrations/google-calendar.md`).
- An incomplete repeat can't be saved (`recurrenceProblem`, which runs `hasValidRecurrenceSelection` for weekly, and caps picked dates at 366); editing a recurring template never silently turns it into a one-off. The Repeat choice stays one line (a select) at every width.
- Editing a plan keeps its `effective_from`, except for a choice that counts from it (Monthly, every N): "Starts" shows and is saved (`editedRepeatStart`).
- Schedule writes invalidate the whole `schedule`/`taskGraph` groups; never give a schedule view its own private query key.
- One item (155) — Google: the Google choice is stored per item (`google_target`; NULL = an old row, read as where it IS, `itemRules.presentGoogleTarget` — never a default, so a save never moves an old item on Google by itself). The item rules live once, in `items/itemRules.ts` (`sheetRules.ts` re-exports them) — never a second implementation.
- An item moving between Google Tasks and Calendar: the new copy first, confirmed, then the old one goes (`calendar/api/itemCalendar.settleItemGoogle`); `'unknown'` removes nothing. `app_save_item` never turns Google Tasks off for a move to Calendar (the browser does, after `'linked'`) and keeps a slot whose event must go (`blockToDrop`).
- A slot's event is built only by `calendarEventRules.blockEventBody` (all-day for no time, Free for no length, "✓ " when its task is done), hand-mirrored into `google-tasks-sync` between `<calendar-event-rules>` markers (`verify-calendar-event-rules`); a repeat with no time is an all-day series (`VALUE=DATE` lines). Pushes read the row as it is, never the caller's copy.
- A server-side change to a linked slot or plan reaches Google through `calendar_outbox`'s `upsert` (155): never call Google from a trigger; a delete wins over a waiting upsert; a drain removes a row only while `requested_at` is what it read. Writes that come FROM Google (the read-back) set `app.calendar_readback` so nothing is sent back.
- Google Calendar → app runs only in `google-tasks-sync`'s read-back (sync token, `apply_calendar_readback`): only ids a slot or plan stores; a deletion turns the Calendar presence off, never deletes or cancels the item; the first run and the run after a 410 are baselines; the token moves only when every change applied. A day held by a moved instance of its series (`<seriesId>_…` on its slot) never gets an EXDATE (`keepDays`). The read-back runs BEFORE the outbox drain; it deletes a slot only under `app_item_drop_block`'s guard (not a split-off day, the task's due is that day). A done / reopen push sends the title only (`eventPatchFor(…, 'title')`, outbox `fields: 'title'`) — never a day or time.
