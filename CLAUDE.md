## Session Workflow

Runs on **Claude Code on the web** (claude.ai/code). Container clones repo fresh each session — git is the only memory.

```
1. User describes task
2. Claude branches: claude/<descriptive-name>
3. Code → npm run build → commit → push → draft PR
4. User marks ready → merges → GitHub Actions auto-deploys (~1 min)
```

- Never push directly to `main`
- Update this file when features complete or architecture changes
- **Small data migrations/inputs**: the in-app AI (Ask AI panel) has a generic DB layer (`db_query/insert/update/delete`, see AI section). For small one-off data loads (seed rows, backlog items, bulk inserts) just hand it a JSON or SQL-ish spec in chat — it inserts the rows — instead of writing a migration. Reserve SQL migrations for schema changes.
- **Direct Supabase data access (curl/REST with the user's own credentials) is opt-in per request** — only query/inspect live production data when the user explicitly asks for it in that turn (e.g. "check the DB", "look at my data"). Never do this proactively/unprompted, even mid-investigation of a bug — it's the user's personal data.
- **No unit-test framework exists in this repo** (`package.json` ships only `@playwright/test`). Logic verification ships as a throwaway `scripts/*.cjs|.mjs` run through `sucrase` against the real modules — precedent: `scripts/verify-health-source-resolver.cjs` (25 assertions), `scripts/generate-matvaretabellen-seed.mjs`. **Do not introduce vitest/jest as a side effect of an unrelated change.**
- **Dev-server gotcha:** an old vite process holding `:5173` serves a STALE Tailwind config (new plugins silently missing). Kill all vite processes; don't trust the port.

**Live URLs:** App: `https://lasciviens.github.io/Project_Daily/#/login` · Repo: `https://github.com/Lasciviens/Project_Daily`

## Communication Style (per user request)

The user is learning software engineering terminology as we go (comes from a SAP/ABAP background). When describing what was done, **use the correct technical term and add a short parenthetical explaining what it means** — e.g. "yeni bir **hook** yazdım (component'ler arası paylaşılan, tekrar kullanılabilir mantık — SAP'deki bir class method'una en yakın karşılık)" instead of just describing it in plain words with no term attached. Do this consistently, not just when explicitly asked — it's meant to build vocabulary over many sessions. Don't overdo it into a glossary dump; one clear parenthetical per term, only for terms actually used that turn.

Also: don't narrate routine PR housekeeping (subscribing to PR activity, "checking CI status", "no comments yet") — the user checks PRs themselves and considers this noise. Only speak up about a PR when there's something requiring their input or a genuinely notable outcome (merged, a real CI failure, a review comment needing a decision).

## Platform & Shell

**PWA / service worker (real bug, fixed):** `vite-plugin-pwa`'s `registerType: 'autoUpdate'` does NOT auto-update the way the name implies — the auto-injected `registerSW.js` is a bare `navigator.serviceWorker.register(...)` with no update-detection logic. A new service worker installs but sits **waiting** until every open tab is fully closed; a hard refresh does NOT activate it, because a hard refresh bypasses the HTTP cache, not an already-controlling service worker. A shipped fix was invisible to the user even after a successful deploy + hard refresh. Fixed: `vite.config.ts` sets `injectRegister: false` + `workbox: { skipWaiting: true, clientsClaim: true }`, and `src/main.tsx` calls `registerSW({ immediate: true })` from `virtual:pwa-register` (types in `src/vite-env.d.ts`) — checks for updates immediately (and periodically) and reloads automatically, so deploys actually reach the browser.

**Mobile app-shell** (each bullet is a device-verified gotcha):
- **The document NEVER scrolls** — `html/body/#root` are fixed-height (index.css) and `<main>` (layout.tsx) is THE scroll container. This is what made custom pull-to-refresh reliable on a real iPhone: with the document as scroller, iOS decides gesture ownership on the FIRST touchmove — one uncancelled move commits the root rubber-band and flips `e.cancelable` false for the rest of the gesture, so the pull only worked when the first move happened to be cleanly downward.
- `usePullToRefresh` has a slop + axis-lock state machine (horizontal swipes on snap strips are never hijacked; pull distance re-anchors at commit) and an `isReady` state (indicator flips to solid accent = "release to refresh").
- Route changes reset `main.scrollTop` (useLayoutEffect in Layout, pre-paint so view-transition snapshots start at top).
- **Tab navigation slides directionally:** BottomTabBar passes `forward`/`back` (tab order) → `useViewTransitionNav` stamps `data-vt-dir` on `<html>` → slide keyframes in index.css; header/tab-bar have their own `view-transition-name` so the bars stay put while content slides.
- **View Transitions don't exist on pre-18 iOS Safari** — there, Layout keys the Outlet wrapper by pathname and plays a `.page-in` rise (universal fallback, else navigation is INSTANT = "animations aren't there" on the primary device); with VT support the key stays constant (no double animation). That wrapper is `h-full` ONLY on /daily|/shop|/recipes — everywhere else it must stay auto-height or tall pages overflow the fixed box and swallow main's bottom padding (last card pinned under the tab bar; real regression, caught by E2E).
- **ALL view-transition CSS lives OUTSIDE `@layer`** — same Tailwind purge gotcha as the recharts rules; the original crossfade rule inside `@layer base` was silently purged from every build.
- `.stagger-in` (mobile-only ≤639px) cascades a container's children in with 30ms-stepped delays — HomePage columns, TodaySummary grid, MediaPage main column.
- **BottomTabBar is a floating glass capsule** (left-3 right-3, rounded-[26px], safe-area offset, active icon in an accent chip) — `<main>` reserves `pb-[calc(5.5rem+env(safe-area-inset-bottom))]`.
- **`.glass-chrome`** (index.css, `@layer components` — safe there because the class name appears in source, unlike runtime-only selectors) gives the fixed header + tab bar iOS "liquid glass": translucent `cream-50/0.62` + `backdrop-filter: blur(20px) saturate(180%)` (the saturate is what reads as real glass, not a plain blur) + an inset top hairline; theme-aware dark override + an `@supports not` near-opaque fallback. **Write only the standard `backdrop-filter`** — autoprefixer emits the `-webkit-` Safari needs; hand-writing both made the minifier drop the standard one. The glass frosts because `<main>` scrolls BEHIND the fixed chrome.
- **iOS input auto-zoom is disabled app-wide** (real bug: tapping the AI chat box zoomed the page and the zoom stuck after blur, misaligning the frame — iOS zooms whenever a focused text control's font-size is <16px): `maximum-scale=1` in the viewport meta (pinch-zoom still works — iOS ignores max-scale for pinch since iOS 10) + a `@media (pointer: coarse)` rule forcing all text-entry controls to `font-size: 16px !important`. This removes the trigger itself — never "fix" this per-field.
- Header gains a shadow once `main.scrollTop > 8`; AIPanel's mobile sheet has a grab handle + `rounded-t-3xl`. Touch polish: `-webkit-tap-highlight-color: transparent` + `touch-action: manipulation`, `:active` scale in `.btn-*`/`.card-interactive`, `animate-tabPop` on the active tab.
- iOS PWA is edge-to-edge (`black-translucent` status bar + safe-area top padding on the header); `theme-color`/manifest colors match the cream design. Pages sizing to the viewport use `min-h-full` — never `min-h-[calc(100vh-56px)]`.
- **CommandBar (⌘K) has a mobile trigger**: the header Search button is icon-only (🔍) below `md` (was `hidden md:flex` — the palette was unreachable on phones since ⌘K can't be typed).

**iOS platform limits — hard constraints for anything "while the app is closed"** (full rationale: `docs/iphone-web-integration.md`):
- **No background execution at all.** PWAs get no Background/Periodic Sync; Shortcuts has no daemon. Unattended runs need a trigger (time/location/NFC) and **iOS forces a visible banner on every auto-run automation**. Server→phone delivery must go through Web Push.
- **iOS Web Push:** home-screen-**installed PWA only** (never a Safari tab), iOS 16.4+, direct-tap permission grant, and **every push must display a visible notification** (no silent data push). Delivery is best-effort and may be minutes late.
- **Web Share Target is unsupported on iOS** — "share a photo into the app to log it" would need a native Share Extension (a real App Store app).
- **Scriptable widgets:** refresh budget ≈40–70/day, ≥5 min apart, iOS decides the real cadence; a **Small widget has ONE tap target** and cannot run code in place — a tap opens a deep link (the `HizliLog` runner pattern).

(There is no `PersonalTabs` component and no in-header tab bar on /daily.)

**Password reset (real bug, fixed):** the app had no recovery flow — Supabase's reset email redirected back with a recovery token, but nothing read it or showed a "set new password" form, so the link silently did nothing (a very common gap — see the `gotrue-js`/`auth-js` issues about apps not handling `PASSWORD_RECOVERY`). Fixed: LoginPage's "Forgot password?" → `requestPasswordReset()` (`security/supabaseClient.ts`) calls `supabase.auth.resetPasswordForEmail(email, { redirectTo })` pointing at `#/reset-password`; `ResetPasswordPage` listens for the `PASSWORD_RECOVERY` auth event (plus a session-check fallback in case the event fires before the listener attaches). **One-time manual step:** the redirect URL (GitHub Pages URL + `http://localhost:5173/#/reset-password`) must be added to Supabase Dashboard → Authentication → URL Configuration → Redirect URLs, or Supabase silently refuses to send the token.

- **Cancel** (⊘, `ToDoItem`/`WorkTaskCard`) sets `status='cancelled'` — `TaskStatus` always had the value but no UI ever set it; distinct from Delete (keeps a record instead of destroying the row). `DayView` has a "Cancelled" section (same 24h window as "Done") so a cancelled task stays visible; the Work board has no cancelled column, so there it simply drops off (matches the "cancelled excluded from active counts" convention used everywhere — WeekWidget/MonthWidget/HomePage/…).
- **`ToDoItem`'s desktop action row (✎/↳/📋/⊘/✕) and the checkbox both silently no-opped into opening the edit modal instead — a real bug in `useSwipeToReveal.ts`, not in `ToDoItem` itself.** `onPointerDown` called `e.currentTarget.setPointerCapture(e.pointerId)` **unconditionally**, on every pointerdown anywhere inside the row — including one that started on a nested interactive child (pointerdown bubbles up regardless of which descendant it began on). Once a pointer is captured, the browser retargets that pointer's subsequent `pointerup` **and the `click` it synthesizes** to the CAPTURING element (the row), never wherever the pointer physically is — so a plain tap on the checkbox or any of the five action buttons fired the ROW's own `onClick` (open edit) instead of the button's own handler: the checkbox never toggled, Delete never deleted, Cancel/Reopen never updated status, and every action looked identical from the outside ("everything opens edit"). The mobile `⋯` menu was unaffected because Headless UI's `MenuItems` portals outside the row's DOM subtree, so its clicks never bubble through this handler at all — this made the bug desktop-only, exactly where it was reported. Fixed by deferring `setPointerCapture` out of `onPointerDown` and into `onPointerMove`, firing only once a genuine horizontal swipe is confirmed (`axisLocked.current === 'x'`) — a plain tap never moves enough to reach that branch, so its click reaches its real target untouched; only an actual swipe gesture (which still needs capture to survive the pointer leaving the row's bounds mid-gesture) ever captures the pointer. `ToDoItem` itself also gained local `handleDelete`/`handleToggle`/`handleCancel`/`handleReopen` wrappers (toast on failure, silent on success except Delete's "Deleted ✓") — the shared hooks (`useDeleteTask`/`useToggleTask`/`useUpdateTask`) stay bare on purpose (see the Toast feedback migration rule below: `UnifiedPlanModal.handleDelete` already wraps the same hooks in its own toast block, so a hook-level fix would have double-toasted that path).
- **The `section` day-leak (real bug, fixed on the READ side only).** `useDayData` maps a whole RANGE of day-offsets onto ONE `section` value (+2…+7 → `this_week`, everything else → `backlog`), and `fetchTasksForDay`'s non-today arm carried `due_date.is.null` — so **one** undated `this_week` row rendered on all six of those days, and **one** undated `backlog` row claimed yesterday *and* every far-future day. The entire fix is one clause: only `section === 'today'` keeps `due_date.is.null,due_date.lte.X` (an undated row parked in Today IS today's work, and an open overdue task must still surface there); every other day view is now `due_date.eq.X` exactly. **No row was rewritten and `section` was not dropped** — a drop is a 4-unit break (`037`'s audit list, `046`'s policy list, `DB_CATALOG`) for zero gain, and **both backfills are verifiably worse than nothing**: `→'backlog'` relocates rows onto an unbounded date range (the same bug, wider), `→due_date=today` manufactures deadlines that go **red tomorrow** out of rows that were never deadlines. Nothing lost its home: undated rows still reach `fetchAllTasks` → `TasksPanel`'s "No date" group, and undated `this_week` rows still reach `fetchTasksByWeek`'s untouched section arm → `DayView`'s "This week — no date" band. `TaskTab`'s `SECTIONS` also dropped the `Tomorrow`/`This Week` pills (neither has a home of its own — picking one only made a task float like Backlog under a date-shaped name; a row already holding one keeps a "(legacy)" pill so the value stays visible and one tap moves it off). **`planForm.ts`'s `section: 'today'` default must NOT be changed** — four server-side `section.eq.today` predicates (`phone-gateway` ×2, `push-send`, `ai-proxy`) drain silently if it becomes `'inbox'`, quietening the brief and the lock-screen push forever.

### Wishes Feature Detail

`/#/wishes` → `WishesPage` (`src/features/wishes/`). A **wish** is something you want to do, or a place you want to go — "go to the hytte this winter", "things to do in Polatlı" — carrying a **reminder period**. The period decides only when the app brings the wish up first; **it is never a deadline and never a visibility rule, so a wish is never late** (see Coding Rules → `NEVER_HIDES`).

- **Its own table — `wish_items`** (migration `069`: owner-only RLS, `trg_audit`, `trg_wish_items_updated_at → update_updated_at()`, `(user_id, period_start)` index): title, notes, `kind` `thing|place`, `period_start`/`period_end`, `period_label` (the user's own word for the window), `city`/`country`/`url` (meaningful when `kind='place'` — the same one-table variant shape `shop_items` uses for its own), `priority`, `status` `idea|planned|done|dropped`, `promoted_task_id`, `sort_order`. Periods are **concrete dates**: no MM-DD, no season enum (a 5-value CHECK can't say "*this* spring, Italy", its `'anytime'` default IS a junk drawer, and CHECK values are duplicated into `ai-proxy`'s catalog string → a redeploy per new period word), and **no generated `is_open` column ever** — `CURRENT_DATE` is STABLE, not IMMUTABLE, so Postgres rejects it in a generation expression. Migration 069 **updates not one existing row**.
- **Not `tasks`:** every one of the five `section` values leaks. An undated row matches `fetchTasksForDay`'s `due_date.is.null` arm and `fetchTasksByWeek`'s unbounded `.eq('section','this_week')` arm, and four server-side `section.eq.today` predicates would put "hytte this winter" on the **lock screen in July**. The obvious repair — a `kind` discriminator filtered OUT of those queries — is forbidden twice: it removes rows (`NEVER_HIDES`), and `ai-proxy`'s `db_query` composes **model-supplied** filters over `select('*')`, so no server-side code can enforce it anyway. **Not `shop_items`:** `category_id` is `NOT NULL` and Daily's `ShopCard` filters `status === 'wishlist'` with **no** category filter, so a place-wish would advertise itself in the Shopping glance cell. Buy vs do: "buy ski gear this winter" is a `shop_item`, "go skiing this winter" is a `wish_item`.
- **Promotion leaves the wish alive.** `+ Plan it` opens `UnifiedPlanModal` with `defaults={{ title }}`; `onSaved` always sets `status='planned'` and adds `promoted_task_id` **only when the save produced a `result.taskId`** (a schedule-only save with no linked task leaves the column null rather than storing a fake id), then invalidates **both** `['tasks']` and `['wish-items']`. The task is the commitment, the wish is the memory — the card then reads "→ scheduled". No trigger and no auto-close: a second completion signal beside `tasks.status` is the documented `user_tv_entries.current_season` mistake. `promoted_task_id` is `ON DELETE SET NULL` because `deleteTask` hard-deletes. A wish never passes through `useCreateTask`, so it never reaches Google Tasks.
- **"Passed" is grey, never red.** Page groups, in reading order: Open now · Coming up · Anytime · **Passed**. A wish whose `period_end` went by stays `'idea'` in the grey group under an explicit "nothing here is late" note; nothing auto-closes, nothing resets, and it leaves only when the user ticks or deletes it. `resolveWishWindow` (`wishRules.ts`) returns `open|upcoming|passed|anytime` from lexicographic `yyyy-MM-dd` compares — no `Date`, no timezone. `wishPeriodLabel` prefers `period_label` over the derived range.
- **Capture is the feature.** `WishQuickAdd` is always visible (never behind a "+ New" modal): title → optionally one season chip → Add, and **only the title clears** so a whole season's wishes go in one after another. Notes/place/priority/kind/status live in `WishSheet` (shared `Sheet`, keyed by row id so a background refetch can't overwrite typing) → `WishForm`. `WishFilters` (kind + status, default Active) only narrows what is **displayed** — "Everything" always brings the list back.
- **`shared/components/windowChips.tsx`** — the one-tap period picker, shared with the task-window control. `seasonWindows(today)` returns Northern-hemisphere/Oslo windows soonest-first (winter 1 Dec → end of Feb · spring 1 Mar–31 May · summer 1 Jun–31 Aug · autumn 1 Sep–30 Nov); `this <season>` = the season you are currently inside, otherwise the **upcoming** one, so tapping `❄️ This winter` in July stores 1 Dec this year → end of Feb next year (three anchor years are probed to cover a season that began last year). End-of-February is `endOfMonth`, **never a hardcoded `'02-28'`** — a leap year yields 29 Feb. `windowRangeLabel` is en-GB day-first ("1 Dec – 28 Feb"), adding the year to **both** ends only when a bound falls past next year (never a mixed "1 Dec 2029 – 28 Feb", which reads as a typo). `📅 Pick dates…` falls back to two `DateInput`s; `✕ No period` clears.
- **Resurfacing — two places, both purely additive.** (1) `DayView` renders one always-visible link when a period is open (`❄️ This winter · 3 things →`, from `useOpenWishes` — the label comes straight from `wishPeriodLabel`, emoji included; several open periods render `<first> +N more`). It belongs **there**: Daily's day band stacks `WeekStrip → DayAgenda → DayView`, so at 393px it is about one screenful down, while the glance board is 2–3 screenfuls down and `DayQuickRail` is `hidden xl:flex` — **neither is a phone surface, so don't "tidy" the row into them.** (2) `push-send`'s `buildMorning` appends a segment **only on the day `period_start` equals today** — once per season, never a daily nag; it adds a segment and adds no predicate to the tasks query. A missing table there surfaces as `{data:null,error}` (the null-check keeps the brief alive, **not** the `catch`). **`period_label` is stored WITH its season emoji** (`WindowChips` writes `❄️ This winter` verbatim), so anything that prepends its own emoji must strip the leading one first — `push-send`'s `labelText()` does, and a label-less row falls back to `A new period starts today (1 Dec – 28 Feb)` because a bare date range doesn't fit the `<name> starts today` sentence. The rest of that brief is still Turkish (`🌅 Günaydın`, `açık iş`) — sanctioned by the on-phone notification-text exception, so the body currently mixes languages until someone decides to translate the older segments.
- **Pre-migration safe.** `wishesApi.ts` returns `[]` on `42P01`/`PGRST205`/"Could not find the table" for **reads** (the `waterApi.ts` precedent), but a **write** throws a named "migration 069 not applied" error — a silent no-op would look exactly like data loss. `useWishes` and `useOpenWishes` share ONE query key `['wish-items']` and one `queryFn`, narrowed with `select`, so mounting both surfaces costs one request. Every mutation uses `useMutationWithFeedback`.
- **AI:** `wish_items` is `rw` in `ai-proxy`'s `DB_CATALOG` for the same reason `dev_requests` is — the user dictates wishes in chat, and the Siri `AI'a Sor` path runs `surface:'general'` with the **full** tool set, so one flat `db_insert` is the app's best capture channel — and it is in `EMBED_SOURCES` for `semantic_search` (needs one Developer → "Reindex AI search" click after the redeploy — embeddings are not written on insert). Its `rules` carry the "a period is a reminder window, never a deadline; never compute lateness, never auto-close on `period_end`" guardrail plus the **four-way** tie-break between the "remember this" targets: `dev_requests` (about this app) · `ai_memory` (a durable fact about the user) · `shop_items` (to buy) · `wish_items` (to do / a place to go). `ai_memory`, `shop_items` and `save_memory` gained the symmetric pointer back. Client-side, `aiApi.buildContext` adds a **`WISHES`** block (open windows then upcoming, each with its period/place/`(already planned)` flag, plus a count of undated ones). It selects only what a line needs, and a passed wish is left out of that **summary** while the block explicitly tells the model to `db_query wish_items` for the rest — a shorter summary, **not** a hidden row (`NEVER_HIDES` is about queries that decide what exists, not about a digest's length).
- **Verified:** `scripts/verify-wish-windows.cjs` (sucrase against the real modules, no test framework — the `verify-health-source-resolver.cjs` precedent) — **42 assertions**, all passing: season-chip math across a year boundary, leap-safe end of February (29 Feb 2028 vs 28 Feb 2027), both inclusive window boundary days, one-sided windows, and en-GB label formatting.

### Food Feature Detail

User-visible name is **Food** (nav tab, CommandBar, page h1); route stays `/recipes` for deep links. `RecipesPage` has 4 tabs: **Today** (default) · **Library** · **Ingredients** · **Meal Plan**, plus `FoodTabs` (Food | Shop) in the header row.

**Data model — 4 tables** (after migration `061` unified plan + diary):
- `recipes` — title, description, `servings` (base count), instructions, `macro_mode` `manual`|`from_ingredients`, per-serving `calories`/`protein_g`/`carbs_g`/`fat_g`/`sugar_g`/`fiber_g`, `category` (breakfast/lunch/dinner/snack/supplement), `image_url`, `source_url`, `times_cooked`, `is_temp`.
- `recipe_ingredients` — name, `quantity` (nullable = to-taste), unit, note, sort_order, `library_ingredient_id` (nullable FK). Quantities are stored for the base `servings`; recipe macros are stored **per serving**.
- `recipe_ingredient_library` — reusable ingredient catalog, macros **always per 100g**, unique per `(user_id, name)`, + `fiber_g`, portion presets (`serving_label`/`serving_grams`, e.g. "1 scoop"=30g), `food_group`, `image_url`, and `source`/`source_ref` provenance (`off`, `dsld`, `matvaretabellen`, user's own; user's own wins on name conflict, attribution travels on the row, idempotent refresh).
- **`food_log_entries` — plan AND diary in one table**, discriminated by `status`: `'planned'` (intent; macros computed live on read) vs `'eaten'` (a real at-log-time **snapshot**). Planning → eating is a status flip. Slots: breakfast/lunch/dinner/snack/**supplement**; unlimited rows per slot; exactly one of `recipe_id` / `library_ingredient_id`+qty+unit / `custom_title`.
- **`water_log_entries`** (migration `067`) — one row per logged amount; the day's total = `SUM(amount_ml)`. **Deliberately its own table, never a food slot** — water carries no macros and must never enter the calorie ring. Owner-only RLS, `user_id DEFAULT auth.uid()`, no audit trigger (high-frequency, low audit value — same reasoning as the bulk-sync exemption).

**Load-bearing contracts (do not break):**
- **Macros are snapshotted at log time.** Editing a library ingredient or a recipe never rewrites history.
- The original `UNIQUE (user_id, date, meal_slot)` on the old plan table **had to die** — it physically forbade "lunch = chicken + rice + broccoli".
- **Planned rows render muted "planned" and are NEVER added to the eaten total** (the ring sums `eaten` only) — counting them was visually contradictory with the ring.
- `dayNutritionApi`'s plan-side query deliberately does **NOT** select `recipes.fiber_g` (a missing column would error the whole plan query on old schema; plan rows don't feed the ring anyway).
- **Pre-migration fallback pattern (reused across the feature):** on a column-missing error (`42703` / `PGRST204`) retry once with the new column dropped — `createRecipe`/`updateRecipe` for `fiber_g` and `is_temp`, `create/updateIngredientLibraryItem` for `image_url`, and `foodLogApi`/`mealPlanApi`/`dayNutritionApi` for `status` (they fall back to the old two-table behaviour). This is what let the frontend deploy before migration 061 was applied.
- **Cache-key bug (real):** food-log hooks invalidated `['day-nutrition']`, which does NOT prefix-match the card's `['meal-plan','day-nutrition',date]` key — the card showed stale totals. Invalidate the actual key.
- `macro_mode: 'from_ingredients'` is computed on save (`computeMacrosFromIngredients` in `recipesApi.ts`): sum each linked library ingredient's per-100g macros × `quantity/100`, ÷ servings. Only rows with a `library_ingredient_id` AND a weight/volume unit contribute; the rest are skipped and surfaced in the UI. `RecipeModal` previews the same math client-side (`previewMacros`). `dayNutritionApi` imports recipesApi's `WEIGHT_UNITS` (a narrower local copy once dropped 'milliliter(s)').

**Components / flows:**
- **`FoodLogModal`** — the build-a-meal logger (`sm:max-w-xl lg:max-w-3xl`, 2-column on `lg`: left = recents / saved meals / search / new ingredient, right = the basket). **Recents-only suggestions** — the alphabetical library dump was removed; ingredient match chips render only while searching. Grams or portion-preset tap; live kcal/protein total; footer shows remaining protein/kcal **after** this meal. "Save meal" is **save-only** (no auto-log) with a "Makes N portions" field, so a batch is stored at correct per-serving macros and you log your portion later.
- **Temp meals (migration `066`, `recipes.is_temp`)** — a saved meal is **temp by default**: hidden from the Library grid (`RecipesPage` filters `!is_temp`) but fully usable — it appears in the logger's "Saved meals" strip, and hover (desktop) / the ✎ editor (mobile, `onEditRecipe` → RecipeModal) reveal its ingredients. An inline "Library" checkbox on the save row promotes it to a permanent Library recipe.

### Training Feature Detail

Page layout (`TrainingPage`): faint training-photo header banner; **Hevy / Strava / Health / 🧠 Coach** pill tabs + Sync/Settings on the **left**; content column (`max-w-4xl`, left-aligned) with `TrainingCalendar` **pinned to the right edge (440px)**, independent of the active tab. `HevyTab` sub-tabs: Workouts, Routines, Personal Records, Progress, Muscles, Body, Exercises.

**WIDTH STANDARD PILOT (decision pending — DO NOT spread beyond Training without explicit user approval; see the "Alan/yoğunluk standardı" dev request).** What stands here: Workouts = content-width card columns (`repeat(auto-fill,minmax(19rem,22rem))`, leftover space stays right); Personal Records = the same fixed-width column flow (15–18rem) + a hover/tap peek card (GIF + est-1RM) + capped search/banner; Muscles = container queries (`@container` root, `@3xl:` row, `@4xl:` 2-col overview); Body = bento auto-fill grid + a container-query-adaptive chart + a View-Transition zoom that keeps the chart's aspect ratio and caps at `max-w-4xl` (a full-width stretch was rejected). `NextSessionBanner` sits in the right rail under the calendar, not as a full-width band. See Coding Rules → Width Standard for the 6 rules themselves.

- **AI PT Coach** (`PTCoachTab.tsx` + `api/ptCoachApi.ts`): user-initiated (NEVER auto-runs) daily assessment acting as a decisive personal trainer. **Token-minimal BY CONSTRUCTION** — `buildTrainingSnapshot()` pre-aggregates everything client-side (latest workout's per-exercise set summaries with previous-same-exercise comparison from up to 10 sessions back, weekly hard-sets-per-muscle vs `MUSCLE_LANDMARKS`, last-night + 7d-avg sleep, steps/active energy, 30d weight trend) into ONE compact text block → a single one-shot `invokeAI` call, zero tool loop (same pattern as the daily briefing). The coaching brain (recovery gate on <6h sleep, MRV deload cues, double-progression +2.5/+5kg engine, volume steering vs MEV) was distilled by the `strength-coach` agent and bounded by the `sports-scientist` agent's evidence guardrails — **the snapshot line formats are a CONTRACT with that prompt; change them together.** Input: feeling chips + optional free text. Every assessment is saved to `pt_assessments` (migration `051`: date, feeling, note, the exact snapshot the coach saw, the reply, which model served it); the next run feeds the previous one back in and the prompt's FOLLOW-UP rule makes the coach open with whether its last advice was applied. History is browsable in the tab; a localStorage fallback still displays results if the migration isn't applied.
- **Coach mode in the main chat** (`AIPanel`'s 🏋️ toggle → `sendCoachMessage`/`buildCoachContext`): a SEPARATE surface from the daily assessment — open conversation over a prepared last-30-days compact JSON (workouts w/ sets, current routines incl. ids, sleep, steps, active kcal, weight/body-fat, the diary's logged nutrition, the coach's own past assessments, the athlete profile + active limitations below; ~7k chars measured live), blunt science-over-feelings persona, and REAL program edits via `update_hevy_routine` plus new-routine creation via `create_hevy_routine`. Both forward to `hevy-api` so every documented Hevy payload trap stays handled in one place and **Hevy stays the source of truth** (the local mirror is upserted by hevy-api, never written directly); both confirm first, and create requires resolving real `exercise_template_id`s via `db_query` on `hevy_exercise_templates`. The general Ask AI chat also carries a TRAINING QUESTIONS persona block (client-side in `aiApi.ts`'s `SYSTEM_PROMPT`, no edge deploy needed), which now tells the model to check the `get_athlete_profile` tool before giving programming advice.
- **Athlete profile** (migration `070`: `athlete_profile` + `athlete_limitations`) — a second strength-coach/sports-scientist design pairing, this time over durable facts about the person rather than volume math. **Two tables, not one `text[]` column**, because the repo's real convention for a one-to-many attribute list is a child table (`recipe_ingredients`, `hevy_exercise_template_muscles`), and a limitation needs its own identity/`created_at`/CHECK that an array element can't carry. `athlete_profile` is a true **singleton** — `user_id` is the PRIMARY KEY (no `id` column) — holding `goal` (strength/hypertrophy/fat_loss/general, read-only metadata for the coach's tone — it never forks the volume algorithm), `experience_level` (novice/intermediate/advanced), `training_age_years`, `training_days_per_week`, `equipment_access`, `notes`. `athlete_limitations` is a normal list: `movement_pattern` + `severity` (`avoid`/`limit`/`monitor`, **defaults to `monitor`** — escalating to avoid/limit is always an explicit, separate update, never automatic on log) + `note` + `active`.
  - **`movement_pattern`, never a muscle slug.** A physical limitation is almost always movement-shaped, not muscle-shaped — a shoulder issue rules out overhead pressing, but flat press/flyes are frequently still safe despite training the same chest muscle; flagging at the muscle level would suppress a still-safe stimulus. `muscleMap.ts`'s `MovementPattern` (9 values: squat/hinge/horizontal_press/vertical_press/horizontal_pull/vertical_pull/lunge/carry/isolation — a standard S&C taxonomy, not exotic) is free text on the DB side (no CHECK enum — a fixed value list would force an `ai-proxy` redeploy for every new phrasing a real conversation surfaces, the same reasoning `069`'s rejected season-CHECK already established).
  - **`PATTERN_AFFECTED_SLUGS`** (`muscleMap.ts`) is the derivation seam: which `Slug`s a pattern restriction realistically touches, and how hard (`'avoid'` = no comparable substitute at heavy load; `'limit'` = other patterns/isolation work still train it safely). This is what lets `WorkedMuscles.tsx` — a pipeline keyed entirely by muscle `Slug`, with zero pattern dimension of its own — render a per-muscle flag without the DB ever storing a muscle slug directly. A flagged muscle is a **third visual state** (violet, `FLAG_META`), deliberately never green or red: most flagged muscles are still safely trainable through a non-conflicting exercise, so a danger colour would overstate the restriction. Shown even at 0 logged sets (the flag is the point, not the volume).
  - **Experience-scaled landmarks** (`scaleLandmarksForExperience`, `EXPERIENCE_MULTIPLIER`): novice ×0.85 / intermediate ×1 / advanced ×1.15, applied to **MEV and MRV only** — MV and MAV are deliberately left unscaled, a cross-examined agreement (RP framework: training age shifts MEV/MRV; scaling the WHOLE landmark set would overclaim precision on a table that's already a heuristic, not a measurement). Every `InfoBubble` showing an adjusted landmark says so explicitly: *"Adjusted ±15% for your experience level — an unvalidated adjustment on top of an already-heuristic baseline, not a measured number."*
  - **`ptCoachApi.ts`'s snapshot** gets one new block — a `PROFİL:` line (goal/experience/equipment/days, only the fields actually set) + one `Kısıtlama:` line per active limitation — inserted before the workout lines, respecting the file's snapshot-line-format contract; `PT_SYSTEM_PROMPT`'s rule 1 (safety) was extended to ground `avoid`/`limit`/`monitor` into concrete behaviour. Absent entirely when the user has never touched the profile — zero snapshot-line change for anyone who doesn't use this feature.
  - **`ai-proxy`**: `athlete_profile`/`athlete_limitations` are `rw` `DB_CATALOG` entries (per the user's explicit instruction to give the AI authority here) plus a new single-shot tool, `get_athlete_profile` — returns both tables in ONE call (mirroring `get_day_summary`'s shape) instead of two separate `db_query` round trips, because token efficiency was an explicit requirement. `athlete_profile` being a singleton keyed by `user_id` (no `id` column) means `db_update` needs a non-empty `filters` object even though the function already scopes to `user_id` internally — the catalog's `rules` text spells out the exact `filters={"user_id":...}` shape to use. Not added to `EMBED_SOURCES` (semantic search) — this is structured settings data consulted deterministically, not free text worth fuzzy-recalling.
  - **Settings UI**: `PTCoachTab.tsx` gained a slim summary strip (`🎯 hypertrophy · intermediate · gym · 2 limitations` + a ⚙ button) opening `AthleteProfileSheet.tsx` (pills/stepper autosave on tap, `notes` autosaves on blur — matching Media's `personal_note` convention, no Save/Cancel footer) and `LimitationsList.tsx` (every limitation stays visible even when inactive — muted, one tap to reactivate; deleting is a separate confirmed action, never implied by "inactive"). Pre-migration-safe throughout: every new read degrades to `null`/`[]` on a missing table, every write throws a named "migration 070 not applied" error rather than failing silently.
- **Progress sub-tab** (`ProgressTab.tsx` + `progressAggregate.ts`) — three charts answering "how am I actually changing over time", added from an explicit `strength-coach` (what metric per exercise type) + `sports-scientist` (which other charts are evidence-worthy) agent consultation (2026-08-28), the same pairing behind Muscles/athlete-profile. **Data:** `hevyApi.fetchTrainingHistory(fromISO,toISO)` fetches the last 182 days of `hevy_workouts` → `hevy_workout_exercises` → PAGINATED `hevy_sets` (1000-row chunks) → `hevy_exercise_templates`, joined client-side (the `fetchMuscleVolume` precedent), via `useTrainingHistory()` (10-min `staleTime`). All three charts share this one fetch.
  - **Exercise Progress** (`ExerciseProgressChart.tsx`) — the user picks ONE exercise (mandatory `Combobox`/`ComboboxInput`/`ComboboxOptions`; **`immediate` goes on the root `<Combobox>`, not `<ComboboxOptions>`** — a real bug this session: `immediate` on the wrong element type-errored AND left the picker showing zero options on focus) and sees its own progression across every session it appears in. **The metric plotted is NOT one universal formula** — `metricKindForExerciseType(type)` dispatches on the exercise's own Hevy `CustomExerciseType`: `weight_reps`/`short_distance_weight` → **Est. 1RM** (Epley, matching `HevyPRList.tsx`'s existing `est1RM()` exactly — never a second formula for the same number), `bodyweight_reps`/`reps_only` → top-set reps, `bodyweight_weighted` → added weight, `bodyweight_assisted` → **assistance, inverted** (less assistance over time = the improvement, so the line trending down is the win), `duration`/`weight_duration` → top-set duration, `distance_duration`/`floors_duration`/`steps_duration` → top-set distance; an unrecognized/future type falls back to `est1rm` rather than crashing. `computeExerciseProgression` groups sets by `date|workout_id`, excludes `type==='warmup'` entirely, and picks the SINGLE BEST set per session (never an average) — a `dropset` can never win (lighter by construction), a `failure` set legitimately can (a real top effort). An `est1rm`/`addedWeight` exercise gets a toggle to **Session Volume** (Σ weight×reps that session, warm-ups excluded) — never offered for a rep/duration/distance exercise, which has no weight-based "volume" to switch to. Guardrail copy (always visible, never buried in an ℹ️, matching the Muscles feature's tone) covers: the Epley ±10%-at-low-reps caveat and its 12-rep cutoff (`est1RM` returns `null` above 12 reps — those sets are excluded from the estimate), volume-vs-strength, added-weight understating true load, the assisted-exercise inversion, a rep-range-swing warning (`repRangeVariedSignificantly`, triggers at a ≥4-rep swing across the period), "read the trend over sessions, not day to day," and an explicit disambiguation from Personal Records (all-time best single set) and Muscles (a muscle's total weekly dose) — this chart is neither.
  - **Weekly Training Volume** (`WeeklyVolumeChart.tsx`) — the sports-scientist agent's #1-priority chart: total weekly tonnage (Σ weight×reps, warm-ups excluded, weight-based exercise types only via `computeWeeklyVolumeTrend`) as a **trend**, not the Muscles feature's current-window snapshot, with a 4-week rolling average line (`rollingAverage`) overlaid. Uses its own `ComposedChart` (bar + line, two independent series) rather than the shared `BarLineChart` (which only supports one dataKey driving both a bar and a line). Guardrail: tonnage is a training INPUT, not a stimulus or outcome — it conflates load and reps freely (100kg×5 and 50kg×10 tally identically) and shifts with exercise-mix changes; read it over months, not weeks.
  - **Training Consistency** (`TrainingConsistencyCalendar.tsx`) — a diverging-colour week-cell calendar (`computeConsistencyByWeek`) plus a current-streak readout (`currentStreakWeeks`), grounded in the sports-scientist finding that frequency is largely a volume-equating variable, not an independent driver — the guardrail copy says so explicitly, framing this as an adherence view rather than a second "more is better" signal. **`computeConsistencyByWeek` builds a DENSE week series** (every Monday from the earliest to the latest logged week, explicit `sessionCount: 0` for an untrained gap week) — a real bug caught in test-writing: the original sparse version only returned weeks with data, which silently glued two non-consecutive trained weeks into one fake unbroken streak.
  - **Follow-up review (2026-08-31)** implemented the three originally-deferred items plus each agent's own top "extra" recommendation, reconciling two independent agent passes (a sports-scientist review superseded the strength-coach's initial bucket/threshold proposals where the two disagreed — see each file's own header comment for the reasoning):
    - **`RelativeStrengthChart.tsx`** — bodyweight-normalized strength trend, **`est1rm`-type exercises only** (a ratio built from reps/added-weight/assistance/duration/distance has no interpretable meaning normalized by bodyweight — the strength-coach's separate "total load" formula for `bodyweight_weighted` lifts was considered and dropped, since two different ratio formulas on one chart is exactly the kind of silent misread this feature exists to prevent). `resolveBodyweightForDate` (`progressAggregate.ts`) is a 3-rung ladder — exact same-day match → linear interpolation between two anchors ≤21 days apart → nearest single anchor within ±14 days → otherwise **no point at all** — deliberately never an indefinite carry-forward, which would flatten the denominator across a cut/bulk and make the ratio lie about which side (strength or bodyweight) actually moved. `computeRelativeStrengthTrend` combines this with `computeExerciseProgression(sets, id, 'est1rm')`'s own session points — reusing that function rather than a parallel one. `hevyApi.fetchBodyweightHistory` unions `hevy_body_measurements.weight_kg` (the user's own manual log) with `health_metrics.weight_body_mass` (an automated scale synced through Apple Health), same-day conflicts resolved manual-wins. The chart always plots BOTH lines (ratio + a muted dashed bodyweight line) — never just the ratio — specifically so a rising number during a cut is visibly attributable to the denominator, not silently read as new strength. Estimated (non-same-day) points render as a hollow dot. **No strength-standard reference lines** (1×/1.5×/2×BW-style bands) — what counts as strong varies by height, limb length, age and sex, none of which this app knows.
    - **`RepRangeDistributionChart.tsx`** — a set-count histogram by rep bucket, **boundaries `1–5 / 6–12 / 13–20 / 21–30 / 31+`** (`REP_BUCKETS`, `computeRepRangeDistribution`) — the sports-scientist review's call, not the strength-coach's originally-proposed `6-8/9-12` split: Schoenfeld et al. 2017 (JSCR 31(12):3508-3523) and Morton et al. 2016 (J Appl Physiol 121(1):129-138) found hypertrophy roughly equivalent from ~5 to ~30 reps taken near failure, so there's no evidence for a boundary at rep 8, and the chart deliberately does NOT frame any bucket as "the hypertrophy range." Warmups excluded, dropsets/failure sets counted (each drop its own set, matching `computeExerciseProgression`'s own eligibility). Period toggle 30/90/182 days (default 90) + an optional muscle-group filter (primary-attribution only — deliberately NOT the Muscles tab's fractional secondary credit, since a histogram counts whole sets and crediting half a set to a second bar would double-count it). No target-distribution overlay.
    - **`WeeklySetsPerMuscleChart.tsx`** — the sports-scientist review's top-priority "what else": the SAME currency the Muscles tab already uses (hard sets/muscle/week vs `MUSCLE_LANDMARKS`' MEV-MAV) — the one training measure in this app with an actual dose-response meta-analysis behind it (Schoenfeld 2017; Pelland 2025) — but as a per-week **trend** rather than a single rolling-window snapshot. `computeWeeklySetsPerMuscleTrend` reuses `muscleMap.ts`'s `contribution()`/`HEVY_TO_SLUG` exactly (primary 1.0, secondary 0.5), no parallel volume model; `fetchTrainingHistory` was extended to also join `hevy_exercise_template_muscles` (the same query `fetchHevyExerciseTemplates` already does) so `TrainingExerciseTemplate` carries `secondary_muscle_groups` for free. A muscle chip row (reusing `MAJOR_MUSCLES`/`labelForSlug`) picks one muscle at a time; the chart shades the MEV–MAV band and an MRV reference line, scaled by `scaleLandmarksForExperience` when an athlete profile exists.
    - **`WeeklyChangesPanel.tsx`** ("Big Changes This Week") — ships **instead of** an acute:chronic workload ratio (ACWR), which the strength-coach review explicitly advised against: ACWR's injury-prediction evidence is team-sport running/GPS load, it has drawn sustained statistical criticism (mathematical coupling between the acute and chronic windows it computes from, unstable "sweet spot" thresholds), and this app's OWN Weekly Volume guardrail already documents tonnage as conflating load and reps — a risk flag can't be built on a quantity already flagged as ambiguous, and a solo lifter's log has none of the sample size the original research relied on. `computeWeeklyChangeFlags` is a plain per-exercise change detector: a top-set-load jump ≥10% or a set-count jump ≥30% vs the **median** of up to the 4 preceding weeks (median, not mean, so one deload week can't manufacture a flag on the return; requires ≥3 prior weeks of history), plus an unconditional `'new'` flag for any exercise not trained in the last 8 weeks (or ever) — unfamiliar-movement soreness is real and otherwise invisible in this data. No score, no colour-coded "risk," no threshold band.
    - **`RecoveryLoadPanel.tsx`** ("Recovery Inputs Alongside Load") — sleep and resting-heart-rate trends alongside weekly tonnage, as **three stacked lanes sharing one weekly X axis**, deliberately NOT a dual-axis overlay (which lets two arbitrary scales be tuned until any two series look coupled — a causality claim made with a scale factor instead of words) and NOT a computed composite "readiness" score (this app's own house rule forbids synthetic derived metrics — see Health's "no derived sleep metrics" precedent). `recoveryAggregate.ts` (new, pure, import-free of runtime deps) computes weekly sleep (mean nightly hours from `computeSleepSummary`) and weekly resting HR (median from `computeDailySeries('resting_heart_rate', ...)`), both keyed to the SAME `mondayOf` weeks `progressAggregate.ts`'s tonnage trend uses — one definition of "a week" for the whole panel — and both gated at **≥4 tracked nights/days per week**, else null (a broken line is more honest than an imputed one). **An HRV lane was deliberately left out**: different HRV measures (e.g. SDNN vs RMSSD) must never share a line or an average, and this app's own rule is to verify an external field's exact shape live before shipping copy that names it — add it once that's confirmed against a real payload.
    - **Deliberately still not built**: a "Stalled & Progressing" exercise roll-up table (the strength-coach's other "extra" suggestion — real value, but a genuinely new UI surface, an OLS-slope-over-time helper plus a sortable table, rather than an extension of what's here; tracked as a fast-follow, not silently dropped).

#### Health data (Apple Health)

**Apple Health is the sole data source** (the Fitbit Air / Google Health API integration was fully removed 2026-09-01 — see the note at the end of this section). Huawei's own Health Kit API is closed to individual developers (requires an AppGallery-published app), so: Huawei Health on iOS syncs into Apple HealthKit → the **Health Auto Export** app reads HealthKit and POSTs to `health-export-webhook`. Lands in `health_workouts` / `health_metrics` (shared `HEVY_USER_ID`, separate from Hevy's tables).

- **Point-in-time grain, not daily** (migration `041`): `health_metrics` was originally one row per `(metric, day, source)` — a real bug confirmed against production exports; every new point for the same day silently overwrote the previous one, so only the LAST point of the day survived (`active_energy` for a full day showing 0.05 kcal instead of ~230). Fixed by storing every incoming point as its own row keyed `(user_id, metric_name, recorded_at, source)`. `date` stays a plain column **computed from the export's own local-time string at ingest, not derived from the UTC `recorded_at`** (avoids a midnight timezone-shift bug). No aggregation at ingest.
- **`source_family`** — values are `apple | manual` (the CHECK constraint still also allows the historical `fitbit` value so old rows aren't rejected, but nothing writes it any more). The column is `NOT NULL DEFAULT 'apple'` **and** explicitly stamped by `health-export-webhook` (belt-and-suspenders, not either/or). Existing rows are legitimately all `apple` — Huawei data already flows through Apple HealthKit before reaching us.
- **Aggregation happens at query time**, per metric, via `healthMetrics.ts`'s `METRIC_AGGREGATION`: `sum` (cumulative — steps/energy/distance/durations), `average` (rates/levels — speeds/dB/physical effort/respiratory rate/HRV), `minmaxavg` (`heart_rate`'s Min/Avg/Max points, and SpO2 — a locked guess pending live shape confirmation), `latest` (point-in-time — weight/body fat/BMI/resting HR), `sleep` (`sleep_analysis`'s own stage-duration merge). **Unrecognized metrics default to `latest`, the safest fallback.** The pure functions live in `healthAggregate.ts` (`computeDailySeries`/`computeHourlyBuckets`/`computeHeartRateDailySeries`/`computeSleepSummary`) and deliberately ignore `source` when merging (a day can have differing source strings, e.g. `"Furkan's Apple Watch"` at midnight vs `"Furkan's Apple Watch|Lasci"` once a second device joins — the UI shows one number; raw rows stay source-separated in the DB).
- **No cross-source resolver any more.** A whole priority-ladder system (`resolveSourcePoints` + `healthSourceDefaults.ts`) used to pick one winning device stream per hour/day/night when Apple and Fitbit both wrote data for the same window. Removed on the user's explicit 2026-09-01 decision, since Apple Health is now the only source and does its own internal source resolution — every `health_metrics` row for a metric+window is summed/merged as-is, with no per-window stream competition. `collapseIntraStreamMinuteDuplicates` (below) is unrelated and stays — it fixes a same-STREAM duplicate, not a cross-source one. There is no more per-section Auto/Apple/Google display switch (`SourceToggle.tsx` was deleted) — every Health chart just shows the one source there is.
- **Intra-stream workout twins (real bug, fixed 21/07/2026):** starting a Fitness-app workout makes HealthKit hold OVERLAPPING step samples (regular + workout-associated); HAE exports each with only its START time, so one stream delivered the same minutes twice as float-noise twins (20/07/2026 showed **15,362** steps vs Apple's own **5,731**; 88 of 94 minutes were twins inside ONE stream). `collapseIntraStreamMinuteDuplicates` (`healthAggregate.ts`, `sum`-metrics only, applied after grouping) keeps only the largest same-minute-same-stream point as a display backstop; the automation's **Time Grouping = Hours** setting is the real source-level fix (Apple dedupes before export).
- **Never destroy health rows without checking `source='manual'` first.** Manual sleep corrections never existed in HealthKit and **cannot** be recovered by re-export.
- **1000-row server cap silently truncated Week/Month views (real bug, fixed):** `fetchHealthMetricSeries` had no pagination — **PostgREST caps every response at 1000 rows server-side regardless of an explicit `.limit()`/`Range` header** (confirmed by testing). High-frequency metrics arrive ~once a minute, so a 7-day range can be 3000+ rows; with ascending order + the silent cap the response kept the OLDEST rows and today/yesterday fell off the end (Day view looked fine, Week/Month was missing the last few days). Fixed by paginating in a loop (`.range(offset, offset+999)` until a page comes back short).
- **kJ→kcal at the source (real bug):** Health Auto Export can export `active_energy`/`basal_energy_burned` in kJ depending on device locale even though every card says "kcal" — `healthAggregate.ts`'s `qtyOf()` converts (÷4.184) for those two metrics, fixing Energy Today, the Energy chart, `HealthStatsPanel` and `ActivityRings`' Move ring in one place. - **Body section: a stale 'latest' reading was silently shown as current, and `lean_body_mass` was invisible despite real data existing — both real bugs, investigated with live raw `health_metrics` rows after a scale swap (Huawei → MovingLife) made the first one visible.** `weight_body_mass`/`body_fat_percentage`/`body_mass_index` are all `aggType: 'latest'` (a genuine point-in-time reading, correct for a scale that only reports when you step on it) — but `BodyMiniChart` rendered the series' last point as the headline number with no regard for HOW OLD it actually is. Live data confirmed: Huawei wrote `weight_body_mass` daily through 13/08/2026 and zero rows since; MovingLife (the replacement scale) writes `body_fat_percentage`/`body_mass_index`/`lean_body_mass` daily from day one but has **never once** written `weight_body_mass` — 0 of 15 logged sessions, not a regression, a characteristic of that scale's own HealthKit export. Because the 90-day window still includes the old Huawei rows, the Weight card kept displaying **84.5 kg from 13/08** as if it were today's reading, day after day, with nothing on screen distinguishing a fresh number from a 2+-week-stale one — this is what read as "the Body section broke" once the scale changed. Verified via `health-export-webhook`'s own code that this is NOT an ingestion bug: the webhook stores `group.name` verbatim with zero per-metric filtering or name-mapping, so a metric simply not being in MovingLife's own export is upstream of anything this app controls (most likely: the MovingLife app was never granted iOS Health write permission for "Weight" specifically — Settings → Health → Data Access & Devices → MovingLife — while Body Fat/BMI/Lean Mass were). Per this repo's own rule against speculative external-field guessing, no code change can manufacture data a source never sent. Fixed on the app side, honestly: `BodyMiniChart` gained a `viewedDate` prop and shows an amber **"Nd old"** chip (mirroring `EnergySection`'s "N/24h measured" honesty pattern) whenever the latest point is `STALE_AFTER_DAYS` (3) or more before the day being viewed — never estimates, just stops presenting an old number as if it were live. Separately, `lean_body_mass` — which MovingLife writes on every weigh-in exactly like the other three — was never fetched or displayed anywhere in `BodySection` at all; added as a fourth `BodyMiniChart` (also added to `METRIC_AGGREGATION` explicitly as `'latest'`, matching its siblings, rather than relying on the unrecognized-metric default).
- **ONE day+period selector for the whole tab (`HealthTab`), not per section.** Steps/Energy/Heart/Sleep each used to own their own `useAnchorDate()` + `useState<Period>` and render their own `DateNav`+`PeriodToggle` INSIDE the section body — so changing the day in Steps left Heart on a different day, the control sat at a different scroll depth in every section, and Overview/Body had no day control at all. `HealthTab` now owns that state once, renders the control row **above the section pills**, and passes a `HealthRange` (`{anchor,setAnchor,period,setPeriod}`, `sectionTypes.ts`) down; switching section keeps the day you were looking at. `setAnchor`/`setPeriod` are passed (not just the values) because the chart drill-down writes them — clicking a bar in a Week/Month chart jumps to Day mode on that date. `ActivityRings` and `BodySection` took a `dateStr` prop in the same pass (both hardcoded `todayStr()` and so ignored the control entirely; Body's 90-day window now ENDS at the viewed day). **`SourceToggle` deliberately stays per-section** — Auto/Apple/Google is a choice about that section's own chart, not a page-wide one.
- **Date navigation** (`DateNav.tsx` + `dateNav.ts`): every view shows the exact date/range (e.g. "1–7 Jul (this week)") with prev/next arrows and a native date-picker; `rangeForAnchor`/`stepAnchor`/`labelForAnchor` compute the window from an `anchor` (defaults to today, resets on period change, never steps past today). **Stale-anchor bug (real, fixed):** `anchor` was plain `useState(todayStr())` — with the tab open across midnight, "today" moved on but the anchor didn't, so a section silently froze on whatever day it was first opened, and since each section has its own anchor two sections could show two different stale dates (confirmed against live data: fresh same-day rows in the DB, UI days behind). Fixed with `useAnchorDate()`: re-checks on focus/visibility/a 60s interval and advances **only if** the anchor still equals the previously-known "today" — an intentional look-back is left untouched.
- **Chart interaction contract** (one rule, all Health charts): **hover shows values immediately** (no `trigger="click"`); the ONLY things that navigate are explicit links inside the tooltip ("Go to this day →", or "Correct manually" for Sleep) — a bar click never navigates. Tooltips need `wrapperStyle={{ pointerEvents: 'auto' }}` or those links are unclickable. Trend-bar **actions** live in a pinned popover anchored AT the clicked bar (`{date,x,y}` from the Bar's own onClick coords, clamped to the wrapper) — an action strip below the chart was explicitly rejected. Steps/Energy also wire drill-down straight on their own `Bar` (`BarLineChart` exposes `onPointClick`). Steps' ugly default tooltip (`": 514 steps"` — empty series name + colon) uses a custom content renderer like the others.
- **Chart click "frame" (real bug, THREE rounds — root cause found by E2E, generalizable gotcha):** clicking any Health chart drew a black rectangle around it. Rounds 1–2 (focus-outline CSS + `cursor={false}`) were the right ideas but **the CSS never shipped**: the `.recharts-*:focus { outline: none }` rules sat inside `@layer base`, and **Tailwind tree-shakes custom rules inside `@layer` blocks whose selectors never appear in source files** — `.recharts-surface` only exists at runtime inside the library, so the rule was silently purged from every build (verified: zero recharts rules in the served CSS; the focused `svg.recharts-surface` computed `outline: auto 5px`). recharts v3's accessibilityLayer gives that svg `tabIndex=0`, so every click focused it → browser focus ring = the frame. Fix: the rules moved OUTSIDE all `@layer` blocks (bottom of `index.css`). **Rule of thumb: any CSS targeting library-runtime class names must live outside `@layer`.** `cursor={false}` on every Tooltip stays.
- **Canonical chart style** (default for any future Health chart): a translucent `Bar` + a `Line` with dots on top, same colour, via the shared `BarLineChart.tsx`. `rangeKey` (optional min–max band) exists but only `HealthWorkoutDetail`'s HR curve uses it. **Tooltip showed the average twice (real bug):** `BarLineChart` renders a Bar and a Line on the same `dataKey`/`name` (the whole point of the style) and recharts' default Tooltip shows one row per graphical element — fixed with a custom `content` renderer that dedupes by `dataKey`.
- **Mini-metric grid** (`MetricMiniCard`/`MetricMiniGrid`/`miniMetrics.ts`): every HealthKit metric without a full chart gets a small card (max 4 per row: `grid-cols-2 sm:grid-cols-4`, never more) below its section's main widget — value + Today/7-day-avg/Latest (per the metric's `AggType`) + a one-line explanation. Grouped onto the closest section: Steps (mobility/gait + activity extras + Running Dynamics), Energy (nutrition), Heart (cardio recovery + VO₂ Max), Sleep (respiratory rate, wrist temp), Body (lifestyle & environment). `showTodayCount` adds "N× today"; `showTodayTimes` lists occurrence times (handwashing/toothbrushing). `push_count` ("wheelchair pushes") is very likely misdetected for non-wheelchair users — continuous per-minute fractional samples all day is not what discrete pushes look like; the card points at Watch Settings → Accessibility → Wheelchair, not at our aggregation.
- **`HealthWorkoutDetail.tsx`** — each `health_workouts` row stores the FULL Health-Auto-Export payload in `raw` (jsonb) but only summary columns used to be shown; the per-interval **HR curve** (`heartRateData`), **GPS route** (`route[]`), cadence, distance, avg/max speed, pace, elevation, weather, HR recovery and step count were all ingested then dropped. The detail surfaces all of it from `raw` client-side (no schema change): a `BarLineChart` HR curve using `rangeKey` for the min–max band + a self-drawn SVG route polyline (green start / red end — **no map tiles, CSP blocks external hosts**) + a stat-chip grid. Never-populated cards (gait/nutrition) are unlogged data, not a hardware gap. SpO₂/skin-temp are no longer a hardware gap either as of 20/08/2026 (Watch upgraded SE 2 → Series 11, which has both sensors) — they stay empty until a real Health Auto Export payload confirms the exact field names; don't assume the old "Watch physically can't" reasoning still applies to any card.
- **Health Auto Export operational facts:** importable automation configs live in `docs/health-auto-export/`. Required app settings, confirmed against production data: **Export Version 2** (v1 is legacy — no `id` field, different field shapes), **Summarize ON**, **Time Grouping: Hours**, **all Health Metrics enabled** (not a curated subset), **Date Range "Since Last Sync"** for the recurring automation with a separate weekly "Previous 7 Days" reconciliation automation, **Batch Requests ON** once route data / many metrics / fine grouping are enabled. If a workout arrives without `id`, the webhook falls back to a deterministic key (`name+start+end`) instead of dropping it — still idempotent, just not a real UUID; only a workout with no id AND nothing to build that key from is skipped (counted in `skipped_workouts`). Numeric workout fields (`duration`, `activeEnergyBurned`, `totalEnergy`, `heartRate.avg/min/max`) arrive as either a plain number or a `{qty, units}` object depending on the field — `numOrQty()` unwraps either. Known gap: `stateOfMind`/`medications`/`symptoms`/`cycleTracking`/`heartRateNotifications` payload arrays are not ingested. **ECG** (`HKElectrocardiogramType`) status is more nuanced, researched 20/08/2026 after the user's Watch upgraded SE 2 → Series 11 (which has the ECG electrodes; the SE line never did): Health Auto Export's own docs claim it exports a full record (`{start,end,classification,severity,averageHeartRate,numberOfVoltageMeasurements,voltageMeasurements,samplingFrequency,source}`) rather than only a classification string, but this contradicts a second doc source from the same vendor and was NOT verified against a real export — treat as unconfirmed until one real ECG recording (run manually on the Watch) round-trips through the webhook. If it does arrive, the existing generic metric ingestion needs no code change to store it; a dedicated UI view would. **Auth:** researched across several passes against the vendor's own docs — no HMAC/request-signing exists for this integration; Bearer token over HTTPS is the documented and only supported model, so `Authorization: Bearer <secret>` is correct, not a workaround. Batch-split behaviour (size/count triggers, ordering, partial-failure semantics) is undocumented, so the webhook deliberately depends on none of it: every request is processed independently and idempotently. Platform reminder: HealthKit is unreadable while the phone is locked and background scheduling is opportunistic — delivery is best-effort by OS design, not a bug in either app.
- **Google OAuth token posture (operational, verified hands-on 21/07/2026):** the consent screen in **Testing = 7-day refresh token; Production (even unverified) = effectively non-expiring** — publishing to Production is mandatory for background sync. **A re-consent can omit a fresh `refresh_token` unless `prompt=consent` is forced** — so a scope-union re-consent can leave the UI reading "connected" while the stored token still covers only the old scopes; verify with Google's `tokeninfo` endpoint after any scope change. Fallback if the posture ever fails: an **Internal** Workspace app (no cap, no verification, no 7-day limit) at the cost of employer-tied identity.

### AI (ai-proxy) Detail

Gemini via the `ai-proxy` edge function. Three call modes: the conversational **tool-calling loop** (default), **`responseSchema`** → `callGeminiStructured` (single-shot, `responseMimeType: 'application/json'` + a Gemini-format schema, returns `{ data }`, no tools/no loop — structured extraction, not chat), and **`{ fetchUrl }`** (server-side page fetch because the browser can't hit arbitrary origins under CORS; SSRF guard blocks localhost/private ranges, 8s timeout).

**Generic DB tool layer** over a curated `DB_CATALOG` allow-list: `describe_database`, `db_query`, `db_insert`, `db_update`, `db_delete`, **`db_aggregate`**. Guardrails: default-deny allow-list (token/secret/auth tables unreachable), `access: 'rw'|'ro'` per table (hevy_*/strava_activities/health_metrics/health_workouts/movies/tv_series are read-only — synced externally), **every op force-scoped to `user_id` server-side** (the model never supplies it), no DDL, update/delete refuse empty filters, 16-turn loop cap. `app_error_logs` is readable so the AI can help diagnose failures. `pt_assessments`/`work_notes`/`work_weekly_goals`/`work_pinned_links` are read-only; **`dev_requests` and `wish_items` are read-write on purpose** — the user dictates backlog notes and wishes in chat (and by Siri) and the AI writing a structured row there IS the intended flow; `wish_items`' catalog `rules` carry the never-a-deadline guardrail and the four-way tie-break against `dev_requests`/`ai_memory`/`shop_items` (see Wishes). **Behavioural guardrails in the system prompt:** announce what it's about to do before any create/update/delete, and require **explicit user confirmation before ANY delete** (never auto-deletes). `DB_CATALOG` stays behind `describe_database` (on-demand, not in the prompt). **Gap:** `water_log_entries` (migration 067) is NOT in the catalog — the AI cannot see water logs.

- **`db_aggregate`** — `sum|avg|min|max|count` + `group_by`; enum'd ops only (never expressions), the same filter grammar as `db_query`, group columns validated against the catalog, hard cap ≤366 groups, rows reduced server-side so only the summary reaches the model. This is what makes "no pre-written query per scenario" true for analytics. **Tool-choice ladder** in the system prompt: current value/list → `db_query` · average/trend/compare → `db_aggregate` · whole-day picture → `get_day_summary` · "that thing I saved" → `semantic_search` then `db_query` by id · writes → `db_insert/update/delete` with the confirm rules · external world → the special tools.
- **`semantic_search`** (migration `065`: pgvector + `ai_embeddings` `vector(768)` hnsw cosine + the `ai_semantic_search()` SECURITY-INVOKER RPC) — `gemini-embedding-001` @768, **cosine index → no manual normalize**, vector `limit ≤ 8`, `user_id` filtered inside the vector query; returns `{source_table, source_id, snippet, score}` and the model then `db_query`s the live row by id. **Embeddings locate, live SQL answers — never use a similarity hit as the factual value of anything current-state.** Reindex is user-triggered (Developer → "Reindex AI search"), not embed-on-write. Caveat: the embedding request shape was confirmed from docs, **not a live call**.
- **`run_read_query`** — the opt-in read-only live-SQL escape hatch. **Its security boundary is the DATABASE, not the edge regex:** ai-proxy's normal ops run under the service role (RLS bypassed), so this path instead builds a **user-JWT client** and calls a **SECURITY INVOKER** RPC (`ai_run_read_query`) that runs as `authenticated` (RLS applies), sets `transaction_read_only = on` + a 5s `statement_timeout`, and wraps in `LIMIT 500` before `jsonb_agg`. Containment = RLS + the read-only transaction + migration 044's revoked OAuth-token-table grants + the hard row cap. The edge guard is a best-effort UX filter that **fails closed** (strip comments first, reject quoted identifiers, `SELECT`/`WITH` only, single statement, block `pg_`/`information_schema`/other schemas, check every `FROM`/`JOIN` target incl. comma-joined lists against the catalog, recognise CTEs only as `name AS (`). **The broad DML-keyword regex was deliberately REMOVED — do not re-add it**: it false-rejected reads containing "update" inside a string literal; write-prevention is the read-only transaction's job.
- **Special-purpose tools** generic CRUD can't cover: `get_calendar_events` · **transit** — `plan_trip`, `get_next_transit`, `get_saved_transit`, `search_transit_stops`, `save_transit_stop`, `save_transit_route` · **media** — `get_media`, `plan_media`, `mark_episode_watched` · **health** — `get_health_stats` · **shop** — `get_shop_categories`, `create_shop_category`, `create_shop_item`, `ask_clarifying_question` · **recipes** — `get_recipes`, `create_recipe` · **training** — `update_hevy_routine`, `create_hevy_routine` (both forward to `hevy-api`), `get_athlete_profile` (see Training's athlete-profile note) · `get_day_summary` · `save_memory` (+ rw `ai_memory`: durable notes the user asks the AI to remember, recalled via `db_query`).
- **`ai_memory` — an "ABOUT ME" context block + a management surface.** Two gaps closed together on user request. (1) `aiApi.buildContext` now appends one more query (last in the array, so no existing `get<T>(i)` index shifts) reading `kind IN ('fact','preference')` only — deliberately **not** `note`/`summary`, which stay on-demand-only via `db_query`/`semantic_search` so they never bloat every single turn's context — capped at 12, newest first, rendered as an `ABOUT ME` block right after `DATE`/`TIME` (before `TODAY'S TASKS`): durable identity facts colour how everything else should be read, so they go first. (2) `save_memory`'s tool description now explicitly covers TWO distinct triggers, not one: remembering a single fact/preference (unchanged), and an explicit **"summarize this conversation"** request ("topla ve not al", "bunu özetle", "summarize this conversation", …) — compact the WHOLE conversation so far into one `kind="summary"` call, not just the last message. (3) A new Developer → **Memory** tab (`MemoryTab.tsx`/`MemoryRow.tsx`/`MemoryEditSheet.tsx`, `src/features/ai/api/memoryApi.ts`) lists/edits/deletes every row and is the only path that ever writes `source='user'` (every other row is `'ai'`, from `save_memory`, or `'auto'`) — before this, `ai_memory` had no UI at all: nothing to see what was remembered, nothing to correct a wrong entry. (4) `AIPanel` gained a 📝 header button, gated on `messages.length > 0`, that sends a normal chat message ("Summarize this conversation and save it to memory." / the Turkish equivalent, following the existing voice-chat TR/EN chip) down the same `handleSend` path as any other turn — the model's `save_memory` call still lands in the transcript like any other tool use, nothing hidden.
- **`get_health_stats` — two fixes worth remembering.** (1) It and the catalog both pointed at `health_daily_stats`, a table dropped when migration 041 moved Health to point-in-time grain, so the AI's health answers were silently broken (empty/stale) ever since; rewritten to query `health_metrics` directly and aggregate with the same rules as `healthAggregate.ts` (sum steps/energy, min/max/avg heart rate, latest resting HR, kJ→kcal). (2) **It now returns SLEEP too** — `computeSleepNights` (absolute-time overlap-merge keep-longest, Oslo wake-day attribution, per-night hours + deep/core/rem/awake, last night + period average). That closed the "no sleep data" answers in the phone `sleep` action and the Coach. The prompt tells the AI to *analyze* health data (trends, comparisons, honest criticism), not recite numbers.
- **Latency design for `plan_trip` (was a real 3–4 min pain point).** It is a ONE-SHOT call: the prompt and tool description tell the model to call it directly with the user's own words (`from:"ev", to:"iş"`) and NOT to look things up first — earlier "investigate first" wording caused ~5 sequential Gemini turns (each a full round-trip) vs ~2 now. `plan_trip` resolves both endpoints itself against saved stops/routes loaded ONCE (not re-queried per endpoint), in parallel: empty → default saved stop; an exact `NSR:StopPlace:` id → used as-is (name backfilled from the trip legs, no extra lookup); "home"/"ev"/"work"/"iş" (+variants) → saved-label fuzzy match; else → geocoder top match. When a side won't resolve it returns `{success:false, needs_clarification:true, candidates:[…]}` so the model asks ONE `ask_clarifying_question` instead of firing more search turns. **Only a regex-validated `NSR:StopPlace:` id or finite coords are ever interpolated into GraphQL** (injection safety). Anti-hallucination is structural (report only what the tool returns; call once and report), not extra verification turns. New EnTur GraphQL fields are deliberately NOT added speculatively — verify live first.
- **Model chain + retries.** Gemini returns transient "model overloaded" 5xx that clear within seconds, distinct from a 429 (real quota — surfaces immediately via `throwRateLimit`). Overload waves hit different models' capacity pools unevenly, so retrying a DIFFERENT model beats retrying the same one. `fetchGeminiWithFallback` tries `MODEL_CHAIN` = `gemini-3.5-flash` → `gemini-3.1-flash-lite` → `gemini-2.5-flash` → `gemini-2.5-flash-lite` with jittered exponential backoff, position-weighted attempts (`RETRIES_BY_POSITION` [4,3,2,2]) so better models are tried hard before falling to lite tiers. **Every model id must be live-verified before entering this list** (real bug: two guessed ids 404'd in production; a 404 also used to abort the whole chain — it now skips to the next model). Probe with ai-proxy's `{listModels:true}` debug branch, which returns the key's REAL available models. The client can pass a `model` — it becomes the chain's **preferred starting point**, not an exclusive choice (`AIPanel`'s header picker, localStorage `lasci-ai-model`, "Auto" by default); `AIResponse.model` reports which model actually answered.
- **`thinking_config` per-model body (real bug, round 3):** `thinking_config`/`thinking_level` is a `generationConfig` field that is **Gemini-3.x-only** — explicitly picking `gemini-2.5-flash` 400'd with "Thinking level is not supported for this model" the moment a real user tried it, because ONE fixed request body was built once and reused across every model in the chain. `fetchGeminiWithFallback`'s `body` param became **`buildBody: (model) => AnyRecord`** — the body is constructed PER MODEL inside the retry loop, and `supportsThinking(model)` (`model.startsWith('gemini-3')`) gates whether `thinking_config` is included. Applies to all three call sites (the tool loop, the turn-limit summary, `callGeminiStructured`). `thinking_level: MINIMAL` in the loop — thinking tokens are not the cost leak.
- **Prompt-caching contract (don't regress it).** Live context used to be baked into `systemInstruction`, which made Gemini's implicit prefix cache (~90% off a repeated byte-identical prefix) structurally unable to hit — a ~7,270-token fixed block (system + serialized TOOLS) was billed at full price on every turn of every tool loop. Now: **`SYSTEM_PROMPT` and the per-surface tool declarations must stay byte-identical per call** — never interpolate a date, timestamp or any volatile value into them (instant cache-buster; the current date belongs in the context turn), and serialize tools deterministically. Live context rides as `contents[0]` (`prependContext` in `aiApi.ts`). `buildContext` is skipped for clearly transit-only questions (a conservative client-side `TRANSIT_RE` gate). **`ai_usage_log.cached_tokens`** (← `usageMetadata.cachedContentTokenCount`) is the proof metric and the documented trigger for escalating to explicit `cachedContent`. `ai_query_log` records every `db_query` + live SQL with the exact statement — the substrate for later promoting hot queries into the UI.
- **Tool slicing + model routing.** Slicing is deliberately narrow: **only the bounded `shop` surface is sliced, and the `phone` surface gets NO tools at all** (its brief context is pre-built server-side by `phone-gateway`, so a single-shot answer is the biggest latency win) — **coach and general keep the FULL tool set** so the assistant is never weakened. `SURFACE_MODEL` changes only the **starting** model: `shop: 'gemini-2.5-flash'`, `phone: 'gemini-3.1-flash-lite'` (skips the frequently 503-overloaded 3.5-flash primary, which burned ~7–13s of retry budget before falling through — fatal against the ~25s iOS Shortcuts cutoff). A 503 still falls through the whole chain.
- **Voice chat (`useVoiceChat.ts` + AIPanel):** browser-native Web Speech API — `SpeechRecognition` (prefixed `webkitSpeechRecognition` everywhere that has it) for speech→text and `speechSynthesis` for text→speech. **No key, no edge function, no cost** — nothing server-side changed. Two levels: the 🎤 button dictates into the box (edit before sending), and the header **🎙 Voice** toggle is hands-free mode — utterance auto-sends, the reply is spoken, and the mic reopens when it finishes (`speak(text, onDone)` → `startListening()`), so it's a real back-and-forth loop. TR/EN language chip (`lasci-ai-voice-lang`) drives BOTH recognition and the picked voice. Load-bearing details: `speakableText()` strips `**bold**`/emoji so the voice doesn't read markup; `startListening` cancels any speech first (otherwise it transcribes its own voice); **`primeAudio()` must run inside the enabling tap** — iOS refuses synthesis that no user gesture unlocked, and the reply is spoken much later; the panel's close paths reset voice mode and `voiceModeRef` is `voiceMode && isAIOpen` so the loop can't continue behind a closed panel; a silent utterance ends the loop rather than reopening a hot mic. Everything is feature-detected — the controls simply don't render where the API is missing. **Recognition is unreliable inside an iOS home-screen PWA** (a long-standing WebKit gap); on the phone the `AI'a Sor` Shortcut is the voice path (Siri dictation → gateway → Speak Text), so this mainly serves desktop.
- **Vision:** `Message.images` end-to-end via a shared `messagesToContents()` that attaches base64 photos as Gemini `inline_data` parts (chat + structured). `AIPanel` supports the 📷 attach button (≤3, thumbnails, image-only send) **and pasted images** (Cmd/Ctrl+V on desktop, paste on mobile — `onPaste`); `parseFoodPhoto()` + `fileToCompactDataUrl` downscale before upload.
- **MCP was evaluated and deliberately not pursued:** GitHub Pages is a static host and cannot run a persistent process, so any MCP layer would need a separate always-on server. The generic `DB_CATALOG` + `db_query/insert/update/delete/aggregate` layer shipped instead, and the "AI proposes, user confirms" invariant lives in the system prompt.
- **Removed / never built:** dead `log_workout`/`get_workouts` (hit the dropped `training_sessions` table — training is Hevy/Strava, read via `db_query`; planned sessions = `time_blocks` `category='training'`). The **Weekly Review** Home card added during the AI phases work was **removed on request** — `weeklyReviewApi`/`useWeeklyReview`/`WeeklyReview` no longer exist in `src/`, and `ai_reviews` (migration 065) is an unused empty table left in place.
- Cost model, security invariants, the architectures evaluated and the pricing snapshot: `docs/ai-cost-capability-analysis.md`.

### iPhone surface (Shortcuts · Scriptable · Web Push)

**`phone-gateway`** is the single durable entry point (see the Edge Functions table for auth). **11 actions:** deterministic `log_supplement` · `log_food` · `log_water` · `nutrition_today` (includes `water_ml`) · `recent_foods` · `search_library` · `sleep_stats` · `tasks_today`; AI `ask` · `brief` · `sleep` (forwarded to `ai-proxy` with the same secret). The action table in `docs/iphone-examples.md` is **the contract** — Shortcuts and widgets must match it.

**The ~25s design constraint (why the AI actions look the way they do):** iOS Shortcuts' "Get Contents of URL" times out at roughly 25s, which is short for a tool-looping LLM. Three deliberate choices, all in `phone-gateway`/`ai-proxy`:
1. **`FAST_MODEL = 'gemini-3.1-flash-lite'`** starts every AI action, skipping the frequently 503-overloaded 3.5-flash primary; ai-proxy still falls through the rest of the chain.
2. **Single-shot, not a tool loop** — `brief` pre-builds its context SERVER-SIDE (`buildBriefContext`: today's tasks + schedule + upcoming training, service-role queries explicitly user-scoped, best-effort per section) and sends `surface: 'phone'`, which `toolsFor()` maps to **no tools**, so Gemini answers in one turn. ## Coding Rules (Strict)

### Mobile-first — MANDATORY
Every component mobile-first. `min-h-[44px]` on every interactive element. No exceptions.

```tsx
// ✅
<button className="w-full md:w-auto min-h-[44px]">
// ❌
<button className="w-32 h-8">
```

Hover-only actions need an always-visible mobile fallback. No horizontal page overflow.

Modal pattern — use `@headlessui/react` Dialog (handles Escape, focus trap, portal automatically):
```tsx
import { Dialog, DialogPanel, DialogBackdrop } from '@headlessui/react'

<Dialog open={isOpen} onClose={onClose} className="relative z-[60]">
  <DialogBackdrop transition className="fixed inset-0 bg-ink-900/30 transition duration-200 data-[closed]:opacity-0" />
  <div className="fixed inset-0 flex items-end sm:items-center justify-center p-0 sm:p-4">
    <DialogPanel transition className="w-full rounded-t-2xl sm:rounded-2xl sm:max-w-md max-h-[90vh] overflow-y-auto bg-cream-50 border border-ink-200 transition duration-200 data-[closed]:opacity-0 data-[closed]:translate-y-4 sm:data-[closed]:translate-y-0 sm:data-[closed]:scale-95">
      {/* content */}
    </DialogPanel>
  </div>
</Dialog>
```

### Toast feedback — MANDATORY
Every async action must show feedback on completion. Toasts appear bottom-left.
🟢 success · 🔴 error · 🟡 warning · ⚫ loading.

**For any new TanStack Query mutation, use `useMutationWithFeedback`**
(`src/shared/hooks/useMutationWithFeedback.ts`) instead of bare `useMutation`:
```ts
return useMutationWithFeedback({
  action:         'delete_time_block',   // logError context — the only required extra field
  successMessage: 'Deleted',             // optional — omit for silent-success on in-place edits
  mutationFn:     (id: string) => deleteTimeBlock(id),
  onSuccess:      () => qc.invalidateQueries({ queryKey: ['schedule'] }), // your own logic still runs
})
```
This exists because "every async action must show feedback" was hand-copied per call site —
inconsistently applied and easy to forget (real bugs: the daily timeline's drag/postpone/rename/
delete and the to-do list's toggle/delete/reorder had **zero** feedback on failure; two
Developer-tab "clear logs" mutations toasted but never called `logError`, so a failure to clear
the error log was invisible in the error log itself). `useMutationWithFeedback` bakes the
guarantee into the mutation primitive — like a return-code check that can't be skipped: error is
**always** toasted and logged to `app_error_logs`; success is silent by default (matching the
"edits feel live" convention) unless `successMessage` is given.

**Migration rule for the remaining bare hooks:** several are called from multiple components,
some of which already wrap `mutateAsync` in a complete `toast.loading/success/error` block.
Switching the hook alone would double-toast those. Migrate the hook **and** simplify every call
site to drop its local toast duplication in the same pass — do it the next time one of those
files is touched for another reason, not as a big-bang rewrite.

For genuinely one-off async actions that aren't a TanStack mutation at all (a button
handler calling an API directly), the manual pattern is still fine:
```ts
const tid = toast.loading('Saving…')
try {
  await doSomething()
  toast.dismiss(tid); toast.success('Saved ✓')
} catch (err) {
  toast.dismiss(tid); toast.error((err as Error).message ?? 'Failed')
}
```

### Layout width — content-sized, left-aligned (MANDATORY)
Never stretch content edge-to-edge. Widgets are sized to their content, not the viewport. The complaint that produced the numbered rules below: tiny data stretched wall-to-wall on big monitors. They make "content-sized" **measurable** so it never regresses. (Piloted on Training; roll out page-by-page — Home → Media → Work — only on explicit request per page.)

- Page wrapper: `w-full px-4 sm:px-6 lg:px-8` (left indent, NOT `mx-auto` centered). Page background is `bg-canvas` (#EDE4D5, soft warm cream); cards sit on `bg-cream-50` for contrast.
- Each content block gets a `max-w-*` capped to what it needs, **left-aligned** — leftover horizontal space stays on the right. Small cards flow side-by-side (grid/flex-wrap), never stack full-width.
- **W1 · Container-relative, not viewport.** A widget adapts to its OWN box width — use `@container` + `@sm/@3xl/@4xl:` variants (the `@tailwindcss/container-queries` plugin is installed), not `sm:/lg:` on inner widgets. The same component can then be dense in a narrow slot and rich in a wide one.
- **W2 · Column flow, fixed widths.** List/card collections flow into content-width columns via `grid-cols-[repeat(auto-fill,minmax(MIN,MAX))]` + `justify-start`; the column COUNT derives from available width, rows never stretch. Caps: dense one-line rows `15–18rem`, cards `19–22rem`, large cards `24–28rem`. A single content row must never exceed **40rem (640px)**. (Exception: `TodaySummary` uses explicit `grid-cols-*` steps, not auto-fill — positional stability outranks column flow there.)
- **W3 · Controls are content-sized.** Text/search inputs `≤ max-w-md` (512px); info banners `w-fit`; a one-line control is never full-width. A 1900px search box is a bug.
- **W4 · Charts: aspect-locked + capped.** A chart keeps its aspect ratio and caps by role (small trend `max-w-2xl`, primary `max-w-4xl` = 896px). Growing a chart = grow proportionally, never smear to full width.
- **W5 · Detail on demand.** Secondary info (GIFs, history, explanations) lives in a hover/tap peek, not permanent screen area (desktop hover + mobile tap, per the mobile-fallback rule).
- **W6 · Measurable.** Verified at 393 / 1469 / 2450px: no horizontal overflow at any width; at 2450px no single-line content > 640px, no auto-fill column > 384px, no text input > 512px, no chart svg > 896px. Re-check these numbers when applying the standard to a new page (an audit script was used in-session but was never committed — write a throwaway one under `scripts/` per the no-unit-test-framework convention).
- **Exception — data-dense dashboards on large monitors:** a `max-w-4xl` column next to a fixed side rail leaves a dead zone on 2xl+ (2450px-class) monitors. For these (e.g. Training → Health) drop the cap at `2xl:` (`2xl:max-w-none 2xl:flex-1`) so the column fills the remaining flex space; grids inside can add a `2xl:grid-cols-*` step. Still content-sized below 2xl.
- **Density toggle was tried and REJECTED** (Comfortable/Compact/Dense) — it changed the VERTICAL plane; the complaint was horizontal. Don't reintroduce it.

## Key Patterns

**Toast store:** `import { toast } from '../../../app/store'`

**Tasks — one table for every domain.** `tasks` is the single source of truth for tasks across every page; **never create a per-feature task table.** Enums: `domain` `personal|work|media` · `section` `inbox|today|tomorrow|this_week|backlog` · `status` `open|in_progress|done|cancelled` · `priority` `low|medium|high` · **`source_type` `manual|movie|tv_series|media|calendar|ai|training_session|project_item`** (widened by migrations 039 and 047). Canonical queries: Work board `domain='work' AND status != 'cancelled'` · Today `section='today' OR (due_date = current_date AND status='open')` · media plans `domain='media' AND source_type='media'` · inbox `section='inbox' AND status='open'`.

**`tasks.start_date` (migration `069`) is `due_date`'s OPENING edge**, not a second deadline: `start_date=A` + `due_date=B` means "do this between A and B", and `due_date` stays the **sole** deadline representation — so overdue, the brief, the push, `phone-gateway` and `workMeta.ts` learn no new concept. `ToDoItem` renders **one** range chip *instead of* the due chip (never both — that row's own comment records a real 136px-of-393px title-starvation bug) and still takes its colour and ⚠ from `due_date`. `TasksPanel` gains an **"Open now"** group (`start_date ≤ today < due_date`), computed client-side off `fetchAllTasks`' existing `select('*')`, so before 069 `start_date` simply reads `undefined` and the group stays empty — no probe, no query. The window's last day belongs to Today (on `due_date` the deadline is what matters), and Open now only ever takes rows *from* Upcoming, so nothing renders twice. **A window predicate is NEVER added to `fetchTasksForDay`** — a `42703` there takes down `DayView`, `DayQuickRail`, `HomePage` and Home's `TodaySummary` at once. Written on **both** `UnifiedPlanModal` save paths via `TaskWindowField` (season chips reusing `windowChips`' math; it could not live in `taskExtra`, which is a `React.ReactNode` with no access to `form`/`patch`), and `tasksApi` retries the write without `start_date` on `42703`/`PGRST204` (the `recipes.fiber_g` precedent) while create omits the key entirely when unset. Fixed in the same pass: `CreateTaskInput` had no `description`, so the Notes textarea was **silently dropped on create** while edit persisted it.

**Planning — `UnifiedPlanModal`:** The ONE modal for all task/time-block planning (`src/shared/components/plan-modal/`). **No Task/Schedule tab switcher any more (migration `077`, 2026-08-22)** — a `mode: 'task'|'schedule'|'recurring'` prop decides which ENTITY is being created/edited; the user never picks a tab. Passing `task`/`timeBlock`/`scheduleBlock` for an edit always wins over an explicit `mode` and infers it (`task`→'task', `timeBlock`→'schedule', `scheduleBlock`→'recurring'), so an edit caller never has to think about mode at all — only a CREATE call site needs `mode` explicitly. Shared editable title, always-on-top z-index. Shape it entirely from the call site — never edit the modal folder:
- `mode` → required for create; ignored/inferred for edit (see above)
- `config` → `heading`, `hide*/lock*` field keys (no more `tabs`/`defaultTab` — removed with the tab switcher)
- `defaults` → prefills (title/date/startTime/duration/category/color/section/priority/domain/**startDate**/dueDate/**scheduled**…)
- `source` → `{ sourceType, sourceId, taskSourceType }`; `sourceType` is the block's REAL originating entity and MUST be a valid `time_blocks.source_type` (`training_session`/`movie`/`tv_episode`/`project_item`/`calendar`/`manual` — **never `'task'`**, removed from the CHECK by migration 077)
- `scheduleExtra` / `taskExtra` → caller-owned children injected into a tab
- `task` → edit a Task (mode='task') · `timeBlock` → edit a standalone one-off block with **no** linked task (mode='schedule'; a task-linked block is edited via `task` instead — the modal fetches its own linked block internally) · `scheduleBlock` → edit a recurring template (mode='recurring') · `onSaved` → post-save hook
- Rules + changelog live at the top of `UnifiedPlanModal.tsx`; log every logic change there.

**Task ↔ Schedule model (migration `077`, root-cause fix — read before touching either table):** A Task (deadline: `due_date`/`due_time`) and its optional one-off schedule slot (`time_blocks`, a specific date/time to actually do it) are **independent facts**, never kept in sync by a DB trigger any more. `time_blocks.task_id` (a real FK, `ON DELETE CASCADE`, DB-enforced at-most-one-per-task via a partial unique index) is the **ONLY** representation of "this block belongs to a Task" — `time_blocks.source_type` never equals `'task'` again (that CHECK value was removed). `source_type`/`source_id` on a task-linked block instead carry the block's REAL originating entity (`training_session`/`movie`/`tv_episode`/`project_item`/`calendar`/`manual`), independent of `task_id` and never overwritten by it — the actual bug this migration fixes (creating a task+schedule together used to silently discard the real source by overwriting it with `{source_type:'task', source_id:<task id>}`). The old bidirectional due-date↔block-date/time sync triggers and the "deleting/unscheduling a block soft-cancels its Task" trigger are **retired** (dropped, not disabled — their `link_rules` config rows are marked disabled + re-described instead of deleted). The one remaining cross-table effect is one-directional: a Task title edit mirrors onto its linked block's title via a DB trigger (`sync_time_block_title_from_task`, fires from every write door — browser, `ai-proxy`, Google Tasks pull — not just the modal). Tapping a `DayAgenda` row opens the correct editor for whatever was actually clicked, directly — no select-then-✎ second step (a small always-visible ⋯ toggle is the only way to reach the postpone/delete quick actions instead): a recurring row opens `scheduleBlock`, a task-linked one-off row opens the Task itself (`task`), a standalone one-off row opens `timeBlock` directly; there is no "which tab" decision anywhere in that flow. **Every caller that can encounter a task-linked plan block must apply this same routing** — `TrainingCalendar`'s own plan-block click handler was a real instance of getting this wrong (opened via `timeBlock` unconditionally, which seeded `alsoCreateTask=true` since `buildInitialForm` had no idea a task already existed, and Save then minted a SECOND task and re-pointed the block at it) — fixed to check `task_id` and open via `task` instead, matching `NextSessionBanner`'s pattern. `saveSchedule`'s "Also add to Tasks" branch also gained a defensive `shouldCreateLinkedTask` guard (`planModal.config.ts`) that refuses to create a task at all when the `timeBlock` passed in already has one — `timeBlock` is contractually standalone-only, so this should be unreachable, but it's the last line of defense against exactly the TrainingCalendar-class bug. When writing `time_blocks` from a new call site (edge function or client), always set `task_id` for task-linkage and never write `source_type: 'task'` — and remember the two tables use DIFFERENT TV vocabulary (tasks: `tv_series`; time_blocks: `tv_episode` — mixing them up 400s on the CHECK, a real bug `ai-proxy`'s `planMedia` shipped with; `planMedia` now also stamps `season_number`/`episode_number` when the AI was given a specific episode, matching `EpisodesPanel`'s own single-episode rule, so `cleanup_block_on_episode_watched` can actually match the row). A caller with no `source` prop editing an EXISTING task/timeBlock falls back to that entity's own `source_type`/`source_id` (via `blockSourceTypeForTask`/`taskSourceTypeForBlock` in `planModal.config.ts`) — except `tasks.source_type='tv_series'` deliberately does NOT fall back to a block's `tv_episode` (no season/episode numbers to back that up; overclaiming episode identity generically was reconsidered and dropped). "One task = one Google entry" (see the Google Calendar + Tasks section below) is enforced on BOTH the create path and now every edit that newly makes a task calendar-linked or newly links a calendar-linked block to a task (`needsGoogleTaskDedupe`) — the create-only version of this check was a real gap.

**Calendar-status is a TYPED, tri-state contract — never a message-string guess.** `calendarApi.ts`'s `CalendarApiError` carries the real HTTP status (`isCalendarNotFound(error)` checks `error.status === 404`, never `message.includes('404')` — a Google error body can legally carry only a human message like `"Not Found"` with no digits in it at all). `scheduleApi.ts`'s `updateTimeBlock` and `UnifiedPlanModal`'s `linkCalendarEvent` both return a `TimeBlockCalendarStatus` (`scheduleSyncRules.ts`): `'linked'` (confirmed live this call), `'not_linked'` (confirmed gone — a real 404 whose local-id-clear write ALSO succeeded, or an explicit unlink that completed), or `'unknown'` (no token, a network/401/403/429/5xx failure, or the local clear/persist step itself failed — genuinely unconfirmed either way). The policy this feeds: `needsGoogleTaskDedupe`/`needsGoogleTasksFallback` (`planModal.config.ts`) only ever act on a CONFIRMED status — `'unknown'` triggers neither a dedupe-delete of the Google Task nor a create-time Google Tasks fallback, so an unconfirmed calendar failure can never cost the user their ONLY remaining Google representation of a task. `linkCalendarEvent` also compensates for the split-brain case where the remote Calendar event was created successfully but persisting its id locally then failed: it deletes the orphan it just created (reporting `'not_linked'` on success, `'unknown'` if even that compensation can't be confirmed) rather than leaving a real, untracked event behind. `useUpdateTask`'s own Task-title→Calendar-event push (a DB trigger keeps the block's title in sync, but has no OAuth token to reach Google with) is routed through the SAME `updateTimeBlock` call — not a second, independent `updateCalendarEvent` call with its own inconsistent swallow-everything error handling — so every calendar push in the app shares one lifecycle. An explicit unlink (`google_calendar_event_id: null`) with no Calendar token connected no longer silently drops the local link either — every OTHER patch field still applies, but the id itself is left alone (reported `'unknown'`) since nothing here could act on the remote side to justify clearing it.

**Google Tasks outbox — per-task FIFO + typed 404s (migration `079`).** `claim_google_tasks_outbox` (migration 073's `FOR UPDATE SKIP LOCKED`) now ALSO only ever claims the OLDEST outstanding row per `(user_id, task_id)` — a newer row for the same task can never be claimed while an older one is still outstanding, even mid-backoff or mid-claim by another worker. Real race this closes: an opt-out `'delete'` and a later Reopen `'force_recreate'` `'create'` for the SAME task, processed out of order, could let the stale delete's unconditional id-clear wipe the BRAND NEW `google_task_id` the create just wrote. `clear_google_task_id_if_matches` (new RPC) is the belt-and-suspenders half of that fix: `processDelete` (both `googleTasksOutbox.ts`'s browser drain and `google-tasks-sync`'s cron mirror) now only clears `tasks.google_task_id` when it STILL equals the id THIS delete targeted, instead of the old unconditional `apply_google_task_snapshot(p_clear_google_task_id=true)`. `GoogleTasksApiError`/`isGoogleTaskNotFound` (`googleTasksApi.ts`, mirrored by hand in the edge function) replace every `message.includes('404')` check on the Tasks API side too. `processCreate` also re-checks the LIVE task row after the Google `POST` returns (a real network round trip the user can act during) — if the task opted out/cancelled/hard-deleted while the create was in flight, the just-created remote task is deleted rather than adopted, and a failed compensation delete enqueues a durable retry `'delete'` outbox row (never just a log line) so a later drain finishes the cleanup.
- **The claim query above didn't actually lock anything — a second review pass caught this against a live `EXPLAIN`, before either migration ever went live.** The original `claim_google_tasks_outbox` computed the per-task `rn=1` filter in a `ranked` CTE (a `row_number()` window function over the base table), then applied `FOR UPDATE SKIP LOCKED` in a SEPARATE `claimable` CTE that selected only `id FROM ranked` — not directly from the base table. This is documented Postgres behavior, not a fluke: a locking clause on a query does **not** propagate into a WITH query that it merely selects from; the clause has to be attached to the individual `SELECT` INSIDE the WITH query to have any effect. The live `EXPLAIN` plan for the broken version confirmed it directly — no `LockRows` node anywhere — meaning the whole claim had silently stopped providing ANY concurrency guarantee: two workers could both believe `SKIP LOCKED` protected them while claiming the identical row, reintroducing the exact migration-073 duplicate this function exists to prevent. Fixed by moving `FOR UPDATE OF o SKIP LOCKED` onto a CTE that selects directly from the base table, with the per-task ordering expressed as a `NOT EXISTS` anti-join (`older.task_id = o.task_id AND (older.created_at, older.id) < (o.created_at, o.id)`) instead of a window function in the same query block as the lock clause — the same shape migration 073's own (correct) query already used, just with the anti-join added. A supporting `(task_id, created_at, id)` index ships alongside it.

**Duration bounds — `time_blocks.duration_minutes` had no real upper (or DB-enforced lower) bound.** The custom-duration input (`DurationField`, `fields.tsx`) had `min={1}` and no `max` at all, and — critically — an HTML `min`/`max` attribute doesn't block a form submit regardless; nothing downstream re-validated the parsed value either (`Number(form.customMin) || 60` lets a negative string like `"-30"` through unchanged, since a nonzero negative number is still truthy). This matters because `dayAgendaProjection.ts`'s whole cross-midnight model assumes a block occupies at most its own start day plus a SINGLE spillover day — a >1440-minute (>24h) block would need a third day's worth of spillover nothing in that file (or `TrainingCalendar`'s dot-per-day rendering, or Home's next-session lookup) was ever built to represent; it wouldn't crash, it would just silently vanish past its second day. Fixed with `clampDurationMinutes` (`planModal.config.ts`, pure, `Math.min(1440, Math.max(1, Math.round(raw)))`, falls back to 60 on a non-finite input) applied at all three `effDuration` computations in `UnifiedPlanModal.tsx` (schedule create/edit, recurring create/edit), the input's own `max={1440}` as a visible hint, and migration `080` (`time_blocks_duration_minutes_range` CHECK constraint, clamping any pre-existing out-of-range rows first so the `ADD CONSTRAINT` itself can't fail) as the real enforcement layer — the client clamp alone doesn't cover `ai-proxy`'s generic `db_insert`/`db_update` tool, which writes `time_blocks` directly with no knowledge of this app-layer clamp at all.
- **Google Tasks field coverage (audited + fixed 20/08/2026).** Per-task real-time sync covers create (title/notes/due), toggle-done (complete/reopen via `status`, `completed:null` to clear on reopen), delete, and — **the one real gap found** — edit: `useUpdateTask` used to be a bare passthrough with zero Google sync, so rescheduling a due date or fixing a typo left the Google-side copy silently stale forever. Fixed: it now PATCHes title/notes/due to Google whenever one of those three fields is actually in the patch (a priority/section-only edit doesn't touch Google — nothing there to update). All sync is soft-fail (`logError`, never blocks the Supabase write), matching the create/toggle/delete precedent. `useSyncFromGoogleTasks`/`usePushToGoogleTasks` (previously dead code, no UI trigger) are now reachable via `GoogleTasksSyncButtons` in Settings ⚙ → Google, migrated to `useMutationWithFeedback` (they had zero existing call sites, so no double-toast risk — unlike the four bare hooks in `useTodos.ts` this migration rule is otherwise about). The pull direction (`useSyncFromGoogleTasks`) also gained a fix: it read `rt.notes` from the Google Tasks API response but never carried it into the imported row — a task's detail written in the Google Tasks app used to vanish on import.
  - **Deliberately NOT built** (real Google Tasks fields with no equivalent here, verified via the Tasks API's real resource shape — not guessed): **multiple task lists** (everything reads/writes `/lists/@default/tasks` only; our own `domain`/`section` categorization doesn't map 1:1 onto Google's flat named-list structure, and building that mapping is a real feature, not a wiring fix); **subtasks** (`parent`/indentation — our `tasks` table has no parent-task concept at all, a data-model change, not a sync gap); **manual ordering** (`position` — our own `sort_order` is independent and un-synced either direction); **`links`** (e.g. an attached email) — no use case for a personal task app.

**Schedule cache invalidation:** time-block mutations (`useCreateTimeBlock`/`useUpdateTimeBlock`/`useDeleteTimeBlock`) invalidate the WHOLE `['schedule']` namespace + `['calendar']`, not a single day key — consumers read schedule under different sub-keys (`['schedule','day',date]` for Daily/Home/Work via the shared `useTimeBlocks`, `['schedule','training-range',…]` for the Training calendar / Home next-session). **Never give a schedule view its own private query key** (Work's old `['time-blocks']` key went stale because nothing invalidated it). Same class of bug bit the food card — see Food's cache-key note.

## Edge Functions (Supabase)

**Edge Functions are deployed MANUALLY** (Supabase Dashboard, or `supabase functions deploy` via CLI). A GitHub Actions auto-deploy job was tried and removed — it kept failing on the runner and wasn't worth the noise. Manual deploy is clean because **every function is self-contained (no `_shared/` imports)** — the shared Hevy upsert logic is inlined into all 4 Hevy functions, so a Dashboard paste no longer hits the "Module not found `_shared`" bundling error. **DB migrations are also manual** (Dashboard → SQL Editor or `supabase db push`); they do NOT run in GitHub Actions.

**`verify_jwt = false` applies to SIX functions** — `supabase/config.toml` records them and a CLI deploy applies it automatically; a **Dashboard** deploy needs the "Enforce JWT Verification" toggle set by hand for each: **`hevy-sync`, `health-export-webhook`, `google-tasks-sync`, `ai-proxy`, `phone-gateway`, `push-send`.** Every one of them authenticates with its own Bearer/custom secret rather than a Supabase JWT (checked in-code), so leaving platform verification ON makes Supabase reject the call **before our code runs**. This is a real production gotcha, hit twice.

**Correct-in-the-repo ≠ deployed.** Because functions and migrations are manual, a merged commit can still be running old code in production. Sequence any "must be deployed before X" work against the moment the *user-triggerable* path goes live (a Fetch-now button, a new gateway action) — **not** against a cron being enabled; a single button click can write real rows immediately.
